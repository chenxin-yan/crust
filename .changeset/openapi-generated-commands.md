`defineApi()` generates a command per operation of the pinned spec: `new Crust("acme").extend(acme.extension).add(...acme.commands)`. Each is an ordinary app command in its first tag's group, with path parameters as arguments, typed query, header and top-level body field flags, the JSON body as a `--body` JSON flag whose schema stands alone for `schema` and MCP, and `.output()` with the response's JSON Schema; it prints the result for people and returns it. The handle's chain shapes them: `.use()` (Contexts for the callbacks, typed), `.onConfirm()`, `.each()` and `.override()` (one `OperationOverride` shape: `exclude`, `group`, `name`, `hidden`, `description`, `flagName`, `positional`, `bind`, `confirm`, `paginate`, `unwrap`, `outputSchema`, with names checked against a registered spec), and `.add(group, ...commands)`. An operation that does not fit is left out and marked `[unavailable: <code>]` in `api --list`; nothing throws for one operation. `crust build` fails, listing each problem with its fix, when configuration can settle it (a name clash, a stale or unknown override, positionals out of order, `confirm` without `.onConfirm()`) or when the document is not OpenAPI 3.0 or 3.1, and skips an operation no configuration can make a command (a required non-JSON body, an unsupported required parameter, a missing or shared operationId). `app.snapshot()` shows the generated commands for a snapshot test of the CLI's surface. `Operation` (what `.each()` receives) is an exported type. A built CLI that adds the generated commands reads its `<id>/spec.json` at start.
