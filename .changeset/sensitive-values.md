Add `sensitive: true` for arguments and flags that hold secrets, such as `{ type: "string", env: { name: "ACME_TOKEN" }, sensitive: true }`. Crust never prints the value: any conversion, `choices`, `parse`, or schema failure (a throwing validator included) reports only `Invalid value for --token.` with the field name in `details` and no cause, `input()` reports only `--input is not valid JSON` for malformed JSON when the command has a sensitive field, `nextSteps()` leaves out a sensitive flag with an `env` binding (the environment supplies it) and prints `--token <redacted>` for any other sensitive value, help and man pages start the description with `Secret.`, generated skills tell agents to pass it through its env variable, and `commandInputSchema()` (used by `schema()`, `input()`, and MCP) marks it `writeOnly` (strings also `format: "password"`) without publishing a schema-backed field's `enum`, `const`, `default`, `examples`, or `x-*` keywords. MCP `tools/list` advertises sensitive fields `writeOnly` (strings with `format: "password"`), and `tools/call` errors for them carry only the fixed message. Snapshots carry `sensitive: true`. A sensitive definition that is a boolean (its value is its argv spelling) or declares a `default` or `choices` throws a `DEFINITION` error (`sensitive-boolean`, `sensitive-default`, `sensitive-choices`). This is redaction, not a security boundary: Crust can't hide argv from the OS (`ps`, shell history, transcripts), so `execute()` prints one stderr warning per sensitive field given on argv, through the renderer's `diag` and without changing the exit code, suggesting its env variable instead. `run()` never warns.
