New `telemetry({ env, enabled, send, command? })` Extension: after each invocation it passes one event, `{ command, outcome, durationMs, ci }`, to your `send`. `command` is the command path (`["acme", "deploy"]`), never argument or flag values; `outcome` is `completed`, `failed`, or `handled`. Crust has no network code and no default: `enabled` is `"opt-in"` or `"opt-out"`. `send(event, { signal })` is waited for at most 1 second, when `signal` aborts with a `TimeoutError`: pass it to your request so it does not keep the process alive. Its failures are ignored. An unknown command or flag fails before setup and sends nothing.

It adds a `telemetry` command (rename it with `command`): bare or `status` shows whether events are sent and which setting decides, and `enable` / `disable` save the user's choice in `telemetry.json` in the CLI's config directory. Each returns the state as data (`{ sending, decidedBy, saved?, default }`), printed by `--json` under `json()`. The first setting that decides wins: `DO_NOT_TRACK` set to anything but empty or `0` turns it off; then the `env` variable (`0` or `false` off, any other non-empty value on) for the runs where it is set, without changing what is saved; then the saved choice; then `enabled`. So under `"opt-out"`, a non-empty variable such as `ACME_TELEMETRY=1` also sends for that run after the user ran `telemetry disable`. A saved file that cannot be read sends nothing until `enable` or `disable` rewrites it. The store loads only when the command runs or neither variable decides.
