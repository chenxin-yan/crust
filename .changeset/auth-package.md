"@crustjs/auth": minor
---

New package `@crustjs/auth`: OAuth sign-in for a CLI. `createAuth({ app, issuer, clientId, apiOrigins, scope, env, resource })` returns a client. `login()` runs the whole sign-in: a browser login over a `127.0.0.1` loopback redirect with PKCE `S256` and `state`, or a device-code login (RFC 8628) over SSH, without a display, or with `device: true`; on CI or without a terminal it refuses with `LoginRequiresInteractionError`. It prints nothing itself: your `onUrl` and `onCode` callbacks show the URL (and may call `open()` to launch the browser) and the code. The login is stored in a private credentials file in the app's state directory (a strict `@crustjs/store` file, `0600` on POSIX). `token()` returns the token for your API: the `env` variable's value when it is set, otherwise the stored login, refreshed when it is about to expire and sent only to `apiOrigins`; pass it to `bearerAuth()` from `@crustjs/openapi`. `status()` says where the token comes from without a request, and `logout()` deletes the login and revokes it at the server. The building blocks the client is made of are exported from `@crustjs/auth/oauth`: `defineServers()` declares several authorization servers and `discover()` validates their metadata and exposes its `userinfoEndpoint`; `createAuthorizationSession()`, `startDeviceFlow()` and `createTokenClient()` run each step, `detectLoginMode()` picks the login, and `openBrowser()` launches the system browser without a shell. Several servers must each send `iss` or use their own `redirectPath`, or the browser login refuses (mix-up protection). `credentialStore()` and `createTokenSource()` keep and refresh logins, refreshing once across processes and never resending a refresh whose outcome is unknown, and `resolveCredential()` picks a token from a flag, stdin, the environment, an env file, or the stored login.
