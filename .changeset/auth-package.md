"@crustjs/auth": minor
---

New package `@crustjs/auth`: OAuth sign-in for a CLI. `createAuth({ app, issuer, clientId, scope, resource })` returns a client whose `login()` runs the whole sign-in: a browser login over a `127.0.0.1` loopback redirect with PKCE `S256` and `state`, or a device-code login (RFC 8628) over SSH, without a display, or with `device: true`. On CI or without a terminal it refuses with `LoginRequiresInteractionError`. The client prints nothing itself: your `onUrl` and `onCode` callbacks show the URL (and may call `open()` to launch the browser) and the code. The building blocks it is made of are exported from `@crustjs/auth/oauth`: `defineServers()` declares several authorization servers and `discover()` validates their metadata and exposes its `userinfoEndpoint`; `createAuthorizationSession()`, `startDeviceFlow()` and `createTokenClient()` run each step, `detectLoginMode()` picks the login, and `openBrowser()` launches the system browser without a shell. Several servers must each send `iss` or use their own `redirectPath`, or the browser login refuses (mix-up protection). The building blocks also store logins: `credentialStore({ app })` keeps them in one private credentials file (a strict `@crustjs/store` file, `0600` on POSIX), and `createTokenSource()` binds one login to its issuer, client, and API origins: `get()` refreshes it once across processes, never resends a refresh whose outcome is unknown, `beginLogin()` and `logout()` store and revoke it. `resolveCredential()` picks a token from a flag, stdin, the environment, an env file, or the stored login, and reports which sources it shadowed.
