Core value errors never print the raw value, so a secret read from an `env` binding stays out of CI logs and agent transcripts. They name the argument or flag, plus the variable when the value came from the environment. Message wording changes: `Invalid value "x" for --mode. Expected one of: …` is now `Invalid value for --mode. Expected one of: …`, `Expected number for --port, got "x"` is now `Expected a number for --port.`, `Invalid URL for --base: "x"` is now `Invalid URL for --base.` (the missing-protocol hint stays), and `Invalid JSON for --data` drops the engine's parse reason (the shell-quoting tip stays). Typed `run()` and bound input use the same wording, as in `Expected a number for --port.` (was `Expected number for --port`), `Expected a URL for --home.`, and `Expected a JSON value for --data.`. An environment value adds its source, as in `Expected a number for --port (from $PORT).`; a `noNegate` env message reads `(from $NAME)` too. These errors no longer carry the native `URL` or `SyntaxError` as `cause`, since engines quote the input there. A flag rejected before a subcommand (`flag-not-forwardable`) is named without its inline value in the message and `details.flag` (`--token=x` reports `--token`). Error codes are unchanged. Messages from your own `parse` functions and Standard Schema issues are printed as written; unknown commands and extra positional arguments are still echoed so typos stay visible.
