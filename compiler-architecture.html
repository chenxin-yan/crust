The architectural decision before more syntax

Current Crust can run arbitrary user TypeScript because its own executable is Bun. A Go binary cannot inherit that behavior through an environment variable. Source

Recommended proposal · approval needed

Native Crust; explicit user-code host

Compile Crust's supported source graph to Go. Keep arbitrary project entries/plugins behind a deliberate external Bun boundary initially.

Cost: an approved host-tool adapter and declared Bun requirement for those operations. Not an interpreter fallback for unsupported compiler input.

Stricter alternative

Unchanged source; no Bun dependency

Preserve today's runtime behavior without delegating user TypeScript to Bun.

Cost: a much larger runtime/module compatibility problem. No evidence M0 can meet it; decide scope before promising it.

Recommendation: keep the Go end goal and source-first compilation; do not invent a general JS VM. The original “no interpreter island” rule remains intact. A host adapter is a separate, unapproved product decision.

Express GT's commands, flags, validation and actions with Crust. Reuse existing config, extraction, API and file-writing services.

Migration track · independent of compiler readiness

  1. Capture GT's CLI contract

    Pin its real entry and inventory command names, aliases, flags/defaults, env precedence, help, validation, exit codes and framework selection.

    Gate: behavior fixtures against the existing Commander CLI, with explicit approval for intentional UX changes.

  2. Port one command end to end

    Use a Crust action to call the existing translation services; start with a JSON-only translate --dry-run fixture. Separate Commander-coupled registration from reusable handlers only where needed.

    Gate: equivalent parsed options, config/env behavior, output and exit codes; network denied/instrumented and file diffs checked in a disposable project.

  3. Complete and ship the Crust-based CLI

    Migrate the remaining command surface and framework dispatch, then remove superseded Commander wiring. Preserve parsers, API clients and terminal UI unless a concrete incompatibility requires a change.

    Gate: command contract tests, selected extraction fixtures and installed-bin smoke tests pass; remote translation tests require authorization. This proves framework migration—not native compilation.

Later convergence: use the migrated GT source graph as a compiler target once the native Crust foundation is ready; the migration can proceed without waiting for it.

  • Replacing Commander removes one framework dependency; it does not make Babel/esbuild/Ink/React or the remaining npm graph Go-compilable.
  • GT's --dry-run is not proof of read-only or zero-network execution; preprocessing and postprocessing still exist.
  • Native feasibility must be assessed on migrated GT, not assumed from today's Commander-based source or a help-only proxy.

Source resolution, evidence and limits
  • Proposed profile: TypeScript's module: Preserve + moduleResolution: Bundler, no emit, explicit TS extensions and JSON support. This is a resolver mode, not a bundler dependency. Toy TS5.9.3 probe: zero diagnostics.
  • Source selection: recommend an explicit crust:source export condition. Current workspace exports point to dist; adding the condition and deciding whether to publish the complete source graph are follow-up package-policy changes, not implemented here.
  • Fail closed: declarations alone cannot satisfy an executable dependency; unsupported JS and host calls remain diagnostics. Type-only declarations remain valid.
  • Fresh evidence: four-module checker probe preserves private and contextual types; a JS + adjacent dts probe still has three TS7006 errors; parent reran Rolldown/dts and checker probes with exit 0.
  • Not proven: whole-Crust graph linking, native module parity or modern TsProject compatibility. The full Crust JS bundle still lacks local Utils dist artifacts.
  • Alternative still open: JS with reliable implementation-level metadata could work. No inspected maintained tool established that complete contract; this is not an impossibility claim.

    Gate: rerun the native corpus + preserve the real-entry rejection probe. Today's tiny demo passes; the full baseline was not rerun here.

  2. Link typed source; approve the remaining host boundary Input design settled

    Follow the source-graph design: explicit source resolution, checker-backed bindings and ordered module initialization. Inventory the real graph before implementation; settle package-source publication and user-code hosting separately.

    Gate: imported functions/aliases/barrels, name collisions, side-effect order and diamond initialization pass public compile() parity tests. Unsupported cycles, JS-only/value-declaration-only dependencies and TLA fail explicitly. No diagnostic bypasses.

  3. Compile the actual Crust entry

    Add only features required by its dependency graph: modules → state/control flow → objects/classes/collections and closures → async/errors + host APIs, ordered by the probes.

    Gate: compile(packages/crust/src/cli.ts) produces an executable whose --help and --version match the Bun baseline. Disclose any approved host adapter; keep real commands registered.

  4. Run a real build and publish preparation

    Use a disposable Crust project, default snapshot validation and Extension hooks. Reuse existing staging/publishing; do not create a second distribution system.

    Gate: native crust build --target host stages a runnable installed CLI; publish --dry-run invokes no npm process; injected build failure writes no success manifest.

  5. Prove distribution and publishing safety

    Cover interactive npm 2FA, existing-version skips, root-last ordering, registry errors and resumable partial failure. List external tool requirements per profile.

    Gate: fake-npm whole-binary tests + install/run on each claimed target. A real registry canary needs explicit authorization; a dry run does not prove publishing works.

  6. Evaluate native compilation of migrated GT Tracks converge

    Once GT uses Crust and the compiler can build Crust itself, pin the migrated entry and re-inventory its dependency/runtime gaps. Do not target the old Commander shell or rewrite translation internals merely to get a binary.

    Gate: compare compiler-produced GT against the migrated JS-runtime baseline: help + controlled dry run → selected TS/JSX extraction → authorized API upload/poll/download. Native, hybrid and JS-runtime distribution remain separate outcomes.

Acceptance details that are easy to miss
  • Default Crust validation executes the user's entry and expects snapshot/build-report files. --no-validate also skips hooks; it cannot substitute for the real-build gate.
  • Distribution writes the manifest last, but does not promise transactional rollback of the stage directory.
  • compile() currently resolves runtime/m0.d.ts and the Go module beside its JS files. Prove those assets survive relocation/bundling before integrating the compiler into an installed CLI.
  • Current argv prepends the native executable and the source entry path. Decide the installed-command contract rather than shipping build-machine paths by accident.
  • The compiler has no explicit target option; go build inherits its environment. Cross-target support needs its own contract and target runners, not just a successful host build.
  • Publish: an existing registry version is skipped; E404 means missing and eligible for publishing; inconclusive lookup aborts. Test these independently.
  • GT: use a disposable writable project, JSON-only content and stageTranslations: false for an initial translation dry run. Preprocessing/postprocessing still exist. Never infer a network sandbox from a flag name.
  • No performance, binary-size or completion-percentage claim is established by this investigation.
