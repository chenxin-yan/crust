# @crustjs/utils

## 0.3.0

### Minor Changes

- [#510](https://github.com/chenxin-yan/crust/pull/510) [`6fdb8a6`](https://github.com/chenxin-yan/crust/commit/6fdb8a642b79a176d60d9a3d4be3431493201052) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `tryCoerceNumber` returns `undefined` for empty or whitespace-only input instead of `0`. Store `type: "number"` fields reject a persisted blank string with a `VALIDATION` error instead of reading it as `0`, and `@crustjs/env` reports `PORT=""` as invalid for `type: "number"`, as documented.

- [#602](https://github.com/chenxin-yan/crust/pull/602) [`a074f45`](https://github.com/chenxin-yan/crust/commit/a074f454a28611f0a0a1f3d0bab8df50b235960d) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Commands can declare their result with `.output(schema)` (any Standard Schema). Declared before `.action()`, TypeScript requires the action to return the schema's input type; at runtime Crust validates the awaited result and returns the schema's output as the `result`, typed in `run()` and passed to `postRun`. A rejected result fails with the new `OUTPUT` `CrustError` code (`details.issues`, paths relative to the result). `CommandSnapshot.outputSchema` carries the result's draft 2020-12 JSON Schema when the schema implements Standard JSON Schema, and `@crustjs/core/tooling` exports `standardJsonSchema(schema, "input" | "output")`, which returns that JSON Schema or `undefined` when the schema has no converter or it throws. Commands without `.output()` are unchanged. `@crustjs/utils/schema` exports the `StandardJSONSchema` and `InferInput` types.

- [#595](https://github.com/chenxin-yan/crust/pull/595) [`516bb0a`](https://github.com/chenxin-yan/crust/commit/516bb0a6bff1aa10c31080b799ef76c54ec12331) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `@crustjs/core/tooling` exports the command <-> JSON input mapping that `@crustjs/mcp` used internally. `commandInputSchema(command, path)` describes a command's input as one flat JSON Schema object (each arg and flag by name, plus `raw` for passthrough values), and `parseCommandInput(command, values)` turns such an object into structured `run()` input, converting `url` strings to `URL`s (an invalid one fails with the same `PARSE` error as argv, `Invalid URL for --name.`). Also exported: `commandInputFields(command)` (the arg and `url` field names that split uses), `RAW_INPUT_PROPERTY`, and the `CommandInputFields`, `CommandInputSchema`, `CommandInputPropertySchema`, `RunInputPayload`, and `RunInputValue` types. `@crustjs/utils/json` exports `parseJsonValue(value)`, which returns a detached copy of plain JSON data (reading each property once) and throws a `TypeError` for anything JSON would not round-trip, such as `undefined`, `NaN`, class instances, array holes, or cycles (`-0` is the one exception: it is kept, though `JSON.stringify` writes it as `0`); core uses it for this input and `@crustjs/mcp` for tool results.

- [#539](https://github.com/chenxin-yan/crust/pull/539) [`ce12aed`](https://github.com/chenxin-yan/crust/commit/ce12aed7a34275c49b54340d1995378afedfa2a6) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Drop Deno support. Crust now targets Bun and Node.js only.
  
  - `@crustjs/crust`: `crust.runtime: "deno"` and Deno targets are removed; `deno.json`/`deno.jsonc` no longer selects a runtime. `--minify` now defaults to `true` in `--help`.
  - `create-crust`: `--runtime deno` is no longer accepted.
  - `@crustjs/utils`: `PACKAGED_BUILD_KEY` and `isPackagedBuild` are removed from `@crustjs/utils/artifacts`, and Deno compiled executables are no longer detected.
  - `@crustjs/core`: the snapshot protocol no longer checks the packaged-build marker.
  - `@crustjs/mcp`: Deno standalone builds are no longer detected as compiled executables.

- [#540](https://github.com/chenxin-yan/crust/pull/540) [`643beb2`](https://github.com/chenxin-yan/crust/commit/643beb264f5b206177110dd947b258f47cc68073) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - On Bun on Linux, a CLI started with a signal ignored (SIGHUP under `nohup`, SIGINT for a background job in a script) now keeps ignoring it. Core's Ctrl-C handling, timed `runProcess()` calls, and `crust build`'s snapshot step no longer listen for an ignored signal; listening replaced the ignore, and Bun restores the default action when the listener is removed, so the process could die from a signal it was started to ignore. Node already resets inherited ignores at startup, so nothing changes there. macOS on Bun still loses the ignore until Bun keeps the previous disposition (oven-sh/bun#47574). Adds `isSignalIgnored()` from `@crustjs/utils/signals`.

- [#532](https://github.com/chenxin-yan/crust/pull/532) [`3a6dbb1`](https://github.com/chenxin-yan/crust/commit/3a6dbb1702cff684c17054cd476ddef0b5d56f99) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `packageManagerFromUserAgent` and `PackageManager` moved from `@crustjs/utils/process` to the new `@crustjs/utils/package-manager`, which does not load `child_process`, so `updateNotifier()` no longer pays for it at startup.

- [#601](https://github.com/chenxin-yan/crust/pull/601) [`a411ccb`](https://github.com/chenxin-yan/crust/commit/a411ccb1b09eb05dd372757549631f429587981f) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `@crustjs/utils/process` exports `readStdin(signal)`, which reads all of stdin as UTF-8 text without blocking the event loop, so aborting `signal` cancels a read waiting on an open pipe or terminal. It reads stdin that already has an encoding or was paused, and returns `""` for stdin an earlier consumer already read to the end instead of waiting for an `end` event that cannot fire again.

- [#608](https://github.com/chenxin-yan/crust/pull/608) [`0cdd29f`](https://github.com/chenxin-yan/crust/commit/0cdd29fb72ff71e67348f5d7e8cae75753cfaed5) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `@crustjs/utils/process` exports `shellQuote(token)`, which returns a string as one POSIX shell word: unchanged when it contains only safe characters, otherwise single-quoted with apostrophes escaped. `@crustjs/mcp` and `@crustjs/extensions` share it to print commands.

### Patch Changes

- [#558](https://github.com/chenxin-yan/crust/pull/558) [`708e181`](https://github.com/chenxin-yan/crust/commit/708e181f0de97b81b77d64261f754e2649af1761) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Start faster on Node. Core, Extensions, and utils load Node built-ins with `process.getBuiltinModule()` where they are used instead of static `node:*` imports, which made Node evaluate every lazy export of `node:fs` and `node:util` at startup. `node:stream`, which is expensive to load on Bun, now loads only for `run()` and for `execute()` with injected `io`.

- [#517](https://github.com/chenxin-yan/crust/pull/517) [`4a4386d`](https://github.com/chenxin-yan/crust/commit/4a4386d64fdef5440e77cebd8b9ac85e7a1d7350) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `createMcpServer()` and `toolsFromSnapshot()` now throw when an `exclude` path is not a canonical command path, listing each unknown path, so a bad `mcpExtension({ exclude })` path fails when the `mcp` server starts. Previously a misspelled path or an alias was silently ignored and the command stayed exposed as an MCP tool.
  
  `mcp config` now detects a Node single executable application as a compiled executable and prints `<executable> mcp` instead of passing the executable path back to itself as an entry.
  
  `@crustjs/mcp` loads the MCP SDK only when the server starts, so importing the package (and every command of a CLI using `mcpExtension`) no longer pays the SDK's load time.

- [#592](https://github.com/chenxin-yan/crust/pull/592) [`4208178`](https://github.com/chenxin-yan/crust/commit/420817832f065c875e836b86deac832f84d86828) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Spinners and progress indicators without a `sink` or ambient terminal output now write standard error through the same writer as `@crustjs/core`'s default `stderr`, so inside a Command Action they stay in order with the action's `stderr()` lines and restore the cursor even when the process exits right away. Their default colors now follow only their own output, so creating a spinner no longer touches `process.stdout`, and `@crustjs/style` no longer reads `process.stdout` when `overrides.isTTY` is given.
  
  **Behavior change:** on macOS and Linux the default output is written synchronously to file descriptor 2, so replacing `process.stderr.write` no longer captures it. Pass a `sink` or use `withTerminalIO()` to capture spinner output.

- [#522](https://github.com/chenxin-yan/crust/pull/522) [`d64f307`](https://github.com/chenxin-yan/crust/commit/d64f30727fd3d28dcb26b7edeb6aed929a3efe19) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - A Standard Schema without the optional `types` member now infers its output from the successful `validate()` result (awaited) instead of `unknown` in store fields, env variables, and schema-backed flags and arguments; declared `types.output` still wins. `defineEnv()` now rejects a literal default outside literal `choices` and an async `parse` at compile time, as `defineFlag()` does. A store schema whose output is not JSON data now fails with a `FIX_JSON_OUTPUT` message instead of "not assignable to type 'never'". `@crustjs/effect` exports the `HandlerInput` type that `service()` requires, and `@crustjs/core/tooling` exports `LocalValueBrand`.

- [#518](https://github.com/chenxin-yan/crust/pull/518) [`e802ec7`](https://github.com/chenxin-yan/crust/commit/e802ec7c09c6635d77716e3c1c545faa99fe7759) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Generated skill tables fold line breaks in descriptions into spaces, so a multi-line flag, argument, or command description no longer breaks the markdown table.
  
  An authored `SKILL.md` whose `name` or `description` uses a YAML block scalar (`|`, `>-`) is now rejected with an error asking for a one-line value. Previously the indicator itself (`">-"`) became the skill's description.
  
  The background auto-repair before ordinary commands now repairs only owned links whose target no longer exists. A link to another live installed copy of the CLI (global versus project-local, `npx`) is left alone, so two copies no longer move the link back and forth on every run. `skills repair` and `installSkill()` still re-point such links.
  
  `@crustjs/skills` loads `@crustjs/prompts` and `@crustjs/progress` only when the `skills` command runs. `installSkill()`, `uninstallSkill()`, and `getSkillStatus()` accept readonly `agents` arrays.
  
  Relative skill source paths now resolve from the package that owns a symlinked entrypoint (an npm-linked `node_modules/.bin` script) instead of the consumer's package.

- [#520](https://github.com/chenxin-yan/crust/pull/520) [`7811b12`](https://github.com/chenxin-yan/crust/commit/7811b12f73827e1d47a1574c4b88736eb82632b0) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - On POSIX, `runProcess()` with a `timeout` now also kills the child's process group when the calling process receives `SIGINT`, `SIGTERM`, `SIGHUP`, or `SIGQUIT`, or exits synchronously. The call rejects, and the signal is re-raised when no other listener handles it. Previously the detached child and its descendants outlived an interrupted parent. `crust build` uses this for its compiler `--version` probe, so interrupting a build no longer leaves a stuck probe running.
  
  `@crustjs/utils/process` exports `bindToProcessLifetime()`, the signal and exit policy `runProcess()` and `crust build`'s entry preparation now share.

## 0.2.0

### Minor Changes

- [#456](https://github.com/chenxin-yan/crust/pull/456) [`0da2c5c`](https://github.com/chenxin-yan/crust/commit/0da2c5ce54f71acc5d51fad1dcb2c5546a71948e) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Breaking: `crust build` and `build()` now require an explicit artifact kind, set with `"crust": { "artifact": "package" | "binary" }` in package.json, `--artifact`, or the `artifact` build option (the option overrides the config). The implicit defaults are gone: to keep the previous output, set `"artifact": "binary"` for bun and deno projects and `"artifact": "package"` for node projects; the error names the old default for the inferred runtime. Runtime inference is unchanged. New Bun runtime packages (`"runtime": "bun", "artifact": "package"`) stage one root-only package whose commands are Bun-targeted bundles behind `#!/usr/bin/env bun`, so installed commands run on the consumer's Bun. Runtime packages reject `--target` and `crust.targets`. Binary builds select the compiler once (external `bun` on PATH first, then the embedded Bun; `deno` on PATH), check its reported version against `engines.bun`/`engines.deno` before replacing `.crust/` (a `--version` probe that does not exit within 30 seconds is killed and fails the build), print it as `Compiler:`, and record it as `embeddedRuntimeVersion` in `manifest.json`, which now also records `runtime` and `artifact`. Crust never installs or upgrades a compiler. create-crust templates set `crust.artifact` to keep each runtime's existing output.

- [#457](https://github.com/chenxin-yan/crust/pull/457) [`4977f33`](https://github.com/chenxin-yan/crust/commit/4977f33e87a928d968202af40f9729e390b7df93) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Add experimental Deno runtime packages. With `"crust": { "runtime": "deno", "artifact": "package" }` (or `--artifact package`), `crust build` bundles each command with native `deno bundle`, which Deno marks experimental, into a root-only npm package whose `bin/<command>.js` files run on the consumer's installed Deno through `deno run npm:<package>/<command>` or `deno install -g`. The package embeds no runtime, carries no shebang or permission flags, and leaves every grant to the consumer. Building needs `deno` 2.5.0 or newer on PATH, checked in the project directory before `.crust/` is replaced; the bundler version is printed as `Compiler:` but not recorded as `embeddedRuntimeVersion`, and `engines.deno` stays a consumer requirement. `--minify`, `--env-file`, `crust.bunPlugins`, `--target`, and `crust.targets` are rejected for this mode. Deno binaries and their permissions are unchanged.
  
  Finished Deno packages mark themselves through a marker prepended to the bundle, preserving `import.meta.main` for the declared command, so `@crustjs/core` skips Command Snapshot and build-hook execution and `resolveArtifactDir()` from `@crustjs/utils/artifacts` resolves assets beside the installed package, without reading any environment variable. The package must be built against this `@crustjs/core` release or newer: with an older core, the finished package needs `--allow-env` and obeys build-only snapshot variables.

### Patch Changes

- [#458](https://github.com/chenxin-yan/crust/pull/458) [`4360cb1`](https://github.com/chenxin-yan/crust/commit/4360cb1cefca245e76967ade43c82b5361c039e5) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Node standalone binaries: `"runtime": "node", "artifact": "binary"` (or `--artifact binary` for a node project) now builds one Node.js single executable per command and platform with tsdown's executable builder, behind the usual Node launcher and platform packages. `@crustjs/crust` now optionally depends on `tsdown` and `@tsdown/exe`, which the installed crust runs with the external `node` on PATH; no global tsdown is needed. Package managers skip them, rather than failing an engine-strict install, under a Node outside tsdown's engines or with optional dependencies disabled; every other build still works, and Node binary builds then report the missing backend, or a reachable tsdown other than the version crust pins (such as the project's own), before replacing `.crust/` (reinstall with optional dependencies under a compatible Node). That node is the embedded runtime for every target: it must satisfy `engines.node` and the installed tsdown's own requirements (its package engines and executable minimum, Node 26+ with tsdown 0.23), checked before `.crust/` is replaced. Crust never installs or upgrades it. Targets use Node's release names (`linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64`, `win-x64`, `win-arm64`; no musl); every target's official Node.js archive of the same version is downloaded, verified, unpacked, and cached before `.crust/` is replaced, so a missing `tar` (GNU tar also needs `xz` for Linux targets) or `unzip` (Windows targets on other hosts) keeps the previous build, and macOS executables are only signed when built on macOS. Bun first bundles each command for Node exactly like a Node runtime package (so main-module guards, CommonJS entries, and env-file `PUBLIC_*` values behave as in every other build), which makes Bun required for Node binary builds even with `--no-validate`, checked before `.crust/` is replaced; application dependencies are bundled and any other leftover import fails the build; `crust.bunPlugins` is rejected for Node binaries. Staged Node binary packages omit `engines.node`, except on a root that publishes library `exports`. `resolveArtifactDir()` now resolves next to the executable inside a Node single executable application.

- [#457](https://github.com/chenxin-yan/crust/pull/457) [`4977f33`](https://github.com/chenxin-yan/crust/commit/4977f33e87a928d968202af40f9729e390b7df93) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Clean up timed-out subprocess trees instead of only their direct child.
