# @crustjs/openapi

## 0.2.0

### Minor Changes

- [#695](https://github.com/chenxin-yan/crust/pull/695) [`f33da63`](https://github.com/chenxin-yan/crust/commit/f33da63cfb00fda51e6011b8aa7beb081fc42ead) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `api preview` prints the request a generated command or a request path would send, and sends nothing: `acme api preview users delete -- 42` (the command's own arguments and flags after `--`) or `acme api preview /users/42 -X DELETE`. It builds the request with the same plan and checks as the command, returns `{ method, url, headers, bodyKind, body, bound? }` through `.output()` (so `--json` and MCP get it as data), never calls `auth()`, a Context of the command, `.onConfirm()`, a `bind` function or `fetch`, shows a bound value as its `{name}` placeholder, and redacts `Authorization`, `Proxy-Authorization`, `Cookie` and `X-Api-Key` headers. Like `api`, MCP offers it only when `include` names it: `include: [["api", "preview"]]` exposes the preview without the request-sending `api` tool. `api preview …` without a leading `/` used to request the path `preview`; a request path starts with `/`. An override's `paginate` on a result that is not a list leaves the operation out; in an app that adds the generated commands, `api --list` marks it and `crust build` fails (`paginate-needs-array`). `api`'s description now reads "Send a request to any endpoint, or browse the OpenAPI spec; prefer a specific command when one exists", as help, skills and `schema()` show it beside the generated commands.

- [#701](https://github.com/chenxin-yan/crust/pull/701) [`930bed4`](https://github.com/chenxin-yan/crust/commit/930bed44817e815b63ede1058223cc1dbea81ae8) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `auth` moves from `defineApi()`'s options to the handle's chain: `defineApi({ spec, baseUrl }).auth(bearerAuth(auth.token))`. `.auth()` reads the Contexts of the Context factories `.use()`d before it from `input.ctx`, and `bearerAuth()`'s resolver gets them as `ctx`: `.use(profile).auth(bearerAuth(async ({ ctx, signal, baseUrl }) => …))` puts `--profile` on the generated commands, `api`, and the commands that `.use(acme.client)`, and the app `.provide()`s `profile` before `.extend(acme.extension)`. Each `.auth()` makes a new `client`, which the handles after it share; a second `.auth()` replaces the first, and without one requests carry no credentials. `ApiClient` gains a second type parameter, the Contexts its `auth` reads, so a command that uses the client of another `.auth()` than the handle the app extends fails to compile when the two read Contexts of different types; a helper that takes any handle's client is generic in it. `ApiClientOptions` is no longer exported; `ApiAuth<Ctx>` types what `.auth()` takes. `api preview` sets up no Context.

- [#684](https://github.com/chenxin-yan/crust/pull/684) [`75e0938`](https://github.com/chenxin-yan/crust/commit/75e09388f095c0df3a451d63cc5ad66917b9b7a8) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `auth` may return an `AuthAttempt` (`{ headers, retry }`): a 401 to a request that carried its headers is retried once, with a replayable body, with the attempt `retry` returns, which later requests and pages then use. `bearerAuth(resolve)` builds one for a bearer token that `resolve` can refresh, such as the `token` of an `@crustjs/auth` client. `auth` receives `{ baseUrl }` as its second argument. An `auth` that returns plain headers works as before.

- [#689](https://github.com/chenxin-yan/crust/pull/689) [`0b5b41f`](https://github.com/chenxin-yan/crust/commit/0b5b41f4952a3fac2064841b2a152f8fe5e952c8) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `defineApi(options)` replaces `apiCommand()` and the `apiClient` export: it returns `extension`, which contributes the `api` command, and `client`, the `api` Context commands `.use()`. The client's new `call(operationId, input?)` builds the request from the spec and resolves to the 2xx JSON body; with the inspex content mapper on TypeScript 7.1 (experimental), it is typed from the spec through the new `Specs` registry, else its result is `unknown`. `spec` is a `file:` URL (JSONC allowed), which `crust build` writes to `<id>/spec.json` so it stays out of the bundle, or a plain object; a loader is now a `DEFINITION` error.

- [#693](https://github.com/chenxin-yan/crust/pull/693) [`224c684`](https://github.com/chenxin-yan/crust/commit/224c684dfc59be282a1ef4319ade4c017b62283b) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `defineApi()` generates a command per operation of the pinned spec: `new Crust("acme").extend(acme.extension).add(...acme.commands)`. Each is an ordinary app command in its first tag's group, with path parameters as arguments, typed query, header and top-level body field flags, the JSON body as a `--body` JSON flag whose schema stands alone for `schema` and MCP, and `.output()` with the response's JSON Schema; it prints the result for people and returns it. The handle's chain shapes them: `.use()` (Contexts for the callbacks, typed), `.onConfirm()`, `.each()` and `.override()` (one `OperationOverride` shape: `exclude`, `group`, `name`, `hidden`, `description`, `flagName`, `positional`, `bind`, `confirm`, `paginate`, `unwrap`, `outputSchema`, with names checked against a registered spec), and `.add(group, ...commands)`. An operation that does not fit is left out, and nothing throws for one operation. In an app that adds the generated commands, `api --list` marks it `[unavailable: <code>]`, and `crust build` fails, listing each problem with its fix, when configuration can settle it (a name clash, a stale or unknown override, positionals out of order, `confirm` without `.onConfirm()`) or when the document is not OpenAPI 3.0 or 3.1, and skips an operation no configuration can make a command (a required non-JSON body, an unsupported required parameter, a missing or shared operationId). `app.snapshot()` shows the generated commands for a snapshot test of the CLI's surface. `Operation` (what `.each()` receives) is an exported type. `crust build` writes the spec's data files to `<id>/` beside `spec.json`: an index of the generated root commands and top-level groups, which a built CLI reads at start, and the part of the spec the root commands and each top-level group need, which a command reads when it first runs, so start-up does not grow with the size of the API. Above twice the spec's size, those parts are not written and every command reads `spec.json`. A built CLI without its `<id>/` directory has no generated commands, and every invocation fails with a message naming the directory, without a stack. The build fails when the app's generated commands are not those of the handle whose `extension` it uses.

### Patch Changes

- [#707](https://github.com/chenxin-yan/crust/pull/707) [`aa64910`](https://github.com/chenxin-yan/crust/commit/aa64910af94f0659c2790fb4ea3a5729852d3520) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Paths now follow one rule everywhere: a relative path resolves against the place it was written.
  
  - A path the user types resolves against the working directory, with a leading `~` as the home directory. That now covers `create-crust [directory]` and its prompt, `completion --output-dir`, `--input @path`, and `api --body @path`, so `--output-dir=~/completions` and `--input @~/args.json` work where they used to name a directory called `~`.
  - `type: "path"` also expands `~\` on Windows.
  - A path passed in code resolves against the working directory, as Node's `fs` does.
  
  **Behavior change:** in `@crustjs/skills`, a relative `sourceDir` (`installSkill()`, `getSkillStatus()`) or `extras` entry (`skill()`, `writeSkills()`) resolves against the working directory. It used to resolve against the nearest `package.json` above the CLI's entry file, which depended on how the CLI was distributed. During `crust build` the working directory is the project root, so `skill({ extras })` is unaffected there. Elsewhere, pass a path under `artifactPath()`, an absolute path, or a `file:` URL.
  
  **Behavior change:** in `@crustjs/create`, a `command` step's relative `cwd` resolves against the directory passed to `runSteps()`, where it used to resolve against the process working directory. `scaffold()` rejects an empty `template`, and a `template` URL that is not `file:` fails with `Path URL must use the file: protocol`.
  
  **Behavior change:** the `create-crust` prompt accepts the same directory paths as the positional argument, including `:` and `\`, so a Windows path such as `C:\projects\my-cli` can be typed. Only the basename is checked.
  
  **Behavior change:** `resolveSourceDir()` is removed from `@crustjs/utils/source`. Use `resolvePathLike()` from `@crustjs/utils/path`.

## 0.1.1

### Patch Changes

- [#660](https://github.com/chenxin-yan/crust/pull/660) [`efdf932`](https://github.com/chenxin-yan/crust/commit/efdf932eac278054e173dd1b433923b11e25345c) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - `api` works with the `json()` Extension, binary bodies, and large OpenAPI documents.
  
  - **Behavior change:** under `--json`, `api` returns its data, so stdout carries JSON instead of the output moving to stderr. `api <path>` prints the parsed response body (text as a JSON string, nothing for an empty body), `api --list` an array of `{ method, path, operationId?, summary? }`, and `api --spec` the definition. `--paginate` streams one `{"type":"event","data":…}` line per page, then `{"type":"result"}`. A non-2xx response writes its body to stderr and its error JSON has `details` with the HTTP `status`; `json()` prints it for `@crustjs/openapi`'s `ApiResponseError`, and still prints only `message` for other non-Crust errors.
  - **Behavior change:** when stdout is a pipe or file, `api <path>` writes the response body as its exact bytes, like `gh api` and `curl`, so `api /export.zip > export.zip` works. It used to decode every body as UTF-8, which corrupted binary ones, and to end the output with exactly one newline; a text body now keeps its own ending, so one without a final newline no longer gains one. When stdout is a terminal, when output is captured as text (`run()`, `captureExecute()`), under `--json`, or on a `--paginate` page, a body prints as text as before, and one that is not valid UTF-8 fails the command instead of printing corrupted (`gh api` and `curl` also refuse to print binary to a terminal).
  - `api --spec` writes each `$ref` target once: one used once is inlined as before, and one used several times or recursively stays a `$ref` and is written once under a top-level `$refs` object. It used to inline every use, so output grew exponentially and `--spec` hung on large public specs such as Stripe's.
  - `api --spec <operationId>` includes the operation's `method` and `path`, and merges the path item's shared `parameters` into its own, so a path parameter declared on the path item, such as `{petId}`, is no longer missing. An `operationId` several operations share fails, naming them, instead of silently picking the first.
  - `-X` must be an HTTP method token. An empty value or one with spaces, such as `"DELETE "`, fails with a `PARSE` error before any request, and so does a method the runtime's `fetch()` would not send, naming what it would send: Bun's `fetch()` sends a method it does not know as `GET`. Methods are upper-cased as before.
  - `ApiResponseError` messages no longer include the request's query, where `-F` fields of a `GET` (such as a token) end up.

- [#662](https://github.com/chenxin-yan/crust/pull/662) [`08ede40`](https://github.com/chenxin-yan/crust/commit/08ede40377c4749f73e5c4dd8130321b17b8890a) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - The optional `typescript` peer dependency now accepts TypeScript 5.9 and later (`>=5.9.0`) instead of only 7.x, so `npm install` no longer fails with `ERESOLVE` in projects on TypeScript 5.9 or 6. Before TypeScript 7, a one-character emoji `short` flag is rejected, and on 5.9 a `@crustjs/store` field's `validate` callback needs an explicit parameter type.

## 0.1.0

### Minor Changes

- [#613](https://github.com/chenxin-yan/crust/pull/613) [`8313fa7`](https://github.com/chenxin-yan/crust/commit/8313fa7058bb161ead0dd3bc5c4a63ae418d87ee) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - New package `@crustjs/openapi`. `apiCommand({ spec, baseUrl, auth, paginate })` adds a `gh api`-style `api` command: `api --list` and `api --spec <operationId|path>` read the bundled OpenAPI document offline, or call a lazy `spec` loader only then (local `$ref`s resolved, recursive ones kept), and `api <path>` sends a request with `-X`, `-H`, gh-typed `-F key=value` fields, `--body <inline|@file|->`, and `--paginate` (one JSON line per page; fails instead of looping when the next page repeats the previous request). The response body goes to stdout; a non-2xx status also fails with `ApiResponseError` (exit code 1). It provides the `apiClient` Context, so app commands share the base URL and auth through `(await ctx.api).fetch(path, init)`: `auth` runs only on the first request that sends credentials, and `init.auth: false` sends a public request without it.
