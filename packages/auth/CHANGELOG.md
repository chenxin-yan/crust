# @crustjs/auth

## 0.1.0

### Minor Changes

- [#690](https://github.com/chenxin-yan/crust/pull/690) [`1a27f7a`](https://github.com/chenxin-yan/crust/commit/1a27f7abfeae51afdf415a7d9667b79684c9ba85) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Stored logins are encrypted under a key kept in the OS keyring.
  
  - `createAuth()` encrypts the login's tokens with AES-256-GCM under one key per app in the OS keyring: `Bun.secrets` on Bun, the optional peer dependency `@napi-rs/keyring` on Node (pinned to the Secret Service on Linux). The key is created once, under an app-wide `key-init` lock, and never rewritten; the credentials file records its id. Without a keyring the tokens are stored in plaintext in the same `0600` file and the new `onWarning` option receives `{ code: "plaintext-storage" }` once per process (nothing is printed); the new `strict: true` option refuses instead. `status()` adds `storage: { kind, plaintextRecords }`; with an `env` token it still reads neither the file nor the keyring, and has no `storage`.
  - A missing or replaced key fails closed: reading an encrypted login throws `LoginRequiredError` with the new reasons `key-missing`, `key-mismatch`, or `key-other-keyring` (the key is in the other runtime's keyring: on Linux and Windows, `Bun.secrets` and `@napi-rs/keyring` keep it in different entries), and an unreadable keyring throws the new `CredentialKeyError` (`code` `"credential-key"`, `reason` `"unreadable"`, or `"unavailable"` when a login can't be stored). Nothing is reset or downgraded to plaintext; the next login reuses the keyring's key and logs out the logins encrypted under the old one.
  - Plaintext logins are encrypted the next time a login or refresh writes them; a file that records a key never takes plaintext again.
  - `@crustjs/auth/oauth`: `credentialStore()` takes `keyring: { strict?, onWarning? }` (without it, no keyring is used) and gains `status()` (`kind`, `encryption`, `keyReadable`, `plaintextRecords`); `ticket.commit()` reports `discarded`, the logins a key-replacing login logged out.

- [#680](https://github.com/chenxin-yan/crust/pull/680) [`d4252bd`](https://github.com/chenxin-yan/crust/commit/d4252bdedc5f3608d42578008b7c2b0c630987f3) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - New package `@crustjs/auth`: OAuth sign-in for a CLI. `createAuth({ app, issuer, clientId, apiOrigins, scope, env, resource })` returns a client. `login()` runs the whole sign-in: a browser login over a `127.0.0.1` loopback redirect with PKCE `S256` and `state`, or a device-code login (RFC 8628) over SSH, without a display, or with `device: true`; on CI or without a terminal it refuses with `LoginRequiresInteractionError`. It prints nothing itself: your `onUrl` and `onCode` callbacks show the URL (and may call `open()` to launch the browser) and the code. The login is stored in a private credentials file in the app's state directory (a strict `@crustjs/store` file, `0600` on POSIX). `token()` returns the token for your API: the `env` variable's value when it is set, otherwise the stored login, refreshed when it is about to expire and sent only to `apiOrigins`; pass it to `bearerAuth()` from `@crustjs/openapi`. `status()` says where the token comes from without a request, and `logout()` deletes the login and revokes it at the server. The building blocks the client is made of are exported from `@crustjs/auth/oauth`: `defineServers()` declares several authorization servers and `discover()` validates their metadata and exposes its `userinfoEndpoint`; `createAuthorizationSession()`, `startDeviceFlow()` and `createTokenClient()` run each step, `detectLoginMode()` picks the login, and `openBrowser()` launches the system browser without a shell. Several servers must each send `iss` or use their own `redirectPath`, or the browser login refuses (mix-up protection). `credentialStore()` and `createTokenSource()` keep and refresh logins, refreshing once across processes and never resending a refresh whose outcome is unknown.

- [#698](https://github.com/chenxin-yan/crust/pull/698) [`f3b618c`](https://github.com/chenxin-yan/crust/commit/f3b618c3ba47d3c2903d7395943402d8953969a6) Thanks [@chenxin-yan](https://github.com/chenxin-yan)! - Login profiles: one CLI can keep several named logins, such as a work account and a personal one.
  
  - `createAuth({ ..., profiles: { env?: "ACME_PROFILE" } })` turns them on and returns a client with `profile(name?)` and `profiles` (new types `ProfileAuthClient`, `ProfileClient`, `ProfileAuthStatus`, `ProfilesOptions`, `AuthProfile`). Without `profiles`, the client, its types, its environment reads and the bytes it writes to the credentials file are unchanged. The profile variable must differ from `env`.
  - `auth.profile(name)` returns `login`, `token`, `status`, and `logout` for that named login; no name means the current profile. The current profile is the profiles `env` variable's, else the one chosen with `auth.profiles.use(name)`, else `"default"`; the `env` token still wins over every profile.
  - `auth.profiles.list()` returns `{ name, current }` for every profile `profile()` can reach with a stored login for this server and client id, from the file only. `auth.profiles.use(name)` remembers the current profile in the credentials file (`currentProfile`) and fails with `LoginRequiredError` (`missing`) for a profile without a login; logging out of it forgets it.
  - `status()` adds `profile: { name, via }` with profiles on. A profile name is 1 to 64 letters, digits, `-`, `_`, and `.`, not starting with `.` or `-`; another is an `OAuthConfigError`. With profiles on, `LoginRequiredError`'s message names the profile.
  - `@crustjs/auth/oauth`: nothing new; token sources ignore `currentProfile` and keep it as written.
