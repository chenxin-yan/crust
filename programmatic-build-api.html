First, separate compile from build

Exists on the private compiler PR stack

A source file → a binary

import { compile } from "@crustjs/compiler";

const binary = await compile("hello.ts", {
  outputPath: "./out/hello",
});
  • hello.ts can contain console.log("hello"); this is not yet arbitrary Crust source.
  • TypeScript checker → typed IR → Go → go build. Returns an absolute path.
  • No npm staging, hooks, target option or hybrid option. Not on main or published for installation.

Suggested public surface · does not exist yet

A CLI project → a staged package

// Proposed import and result shape.
import { build } from "@crustjs/crust/build";

const result = await build({
  cwd: "/projects/my-cli",
});
console.log(result.stageDir);
  • Reads the same package.json entries/config as crust build; keeps validation/hooks on.
  • Returns the completed .crust/ stage location; rejects on failure. Publishing stays separate.
  • Can be exposed for current Bun/Deno/Node outputs before the Go compiler is ready for Crust.

Extract orchestration, keep the existing work

Today the command action owns this sequence; the proposal moves it into one importable function that both callers await.

Responsibility boundaries for a shared build API
Layer Owns Does not own
CLI adapter Flags, progress display, process exit A duplicate build pipeline
Build function Config, hooks, output ownership, staging, errors Argument parsing or npm publishing
Backend Produce the requested artifact at the assigned path Crust command registration or release policy

Hybrid changes the backend, not the caller

The agreed post-M0 direction fits beneath this API—but graph ownership, the JS engine and its embedding still need implementation.

  • Explicit selection. An unsupported native module fails compilation; it never silently moves to the interpreter. No hybrid or go runtime value is accepted by today's build config.
  • A narrow runtime bridge. Go calls selected JS operations through declared, validated data/result interfaces—not arbitrary shared objects or closures. Errors, async completion, cancellation and cleanup need a defined contract.
  • Reuse the existing execution callback. Distribution.execute(entry, outfile, target) is already the binary-producing integration point; target metadata, engine assets and launcher/runtime assumptions still need adaptation.

Build host ≠ output runtime

A Bun-hosted API can produce a Go executable, but QuickJS cannot run Bun.build, and a Go-based Crust cannot turn itself into Bun with BUN_BE_BUN=1.

What exposing it actually requires
  1. Move the action's orchestration into a library module. Keep planBuild, snapshot preparation and distribution implementation behind build(). Let the CLI translate flags into options. Do not import src/cli.ts: it calls await crustApp.execute() at module load.
  2. Keep one source of configuration truth. Resolve cwd explicitly, without process.chdir(). Keep package.json as the source for bin, runtime, plugins and included directories; map deliberate API overrides into the existing planner. Omitted targets currently mean every configured/supported Bun or Deno target—not only the host. Node outputs have no target option.
  3. Define a small library contract. Initially return { stageDir } only after successful manifest creation. Accept output callbacks using the existing InvocationIO shape; reject with errors rather than exiting the caller. Do not advertise cancellation until it reaches snapshots, tool subprocesses and cleanup.
  4. Ship the import, not just a source export. The proposed @crustjs/crust/build subpath needs a built JS module, declarations and an export map in the actual published tree. Today's package is CLI-oriented; staging explicitly lists bin plus artifact/include directories. Retain library files and resolve their dependencies in that staged package; a repository-only import test is insufficient.
  5. Prove parity before adding another backend. Reuse current build tests, then compare CLI and API staging for the same disposable project. Test installed-package imports, hook errors, artifact collisions and failed compilation with no success manifest. Add Go/hybrid integration only after its own capability gates pass.

Keep the current sharp edges visible

  • .crust/ is deleted before hooks run: no atomic rollback and no concurrent builds sharing that directory.
  • Snapshot preparation executes project code and hooks in a subprocess. It is not a sandbox; validate: false also skips hooks.
  • Snapshot execution currently uses process.execPath with Bun conventions. Start by documenting a Bun build host; Node-hosted or native-hosted API support needs explicit runner work.
Current behavior, evidence and limits

What the compiler API does today

  • CompileOptions has only outputPath. No engine, target, watch, cache, cancellation or hybrid fields.
  • With an explicit path it removes its temporary Go workspace and retains the binary; otherwise the caller owns the returned binary's temporary directory.
  • Source failures reject with CompilerError.diagnostics; Go/tool failures also reject, but are not source diagnostics.
  • The build needs Go on PATH and the compiler's adjacent runtime assets. The compiler does not depend on Crust packages.

What Crust build does today

  • Bun and Deno produce platform binaries behind a Node launcher. Node produces a root-only JS bundle; Bun still performs that bundling.
  • Snapshots validate commands and collect Extension build output. They are not typed IR and cannot replace original TS as native compiler input.
  • The completion manifest is written last; crust publish consumes staged packages separately.
  • The compiler stack cannot yet compile the real Crust CLI. Exposing a library function alone does not change this.
