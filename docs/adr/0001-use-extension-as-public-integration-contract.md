# Use Extension as the public integration contract

Crust will name reusable CLI capabilities Extensions throughout its supported API, including `.extend()`, `extension()`, and the `@crustjs/extensions` package. Extensions apply to the whole application, own the flags and commands they contribute, and do not alter application handler types. Their global flag, alias, and root-command names must not collide with application or other Extension definitions; collisions are definition errors. `extension(name, config)` returns a frozen structural value whose plain config may declare owned flags and commands, one `intercept(context, next)` primitive, and `handleError`. `intercept` executes after routing and syntax parsing but before application value validation and Context construction, so Extensions can short-circuit without exposing nullable parser state; Extension-owned inputs are validated before the hook, while routing and syntax failures flow directly to error handling. Multiple `handleError(error, context, next)` hooks form a presentation-only chain ending in Core's default renderer; an Extension may replace or delegate rendering, but Core always preserves a nonzero failure outcome. Extension hooks and public errors receive readonly, serializable Command Snapshots rather than internal command nodes. Internal execution machinery will not be a supported public contract; this favors one coherent beta vocabulary and a narrow, structurally typed application-level contract over preserving the pre-beta `@crustjs/plugins` name, scoped extension inheritance, generic composition with application inputs, redundant lifecycle sugar, or recoverable error-hook protocols.
