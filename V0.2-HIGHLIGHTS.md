# crust v0.2 — noticeable changes since @crustjs/core@0.0.19

Tweet-ready highlights. Each entry: a two-sentence summary and a minimal before/after showing the DX difference.

## Contexts & dependency injection

### Pull typed services with `ctx.use()`

In crust v0.2, commands get lazy, typed services with `await ctx.use(factory)` instead of wiring shared objects into closures. Providers stay cold until pulled, then resolve once per invocation.

**Before:**

```ts
const config = await loadConfig();
const database = await createDatabase(config);

new Crust("status").run(() => database.query("select 1"));
```

**After:**

```ts
const config = defineContext("config", async () => await loadConfig());

const database = defineContext("db", async ({ ctx }) => {
	const cfg = await ctx.use(config);
	return await connect(cfg);
});

new Crust("status").provide(config(), database()).action(async ({ ctx }) => {
	const db = await ctx.use(database);
	await db.query("select 1");
});
```

### Pull dependencies where services are built

In crust v0.2, Context setup pulls dependencies with the same typed `await ctx.use(factory)` pattern as command actions. Provide in any order — crust builds only the services actually pulled.

**Before:**

```ts
const config = loadConfig();
const database = connect(config);
```

**After:**

```ts
const config = defineContext("config", () => loadConfig());
const database = defineContext("db", async ({ ctx }) => {
	const cfg = await ctx.use(config);
	return connect(cfg);
});
```

### Context setup gets invocation I/O

In crust v0.2, Context setup receives the invocation's injected `stdout` and `stderr`, just like the command action. Service output now lands in the same capture path instead of escaping through global console calls.

**Before:**

```ts
const logger = { info: (msg: string) => console.error(msg) };
```

**After:**

```ts
const logger = defineContext("logger", ({ stderr }) => ({
	info: (msg: string) => stderr(msg),
}));
```

## Typed run & testing

### Programmatic runs are typed end to end

In crust v0.2, programmatic `run()` takes an inferred command path plus structured args and flags instead of an untyped argv blob. Typos fail in the editor, while the same routing and parser pipeline still does the real work.

**Before:**

```ts
await app.execute({ argv: ["remote", "add", "origin", "--fetch"] });
```

**After:**

```ts
await app.run(["remote", "add"], { args: { name: "origin" }, flags: { fetch: true } });
```

### Output tests get a typed capture harness

In crust v0.2, the new `@crustjs/testing` package turns output assertions into a typed `captureRun()` call with command, argument, and flag autocomplete. It preserves stdout and stderr even when the action fails, returning the original error beside them.

**Before:**

```ts
const lines: string[] = [];
console.log = (...a) => void lines.push(a.join(" "));
await app.execute({ argv: ["build", "--minify"] });
```

**After:**

```ts
const result = await captureRun(app, ["build"], { flags: { minify: true } });
expect(result.stdout).toBe("Built");
```

### Interactive tests get a fake TTY

In crust v0.2, `runInteractive()` gives prompt-heavy commands a fake TTY with `waitFor()`, `type()`, `keys()`, and `screen()`. Interactive tests stay in-process and fail fast instead of hanging on a missed prompt.

**Before:**

```ts
const proc = Bun.spawn(["bun", "run", "src/cli.ts"], { stdin: "pipe" });
proc.stdin.write("my-app\n");
await proc.exited;
```

**After:**

```ts
const run = runInteractive(app, []);
await run.waitFor(/Project name/);
run.type("my-app");
run.keys("return");
```

### Terminal behavior is testable in process

In crust v0.2, `captureExecute()` drives raw terminal argv through rendered errors and real exit codes without a subprocess. `execute({ argv, io })` accepts injected streams, and the helper restores `process.exitCode` after every assertion.

**Before:**

```ts
await app.execute({ argv: ["--unknown"] });
expect(process.exitCode).toBe(1);
```

**After:**

```ts
const result = await captureExecute(app, ["--unknown"]);
expect(result.exitCode).toBe(1);
expect(result.stderr).toContain("Unknown flag");
```

## Schemas & choices

### One schema lane across prompts and store

In crust v0.2, `input()` and `password()` take Standard Schemas through `schema`, leaving `validate` exclusively for throw-on-failure functions. Store fields drop the `field()` factory for the same direct `{ schema }` shape, so the schema solely owns validation, defaults, and the inferred type.

**Before:**

```ts
const port = await input({ validate: z.coerce.number().int() });
fields: {
	port: field(z.number(), { default: 3000 });
}
```

**After:**

```ts
const port = await input({ schema: z.coerce.number().int() });
fields: {
	port: {
		schema: z.number().default(3000);
	}
}
```

### Invalid choice defaults fail up front

In crust v0.2, a flag or argument default outside its own `choices` is rejected during definition validation instead of lurking until the default is applied. Bad definitions fail fast on every build or parse path.

**Before:**

```ts
.flags({ mode: { type: "string", choices: ["dev", "prod"], default: "test" } })
// accepted, breaks later
```

**After:**

```ts
.flags({ name: "mode", type: "string", choices: ["dev", "prod"], default: "test" })
// throws at definition time
```

## Extensions

### Plugins become lifecycle-aware Extensions

In crust v0.2, Plugins become Extensions: `@crustjs/extensions`, short factory names, and `.extend()` replace `@crustjs/plugins`, `*Plugin()`, and `.use()`. Custom middleware chains become named `preRun`, `postRun`, and `onError` hooks, with `ctx.finish()` for successful short-circuits.

**Before:**

```ts
import { helpPlugin } from "@crustjs/plugins";
const audit: CrustPlugin = {
	async middleware(ctx, next) {
		await next();
	},
};
new Crust("cli").use(helpPlugin()).use(audit);
```

**After:**

```ts
import { help } from "@crustjs/extensions";
const audit = defineExtension("audit", {
	hooks: { postRun: (ctx, outcome) => console.log(outcome.status) },
});
new Crust("cli").extend(help(), audit);
```

### Extension flags become declarative and typed

In crust v0.2, Extension flags are declared as named readonly definitions instead of being injected imperatively during setup. Hook contexts infer their typed values, and duplicate names or aliases fail right at `defineExtension()`.

**Before:**

```ts
setup(ctx, actions) {
  actions.addFlag(ctx.rootCommand, "trace", { type: "boolean" });
},
```

**After:**

```ts
flags: [{ name: "trace", type: "boolean" }],
hooks: { preRun: (ctx) => ctx.flags.trace && ctx.stderr("tracing") },
```

### Extensions can own build artifacts

In crust v0.2, Extensions can own build-time artifacts with an async `build({ snapshot, outDir })` hook. `crust build` runs every registered hook against the unified command snapshot, so installing the Extension is the build switch.

**Before:**

```ts
const { root } = await app.prepareCommandTree();
await Bun.write("dist/commands.json", JSON.stringify(root));
```

**After:**

```ts
defineExtension("artifacts", {
	async build({ snapshot, outDir }) {
		await Bun.write(`${outDir}/commands.json`, JSON.stringify(snapshot));
	},
});
```

### Extensions can enrich every command's docs

In crust v0.2, Extensions append ordered plain-text sections to any command path, flowing through help, man pages, and generated agent skills alike. Long-form guidance no longer hides inside a description string.

**Before:**

```ts
rootCommand.subCommands.deploy.meta.description = "Deploy. Approval required.";
```

**After:**

```ts
sections: () => [{ command: ["deploy"], title: "Policy", body: "Approval required." }],
```

### Documentation sections name their audience

In crust v0.2, sections target specific consumers with `only` and `except` — write agent-only guidance that never clutters `--help`, or human-only notes that stay out of generated skills. Core hardcodes no consumer names: help, man, and skills each export a token (`HELP`, `MAN`, `SKILLS`), and any renderer can mint its own with `defineSectionConsumer()`.

**Before:**

```ts
sections: [{ title: "Agent notes", body: "Diff the plan before deploying." }];
// renders in --help and man pages too
```

**After:**

```ts
import { SKILLS } from "@crustjs/skills";
sections: [{ title: "Agent notes", body: "Diff the plan before deploying.", only: [SKILLS] }];
// generated skill only — humans never see it
```

### Authored skills build from the extension config

In crust v0.2, the skills extension accepts hand-authored skill directories through `extras`, and `crust build` regenerates the command-reference skill from the snapshot and packages the authored skills beside it. No more hand-maintaining a prebuilt source directory just to ship your own SKILL.md files.

**Before:**

```ts
skill({ source: "./skills" });
// build copies the prebuilt source verbatim — authored skills
// must be manually merged into it and survive every rebuild
```

**After:**

```ts
skill({ source: "./skills", extras: ["./docs/skills/deploy-guide"] });
// build emits the generated command skill + deploy-guide together
```

### Tooling consumes one command snapshot

In crust v0.2, build validation and man generation share a single command-snapshot protocol. `writeManPage()` accepts a prepared `root` snapshot instead of a live app, so entry modules no longer need to export their builder.

**Before:**

```ts
await writeManPage({ app, name: "my-cli", outfile: "man/my-cli.1" });
```

**After:**

```ts
const root = await app.snapshot();
await writeManPage({ root, name: "my-cli", outfile: "man/my-cli.1" });
```

## Runtime & CLI UX

### Boolean aliases negate like their canonical flags

In crust v0.2, long boolean aliases are true synonyms: `--no-loud` negates `--verbose` when `loud` is its alias, and `noNegate` rejects every negated spelling. Help closes the loop by printing callable long aliases alongside canonical and short names.

**Before:**

```sh
$ app --no-loud
Unknown flag "--no-loud"
```

**After:**

```sh
$ app --no-loud
# flags.verbose === false
```

### Pre-subcommand flags route predictably

In crust v0.2, recursive flags before a subcommand follow that subcommand, so `app --help deploy` shows deploy's help instead of root help. A local flag the routed child cannot accept is rejected immediately with a targeted parse error.

**Before:**

```sh
$ app --help deploy
# ...root help, deploy ignored
```

**After:**

```sh
$ app --help deploy
# ...deploy help
$ app --quiet deploy
Flag "--quiet" cannot be used before subcommand "deploy"
```

### Standard environment variables own color

In crust v0.2, `NO_COLOR` and chalk-compatible `FORCE_COLOR` replace crust's private global color switch, re-read on every call. The `--color`/`--no-color` Extension scopes those variables per run, so child processes and other libraries follow the same choice.

**Before:**

```ts
setGlobalColorMode("never");
style.red("error");
```

**After:**

```ts
process.env.NO_COLOR = "1";
style.red("error");
```

### Prompts gain injectable IO and standard cancellation

In crust v0.2, every prompt accepts injected IO and `withPromptIO()` scopes streams for clean in-process tests. Ctrl+C now rejects with the platform-standard `AbortError` `DOMException` instead of crust's removed `CancelledError`.

**Before:**

```ts
catch (err) {
  if (err instanceof CancelledError) cancel();
}
```

**After:**

```ts
catch (err) {
  if (err instanceof DOMException && err.name === "AbortError") cancel();
}
```

### Progress escapes the task callback

In crust v0.2, `spinner()` without a task returns an imperative handle, and the new `progress()` renders determinate current-over-total updates across call frames. Finish with an error state without throwing, and opt out of SIGINT handling when you own cancellation.

**Before:**

```ts
await spinner({ message: "Deploying", task: deploy });
```

**After:**

```ts
const bar = progress({ total: files.length, message: "Files" });
bar.advance();
bar.stop();
```

### Help advertises packaged agent skills

In crust v0.2, root help and generated man pages list every packaged agent skill with its description and resolved source path. Skills install symlink-first from the package source, so `--help` is now the discovery surface for agent-facing docs.

**Before:**

```sh
$ app --help
# skills invisible unless you read the package
```

**After:**

```sh
$ app --help
...
Agent skills:
  deploy-guide   How to drive app deploys safely
```
