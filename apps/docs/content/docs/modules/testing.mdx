`@crustjs/testing` adds helpers for raw `execute()` capture and fake interactive terminals. For ordinary typed action tests, use Core's [`app.run()`](/docs/api/crust#runpath-input-options), which already captures output and returns the action result; see [Testing](/docs/guide/testing).

## Install

```npm
npm install -D @crustjs/testing
```

`@crustjs/core` is a required peer. `@crustjs/prompts` is an optional peer needed only by the `@crustjs/testing/interactive` entry point; the root entry point works without it. TypeScript is an optional peer.

## `captureExecute(app, argv)`

<include lang="ts">../../../examples/modules/testing.ts#execute</include>

`captureExecute()` drives raw argv through `execute()` in-process and returns `stdout`, `stderr`, and `exitCode`. It restores the previous process exit state after capture. Use it for parser errors, rendered failures, and Extension `onError` output. `app` is anything with Crust's `execute({ argv, io })` method (`ExecutableApp`).

`stdout` and `stderr` hold each `stdout()` or `stderr()` call's text joined with newlines, like `run()`'s outcome: the newline `execute()` appends to every line in a terminal is between lines, not after the last one, so a single line compares as `"Error: …"`, not `"Error: …\n"`.

## `runInteractive(app, path, input?)`

Import from `@crustjs/testing/interactive`; this entry point requires `@crustjs/prompts`. `path` and `input` are typed like `app.run()`, so a definition must be added to the application before it can be addressed.

<include lang="ts">../../../examples/modules/testing.ts#interactive</include>

`waitFor()` polls the ANSI-stripped screen and defaults to a 5000 ms timeout. It fails as soon as the invocation fails or completes without a match, rather than waiting for the timeout. Call `type()` or `keys()` after the expected prompt appears, then await `done`.

`done` settles after cleanup like `app.run()`. It resolves with the `completed` outcome, carrying the typed `result`, or the `handled` one, each with the captured `stdout` and `stderr` (the action's `stderr()` lines, without prompt frames). It rejects with the error from a failed outcome. One ambient [`withTerminalIO`](/docs/modules/progress#output-sinks) scope sends prompts, progress, and `stderr()` output to the fake screen.

The action's `stdout()` output stays off the screen; read it with the handle's `stdout()` method.

The fake terminal counts as interactive even when `CI` is set, so a test that answers a [`confirm()`](/docs/modules/extensions/confirm) prompt passes on CI runners too. `runInteractive()` has no exit code, because it runs through `run()`; use `captureExecute()` to assert one. It does not inject stdin or environment variables: test `readStdin()`, `--input -`, and `env`-sourced flags in a subprocess, or pass the values as `run()` input.

## Styled output

Captured `stdout` is plain text: [`@crustjs/style`](/docs/modules/style) emits no ANSI codes for text bound for `run()`, `captureExecute()`, or `runInteractive()`, whether or not the test runner's own stdout is a terminal. Set `FORCE_COLOR` in the test environment to assert on escape codes.

Some runners set `FORCE_COLOR=1` for their workers when their own output is a color terminal, such as Jest's child-process workers and `bun test --parallel`, which brings the escape codes back. For plain output under those runners, delete `process.env.FORCE_COLOR` in a setup file.

## Custom prompts

`@crustjs/testing` does not re-export prompt-author helpers. Test custom prompts with [`renderPrompt()`](/docs/modules/prompts#testing-custom-prompts) from `@crustjs/prompts/testing`.
