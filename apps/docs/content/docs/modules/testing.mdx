title: Testing

`@crustjs/testing` runs an app's command line in-process, as a user types it, and returns what it wrote and its exit code. For typed action tests, use Core's [`app.run(path, input)`](/docs/api/crust#runpath-input-options), which returns the action's typed result; see [Testing](/docs/guide/testing).

## Install

```npm
npm install -D @crustjs/testing
```

`@crustjs/core` is a required peer. `@crustjs/prompts` is an optional peer needed only by the `@crustjs/testing/interactive` entry point; the root entry point works without it. TypeScript is an optional peer.

## Command line or typed `run()`

| Test                                                   | Use                                        |
| ------------------------------------------------------ | ------------------------------------------ |
| The typed result or error of one action                | `app.run(path, input)`                     |
| Parsing, rendered errors, Extension output, exit codes | `captureExecute(app, argv)`                |
| Prompts answered on a terminal                         | `runInteractive(app, argv)`                |
| A typed `run()` with its own environment               | `withEnv(env, () => app.run(path, input))` |

`captureExecute()` and `runInteractive()` take argv, run it through `execute()`, and resolve to `{ stdout, stderr, exitCode }`. Argv cannot be tied to a command's result type, so neither returns a typed result.

## `captureExecute(app, argv)`

<include lang="ts">../../../examples/modules/testing.ts#execute</include>

`captureExecute()` runs `argv` through `execute()` in-process and resolves to `stdout`, `stderr`, and `exitCode`. It leaves `process.exitCode` as it was. Use it for parser errors, rendered failures, Extension `onError` output, and exit codes. `app` is anything with Crust's `execute()` method (`ExecutableApp`).

`stdout` and `stderr` hold exactly what was written, decoded as UTF-8: `stdout(text)` writes `text` and a newline, so a one-line error compares as `"Error: …\n"`.

<auto-type-table path="../../../../../packages/testing/src/capture.ts" name="CapturedExecute" />

An optional third argument takes [`CaptureOptions`](#captureoptions), plus the streams the action sees:

- `stdin` is the text the action reads from [`stdin`](/docs/guide/terminal-io#read-stdin); `stdin.isTTY` is then `false`, as for a pipe. Without it, stdin is empty.
- `isTTY: true` makes `stdout.isTTY` and `stderr.isTTY` `true`, and `stdin.isTTY` too unless `stdin` is given. `columns` sets their width, `80` by default, and needs `isTTY: true`. Without `isTTY`, the streams are no terminal and `columns` is `undefined`.

```ts
await captureExecute(app, ["-"], { stdin: "a\nb\n" });
await captureExecute(app, [], { isTTY: true, columns: 120 });
```

## `runInteractive(app, argv)`

Import from `@crustjs/testing/interactive`; this entry point requires `@crustjs/prompts`. `runInteractive(app, argv, options?)` runs `argv` through `execute()` on a fake terminal and returns a handle to drive it. The options take [`CaptureOptions`](#captureoptions).

<include lang="ts">../../../examples/modules/testing.ts#interactive</include>

- Prompts, progress, and the action's `stderr` draw on the terminal; `screen()` returns it as plain text. The action's `stdout` is captured apart, as a pipe: read it with the handle's `stdout()` method or from `done`.
- `waitFor()` polls the screen and defaults to a 5000 ms timeout; on a timeout it cancels the run. It fails as soon as the run ends without a match, rather than waiting for the timeout. Call `type()` or `keys()` after the expected prompt appears, then await `done`.
- `type(text)` types text. `keys()` presses named keys (`"return"`, `"up"`, `"space"`, `"escape"`, …) and `ctrl+<letter>`; any other name is a compile error.
- `resize(columns, rows)` resizes the terminal: later output wraps at the new width, `stderr.columns` reports it, and the terminal emits `resize`. It starts at 80 by 24.
- `cancel()` cancels the run as Ctrl-C does, with `signal.reason.cause` set to `"SIGINT"`: a waiting prompt, or any work that honors [`signal`](/docs/guide/error-handling#cancellation), ends it with exit code `130`.
- `done` resolves after cleanup with `stdout`, `stderr` (what the run wrote to stderr, without prompt frames), and `exitCode`, as `captureExecute()` does. It never rejects: a failure is its rendered error and exit code.

The action's `stdin` is the terminal. The fake terminal counts as interactive even when `CI` is set, so a test that answers a [`confirm()`](/docs/modules/extensions/confirm) prompt passes on CI runners too. Test reading piped stdin and `--input -` with `captureExecute()`'s `stdin` option.

## `CaptureOptions`

Options for `captureExecute()` and `runInteractive()`:

- `env` replaces `process.env` for the run and restores it afterwards. Flags' [`env` fallbacks](/docs/api/types#flagdef), settings, config and state directories, app code reading `process.env`, and child processes all see only these variables, so a result doesn't depend on the shell that runs the tests. `{}` is an empty environment; `{ ...process.env, NAME: "value" }` keeps the shell's and changes one; a variable set to `undefined` is left out, as with Node's `spawn()`. An empty environment does not move the config, data, state and cache directories: without `XDG_*` variables (`APPDATA` and `LOCALAPPDATA` on Windows) they are under the real home directory. A test that writes them points those variables at a temporary folder; see [Storage paths](/docs/modules/store#storage-paths). A `HOME` in `env` moves them on Node on macOS and Linux but not under Bun.
- `cwd` sets the working directory for the run, resolved against the current one, and restores it afterwards.
- Captured `stdout` and `stderr` are plain text: ANSI escape sequences are stripped, like `@oclif/test` and `@inquirer/testing` do. Set `raw: true` to keep them and assert on styling.

<include lang="ts">../../../examples/modules/testing.ts#env</include>

Both helpers also take `provide`: Context instances, such as [`.of()`](/docs/guide/contexts#replace-a-context-in-tests) doubles, that replace the app's same-name Contexts for this run only, so a test needs no app factory. It is typed against the Contexts the app provides at its root:

```ts
await captureExecute(app, ["ps"], { provide: [engine.of(fakeEngine)] });
```

The environment and the working directory belong to the process, so one run at a time may replace them: a call with `env` or `cwd`, or `withEnv()`, throws while another run is active. A run without them that starts during a replacement sees the replaced environment and directory. Run these tests one after another (Vitest runs the tests of one file in order unless they are `concurrent`). For `runInteractive()`, the replacement lasts until `done` settles: a `waitFor()` that times out cancels the run, and a test that can fail before awaiting `done` otherwise should call `cancel()` and then await `done`, for example in `afterEach`. An action that ignores `signal` keeps the replacement until it returns.

## Styled output

`app.run()` returns what the app wrote, escape codes included: [`@crustjs/style`](/docs/modules/style#color-control) decides from the test process's stdout and environment. For plain text, set `process.env.FORCE_COLOR = "0"` in a test setup file (Bun's `preload`, Vitest's `setupFiles`), or use `captureExecute()` and `runInteractive()`, which strip escape codes. A setup file also works under `bun test --parallel`, which gives its workers `FORCE_COLOR=1` on a color terminal even when the command line sets `FORCE_COLOR=0`. To assert on escape codes, set `FORCE_COLOR=1` in the test and, with the helpers, pass `raw: true`.

## Custom prompts

`@crustjs/testing` does not re-export prompt-author helpers. Test custom prompts with [`renderPrompt()`](/docs/modules/prompts#testing-custom-prompts) from `@crustjs/prompts/testing`.
