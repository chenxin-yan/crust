`@crustjs/testing` adds helpers for raw `execute()` capture, property-based input round-trips, and fake interactive terminals. Use core `run()` for ordinary typed action tests.

## Install

```npm
npm install -D @crustjs/testing
```

`@crustjs/core` is a required peer. `@crustjs/prompts` is an optional peer needed only by the `@crustjs/testing/interactive` entry point; the root entry point works without it. TypeScript is an optional peer.

## Application contracts

```ts
interface ExecutableApp {
  execute(options?: { argv?: string[]; io?: CaptureIO }): Promise<number>;
}
```

`captureExecute()` accepts this structural contract. `fuzzRoundTrip()` and `runInteractive()` (from `@crustjs/testing/interactive`) accept a Crust application and infer its command paths.

An inert definition must be added to an application before the typed helpers can address it. Core's typed invocation rules are documented under [`run()` path and input](/docs/api/crust#runpath-input-options).

## `app.run(path, input?)`

```ts
const outcome = await app.run(["build"], { flags: { minify: true } });
if (outcome.status === "failed") throw outcome.error;
expect(outcome.stdout).toContain("Built");
```

Use `run()` to capture stdout, stderr, and the Command Action outcome without terminal parsing. See the [core `run()` reference](/docs/api/crust#runpath-input-options) for result branches and capture boundaries.

## `fuzzRoundTrip(app, path, options?)`

<include lang="ts">../../../examples/modules/testing.ts#fuzz</include>

`fuzzRoundTrip()` generates structured `run()` inputs for the command at `path` from its Command Snapshot, encodes each as canonical argv (`--name=value`, `--flag`/`--no-flag`, one token per occurrence, `--` before `raw`), and binds both through [`bindInput()`](/docs/modules/core#tooling-subpath) from `@crustjs/core/tooling`. Bound `commandPath`, `args`, `flags`, and `rawArgs` must be deeply equal (`URL`s compare by `href`). Generators honor `type`, `choices`, `required`, `default`, `variadic`, `multiple`, and `noNegate`; values argv cannot express (dash-led positionals, a first positional spelled like a subcommand or alias) are never generated.

What runs: definition materialization (as for `app.snapshot()`), the production parser and validation, and any `parse` function or Standard Schema on the command's definitions. What never runs: Command Actions, Extension `preRun`/`postRun`/`onError` hooks, Contexts, output sinks, and process exit handling.

Snapshots omit `parse` functions and schemas, so generators supply raw token values to those definitions and the callbacks receive the same value on both paths: a string, a boolean for boolean-token flags, an array for `variadic`/`multiple` definitions, or `undefined` when the value is omitted. Argv binds against an empty environment, so a flag with `env` falls back to its `default` on both paths whatever the process environment holds, and a flag's `delimiter` never appears inside a generated value (nor does an empty value), since splitting would make the two inputs inequivalent by design. When both paths reject such a value with the same `CrustError` code, the case counts as `rejected`; a rejection on only one path, differing codes, or any rejection for a command without `parse`/schema definitions fails. A run with zero `accepted` cases also fails because it proved nothing. The helper does not fuzz argv syntax (short bundles, aliases, `--no-` spellings): it checks binding equivalence, not the parser's spelling table.

The `seed` option wins, then `CRUST_FUZZ_SEED`, then a fixed default; pass `env` to read the variable from somewhere other than `process.env`. A failure message contains the seed, the case number, the structured input, the argv, and both outcomes.

## `runInteractive(app, path, input?)`

Import from `@crustjs/testing/interactive`; this entry point requires `@crustjs/prompts`.

<include lang="ts">../../../examples/modules/testing.ts#interactive</include>

`waitFor()` polls the ANSI-stripped screen and defaults to a 5000 ms timeout. It fails as soon as the invocation fails or completes without a match, rather than waiting for the timeout. Call `type()` or `keys()` after the expected prompt appears, then await `done`.

`done` rejects with the error from a failed outcome. One ambient [`withTerminalIO`](/docs/modules/progress#output-sinks) scope sends prompts, progress, and `ctx.stderr()` to the fake screen.

`ctx.stdout()` is not included, so use `run()` for stdout assertions.

## Custom prompts

```ts
import { renderPrompt } from "@crustjs/prompts/testing";
```

`@crustjs/testing` does not re-export prompt-author helpers. Use [`renderPrompt()`](/docs/modules/prompts#testing-custom-prompts) for custom `(options, io?)` prompts.
