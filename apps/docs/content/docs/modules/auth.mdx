---
title: "Auth"
---

`@crustjs/auth` signs a CLI in with OAuth. `createAuth()` returns one client: `login()` runs a browser login over a loopback redirect with PKCE, or a device-code login, and stores the login in a private file, encrypted under a key in the OS keyring; `token()` returns the token for your API, refreshed when it expires, or one from an environment variable; `status()` and `logout()` complete the set. [Add login to your CLI](/docs/guide/login) builds the commands with it. The pieces it is made of (discovery, the browser and device logins, the token client, the credentials file) are exported from `@crustjs/auth/oauth` for flows the client does not cover. It is standalone: no Crust Context, and no external OAuth library; it builds on the runtime's `fetch`, Web Crypto, and `node:http`, with [`@crustjs/store`](/docs/modules/store) for the credentials file and the OS keyring (`Bun.secrets`, or the optional `@napi-rs/keyring` on Node) for its key.

## Install

```npm
npm install @crustjs/auth
```

## The client

`createAuth(options)` validates the settings with the same rules as the building blocks, does no I/O, and returns a frozen client. Its methods work detached, so you can pass `auth.token` around.

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="CreateAuthOptions" />

- `app` is your CLI's name: non-empty, without `/` or `\`. The login is stored in `credentials.json` in its state directory, as [Storing tokens](#storing-tokens) describes. The device-login message shows `name`, which defaults to `app`.
- `apiOrigins` are the only origins the stored login's token is sent to. Declare them in code, never from the environment.
- `env` names a variable, such as `ACME_TOKEN`, whose value `token()` returns, trimmed, instead of the stored login when it is not blank, so CI and agents need no login. It is never stored, refreshed, or revoked, and not checked against `apiOrigins`.
- `issuer`, `clientId`, `clientSecret`, `redirectPath`, and `allowInsecureLoopback` follow the rules of [Servers](#servers); `hosts` and `ports` those of [Browser login](#browser-login).
- `resource` names the API every login asks tokens for (RFC 8707 resource indicators, absolute URIs without a fragment), for a server that issues tokens per API; both logins and the code exchange send it, and the stored login records it, so every refresh sends it too. Nothing is derived from `apiOrigins`.
- The login's tokens are encrypted under a key in the OS keyring. Without a keyring they are stored in plaintext, and `onWarning` receives `{ code: "plaintext-storage" }` once per process; with `strict: true` the login fails with `CredentialKeyError` instead. See [Encryption and the OS keyring](#encryption-and-the-os-keyring).

### Signing in

`auth.login(options)` runs the whole sign-in and resolves once the login is stored.

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="LoginOptions" />

1. It picks the login as [Choosing a login](#choosing-a-login) describes, with `device` as the user's `--device` flag. On `"refuse"` it throws `LoginRequiresInteractionError`, whose message says to use the device login, before any request.
2. It discovers the server, once per process.
3. **Browser:** it listens on the loopback address, calls `onUrl`, waits for the browser, and exchanges the code once. The listener closes on every path.
4. **Device code:** it starts the device login, calls `onCode`, and polls until the user approves.
5. It stores the tokens. A login opens its place in the file before the browser or device step, so a logout (or another login) that commits while it waits is not undone: this login then fails with `StaleCommitError` and stores nothing.

The client prints nothing and opens no browser by itself: it does not know your command's output stream. Show the prompts yourself, usually in two lines:

```ts
onUrl: async ({ url, open }) => { stderr(`Sign in at: ${url}`); await open(); },
onCode: ({ message }) => stderr(message),
```

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="BrowserLoginPrompt" />

`open()` calls [`openBrowser()`](#opening-the-browser) with the URL and resolves `true` when a browser was launched, `false` when none could be, so you can ask the user to open the URL by hand. It never throws; show the URL in any case. You may skip it, or ask first.

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="DeviceLoginPrompt" />

`message` is the [`deviceCodeMessage()`](#device-login) text for this login: the URL and its host, the code, and the anti-phishing warning. The prompt never carries the device code.

If `onUrl` or `onCode` throws or rejects, the login fails with that error, closes the listener, and stores nothing. `signal` cancels any wait with `AbortError`, including a pending `onUrl` or `onCode`: the login rejects at once, closes the listener, and ignores the callback's later result; `page` renders the browser's result page as in [Browser login](#browser-login).

### The token, status, and logout

<include lang="ts">../../../examples/modules/auth.ts#token</include>

- `auth.token({ signal?, baseUrl? })` returns the `env` variable's value, trimmed, when it is set and not blank, with `source` `"env"` and no `refresh`. Otherwise it returns the stored login's token, refreshed first when it expires within 30 seconds; with `baseUrl`, its origin must be one of `apiOrigins`, or it throws `CredentialMismatchError` before anything is sent. A token from `env` is not checked against `apiOrigins`. No login → `LoginRequiredError`.
- `refresh()` on a stored login's token refreshes it unless another process already did, for a 401 retry.
- `auth.status()` reads where the token would come from, the stored login's `expiresAt` and `scope`, and `storage`: the keyring `kind` (`"file"` without one) and `plaintextRecords`, the logins not yet encrypted. It sends no request, refreshes nothing, and waits for no lock; it asks the keyring for the key once, within 5 seconds, and never writes it. A corrupt file or an unsafe directory still throws its error. When the `env` variable is set, it returns `{ source: "env" }` without reading the file or the keyring.
- `auth.logout({ signal? })` deletes the login, then revokes it at the server, and reports both outcomes as in [Login and logout](#login-and-logout).

### Errors by code

Errors the library raises are `AuthError`s with a stable `code`, typed as the `AuthErrorCode` union; match on `code`, never on `message`. An error thrown by your own `onUrl` or `onCode` reaches you unchanged. `createAuth()` itself throws `OAuthConfigError` for an invalid option, and, since it resolves the state directory's path (without touching the disk), the store's `CrustStoreError` (`PATH`) on an unsupported platform or when `XDG_STATE_HOME` (`LOCALAPPDATA` on Windows) is unset or relative and the home directory is not an absolute path.

## Servers

`defineServers({ servers, allowCustomIssuers? })` validates every authorization server your CLI signs in with and returns a frozen config. `discover(config, issuer, { signal?, clientId?, fetch? })` then fetches the server's metadata and returns a frozen `AuthServer` that every other function takes.

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="AuthServerOptions" />

- An issuer is an `https` URL with no query, fragment, or user info. Each issuer, and each `redirectPath`, may appear once in `servers`. A `redirectPath` is plain ASCII that a browser sends unchanged: no `%`, query, fragment, dot or empty segments, spaces, or characters such as `<` or `é`.
- `clientId` on `discover()` replaces the declared client id; two client ids at one issuer are the same server.
- Discovery reads `/.well-known/oauth-authorization-server` (inserted before the issuer's path, as RFC 8414 says) and, only on a 404, `<issuer>/.well-known/openid-configuration`. The document's `issuer` must equal yours exactly, trailing slash included.
- Every endpoint must be an `https` URL without user info or a fragment. A query is kept byte for byte, but it must not set a parameter the library sends (`client_id`, `scope`, `redirect_uri`, …) or repeat a name. An endpoint on another host than the issuer is fine.
- A server that lists `code_challenge_methods_supported` without `S256` is refused.
- Metadata is cached in memory for the process, never on disk.

Declare `servers` in code. Do not build the list from environment variables or other runtime input: the list is what decides which servers your users' tokens may reach.

### Who is signed in

`server.userinfoEndpoint` is the OpenID Connect user-info address from the metadata (`userinfo_endpoint`), checked like the other endpoints, or `undefined` when there is none. The library never requests it and drops the `id_token` unread: fetch it yourself with the token from `auth.token()` or a token source's `get()`, without `baseUrl`, since the address is on the issuer rather than one of `apiOrigins` and `baseUrl` there would be refused.

<include lang="ts">../../../examples/modules/auth.ts#userinfo</include>

### Public clients

Register your CLI with each server as a **public client** (token endpoint authentication `none`), with the loopback redirect URIs below. Every user can read a `clientSecret` shipped inside a CLI, so it is not confidential and does not make your client confidential; set one only for a server that insists. With a secret, the token client authenticates with HTTP Basic; without one, it sends only `client_id`.

### Several servers and mix-up

When a CLI can sign in with more than one server, a malicious server can name an honest server's sign-in page as its own and receive the honest server's code and PKCE verifier (a mix-up attack, RFC 9700 §4.4). Each `AuthServer` carries the `issPolicy` that decides how a browser login checks the `iss` parameter of the response:

| Setup                                                               | Browser login                                          |
| ------------------------------------------------------------------- | ------------------------------------------------------ |
| The server's metadata says it sends `iss`                           | `iss` is required and must equal the issuer            |
| One server in `servers` and no `allowCustomIssuers`                 | A missing `iss` is accepted; a present one must match  |
| Several servers; this one has its own `redirectPath`                | A missing `iss` is accepted; a present one must match  |
| Several servers (or `allowCustomIssuers`); no `iss` and no own path | Refused with `OAuthConfigError` (`mix-up-unprotected`) |

<include lang="ts">../../../examples/modules/auth.ts#servers</include>

A `redirectPath` protects a server only if you register that path with that server alone; the default path is `/callback`. A custom issuer (`allowCustomIssuers`, with `clientId` passed to `discover()`) has no path of its own, so it must send `iss`. The device login has no redirect and is not affected.

## Browser login

`createAuthorizationSession(server, options?)` starts one login. It checks the mix-up policy and every option first, and only then listens on the loopback address; a refused login binds nothing. The session freezes the issuer, client id, redirect URI, `state`, the PKCE pair, and the authorization URL `url`, which you open or print.

Every session makes a fresh PKCE verifier of 256 random bits with its `S256` challenge, and a `state` of 256 random bits; the verifier is sent only in the token request and never exposed. The authorization URL is safe to print, since its `state` and challenge are not secrets. Never print a callback URL, a code, a token, or `deviceCode`.

<auto-type-table
  path="../../../../../packages/auth/src/types.ts"
  name="AuthorizationSessionOptions"
/>

- The listener binds `127.0.0.1` on a free port: `http://127.0.0.1:<port>/callback`. Register that redirect URI; servers must accept any port for loopback IP redirects. With `hosts: ["127.0.0.1", "::1"]` it falls back to `http://[::1]:<port>/…`, which you must register as well. Fixed `ports` are tried in order, for servers that need pre-registered ports. The listener uses the default bind, without `reusePort`, which refuses a second listener on its port; Node and Bun offer no Windows `SO_EXCLUSIVEADDRUSE`.
- `extra` adds parameters such as `audience`, and must not repeat a parameter the library sends or the endpoint's query sets. There is no `nonce`, `response_mode`, `request`, or `request_uri`: the session asks only for an authorization code, always with PKCE `S256` and `state`.

`session.wait(onCallback, { timeoutMs?, signal?, page? })` waits for the browser, runs `onCallback({ code })` once, then answers the browser and closes the listener. Pass `client.exchangeCode(session, code)` as `onCallback`; the result page shows its outcome.

- It serves only `GET` on the exact redirect path, compared byte for byte before any decoding, with a `Host` header of exactly `127.0.0.1:<port>` (or `[::1]:<port>`); on port 80 the browser's `127.0.0.1` (or `[::1]`) without the port also matches. Anything else gets a 404 or 421.
- A request whose `state` is wrong or missing, or that repeats `code`, `state`, `error`, or `iss`, gets a 400 and the session keeps waiting: a stray or forged request cannot end the login.
- The `iss` check runs before `error` or `code` is used. An `error` response rejects with an `OAuthError` and is never exchanged.
- It rejects with `TimeoutError` after `timeoutMs` (5 minutes) and with `AbortError` on `signal` or `session.close()`, also while `onCallback` is still running (its late result is ignored). The listener and every open connection close on every outcome; a connection idle for 10 seconds is dropped.
- `page` renders the result page from `{ outcome, errorCode? }` only, never server text or the code. The library sets `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` on every page. If `page` throws, the default page is served.

Call `session.close()` in a `finally`, as above, so an early error never leaves the port open.

## Device login

`startDeviceFlow(server, { scope?, resource?, signal?, fetch? })` starts an RFC 8628 device login and returns `{ userCode, verificationUri, verificationUriComplete?, expiresAt, poll }`. Show the code and the URL, then call `flow.poll({ signal? })` once.

- `deviceCodeMessage({ app, userCode, verificationUri })` prints the default instructions: the URL and its host, the code, and a warning to continue only if the user started this sign-in, each value stripped of control characters and escape sequences. Always show `userCode` and `verificationUri`, even when you also open `verificationUriComplete`.
- The response is checked before anything is shown: `verificationUri` must be `https`; `userCode` is stripped of control characters and escape sequences. The device code is never exposed.
- Polling waits at least the server's `interval` (and no less than 5 seconds) before each request, adds 5 seconds for every `slow_down`, and doubles the wait after a network error. It stops at the code's expiry, aborting a request in flight, and rejects with `OAuthError` `expired_token`.
- A server whose metadata has no device endpoint, or whose `grant_types_supported` lacks the device grant, is refused with `OAuthConfigError` (`unsupported`).

## Choosing a login

`detectLoginMode({ device?, noBrowser?, env?, platform?, stdin?, stdout?, stderr? })` returns `"browser"`, `"device"`, or `"refuse"`. The first matching row wins:

| Condition                                                                          | Mode        |
| ---------------------------------------------------------------------------------- | ----------- |
| `device` or `noBrowser` (the user passed `--device` or `--no-browser`), even on CI | `"device"`  |
| `CI` is set (`isCI()` from `@crustjs/utils/terminal`)                              | `"refuse"`  |
| No terminal: stdin is not a TTY, or neither stdout nor stderr is                   | `"refuse"`  |
| A terminal, but an SSH session or Linux with no display                            | `"device"`  |
| Otherwise                                                                          | `"browser"` |

On `"refuse"`, nobody is there to read a code, or nobody asked for one that someone else might approve. `auth.login()` throws `LoginRequiresInteractionError` then; with the building blocks, throw it yourself with a message naming your device-login flag and your token environment variable. With `"device"`, show `deviceCodeMessage()` on the terminal the user is at. It does not check that the server offers a device login; `startDeviceFlow()` does.

## Opening the browser

`openBrowser(url, { allowInsecureLoopbackOrigin? })` resolves `true` when a launcher started and `false` otherwise; it never throws. Always print the URL too.

- Only `https` URLs without user info or control characters open, and plain `http` only on the development origin you pass.
- The URL is one argument to `open` (macOS), `xdg-open`, or on Windows `rundll32 url.dll,FileProtocolHandler`, never through a shell, so `&` in a URL stays part of it. On Windows, CI checks only the launcher arguments; a real browser launch is a manual check on a Windows host.

## Token client

`createTokenClient(server, { fetch? })` returns:

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="TokenClient" />

- `exchangeCode(session, code)` uses the session's token endpoint, redirect URI, and verifier; it has no parameter for either. It runs once per session and never retries.
- Every request is a form `POST` to the endpoint URL as configured, with a 30-second timeout (10 for `revoke()`), a 1 MiB response cap, and no redirects: a 3xx response is an error.
- A token response needs a non-empty `access_token` and a `Bearer` `token_type`; `expires_in` must be a positive number. `id_token` and unknown fields are dropped.

## Storing tokens

`credentialStore({ app, name?, lockTimeout?, keyring? })` names the credentials file, and `createTokenSource({ config, identity, store, skewMs?, fetch? })` one login in it. Neither touches the disk or the network until you call a method.

The client keeps its login this way too: `createAuth()` opens `credentialStore({ app, keyring: { strict, onWarning } })` and a token source for `{ issuer, clientId, apiOrigins }`, so everything below about the file, refreshes, and locks applies to it.

<include lang="ts">../../../examples/modules/auth.ts#credentials</include>

<auto-type-table path="../../../../../packages/auth/src/types.ts" name="TokenSource" />

- **The file** is `credentials.json` in the app's state directory: `$XDG_STATE_HOME/<app>` when that variable holds an absolute path, else `~/.local/state/<app>`, or `%LOCALAPPDATA%\<app>\State` on Windows. On POSIX the file is `0600`, and a directory the store creates is `0700`. An existing directory, such as one `updateNotifier()` created first, must be yours and not writable by other users, and neither it nor the file may be a symbolic link; otherwise every call fails with `UnsafeStorageError` before writing anything. On Windows, the file is protected by the access rules (ACLs) of your user directory, not by file modes: there are no mode or owner checks, and a symbolic link is still refused. With `keyring`, the tokens in it are encrypted (see [Encryption and the OS keyring](#encryption-and-the-os-keyring)); without it, or without a keyring, they are plaintext, and anyone who can read the file can use them.
- **The identity** binds a login to `issuer`, `clientId`, `profile` (default `"default"`), and `apiOrigins`, and is stored with its tokens. Every use checks that the stored identity equals the one in your code, and, with `baseUrl`, that its origin is one of `apiOrigins`; otherwise `CredentialMismatchError` (`reason`: `issuer`, `client`, `profile`, or `origin`) is thrown before any request. So an issuer or API URL taken from an environment variable never receives a token stored for another. Declare `apiOrigins` in code, like `servers`; `resource` values are sent and stored but never widen them.
- **`get()`** returns the access token, refreshed first when it expires within `skewMs` (30 seconds). The refresh keeps the old refresh token when the server sends none, keeps the granted scope, sends the stored `resource` values, and stores the new tokens before it returns them. Concurrent refreshes of one login share one request: within a process, and across processes through a lock.
- **`forceRefresh({ ifGeneration })`** is for a 401: if the login changed since the failed token's `generation`, it returns the newer token without a request.

### Encryption and the OS keyring

With `keyring` (which `createAuth()` always passes), the tokens in the file are encrypted with AES-256-GCM under a key kept in the OS keyring.

- **The key** is one keyring entry per app, service `<app>` and name `credentials-key`, holding a random 256-bit key and its id; no token ever goes to the keyring. On Bun it is kept with `Bun.secrets`, which on Windows is asked to keep it on this computer (`persist: "local"`); Bun honors that from 1.4.3, while Bun 1.4.0 to 1.4.2 and `@napi-rs/keyring` store it with enterprise persistence, so a roaming Windows profile copies it to the user's other machines. On Node it is kept with [`@napi-rs/keyring`](https://www.npmjs.com/package/@napi-rs/keyring), an optional peer dependency you install; on Linux it is pinned to the Secret Service (GNOME Keyring, KWallet), never the kernel keyring, which forgets the key at reboot. No keyring command such as `security` or `secret-tool` is ever run.
- **Created once.** The first login or refresh that stores a secret creates the key. Creation holds an app-wide lock, `key-init.lock` in the state directory, until the keyring has stored the key, so two processes never create two keys. Nothing rewrites it afterwards. Every keyring call has a 5-second deadline.
- **The file** records the key's id and the backend that holds it: `encryption: { kind: "aes-256-gcm", keyId, keyring }`, with `keyring` `"bun-secrets"` or `"napi-keyring"`. Only each login's access and refresh tokens are encrypted, with a fresh random IV every time and bound to the login (app, key, issuer, client id, profile, API origins, and generation). A ciphertext changed or copied to another login fails as `CredentialStoreCorruptError` for that login. The rest stays readable, so locks and logouts work without the key.

**No keyring.** When a secret must be stored in a file that records no key and there is no keyring (Node without `@napi-rs/keyring`, a Linux host without a Secret Service, or a keyring that does not answer within 5 seconds), the secret is stored in plaintext in the same `0600` file, and `onWarning` receives `{ code: "plaintext-storage" }` once per process. Nothing is printed: tell the user yourself. With `strict: true`, the write fails with `CredentialKeyError` (`unavailable`) and stores nothing. A key write that fails or runs past its deadline fails the same way; it never falls back to plaintext. Without the `keyring` option, `credentialStore()` never touches a keyring and stores plaintext without a warning.

**Encrypted on the next write.** A file is never converted at once. Once a keyring is available, each login is encrypted the next time a login or a refresh writes it, so a file can hold encrypted and plaintext logins until then, and `status()` reports the plaintext ones as `plaintextRecords`. A file that records a key never takes a plaintext write again.

**When the key can't be used,** reading or refreshing an encrypted login writes nothing, to the file or the keyring:

| The OS keyring                                                   | Error                                      | What the user does                                           |
| ---------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| Locked, refused, no answer within 5 seconds, or an invalid entry | `CredentialKeyError` (`unreadable`)        | Unlock the keyring and try again                             |
| Has no key                                                       | `LoginRequiredError` (`key-missing`)       | Log in again                                                 |
| Has another key than the one the file records                    | `LoginRequiredError` (`key-mismatch`)      | Log in again                                                 |
| Is the other runtime's, and does not hold the file's key         | `LoginRequiredError` (`key-other-keyring`) | Run the CLI with the runtime that logged in, or log in again |

An unreadable key is never replaced, since the old one may still exist. The next login reuses the key in the keyring, creating one only when there is none, and records it in the file. In the same write it logs out every login encrypted under the old key, in every profile of the app, and `ticket.commit()` reports their number as `discarded`: present it as an app-wide sign-out, since the user may have to log in again once per profile. Plaintext logins are kept, and a login or refresh of a discarded login that was under way fails as for a logout. A process that already read the key may not notice a replaced keyring entry until it reads the keyring again. If a process is killed while its first key write is in flight, that write can land later and replace the key another process created meanwhile; one more login restores service, once per such crash.

**One runtime per CLI.** On Linux and Windows, `Bun.secrets` and `@napi-rs/keyring` keep the same service and name in different native entries, so neither finds the other's key; on macOS both reach the same Keychain item. A CLI should therefore run under one runtime. Run under the other one on Linux or Windows, it fails with `key-other-keyring`, and a login there discards the logins stored under the first runtime's key, as above.

**A keyring that hangs.** On Linux, `@napi-rs/keyring` connects to the D-Bus session bus synchronously, which would block the whole process if the bus never answered. So the Node backend first checks, within the 5-second deadline, that the bus at a `unix:path=` or `unix:abstract=` `DBUS_SESSION_BUS_ADDRESS` answers its authentication, and counts a bus that does not as no keyring; other address forms are not checked. A bus that authenticates but whose Secret Service then blocks can still hold the Node backend until the D-Bus library gives up. On Bun, `Bun.secrets` runs on a worker thread: the call is bounded by the deadline, but the process stays alive until the native call returns.

**What the encryption does not cover.** Without the key, anyone who can read the file still sees each login's identity, profile, API origins, scope, resource, expiry, and its refresh and logout times, and lock files show host names, platforms, machine, boot, and process ids. Nothing protects the file as a whole: someone who can write to it can edit those fields or put back an older copy. Both rest on the file's permissions (ACLs on Windows). Rewriting a plaintext file does not erase the old plaintext from freed disk blocks.

### Where are my tokens

| Runtime and host                                                               | The key                                                            | The tokens in `credentials.json`                                                  |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Bun on macOS, Windows, or Linux with a Secret Service                          | `Bun.secrets`: the Keychain, Credential Manager, or Secret Service | Encrypted                                                                         |

On Node, add `@napi-rs/keyring` to your `dependencies`. A CLI that `crust build` bundles for Node should also list it in [`crust.external`](/docs/guide/build-and-distribution#keep-dependencies-external), so npm installs the native module for the user's platform; bundled, the build machine's native module would be copied instead. On a platform that module does not fit, it fails to load, which counts as no keyring: tokens go to the file in plaintext with the `plaintext-storage` warning, or `strict: true` refuses the login. A CLI that runs only on Bun does not need it.

### Login and logout

`beginLogin()` opens a login before you run the browser or device flow, and `ticket.commit(tokens, { resource? })` stores the result. A commit fails with `StaleCommitError`, storing nothing, if another login, a logout, or a reset of the same credential committed since `beginLogin()`, so a login that started before a logout can't bring the session back. A second open login in the same process fails with `LoginInProgressError`. Commit, a failed commit, `cancel()`, and an abort of `beginLogin()`'s `signal` each finish the ticket, so call `cancel()` in `finally` as above.

`logout()` replaces the login with a logged-out record, then revokes the refresh token (and the access token, where the server can) at the server's revocation endpoint, and reports both outcomes:

| `local`     | `remote`        | Meaning                                                                            |
| ----------- | --------------- | ---------------------------------------------------------------------------------- |
| `"deleted"` | `"revoked"`     | Logged out, and the server revoked the token                                       |
| `"deleted"` | `"unsupported"` | Logged out; the server has no revocation endpoint                                  |
| `"deleted"` | `"failed"`      | Logged out; the server refused or failed (such as a 503): the token may still work |
| `"deleted"` | `"unknown"`     | Logged out; the request was sent but no answer came (a timeout or an abort)        |
| `"deleted"` | `"skipped"`     | Logged out; there was no readable token of this identity, or no key to decrypt it  |
| `"failed"`  | `"skipped"`     | The file could not be written: still logged in, and nothing was sent               |

A failed revocation is a result, not an error. Revocation waits at most 10 seconds.

### When a refresh is uncertain

A refresh is marked in the file before it is sent, and holds the login's lock until its result is stored, so a call that finds the mark waits for that lock and then uses the refreshed token. If the server answers with a protocol error (a 400, or a 401 for `invalid_client`), or the runtime's own `fetch` could not resolve or connect to the server, nothing was rotated and the mark is cleared: `invalid_grant` throws `LoginRequiredError`, any other code an `OAuthError`, a connection failure `RefreshFailedError`, and a later call may try again. After any other outcome, such as a 5xx, a timeout, a lost connection, an invalid response, or a crash, the server may have rotated the refresh token, and sending the old one again could make it revoke the login. So the mark stays, and every later `get()`, `forceRefresh()`, or 401 retry, in any process, throws `RefreshOutcomeUnknownError` without a request until the user logs in again (or logs out). Through a custom `fetch`, a connection failure is uncertain too, since a proxy or a retry may have sent the request.

A failed refresh never deletes the login; call `logout()` when you want that.

### A corrupt file

A file that is not valid JSON, has an unknown structure, or comes from a newer version of your CLI makes every call fail with `CredentialStoreCorruptError`. A JSON object with none of the credentials fields (`version`, `storeId`, `encryption`, `records`), such as `{}`, counts as an empty file, and its other keys are kept; one with any of them must have all of them, valid. It is never repaired or replaced automatically. `store.resetCredentials()` deletes it; copy it first if you want to keep it. A single invalid login fails only for its own key (`error.key`), and `resetCredentials({ key })` replaces just that one with a logged-out record.

### Locks

A refresh, login, logout, or reset of one login holds a lock file next to `credentials.json` for its duration, and every write holds the file's own lock, so other logins in the file are never lost. Creating the keyring's key holds `key-init.lock`. A lock is taken over only from a process that provably no longer runs: on Linux, one on the same machine, boot, and PID namespace whose process is gone; on macOS and Windows, one written on the same platform and host name whose process is gone. This assumes no two machines with the same host name share the directory. Any other owner is waited for until `lockTimeout` (40 seconds), then the call fails:

- `LockTimeoutError`: the owner is still running. Try again when it is done.
- `LockRecoveryRequiredError`: the owner can't be judged from here, such as a process in a container. Both errors carry the lock file's `path`, its recorded `owner`, and `manualStep`: stop every process of your CLI that uses this directory, including on other machines or containers that share it, and keep new ones from starting; only then delete the file. If you can't be sure of that, leave it in place.

## Errors

Every error the library raises extends `AuthError` and has a stable `code`. Match on `code` or the class, never on `message`. The classes are exported from `@crustjs/auth/oauth`; the root exports `AuthError` and `AuthErrorCode`.

| Error                           | `code`                       | When                                                                                                                                                                                                                    |
| ------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OAuthError`                    | The protocol code            | The server returned an OAuth error (`access_denied`, `invalid_grant`, …) or an invalid response (`invalid_response`); an unknown code is `unknown`                                                                      |
| `OAuthConfigError`              | `oauth-config`               | A config, option, or server value was refused; `reason` says which                                                                                                                                                      |
| `HttpError`                     | `http`                       | A response without an OAuth error, including any 3xx; `status` holds the code                                                                                                                                           |
| `IssuerMismatchError`           | `issuer-mismatch`            | Metadata or a response named another issuer, or lacked a required `iss` (`reason`)                                                                                                                                      |
| `TimeoutError`                  | `timeout`                    | A request or the browser wait ran out of time                                                                                                                                                                           |
| `AbortError`                    | `abort`                      | Your `signal` was aborted                                                                                                                                                                                               |
| `ResponseTooLargeError`         | `response-too-large`         | A response body was over 1 MiB                                                                                                                                                                                          |
| `NetworkError`                  | `network`                    | The request could not be sent or its response not read (DNS, connection, TLS, a broken stream); the underlying error is dropped                                                                                         |
| `LoginRequiresInteractionError` | `login-requires-interaction` | `auth.login()` (or your code) found no person at a terminal: `detectLoginMode()` returned `"refuse"`                                                                                                                    |
| `LoginRequiredError`            | `login-required`             | No login, or it was logged out, expired without a refresh token, refused (`invalid-grant`), reset during a refresh, or its key is gone from the keyring (`key-missing`, `key-mismatch`, `key-other-keyring`) (`reason`) |
| `CredentialMismatchError`       | `credential-mismatch`        | The stored login is for another issuer, client, profile, or API origin (`reason`); nothing was sent                                                                                                                     |
| `RefreshFailedError`            | `refresh-failed`             | A refresh failed before anything could be rotated; try again                                                                                                                                                            |
| `RefreshOutcomeUnknownError`    | `refresh-outcome-unknown`    | An earlier refresh may have rotated the token; log in again                                                                                                                                                             |
| `LoginInProgressError`          | `login-in-progress`          | `beginLogin()` while another login of the same credential is open in the process                                                                                                                                        |
| `StaleCommitError`              | `stale-commit`               | A login, logout, or reset committed after `beginLogin()`; nothing was stored                                                                                                                                            |
| `CredentialStoreCorruptError`   | `credential-store-corrupt`   | The credentials file, or one login in it (`key`), can't be read                                                                                                                                                         |
| `CredentialKeyError`            | `credential-key`             | The OS keyring's key can't be read (`unreadable`), or a login can't be stored without a keyring under `strict` or after a failed key write (`unavailable`)                                                              |
| `UnsafeStorageError`            | `unsafe-storage`             | The credentials directory or file is open to other users or a symbolic link                                                                                                                                             |
| `LockTimeoutError`              | `lock-timeout`               | A running process held a credentials lock past `lockTimeout`                                                                                                                                                            |
| `LockRecoveryRequiredError`     | `lock-recovery-required`     | A credentials lock needs the manual step in `manualStep`                                                                                                                                                                |

Errors carry local text, the `status`, and the allowlisted code only. A server's `error_description` and `error_uri`, response bodies, and URLs never appear in a message, property, or `cause`, since a hostile server could echo a secret into them. Neither does the content of a corrupt credentials file. Other file system failures surface as the store's `CrustStoreError` (`IO`).

## Cancellation

`auth.login()`, `auth.token()`, `auth.logout()`, `discover()`, `createAuthorizationSession()`, `session.wait()`, `startDeviceFlow()`, `flow.poll()`, the token client's `exchangeCode()`, `refresh()`, and `revoke()`, a token source's `get()`, `forceRefresh()`, `beginLogin()`, `ticket.commit()`, and `logout()`, and a store's `resetCredentials()` and `status()` take a `signal`. An aborted signal rejects with `AbortError` before any request or listener; aborting mid-way stops the request, sleep, or wait and closes the listener. Handle Ctrl-C in your command (a Crust command's `ctx.signal` already does) and pass its signal down.

A change to the credentials file can be cancelled until its first write, including while it waits for a lock; from then on it completes and reports its real outcome:

- A refresh, once its mark is written: an abort only stops waiting for it, and another caller sharing the refresh still gets the token. When every caller has left before the mark, nothing is sent.
- A login commit, once its write starts.
- A logout, once the login is replaced. An abort afterwards stops the revocation, reported as `remote: "unknown"`.
- `resetCredentials()`, once the file is deleted (or the record replaced).
