`@crustjs/create` writes a new project from a template directory, copied as it is, and from files your code writes, then runs post-scaffold steps. It does not provide prompts or terminal UI.

## Install

```npm
npm install @crustjs/create
```

Pair it with any CLI and prompt libraries needed by your create tool.

## Locating templates

| `template` value                                | Resolves from                                | Use for                                                       |
| ----------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------- |
| `artifactPath("templates/base")`                | The `crust.include` directory beside the CLI | Templates shipped with a CLI built by `crust build`           |
| `new URL("../templates/base", import.meta.url)` | The module that contains the call            | Templates inside a package published unbundled                |
| `"./templates/base"`                            | The user's current working directory         | Templates in the project where the command runs               |
| `"/srv/templates/base"`                         | That exact filesystem path                   | A location already resolved by your own code or configuration |

Ship templates with [`crust.include`](/docs/guide/build-and-distribution#ship-extra-directories-with-crustinclude) and locate them with [`artifactPath()`](/docs/api/crust#artifactpathpath): it finds them from the staged tree, an npm install, or a standalone executable. An `import.meta.url` URL follows the module file, which moves once the CLI is bundled or compiled. `npx`, `bun x`, and global installs run the generator from a cache while the working directory is the user's project, so a relative string resolves there.

- Only `file:` URLs are accepted, and the template must be a directory.
- Convert an existing filesystem path with `pathToFileURL()` rather than concatenating `file://`.

## Template conventions

The template directory is copied exactly: every file's bytes and permission bits. Nothing in it is read or replaced, so it can hold binaries, executable scripts, and files in any syntax.

```text
templates/base/_gitignore   -> my-project/.gitignore
templates/base/__tests__/   -> my-project/__tests__/
```

- A single leading `_` on a copied file's name becomes `.`; `__` stays unchanged. Directory names are never renamed.
- Symlinks in the template are skipped.
- To layer templates, call `scaffold()` more than once with `conflict: "overwrite"`.

## Files written from code

A file that depends on the user's answers is written from code: `files` maps a path in the new project to its text. TypeScript checks the code that produces each file.

<include lang="ts" meta='title="src/index.ts"'>
  ../../../examples/modules/create-files.ts
</include>

- A `files` entry wins over the template file at the same path and keeps that file's permission bits.
- Keys are written as given, with no `_` rename. A key must stay inside the new project and outside `.git`.
- Values are text. Binaries and executables belong in the template.
- Import a JSON file from the template to start from its typed contents, as with `package.json` above.
- To change one line of a template file, read it, replace the line, and pass the result.
- For a prose file with many substitutions, such as a README, keep it as a real file outside the copied directory and render it into `files` with a template engine of your choice. `create-crust` renders its README with [Eta](https://eta.js.org).

TypeScript checks the code that produces the text, not the text itself: a misspelled key writes a new file and leaves the template's file as it was. Keep one test that runs your scaffolder and checks its output.

## `scaffold(options)`

<auto-type-table path="../../../../../packages/create/src/types.ts" name="ScaffoldResult" />

See [Locating templates](#locating-templates) for how `template` resolves. A call needs `template`, `files`, or both; one that names neither does not compile.

| `conflict`          | Destination with files                                                  |
| ------------------- | ----------------------------------------------------------------------- |
| `"abort"` (default) | Throws before writing                                                   |
| `"overwrite"`       | Replaces conflicting files and leaves unrelated destination files alone |
| `"replace"`         | Deletes everything but `.git`, then writes                              |

A destination holding only `.git` counts as empty, so `git init` before scaffolding needs no `conflict`.

Every check runs before anything is deleted or written: the template exists, there is something to write, every `files` key stays inside the new project, nothing is written inside `.git`, no planned file is also the directory of another, the conflict rule, and the symlink rules below. `"replace"` also refuses a template inside the destination, or a destination inside the template, since it would delete template files before copying them. `"overwrite"` refuses an existing directory where a file goes, or an existing file where a directory goes. `dryRun: true` runs the same checks and returns the same `{ files }` without writing or deleting anything.

Symlinks in the destination:

- `dest` itself may be a symlink; its target is the destination.
- Symlinks that stay inside the destination are followed.
- An existing file or directory that is a symlink resolving outside the destination, to a missing target, or into `.git` throws before any file is written.

<Callout type="warn">
  These path checks are not atomic with filesystem writes. Use a destination whose directories
  untrusted processes cannot modify concurrently.
</Callout>

## `runSteps(steps, cwd, options?)`

```ts
await runSteps(
  [{ type: "install" }, { type: "git-init", commit: "Initial commit" }],
  "./my-project",
);
```

Steps run in order and stop at the first error. A failed step throws an `Error` whose `exitCode` is the child's exit status (`null` when a signal ended it). The `install` and `command` children write their output to standard error, so it never mixes with your CLI's standard output, such as `--json` results. A relative `cwd` resolves against the working directory, and a `command` step's relative `cwd` against the `runSteps` directory. Inside a Crust command, pass the action's `stderr` as `options.stderr` so non-fatal warnings go through the invocation's output.

`options.signal` cancels the steps: on abort, the running step's child gets `SIGTERM`. Once it exits, `runSteps()` rejects with `signal.reason` and skips the remaining steps. A child still running 5 seconds later gets `SIGKILL`, so a step that ignores `SIGTERM` cannot hang the command. On Windows, which has no graceful signal, the child's whole process tree ends at once. On macOS and Linux only that child is signalled, so a worker started by a compound `command` step such as `build && test` can outlive a signal sent only to the CLI's process (a terminal Ctrl-C still reaches the whole foreground process group). A second Ctrl-C ends the command right away without waiting. It defaults to the ambient terminal signal, which inside a Crust command is the invocation's `signal`, so Ctrl-C and `SIGTERM` end the command with exit 130 or 143.

| `install`     | Install dependencies with `packageManager`, else the detected one     |

| `open-editor` | Open `$EDITOR` or VS Code; warn instead of failing when unavailable   |

If Git has no `user.name` or `user.email`, `git-init` uses `Crust` / `crust@scaffolded.project` for the missing field on the initial commit only. Nothing is written to the repository config.

## Utilities

- `detectPackageManager(cwd?)` returns the `PackageManager` named by a lockfile in `cwd`, else by `npm_config_user_agent`, else `undefined`. The `install` step falls back to npm.
- `packageManagerFromUserAgent(userAgent)` reads the package manager from an `npm_config_user_agent` value, which package managers set for the scripts and `create` commands they run; `null` when it names none.
- `isInGitRepo(cwd?)` reports whether the path is inside a Git work tree.
