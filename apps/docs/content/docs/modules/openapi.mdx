`@crustjs/openapi` connects a CLI to the HTTP API behind it, from the API's pinned OpenAPI document. Each operation becomes a command, shaped by your overrides; your own commands call operations by `operationId` through a client typed from the spec; and `<cli> api` is a `gh api`-style escape hatch: it browses the spec offline and sends authenticated requests to any endpoint.

## Install

```npm
npm install @crustjs/openapi
```

The package has a peer dependency on `@crustjs/core` and uses the runtime's global `fetch`.

## `defineApi(options)`

`defineApi()` returns a frozen handle:

- `acme.extension` is the Extension to pass to `.extend()`. It contributes the `api` command, with its [`api preview`](#preview-a-request) subcommand, and provides the `api` Context; `acme.extension.id` is its identity.
- `acme.client` is the `api` [Context](/docs/guide/contexts): a command declares it with `.use(acme.client)` and reads it with `await ctx.api`. Each `.auth()` makes a new one; see [The API client](#the-api-client).
- `acme.commands` are the [generated commands](#generated-commands), to pass to `.add()`.

Its chain shapes the generated commands, like `defineCommand` and `defineExtension`: every method returns a new frozen handle and leaves the one it was called on unchanged.

| Method                                   | Does                                                                                                                                                    | A second call                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `.use(...sources)`                       | Context factories or Extensions every generated command `.use()`s; types `ctx` in the callbacks after it                                                | Appends                                                                                   |
| `.auth((input, { baseUrl }) => …)`       | Sends credentials with requests; reads the Contexts of the factories `.use()`d before it. See [`.auth()`](#authfn)                                      | Replaces, with a new `client`                                                             |
| `.onConfirm((ctx, message) => …)`        | Asks to confirm an operation's [`confirm`](#confirmation) message: resolving to nothing or `true` confirms; resolving to `false`, or throwing, declines | Replaces                                                                                  |
| `.each((op) => override)`                | The [override](#overrides) for every operation                                                                                                          | Replaces                                                                                  |
| `.override({ [operationId]: override })` | Overrides for single operations, whose fields replace the rule's                                                                                        | Appends; an entry for the same operationId replaces the earlier entry's fields one by one |
| `.add(group, ...definitions)`            | Puts your own commands in a group path, such as `"users"` or `"dns records"` (`""` is the root), creating the group when no operation maps to it        | Appends                                                                                   |

Declare a source with `.use()` before the callbacks that read it. The Contexts of the commands you `.add()` are required from the app too, but the callbacks see only those of `.use()`, which the generated commands use. A command you `.add()` uses the client of an earlier handle after the same `.auth()`, as `whoami` does with `api.client`: see [which client](#the-api-client).

### The spec

Pin the API's OpenAPI 3.0 or 3.1 document in your project and pass its location, a `file:` URL:

```ts
spec: new URL("./acme.openapi.jsonc", import.meta.url),
```

- Running from source (`bun run`, `node`, tests), the file is read when it is first needed: when the app reads `acme.commands` (at start, when it adds them), for `crust build`, or for `api --list`, `api --spec`, or a `call()`. Requests through `fetch()` and `api <path>` never read it. It is read once per process.
- The file may be JSONC: comments and trailing commas are allowed, whatever its name. Name it `<name>.openapi.jsonc` to have it [typed](#typed-client).
- A file that cannot be read or parsed fails with `api: cannot read the OpenAPI document "<file>" (<reason>)`, and exit code 1.

[`crust build`](/docs/guide/build-and-distribution) writes the document's data files to `<id>/` in the build output (`id` defaults to `"openapi"`), and a built CLI reads them there with [`artifactPath(id)`](/docs/api/crust#artifactpathpath). The entry never imports the document, so it stays out of the bundle, and start-up depends on the command that runs, not on the size of the API:

| File                                 | Holds                                                                                                                  | Read                                                    |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `index.json`                         | The generated root commands and top-level groups, with their descriptions                                              | At start, when the app reads `acme.commands`            |
| `root.json`, `groups/g-<group>.json` | The part of the document the root commands, or one top-level group, need: their operations and every `$ref` they reach | When one of those commands first runs or shows its help |
| `spec.json`                          | The whole document, as plain JSON                                                                                      | For `api --list`, `api --spec` and `call()`             |

- A command reads only the operations it needs from its file. Anything that walks every command, such as `--llms`, a completion script, or MCP's list of tools, reads every file.
- When the group files would total more than twice the document's bytes (a spec whose schemas all reference each other), they are not written, and every command reads `spec.json`.
- The files describe the commands of the app that was built: take `acme.extension` and `acme.commands` from the same handle, and add `acme.commands` whole (`exclude` an operation to leave it out). Otherwise `crust build` fails with a `DEFINITION` error naming this handle's commands that are missing or different (by path, arguments, flags, description or hidden state), or saying the app's are another handle's, and a run from source fails with one when the app holds the generated commands of another handle of the same call. Commands you `.add()` are yours, so handles may share them. An app that never reads `acme.commands` gets only `spec.json`, whatever commands of its own it has, and nothing of it is checked; one that reads them from a handle that generates none also gets the index, empty.
- Several bins of one CLI can share one API: `crust build` merges the identical files each one writes.
- Like skills and man pages, a standalone executable needs the `<id>` directory beside it, and the directory belongs to the build that wrote it: never copy one from another build. A built CLI without it has no generated commands, and every invocation fails with ``api: the OpenAPI data was not found at "<dir>/index.json". Run `crust build` first, and ship its "<id>" directory with the CLI.`` and exit code 1, or 2 when the arguments are a usage error without the generated commands, such as one of their names. The same message names any other missing file when a command needs it, and an `index.json` that is damaged or of another version of `@crustjs/openapi` fails every invocation the same way, naming it. Extend `acme.extension` before [`didYouMean()`](/docs/modules/extensions/did-you-mean): an Extension extended earlier reports a command it cannot find first.

A plain object, such as a small inline spec or one in a test, works too: it is kept in memory, bundled with the CLI, and the build writes nothing.

Specs are pinned, never fetched: any other `spec`, such as a loader function, an `https:` URL, or a path string, is a `DEFINITION` [`CrustError`](/docs/api/errors) when `defineApi()` runs from source or in `crust build`.

## Which to use

`api` and the generated commands read the same pinned spec, and a CLI ships both: the generated commands are its product, and `api` reaches what they leave out.

|                                                                  | Generated commands                                | `api`                                                                                                                                       |
| ---------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| For                                                              | The operations your CLI offers, by name           | Any endpoint without a command, and browsing the spec                                                                                       |
| Input                                                            | Typed arguments and flags, checked before sending | A path, `-F` fields and a `--body`                                                                                                          |
| Output                                                           | The operation's [output schema](#output)          | The response body as it is                                                                                                                  |
| Your [overrides](#overrides): names, `confirm`, `bind`, `unwrap` | Applied                                           | Not applied: `api /users/42 -X DELETE` asks nothing                                                                                         |
| As [MCP](/docs/modules/mcp#tools) tools                          | Yes, like the commands you write                  | Only when `include` names them: `["api", "preview"]` adds the preview alone; `["api"]` adds `api`, which sends any request, and its preview |

Every operation becomes a command unless an override [excludes](#overrides) it or the spec deprecates it. An operation without a command, for either reason or because of a [problem](#what-crust-build-checks), stays reachable with `api <path>`. To offer fewer commands, give `.each()` a rule:

An agent that runs commands unattended gets every generated command as an MCP tool, the ones that write and delete too. Narrow them with a rule like the read-only one, or with the MCP server's `exclude`, and let it check a request first with [`api preview`](#preview-a-request): `include: [["api", "preview"]]` offers the preview without `api` itself, which could send the requests your rule left out.

## The `api` command

`acme.extension` contributes `api`: it browses the spec and sends requests below the base URL, with the client's auth.

### Browse the spec

```sh
$ my-cli api --list
GET /users listUsers List users
$ my-cli api --spec listUsers
{"method":"GET","path":"/users","operationId":"listUsers","summary":"List users"}
```

`--list` prints one line per operation: `METHOD path operationId summary`, leaving out an `operationId` or `summary` the spec lacks. In an app that adds `acme.commands`, an operation a [problem](#what-crust-build-checks) leaves out of the generated commands ends with `[unavailable: <code>]` (`unavailable` under `--json`); an app that uses `api` alone has no generated commands, and marks nothing. Under [`--json`](#json-output) it prints a JSON array of `{ method, path, operationId?, summary?, unavailable? }` objects instead, which an agent can read without guessing where a summary starts.

`--spec <operationId|path>` prints one line of JSON:

- For a path such as `/users/{id}`, the path item, including its shared `parameters`.
- For an `operationId`, the operation with its `method` and `path` added, and with the path item's shared `parameters` merged into its own: an operation parameter with the same `name` and `in` replaces the shared one.
- An unknown target fails with exit code 1, and so does an `operationId` several operations share, naming their `METHOD path`s; pass the path instead.

Both read the spec this way:

- A path item that is itself a local `$ref` (such as to `components.pathItems`) is followed.
- Keys of `paths` that do not start with `/`, such as `x-*` extensions, are skipped.

`--spec` resolves local JSON Pointer `$ref`s (`#/...`, URI-encoded or not), writing each target once, so the output stays as small as the spec, even for large public specs with schemas shared across thousands of places:

- A target used once in the output replaces its `$ref`, keeping sibling keys such as `description`.
- A target used more than once, or recursively, keeps its `$ref`s and is written once under a top-level `$refs` object, keyed by the `$ref` text:

  ```json
  {
    "method": "POST",
    "path": "/users",
    "requestBody": {
      "content": { "application/json": { "schema": { "$ref": "#/components/schemas/User" } } }
    },
    "$refs": {
      "#/components/schemas/User": {
        "type": "object",
        "properties": {
          "friends": { "type": "array", "items": { "$ref": "#/components/schemas/User" } }
        }
      }
    }
  }
  ```

- Other `$ref`s, such as external files, `#anchor`, or a pointer to nothing, stay as is.

### Send requests

```sh
my-cli api /users                                  # GET
my-cli api /users -F name=ada -F admin=true        # POST {"name":"ada","admin":true}
my-cli api /users -X GET -F page=2                 # GET /users?page=2
my-cli api /users/42 -X PATCH --body @patch.json   # body from a file; - reads stdin
my-cli api /users -H 'Accept: application/vnd.example+json'
my-cli api /users --paginate                       # every page, one JSON line each
```

`api <path>` resolves `path` below `baseUrl`, keeping the base URL's own path; an absolute URL is used as is. Without `<path>`, `--list`, or `--spec`, it fails with a `VALIDATION` error.

| Flag                        | Behavior                                                                                                                                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-X, --method`              | HTTP method. Default: `GET`, or `POST` when fields or a body are given. See [methods](#methods)                                                                                                                |
| `-F, --field key=value`     | Repeatable. `true`, `false`, `null`, and JSON numbers become JSON values; anything else, such as `007`, stays a string. A number too large for a double, such as `1e309`, is rejected                          |
| `--body <value>`            | Request body: inline, `@path` (relative to the working directory, `~` expanded), or `-` for all of stdin. Stdin already read to the end, such as by `--input -` from the `input()` Extension, is an empty body |
| `-H, --header 'Key: Value'` | Repeatable request header. Overrides the `auth` header of the same name                                                                                                                                        |
| `--paginate`                | Fetches every page through the `paginate` option, printing each body as one JSON line                                                                                                                          |

- Fields form a JSON object body. For `GET` and `HEAD`, or when `--body` is given, they become query parameters instead.
- A body is sent with `Content-Type: application/json` unless a header sets it.

#### Methods

`-X` takes an HTTP method token ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#name-methods)): letters, digits, and ``!#$%&'*+-.^_`|~``.

- The method is sent in upper case whatever its case, so `-X patch` sends `PATCH`.
- An empty value or one with spaces or other characters, such as `-X "DELETE "`, fails with a `PARSE` error before any request.
- So does a method the runtime's `fetch()` would not send, naming what it would send instead: one Node's `fetch()` forbids, such as `CONNECT`, or, on Bun, one it does not know, which its `fetch()` would send as `GET`.

#### `--paginate`

After each successful page, `--paginate` calls `paginate(response)` with a copy of the response, so it may read headers or the body. It requests the page `paginate` returns, until it returns `undefined`.

- A returned request without `init` reuses the previous request's method, headers, and body.
- Each page body is printed as one JSON line (NDJSON), so `my-cli api /users --paginate | jq -s` collects the pages into one array, like `gh api --paginate --slurp`. (Without `--slurp`, `gh api` instead joins array pages into one array.) JSON is compacted by removing whitespace outside strings, so numbers keep their exact digits; any other text body, including an empty one, is printed as a JSON string. A page body that is not valid UTF-8 has no JSON line, so it fails the command with exit code 1; pages already printed stay printed.
- If `paginate` returns the request just sent (same resolved URL and method, without a new `init`), it fails with exit code 1 instead of looping. Pages already printed stay printed.
- Without a `paginate` option, `--paginate` fails before any request.

### Origins and credentials

Like `gh api`, the request must stay on the base URL's origin (scheme, host, and port, after URL normalization), so credentials never reach a host given on the command line.

- An absolute URL to another origin, including tricks such as `https://api.example.com@evil.example`, fails with a `PARSE` [`CrustError`](/docs/api/errors) naming the URL and the allowed origin, before any request.
- `..` segments may leave the base URL's path: the boundary is the origin, not the path prefix.
- Only redirects and `--paginate` pages may leave the origin. They must be `http:` or `https:` URLs, and are sent there without `Authorization`, `Cookie`, `Proxy-Authorization`, or any header named like an `auth` header, including values set with `-H`.

### Preview a request

`api preview` prints the request a generated command or `api <path>` would send, and sends nothing:

```sh
$ my-cli api preview users delete -- 42             # a generated command: its own arguments and flags go after --
$ my-cli api preview /users/42 -X DELETE            # a request path, with the flags of api <path>
{
  "method": "DELETE",
  "url": "https://api.acme.example/v1/users/42",
  "headers": {},
  "bodyKind": "none",
  "body": null
}
```

- The result is `{ method, url, headers, bodyKind, body, bound? }`: the absolute URL with its query; the headers by lower-case name; `bodyKind` `"json"` with the parsed body, `"bytes"` with any other body as text, or `"none"` with `body: null`. It is the same request the command would build, from the same plan, with the same `VALIDATION` errors, so a preview cannot disagree with what is sent.
- Nothing runs that could have an effect: no `.auth()` call, no Context set up (so no credential or keyring read), no [`.onConfirm()`](#confirmation) handler, no [`bind`](#overrides) function, no request. A bound parameter or body field stays the placeholder `{name}`, and its name is listed in `bound`. Headers the client adds, such as the `auth` ones, are not shown.
- `Authorization`, `Proxy-Authorization`, `Cookie` and `X-Api-Key` headers given with `-H` show as `<redacted>`. Query parameters and body fields are shown as given.
- The generated command's arguments and flags are parsed with its own definitions, environment fallbacks and defaults. No hook runs, so values other Extensions bind during set-up are not applied: `--input` from [`input()`](/docs/modules/extensions/input) is left out, and the preview fails as the command would without it. A [`@crustjs/config`](/docs/modules/config) setting reaches a request only through a `bind`, so its parameter stays the placeholder too.
- A target starting with `/` is a request path, and `api preview` takes the `-X`, `-H`, `-F`, `--body` and `--paginate` flags of [`api <path>`](#send-requests) for it. It never reads stdin: `--body -` is refused, and `--body @file` reads only a regular file of at most 16 MiB, so `@/dev/stdin` or a FIFO is refused too. Any other target is a generated command's path, through an alias too, and at any place the app adds `acme.commands`, even more than one; its own flags go after `--`. Below the first place, a command is told apart only by its path and shape, so where a path there fits two operations of the same shape, `api preview` refuses it and names the paths to preview instead. `--paginate` previews the first page's request without calling `paginate`, and fails as `api <path> --paginate` does when the CLI configures no pagination.
- It declares an [output schema](/docs/api/crust#outputschema), so `--json` prints only the preview. Like `api`, it is an Extension's command, so [MCP](/docs/modules/mcp#tools) offers it as a tool only when `include` names it: `include: [["api", "preview"]]` exposes the preview without the request-sending `api` tool, and `include: [["api"]]` exposes both.

A request path always starts with `/`, so `api preview` never shadows one: `my-cli api /preview` requests `/preview`.

### Output and errors

The response body goes to stdout:

- When stdout is not a terminal, such as a pipe, a file, or an `execute({ io })` sink, the body is written as its exact bytes, whatever its `Content-Type`, so `my-cli api /export.zip > export.zip` works and a text body keeps its line endings. Output captured by [`run()`](/docs/api/crust#runpath-input-options) or `captureExecute()`, and so an [MCP](/docs/modules/mcp) tool result, is text: those bytes decoded as UTF-8, so a binary body arrives with replacement characters.
- To a terminal, the body is printed as text, ending with exactly one newline; an empty body prints nothing. A body that is not valid UTF-8 can't be printed as text and fails the command with exit code 1 after the request, as `gh api` and `curl` refuse to print binary to a terminal; a non-2xx one is left out, and the command fails with the `ApiResponseError`.

| Failure                                                                                                                              | Result                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Non-2xx response                                                                                                                     | The body still prints to stdout, then an `ApiResponseError` (exit 1) whose `status` holds the code; its message, such as `GET /users/9: HTTP 404 Not Found`, goes to stderr |
| `-F` without `=` or out of number range, `-H` without `:` or with a name or value HTTP rejects, an invalid `-X`, unreadable `--body` | A `PARSE` [`CrustError`](/docs/api/errors) before any request                                                                                                               |

The `-F` and `-H` errors name the flag and the expected shape, such as `Invalid -H value: expected "Name: value".`, never the text given, since a header can hold a token. For the same reason, an `ApiResponseError` leaves out the request's query and fragment, including query parameters `-F` added: its message shows the path as given up to its `?`.

### JSON output

With the [`json()`](/docs/modules/extensions/json) Extension registered, `--json` makes `api` return its data as the command result, so stdout carries only JSON:

```sh
$ my-cli api /users/42 --json
{"id":42,"name":"Ada"}                                     # stdout
$ my-cli api /users/9 --json
{"message":"not found"}                                    # stderr: the response body
{"message":"GET /users/9: HTTP 404 Not Found","details":{"status":404}}   # stderr
```

| Command                 | Result on stdout                                                                                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api --list`            | An array of `{ method, path, operationId?, summary?, unavailable? }`                                                                                                               |
| `api --spec <target>`   | The definition `--spec` prints, as above                                                                                                                                           |
| `api <path>`            | The response body: parsed when it is JSON, otherwise its text as a JSON string; nothing for an empty body. A body that is not UTF-8 fails the command, since JSON can't hold it    |
| `api <path> --paginate` | NDJSON: one `{"type":"event","data":…}` line per page with its body as above (an empty body is `""`), then `{"type":"result"}`, or `{"type":"error","error":…}` for a failing page |
| `api preview …`         | The [preview](#preview-a-request) object                                                                                                                                           |

- A non-2xx body is written to stderr, followed by the error JSON, whose `details` hold the `status`.
- JSON numbers are read as JavaScript numbers, so digits beyond double precision are lost and `-0` becomes `0`. Without `--json`, the body is printed exactly, and `--paginate` pages keep their exact digits.

## Generated commands

`acme.commands` holds a command per operation, built at run time from the pinned spec (in a built CLI, from its [data files](#the-spec)), and your commands from `.add()`: the root commands and the top-level groups, to pass to `.add()`. They are ordinary application commands, so help, completion, [`schema()`](/docs/modules/extensions/schema), [skills](/docs/modules/skills), and [MCP](/docs/modules/mcp) (as tools) treat them like the commands you write. Each one `.use()`s `acme.client`, which `acme.extension` provides, and the sources from `.use()`; adding them to an app that lacks a provider is a TypeScript error.

```sh
$ acme users --help                        # the group of the operations tagged "Users"
$ acme users get 42                        # GET /users/42
$ acme users list-users --role admin --limit 5 --tag a --tag b
$ acme users create-user --name Ada --body '{"profile":{"bio":"hi"}}'
```

| From the operation                                            | The command                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First tag                                                     | Its group, in kebab case; an untagged operation is a root command. A tag's `description` is its group's                                                                                                                                                                   |
| `operationId`                                                 | Its name, in kebab case, without a leading `<group>-`                                                                                                                                                                                                                     |
| `summary`                                                     | Its description                                                                                                                                                                                                                                                           |
| Path parameters                                               | Required positional arguments, in template order                                                                                                                                                                                                                          |
| Query and header parameters                                   | Typed flags: a number for `number` and `integer`, a boolean (`--no-<name>` sends `false`), else a string, with a string enum as its choices (a numeric enum is a plain number: the API checks it); an array of those is a repeatable flag; required when the parameter is |
| Top-level scalar, enum, or scalar-array fields of a JSON body | Typed flags in the same way, never required                                                                                                                                                                                                                               |
| A JSON request body                                           | `--body`, a JSON flag; files and stdin go through `--input @file` or `--input -` of the [`input()`](/docs/modules/extensions/input) Extension                                                                                                                             |
| `security: []`                                                | A public request: `auth` is never called, also for the next pages                                                                                                                                                                                                         |
| The 2xx JSON response schema                                  | The output schema; see [Output](#output)                                                                                                                                                                                                                                  |

Names are [kebab-cased](#how-the-spec-is-read), and the inputs an operation cannot offer are left out as described there. A body field that repeats a parameter's name gets no flag: the parameter keeps its input, and the body field is sent only from `--body`. Cookie parameters are never sent. Deprecated operations are left out unless an override sets `exclude: false`.

### The request

The command sends the request through the client, so it gets the base URL, auth, redirects, the 401 retry and the request rules of [`call()`](#calloperationid-input), and fails with a `VALIDATION` [`CrustError`](/docs/api/errors) before any request for a value `call()` rejects.

- The body is `--body` with the body field flags merged over it. Before the request, the command checks it: a required body or required field that is missing, or a flagged field's value of another type or outside its enum, such as one from `--body`, is a `VALIDATION` error naming it (`missing the body field "name" (--name)`). An optional body with nothing given is not sent.
- `--body` takes a JSON object for an object body. Its published JSON Schema stands alone: every local `$ref` is replaced by its target (in a 3.0 document, translated like the [schemas of the spec's operations](#how-the-spec-is-read)), and the required fields a flag can fill are left out of its `required`. A recursive or very large schema, or one with a `$ref` that cannot be followed or a `$dynamicRef` / `$recursiveRef`, is published as its top-level fields, each standing alone or `{}`.
- A [`bind`](#overrides) runs once before the request and fills every parameter and the body field of its name, and those inputs are not offered. It runs only for an operation that has such an input, so an `.each()` binding is never called for the others.
- A [`confirm`](#confirmation) message is confirmed after the whole request is built and checked, so a rejected one never asks, and before it is sent.

### Output

The command prints the result for people, pretty-printed JSON or text, and returns it as the command's result:

| Response                                                              | Result                                                                        |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 2xx JSON                                                              | The parsed body, after `unwrap`                                               |
| 2xx text                                                              | The text, after `unwrap`                                                      |
| 2xx without content                                                   | `undefined`; nothing is printed                                               |
| A 2xx body that is not UTF-8                                          | An error: use `api <path>` to save it                                         |
| Non-2xx, or 2xx in another media type than the JSON the spec declares | An `ApiResponseError`, as for [`call()`](#calloperationid-input), exit code 1 |

Every generated command declares [`.output()`](/docs/api/crust#outputschema): with the [`json()`](/docs/modules/extensions/json) Extension, `--json` prints only the result as JSON. The output JSON Schema is advertised when every 2xx response is JSON with the same schema, which stands alone like the body's; with `unwrap`, only an override's `outputSchema` is advertised. A command without one still has `output: true` in its snapshot.

### Confirmation

A `confirm` message from `.each()` or `.override()` makes the command call the `.onConfirm()` handler with its `ctx` and the message before the request. Resolving to nothing (as `(await ctx.confirm)(message)` does) or to `true` confirms. Resolving to `false`, as a prompt that returns the answer does, fails the command with `<operationId>: not confirmed: <message> Nothing was sent.`, and throwing fails it with that error; either way no request is sent. `@crustjs/openapi` never asks by itself, and confirms nothing by HTTP method. With the [`confirm()`](/docs/modules/extensions/confirm) Extension, `.use(confirm)` adds `--yes`, as in the example above. An operation with a `confirm` message and no `.onConfirm()` is never built without its confirmation: it is left out, and [`crust build` fails](#what-crust-build-checks).

### `--paginate`

A command gets `--paginate` when a `paginate` function applies (an override's, else `defineApi`'s) and its result after `unwrap` is a list, or unknown: a 2xx schema that is an array (without `unwrap`), an override's `outputSchema` that is one, or an `unwrap` without `outputSchema`, as for an API that wraps every result:

<include lang="ts">../../../examples/modules/openapi.ts#unwrap</include>

A tuple schema (`prefixItems`) gets no `--paginate`. Its result is every page's result joined into one array, as `paginate` requests them, and the advertised schema leaves out the limits of one page's list (`minItems`, `maxItems`, `uniqueItems`, `contains`); the items keep theirs. Without `--paginate` offered, a spec parameter named `paginate` is an ordinary flag. An override's `paginate` on an operation whose result is known not to be a list, or is a tuple, leaves the operation out and fails `crust build` (`paginate-needs-array`); `defineApi`'s `paginate` is offered only where it applies. A page whose result is not a list fails, naming the operation, and so does a `paginate` that returns the request just sent. With and without `--paginate`, the result is a list of the same items, so one output schema describes both. (`api <path> --paginate` instead prints one JSON line per page.)

### Collisions and left-out operations

A generated command that would clash is left out of `acme.commands`, so the CLI works without it, `api --list` marks it `[unavailable: command-collision]`, and [`crust build` fails](#what-crust-build-checks) until an override settles it.

- Two operations that become the same command: the later one, in `api --list` order, is left out with `command-collision`, naming both.
- An operation and a command you `.add()` to its group with the same name: the operation is left out and yours stays. The same goes for the `api` command: an operation that would be the root command `api`, or in a group `api` (such as one tagged `API`), is left out; set `group` or `name` in its override. To replace a generated command on purpose, set `exclude: true` in its override and add yours.
- An alias of an added command, or a flag that clashes with an Extension's or a Context's (such as `--yes`), is a core `DEFINITION` error when the command is added or first used; `await app.snapshot()` in a test checks the whole tree.

## Overrides

One shape, given for every operation by `.each(op)` or for one operationId by `.override()`:

<auto-type-table path="../../../../../packages/openapi/src/overrides.ts" name="OperationOverride" />

- A field left out, or `undefined`, uses the default, so a rule can special-case some operations: `.each((op) => ({ group: op.path.startsWith("/admin") ? "admin" : undefined }))`.
- A field set in `.override()` replaces the same field from `.each()` whole: `bind: {}` removes the rule's bindings for that operation.
- `.each()` runs once per operation, synchronously, and must be pure. Its `flagName`, `bind` and `positional` entries for a parameter an operation does not have are ignored; in `.override()` they fail `crust build` (`override-unknown-param`).
- An `.override()` entry may also set `expect: { method, path }`, the operation it was written for: when the spec moves the operationId elsewhere, `crust build` fails (`override-stale`).
- `positional` takes parameter names, and a body field is never positional. Values fill the arguments in order, so the required ones come first, and a list parameter, a variadic argument, comes last; any other order fails `crust build` (`positional-order`). `flagName` and `bind` also take top-level body field names. An entry set to `undefined` is no entry: the default applies.
- `bind` functions may be async and get the command's `ctx`, typed by `.use()`; they run before every request.

## What `crust build` checks

An operation that does not fit is left out of `acme.commands`, so a CLI run from source keeps working while you fix it: `api --list` of an app that adds them marks it `[unavailable: <code>]`, and nothing throws. When the app takes the generated commands of the handle whose `extension` it registers (it reads that handle's `acme.commands`, to add at any mount), that handle's build hook sorts its problems by one rule: can configuration make the operation a working command? An app that never reads `acme.commands` checks nothing, whatever commands of its own it has, and builds with any document, as without generated commands.

- **Yes: `crust build` fails** until an override (other than `exclude`), `.onConfirm()` or `.add()` settles each one, or `exclude: true` leaves the operation out on purpose. It lists every such problem with its fix:

  ```text
  Error: Extension "crust:openapi" build failed: defineApi: 1 problem needs a decision before this CLI can be built.

    GET /people: the command "users list-users" is also the command of GET /users (listUsers)
      fix: Set `group` or `name` in the override of one of them
  ```

- **No: the operation is skipped**, and the build passes. It becomes no command, so it clashes with none, and none of its own problems fails the build either: its input names, its name, or its override (a stale `expect`, an unknown parameter, a `confirm` without `.onConfirm()`). `api --list` marks it with the code that skips it, and it stays reachable through `api <path>` and `call()`.
- A document that is not OpenAPI 3.0 or 3.1 fails the build: no command can come from it.

| `code`                       | When                                                                                                                     | `crust build` |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------- |
| `unsupported-version`        | `openapi` is missing or not 3.0.x or 3.1.x, as in a Swagger 2.0 document                                                 | Fails         |
| `missing-operation-id`       | An operation has no `operationId` (a deprecated one is left out without a problem)                                       | Skips it      |
| `duplicate-operation-id`     | Several operations share an `operationId`                                                                                | Skips each    |
| `no-success-response`        | An operation has no 2xx response                                                                                         | Skips it      |
| `unsupported-param-style`    | A required parameter in a style or shape no input carries (see [below](#how-the-spec-is-read))                           | Skips it      |
| `content-param`              | A required parameter described by `content`                                                                              | Skips it      |
| `required-cookie-param`      | A required cookie parameter: generated commands send no cookies                                                          | Skips it      |
| `unsupported-body-type`      | A required request body that is not JSON                                                                                 | Skips it      |
| `command-collision`          | Two commands, or a command and a group, with one path, also against a command you `.add()` or the `api` command          | Fails         |
| `flag-collision`             | Two inputs of a command with one name                                                                                    | Fails         |
| `unflaggable-name`           | A flag name core rejects, such as `no-cache` or an empty one                                                             | Fails         |
| `unusable-name`              | A command, group or argument name core rejects, such as the empty name of an operationId without ASCII letters or digits | Fails         |

| `confirm-without-handler`    | A `confirm` message with no `.onConfirm()`                                                                               | Fails         |

## How the spec is read

Generated commands, `api --list` marks and `crust build` read the spec's operations one way. They walk `paths` the way [`api --list`](#browse-the-spec) does, in the same order, and normalize each operation once:

- Local `$ref`s are followed for path items, parameters, request bodies, responses, and each top-level schema. Deeper `$ref`s inside schemas stay as they are, so a recursive schema stays finite.
- Each schema is published as a JSON Schema 2020-12 schema that means what the API's schema means. Only these changes are made; everything else, such as `allOf`, stays as written:
  - In a 3.1 document, a schema `$ref` with keywords beside it applies in place like a one-member `allOf`: the keywords stay as written, and the resolved target becomes the first member of their `allOf`. A `$ref` alone is replaced by its target. Boolean schemas (`true`, `false`) stay booleans.
  - In a 3.0 document, the dialect differences are translated at every inline level: `nullable: true` adds `"null"` to `type` (`{ type: ["string", "null"] }`), the boolean `exclusiveMinimum` / `exclusiveMaximum` become the numeric form, and a `$ref` keeps no sibling keywords, which 3.0 ignores. A schema reached through a nested `$ref` is still in the document's own 3.0 form.
- The path item's `parameters` are merged in: an operation parameter with the same `name` and `in` replaces the shared one. `Accept`, `Content-Type`, and `Authorization` header parameters are left out, as OpenAPI says to ignore them.
- A request body or response with several media types is read through its JSON one (`application/json` or `application/*+json`), else its first.
- `security` is the operation's, else the document's; `[]` marks a public operation.
- The spec is never modified.

Each operation is an `Operation`, the `op` that [`.each()`](#overrides) receives:

<auto-type-table path="../../../../../packages/openapi/src/operations.ts" name="Operation" />

Each of its `params`:

<auto-type-table path="../../../../../packages/openapi/src/operations.ts" name="Param" />

Deprecated operations are read too, and left out of the generated commands unless an override sets `exclude: false`.

`api --list` and `api --spec` stay permissive: they also read documents without a version and operations without an `operationId`, also in a CLI built without generated commands.

When Crust turns spec names (operationIds, tags, parameter and body field names) into command, group, or flag names, it kebab-cases them: a capital after a lowercase letter or digit, and the last capital of a capital run followed by a lowercase letter, start a word, and every run of other characters than ASCII letters and digits is one `-`. So `DeleteWebhook` and `deleteWebhook` both become `delete-webhook`, `notification_url` becomes `notification-url`, and `getHTTPResponse` becomes `get-http-response`, while plural acronyms split before their last capital: `CAs` becomes `c-as` and `AAGUIDs` becomes `aagui-ds`. Names are compared after kebab-casing, so two that differ only in case or separators are the same name.

When Crust maps an operation's inputs to a command, it cannot offer:

- a path parameter that is not a scalar in style `simple`;
- a query (style `form`) or header (style `simple`) parameter in another style, or one that is not a scalar or an array of scalars;
- a parameter described by `content`, or a cookie parameter;
- a request body that is not JSON, such as form-encoded or multipart.

Such an input leaves the operation out only when the operation cannot be called without it: a required one does; an optional one gets no flag, and stays reachable through `api <path>`.

## The API client

`acme.client` is the `api` Context. A command that declares it with `.use(acme.client)` gets the client: `call()` for an operation of the spec, and `fetch()` for any request, both bound to the base URL and [`.auth()`](#authfn).

Each `.auth()` makes a new `client`, which the handles chained after it share; before any `.auth()`, every handle shares one client that sends no credentials. Take a command's client from the handle whose `extension` the app extends, or from one before it after the same `.auth()`. A command with another client fails to compile where the app adds it (`FIX_DEPENDENCY_TYPE`), also one that uses the client of a handle before `.auth()` and is `.add()`ed to a handle after it. The types tell clients apart by the types of the Contexts their `auth` reads only: a client of another `.auth()` that reads Contexts of the same types, or of an `.auth()` that reads none against the handle before it, compiles. Its requests then use the `auth` of the handle the app extends, provided the command parses the flags of the Contexts that `auth` reads; otherwise the command fails with a `DEFINITION` error and sends nothing.

`ApiClient<Operations>` is the client of an `auth` that reads no Contexts. A helper that takes any handle's client is generic in them:

### `call(operationId, input?)`

Sends the operation with that `operationId`, as `whoami` does above. `input` holds the operation's `path`, `query` and `header` parameters by name, and its `body`:

- A parameter value is a scalar, an array of scalars, or an object of scalars, serialized by the parameter's `explode` as OpenAPI says. Cookie parameters are never sent.
- Path parameters fill the path template, percent-encoded (style `simple`): an array as `a,b`, an object as `k,v` or exploded `k=v`. A value that would make an empty, `.` or `..` path segment is rejected, since the URL would address another resource, such as `/users/..` the API's root.
- Query parameters are sent in style `form`: an array repeats the parameter (`?tag=a&tag=b`), or with `explode: false` is comma-separated (`?tag=a,b`); an object sends each property as a parameter (`?role=admin`), or with `explode: false` as `?filter=role,admin`.
- Header parameters are sent as headers (style `simple`), like path values without percent-encoding.
- `body` is sent as JSON, with the operation's JSON media type as `Content-Type`.
- When a 2xx response of the operation declares JSON, the request asks for it with `Accept: application/json` (and the operation's own `+json` types), unless `input.header` sets `Accept` (or `accept`), which the typed input allows for every operation, next to the headers the spec declares.
- The request goes through [`fetch()`](#fetchpath-init), so it gets the same base URL, auth, redirects and [401 retry](#authentication). An operation with `security: []` is public: it is sent with `auth: false`.

It resolves to:

| Response                                                                                                                        | Result                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2xx with a JSON media type                                                                                                      | The parsed body; `undefined` when the body is empty                                                                                                                                    |
| 2xx with a JSON media type whose body does not parse                                                                            | Rejects with an `ApiResponseError` whose `status` holds the code, such as `GET /users/1: HTTP 200 answered application/json that is not valid JSON`; the message never quotes the body |
| 2xx of another media type known to be empty: no body (such as `204` or `205`) or `Content-Length: 0`                            | `undefined`                                                                                                                                                                            |
| Any other 2xx with another media type, where the spec declares JSON for that status (or, for an undeclared status, for any 2xx) | Rejects with an `ApiResponseError` whose `status` holds the code, such as `GET /reports/1: HTTP 200 answered application/xml, not JSON`; the body is not read                          |
| Any other 2xx with another media type, even one whose empty body is only known after reading it                                 | The `Response` itself, unread. For a download or a stream, `fetch()` is usually more direct                                                                                            |
| Non-2xx                                                                                                                         | Rejects with an `ApiResponseError` whose `status` holds the code, such as `GET /users/9: HTTP 404 Not Found`; its message leaves out the query                                         |

Before any request, `call()` fails with a `VALIDATION` [`CrustError`](/docs/api/errors) for a missing required parameter or body, a parameter the operation does not have, or a body it does not take; for a path value that would make an empty, `.` or `..` segment, a header value HTTP does not allow, or a body `JSON.stringify()` cannot send (a function, a symbol, a cycle, a `BigInt`), whose messages never repeat the value; and for an input it cannot send: a body that is not JSON, a parameter in another style or described by `content`, a required cookie. Use `fetch()` for those. An `operationId` the spec does not have, or that several operations share, fails with an error naming it, and so does a spec that cannot be read ([The spec](#the-spec)). Errors of the request itself, such as a network error, a refused redirect or an error `auth` throws, reject `call()` as they reject [`fetch()`](#fetchpath-init); the table above lists the rest. `call()` does not paginate; use `fetch()` with your own loop, or `api <path> --paginate`.

### `fetch(path, init?)`

Resolves `path` like `api <path>` and returns the `Response`.

- A `path` off the base URL's origin rejects with a `TypeError` before any request.
- It adds the `auth` headers the request does not set itself.
- It passes the invocation's cancellation signal unless `init.signal` is given.
- With `init.auth: false`, for a public operation, neither the request nor its redirects call `auth` or carry its headers. Until `auth` has run in the invocation its header names are unknown, so only `Authorization`, `Cookie`, and `Proxy-Authorization` are stripped from such a request on another origin.

Unless `init.redirect` is `"manual"` or `"error"`, `fetch()` follows redirects itself, with the global `fetch()`'s rules:

- `http:` and `https:` targets only, at most 20 redirects per request, counted across origins.
- `301` and `302` turn a `POST`, and `303` any method but `GET` and `HEAD`, into a bodyless `GET`.
- A redirect to another origin continues without `Authorization`, `Cookie`, `Proxy-Authorization`, or any header named like an `auth` header, even when the request set its value.
- After a redirect, the response (and its `clone()`) reports `redirected` as `true` and `url` as the final URL.

### `.auth(fn)`

`fn(input, { baseUrl })` returns the headers to send, or an `AuthAttempt`. Without `.auth()`, requests carry no credentials; a second `.auth()` replaces the first.

- It runs at most once per invocation, on the first request that sends credentials: not when a command only reads the Context, not for `auth: false` requests, and not for `api --list`, `api --spec` or `api preview`.
- It receives the [Context setup input](/docs/api/types#contextsetup-and-contextbag), including `signal`, `stdout`, and `stderr`, and as its second argument `{ baseUrl }`, the base URL as configured.
- `input.ctx` holds the Contexts of the Context factories `.use()`d before `.auth()`, set up only when `fn` reads them; every factory a spread array may hold counts. Those `.use()`d after it are for the other callbacks only. An Extension's Contexts, such as `confirm`, are not readable in `fn`, wherever they are `.use()`d: the client is a Context, and a Context's `.use()` takes only factories.
- Besides credentials, it may return any default headers, such as `User-Agent` or an API-version header. All of them are treated as credentials, so they go only to the base URL's origin.
- It may return an `AuthAttempt` instead of the headers, to have a 401 retried; see [Authentication](#authentication).

## Typed client

<Callout type="warn">
  Experimental: the typed client needs TypeScript 7.1, which is in beta.
</Callout>

`call()` is typed from the spec by [inspex](https://github.com/chenxin-yan/inspex), a TypeScript 7.1 content mapper: no generated file, no type import, and no type argument. Set it up once:

1. Install it with TypeScript 7.1 as development dependencies. The compiler starts the mapper with `node`, so Node.js 26 or later must be on `PATH`.

   ```npm
   npm install --save-dev inspex typescript@beta
   ```

2. Save the spec as `<name>.openapi.jsonc` (inspex reads JSONC; TypeScript does not hand `.json` files to a mapper) in a directory your `tsconfig.json` includes, and pass its URL as `spec`.
3. Register the mapper at the top level of `tsconfig.json`, not in `compilerOptions`, with `register` pointing at `@crustjs/openapi`'s `Specs` interface:

   ```jsonc title="tsconfig.json"
   {
     "compilerOptions": {
       // ...
     },
     "contentMappers": [
       {
         "package": "inspex",
         "extensions": [".openapi.jsonc"],
         "options": { "register": { "module": "@crustjs/openapi", "interface": "Specs" } },
       },
     ],
   }
   ```

4. Pass `--runExternalCode` to every `tsc` run, such as `tsc --noEmit --runExternalCode`. The flag cannot be set in `tsconfig.json`: a mapper is a program the compiler runs.

inspex then adds each `<name>.openapi.jsonc` in the program to `Specs` under `<name>`, and `call()` checks the `operationId`, each parameter and body field, and the fields read from the result:

```ts
const user = await api.call("getUser", { path: { id: "me" } }); // { id: string; name: string }
await api.call("getUsr", { path: { id: "me" } });
//             ~~~~~~~~ not assignable to '"createUser" | "getUser"'
await api.call("createUser", { body: { nmae: "Ada" } });
//                                     ~~~~ 'nmae' does not exist in type '{ name: string; }'
user.nickname;
//   ~~~~~~~~ Property 'nickname' does not exist on type '{ id: string; name: string; }'
```

- `input` has `path`, `query`, `header` and `body` exactly as the operation takes them, each required when the operation requires one of its values. The argument is optional when nothing is required.
- The result is the JSON body of the operation's 2xx responses (a union when there are several; the JSON one where a status also declares another media type), `undefined` for one without content, and `unknown` for another media type or an operation with no 2xx response.
- The [overrides](#overrides) are checked too: `.override()` keys must be operationIds of the spec, and an entry's `flagName` and `bind` keys the operation's parameter or top-level JSON body property names, and its `positional` entries parameter names. `op.id` in `.each()` is the union of the operationIds. (`expect` is checked by `crust build`.)
- With one spec registered, every handle uses it. With several, pass `id` set to the spec's name (`id: "acme"` for `acme.openapi.jsonc`); `id` also names the directory `crust build` writes the document to.

Editors run the mapper only when allowed to: VS Code asks for workspace trust and the content mapper permission. An editor that starts TypeScript's language server (`tsc --lsp --stdio`) itself must pass `runExternalCode: true` in its initialization options (in Neovim, `init_options = { runExternalCode = true }`).

Where the mapper does not run (TypeScript 7.0 or older, 7.1 without `--runExternalCode`, which also reports `TS18068`, an editor without the opt-in, type-aware lint such as oxlint's), or with several specs registered and no `id`, `call()` is untyped: any `operationId` compiles, `input` only has to have the shape above, and the result is `unknown`. Override names are plain strings then, checked by [`crust build`](#what-crust-build-checks). Calls still compile; code that reads a field of a result fails with `TS18046` until the mapper runs. See inspex's README for its diagnostics and limits.

## Authentication

`bearerAuth(resolve)` builds what [`.auth()`](#authfn) takes for a bearer token. `resolve({ signal, baseUrl, ctx })` returns `{ value, refresh? }`, which the [`auth.token`](/docs/modules/auth#the-token-status-and-logout) of an `@crustjs/auth` client does: a token from the environment, or a stored login that checks `baseUrl` against the origins it was issued for.

<include lang="ts">../../../examples/modules/auth.ts#openapi</include>

<auto-type-table path="../../../../../packages/openapi/src/client.ts" name="AuthAttempt" />

When a request gets a 401, it is sent again once with the attempt `retry(response, { signal })` returns, if all of these hold; otherwise the 401 is returned as is:

- `auth` returned an `AuthAttempt` with `retry` (`bearerAuth()` sets it only when the credential has `refresh`, so never for a token from a flag or the environment).
- The request that got the 401 carried an `auth` header the library added: not one the request set itself, and not a redirect to another origin, which carries none.
- Its body can be sent again: none, a string, `URLSearchParams`, an `ArrayBuffer` or typed array, a `Blob`, or `FormData`, never a stream.
- It is not already a retry, and the invocation was not cancelled.

The 401 response's body is cancelled (even if `retry` read it), and only the request that got the 401 is sent again: after a redirect, that is the redirected request, with the method and body it was sent with, never the request before it. Redirects after it are followed as usual. The new attempt replaces the old one for the rest of the invocation, so later requests and `--paginate` pages use it. A 403 or a 5xx is never retried. `retry` returning `undefined` keeps the 401; an error it throws, such as `RefreshOutcomeUnknownError`, rejects the request.

## Out of scope

`@crustjs/openapi` does not generate commands from a live spec (only the pinned one), filter output (`--jq`), template endpoint paths, or send form-encoded or multipart bodies from generated commands (use `api <path> --body`). For an operation that needs more than an override, exclude it and write the command, with `call()` for the request.
