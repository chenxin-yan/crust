`@crustjs/store` creates typed JSON stores from field definitions. It is standalone: it does not inject values into a Crust Context.

## Install

```npm
npm install @crustjs/store
```

## Quick example

<include lang="ts">../../../examples/modules/store.ts#store</include>

Field types and defaults determine the state type. `createStore()` resolves `<dirPath>/<name>.json` once; `dirPath` must be absolute, and `name` cannot contain path separators or end in `.json`. Each name is an independent file, so use one store per file, such as `config` and `auth`.

## Operations

| Method           | Behavior                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `read()`         | Parse, coerce, merge missing defaults, and validate in memory. Returns only declared fields. Never writes. |
| `write(state)`   | Validate a complete state, create parent directories, replace the file atomically, return it.              |
| `update(fn)`     | Read and validate current state, call `fn` with it, then validate and persist the result.                  |
| `patch(partial)` | Shallow-merge the supplied keys, then validate and persist.                                                |
| `reset()`        | Remove the file; the next `read()` returns defaults. Idempotent.                                           |

<auto-type-table path="../../../../../packages/store/src/types.ts" name="Store" />

- `update()` rejects without calling `fn` when current state is invalid or a required value is missing. Use `write()` to initialize or `patch()` to repair.
- `read()` coerces core number and boolean strings; only `"true"` and `"1"` become `true`. Persisted falsy values are kept.
- Malformed JSON and non-object roots reject with `PARSE`. They never fall back to defaults; `write()` replaces such a file.

### Concurrency

- `write()`, `update()`, `patch()`, and `reset()` on one file run one at a time, in call order, even across store instances in the same process. A failed mutation does not block the next one. `read()` is not queued; it always sees a complete file. A field `validate` or schema that awaits a mutation of the same file never settles: it waits behind the mutation that called it.
- Each mutation also holds an advisory lock file, `<name>.json.lock`, created exclusively next to the store file, so parallel processes (`cli add & cli add`) keep every update. Waiters retry with a short backoff. A lock whose process has exited is taken over right away, and any lock older than 10 seconds is taken over then, so a crashed or hung process never blocks the store for longer.
- The lock has two limits. After a crash leaves a lock behind, two processes that start writing at the same instant can both take it, and one of their updates can be lost; the file is never corrupt. A mutation that runs longer than 10 seconds (a slow async `validate`, a suspended process) can lose its lock the same way.
- The file itself is always replaced atomically: written to a temporary `.<name>-<uuid>.tmp` file, flushed to disk, then renamed.
- On Unix, a write keeps the replaced file's owner and, unless `access` sets file bits, its mode.
- The lock is a lock file, not an OS lock (`flock`), and is tested on local disks only; on a network filesystem, it relies on exclusive create and on clocks that agree.

### Unknown keys

Keys in the file that `fields` does not declare are never returned by `read()`. By default (`pruneUnknown: false`), mutations keep them in the file, so an older version of your CLI, or another tool sharing the file, never deletes fields it does not know. Pass `pruneUnknown: true` to drop them on the next mutation. `reset()` removes the whole file either way.

## Storage paths

| Helper      | Linux and macOS        | Windows                      | Override                                    |
| ----------- | ---------------------- | ---------------------------- | ------------------------------------------- |
| `configDir` | `~/.config/<app>`      | `%APPDATA%\<app>`            | `XDG_CONFIG_HOME`; `APPDATA` on Windows     |
| `dataDir`   | `~/.local/share/<app>` | `%LOCALAPPDATA%\<app>\Data`  | `XDG_DATA_HOME`; `LOCALAPPDATA` on Windows  |
| `stateDir`  | `~/.local/state/<app>` | `%LOCALAPPDATA%\<app>\State` | `XDG_STATE_HOME`; `LOCALAPPDATA` on Windows |
| `cacheDir`  | `~/.cache/<app>`       | `%LOCALAPPDATA%\<app>\Cache` | `XDG_CACHE_HOME`; `LOCALAPPDATA` on Windows |

Choose by intent: user configuration, durable app data, runtime state, or regenerable cache. macOS uses the XDG paths. Relative `XDG_*`, `APPDATA`, and `LOCALAPPDATA` values are ignored, as the XDG spec requires for `XDG_*`. When the home directory (`HOME`, or `USERPROFILE` on Windows) is needed but not absolute, the helpers throw `PATH` instead of returning a relative path. Each helper accepts a `PlatformEnv` second argument for deterministic tests.

## Secret files

```ts
const auth = createStore({
  dirPath: configDir("my-cli"),
  name: "auth",
  fields: { token: { type: "string" } },
  access: "private",
});
```

On Unix, `access: "private"` writes the file with mode `0600` and a parent directory the store creates with `0700`; an existing directory keeps its permissions. Pass `{ file, directory }` for custom bits. With the default `access`, a new file gets the umask default and an existing file keeps its mode, so a user's `chmod 600` survives writes. Windows uses inherited ACLs, so the bits are not enforced there.

## Validation

<include lang="ts">../../../examples/modules/store.ts#validate</include>

<auto-type-table path="../../../../../packages/store/src/types.ts" name="FieldDef" />

- Core `validate` callbacks run on read and mutation and throw to reject. They may return `{ value }` to transform, but transforms apply only on mutation.
- A schema field gives validation, transformation, defaults, and optionality to its Standard Schema v1 `schema`, and cannot also set `default` or `validate`. `read()` returns the schema output without writing it. The field's type is the schema's `types.output`, or its successful `validate()` result when `types` is omitted. An output that is not JSON data, such as `Date`, is a `FIX_JSON_OUTPUT` compile error; optional properties (`z.string().optional()`) are accepted, including under `exactOptionalPropertyTypes`.
- Mutations revalidate transformed values and reject transforms whose result would read back differently.
- Mutations reject explicit `undefined` for defaulted core fields, and values JSON cannot round-trip, such as `NaN`, `Infinity`, `-0`, sparse arrays, `undefined` properties, and cycles.

## Errors

```ts
try {
  await store.read();
} catch (error) {
  if (error instanceof CrustStoreError && error.is("PARSE")) console.error(error.details.path);
}
```

`CrustStoreError.code` is `PATH`, `PARSE`, `IO`, `VALIDATION`, or `DEFINITION`; `.is(code)` narrows `details`.

Store has no encryption, migrations, other formats, or synchronous methods. The [package entry point](https://github.com/chenxin-yan/crust/blob/main/packages/store/src/index.ts) lists every export.
