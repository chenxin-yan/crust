`@crustjs/store` creates typed JSON stores from field definitions. It is standalone: it does not inject values into a Crust Context.

## Install

```npm
npm install @crustjs/store
```

## Quick example

Field types and defaults determine the state type. `createStore()` resolves `<dirPath>/<name>.json` once; `dirPath` must be absolute, and `name` cannot contain path separators or end in `.json`. Each name is an independent file, so use one store per file, such as `config` and `auth`.

## Operations

| Method           | Behavior                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `read()`         | Parse, coerce, merge missing defaults, and validate in memory. Returns only declared fields. Never writes. |
| `write(state)`   | Validate a complete state, create parent directories, replace the file atomically, return it.              |
| `update(fn)`     | Read and validate current state, call `fn` with it, then validate and persist the result.                  |
| `patch(partial)` | Shallow-merge the supplied keys, then validate and persist.                                                |
| `reset()`        | Remove the file; the next `read()` returns defaults. Idempotent.                                           |

<auto-type-table path="../../../../../packages/store/src/types.ts" name="Store" />

- `update()` rejects without calling `fn` when current state is invalid or a required value is missing. Use `write()` to initialize or `patch()` to repair.
- `read()` and mutations convert number text, and the boolean text `"true"`, `"1"`, `"false"` and `"0"`; any other text in a boolean field fails with `Expected boolean`, as non-numeric text fails a number field. Persisted falsy values are kept.
- Malformed JSON and non-object roots reject with `PARSE`. They never fall back to defaults; `write()` replaces such a file.
- The store reads only a regular file, or a symbolic link to one (a [strict store](#strict-stores) refuses links). A directory, FIFO, or device at the path rejects with `PATH` at once, without waiting for a writer. A file larger than 16 MiB rejects with `PATH` too, and the store stops reading at the limit: it was not read, so a `write()` that keeps unknown keys does not replace it; a mutation that would write more than 16 MiB rejects with `VALIDATION` and leaves the file as it was. A leading byte order mark, which some Windows editors save, is ignored.
- `write()`, `update()`, `patch()`, and `reset()` take an optional `{ signal }` last argument. Aborting it while the mutation still waits, behind earlier mutations of the same file or for its lock, rejects with `signal.reason` and changes nothing; once the mutation holds the lock, it runs to the end.

### Concurrency

- `write()`, `update()`, `patch()`, and `reset()` on one file run one at a time, in call order, even across store instances in the same process. A failed mutation does not block the next one. `read()` is not queued; it always sees a complete file. A field `validate` or schema that awaits a mutation of the same file never settles: it waits behind the mutation that called it.
- Each mutation also holds an advisory lock file, `<name>.json.lock`, created exclusively next to the store file, so parallel processes (`cli add & cli add`) keep every update. Waiters retry with a short backoff. Unless the store is [strict](#strict-stores), a lock whose process has exited is taken over right away, and any lock older than 10 seconds is taken over then, so a crashed or hung process never blocks the store for longer.
- The lock has two limits. After a crash leaves a lock behind, two processes that start writing at the same instant can both take it, and one of their updates can be lost; the file is never corrupt. A mutation that runs longer than 10 seconds (a slow async `validate`, a suspended process) can lose its lock the same way.
- The file itself is always replaced atomically: written to a temporary `.<name>-<uuid>.tmp` file created exclusively, flushed to disk, then renamed. On Unix, the store directory is then flushed too, after a rename and after `reset()` deletes the file, and so is the parent of each directory this process creates, so a write or reset that resolved survives a power loss; a failed directory flush rejects with `IO`. The one gap: when two processes create the same new directories at the same moment, only the creator of each flushes its entry, so the other's first write survives a power loss only once the creator has finished. Windows has no directory flush. On Windows, a rename blocked by any process holding the file open (another process reading the store, antivirus, indexers) is retried for up to 2 seconds.
- On Unix, a write keeps the replaced file's owner and, unless `access` sets file bits, its mode.
- The lock is a lock file, not an OS lock (`flock`), and is tested on local disks only; on a network filesystem, it relies on exclusive create and on clocks that agree.

`withFileLock(path, fn, { operation, directoryMode, signal })` runs `fn` under this lock on `<path>.lock`, with the same takeover rules and limits. `path` must be absolute, like a store's `dirPath`; a relative one rejects with `PATH`. It needs no store: use it to read, change and replace a file of your own that other processes save too. `operation: "write"` creates a missing parent directory for the lock (with `directoryMode`, if given); `"delete"` runs `fn` without a lock when the directory is missing. `signal` stops the wait as in a mutation. A lock file that cannot be created rejects with `IO`. It does not reenter: calling it for a path whose lock the same process holds waits until it takes the lock over after 10 seconds. So do not pass a store's own file path and change that store inside `fn`.

### Strict stores

`strict: true` is for a file that must not lose an update and must stay private, such as credentials. It turns on three guarantees together: the file's lock is never taken from a process that may still run, the store file may not be a symbolic link, and its directory must be yours and not writable by anyone else.

<include lang="ts">../../../examples/modules/store.ts#strict</include>

- **The lock is never taken from a process that may still run**, however long it holds it. A suspended or slow writer keeps its lock. A waiter takes over only an owner that is provably gone:
  - Linux: the lock was written on the same machine, boot, and PID namespace (`/etc/machine-id`, the boot id, `/proc/self/ns/pid`), and its process is gone or its pid now belongs to a process with another start time.
  - macOS and Windows: the lock was written on the same platform and hostname, and its process is gone. A process with that pid is always treated as the owner. This assumes no two machines with the same hostname share the directory; if they do, two processes can hold the lock at once.
  - Anything else, such as a lock written inside a container or on another machine, or an empty lock file, is never taken over.
- Takeovers are serialized through `<name>.json.lock.recover`, so two waiters never both take a dead owner's lock and a newer owner's lock is never removed.
- Otherwise a waiter retries until `lockTimeout` (40 seconds by default), then rejects with `LOCK`. Its details name the file that blocked (the lock, or a `.recover` file left by a recovery that crashed), what is known about its owner (`alive`, `unknown`, or `dead`), and the manual step: stop every process that uses the directory and keep new ones from starting, including on other machines or containers that share it; only then delete the named file. If you cannot be sure, leave it in place.
- A store file that is a symbolic link is refused with `PATH` (`details.reason: "symlink"`) by every operation on every platform, and nothing is read or written through it. Remove the link yourself.
- On Unix, an existing directory must be a real directory owned by the current user that group and other users cannot write to. Otherwise every operation rejects with `PATH` (`details.reason: "directory"`): a mutation before creating any file in it, and `read()` before reading, since a file in a directory others can write to may have been put there by them. A directory others can only read, such as one a default store created with mode `0755`, is accepted, so a strict store can share your app's directory with its other stores: others could list the file names, not read or replace the files. A missing directory is created with mode `0700`.
- `strict` implies `access: "private"`; combining it with any other `access` throws `DEFINITION`, as does a `lockTimeout` that is not a finite number of at least 0.
- Every process that opens the file must use `strict`: a default store still takes the lock over after 10 seconds.

`withLock(path, fn, { signal, timeout })` runs `fn` under the same strict lock on `<path>.lock`. It needs no store: use it for work that is more than one write, such as asking a server and then saving the answer, on a path of its own. It has the same rules, directory checks, and `LOCK` error, and rejects a `timeout` that is not a finite number of at least 0 with `DEFINITION`. It does not reenter: calling it for a path whose lock the same process holds waits until its deadline. So do not pass a strict store's own file path and change that store inside `fn`, since the store takes the same lock.

### Unknown keys

Keys in the file that `fields` does not declare are never returned by `read()`. By default (`pruneUnknown: false`), mutations keep them in the file, so an older version of your CLI, or another tool sharing the file, never deletes fields it does not know. Pass `pruneUnknown: true` to drop them on the next mutation. `reset()` removes the whole file either way.

## Storage paths

| Helper      | Linux and macOS        | Windows                      | Override                                    |
| ----------- | ---------------------- | ---------------------------- | ------------------------------------------- |
| `configDir` | `~/.config/<app>`      | `%APPDATA%\<app>`            | `XDG_CONFIG_HOME`; `APPDATA` on Windows     |
| `dataDir`   | `~/.local/share/<app>` | `%LOCALAPPDATA%\<app>\Data`  | `XDG_DATA_HOME`; `LOCALAPPDATA` on Windows  |
| `stateDir`  | `~/.local/state/<app>` | `%LOCALAPPDATA%\<app>\State` | `XDG_STATE_HOME`; `LOCALAPPDATA` on Windows |
| `cacheDir`  | `~/.cache/<app>`       | `%LOCALAPPDATA%\<app>\Cache` | `XDG_CACHE_HOME`; `LOCALAPPDATA` on Windows |

Choose by intent: user configuration, durable app data, runtime state, or regenerable cache. macOS uses the XDG paths. Relative `XDG_*`, `APPDATA`, and `LOCALAPPDATA` values are ignored, as the XDG spec requires for `XDG_*`. When the home directory (`HOME`, or `USERPROFILE` on Windows) is needed but not absolute, the helpers throw `PATH` instead of returning a relative path. Each helper accepts a `PlatformEnv` second argument for deterministic tests.

## Secret files

```ts
const auth = createStore({
  dirPath: configDir("my-cli"),
  name: "auth",
  fields: { token: { type: "string" } },
  access: "private",
});
```

On Unix, `access: "private"` writes the file with mode `0600` and a parent directory the store creates with `0700`; an existing directory keeps its permissions. Pass `{ file, directory }` for custom bits. With the default `access`, a new file gets the umask default and an existing file keeps its mode, so a user's `chmod 600` survives writes. For credentials, use a [strict store](#strict-stores), which also checks an existing directory.

Windows uses inherited ACLs, so the bits are not enforced there, and a strict store checks no directory owner or permissions. On Windows, a secret file is only as private as the ACLs of the per-user directory it is in, such as `%LOCALAPPDATA%`; do not rely on it like a `0600` file on Unix, and encrypt secrets that need more.

## Validation

<include lang="ts">../../../examples/modules/store.ts#validate</include>

<auto-type-table path="../../../../../packages/store/src/types.ts" name="FieldDef" />

- Core `validate` callbacks run on read and mutation and throw to reject. They may return `{ value }` to transform, but transforms apply only on mutation.
- A schema field gives validation, transformation, defaults, and optionality to its Standard Schema v1 `schema`, and cannot also set `default` or `validate`. `read()` returns the schema output without writing it. The field's type is the schema's `types.output`, or its successful `validate()` result when `types` is omitted. An output that is not JSON data, such as `Date`, is a `FIX_JSON_OUTPUT` compile error; optional properties (`z.string().optional()`) are accepted, including under `exactOptionalPropertyTypes`.
- A string field, scalar or array, may list `choices`. A literal tuple narrows the field's type to their union. `read()` and mutations reject any other value with `Expected one of: …`, which never repeats the value; a `default` outside the choices throws `DEFINITION`.
- Mutations revalidate transformed values and reject transforms whose result would read back differently.
- Mutations reject explicit `undefined` for defaulted core fields, and values JSON cannot round-trip, such as `NaN`, `Infinity`, `-0`, sparse arrays, `undefined` properties, and cycles.

## Errors

```ts
try {
  await store.read();
} catch (error) {
  if (error instanceof CrustStoreError && error.is("PARSE")) console.error(error.details.path);
}
```

`CrustStoreError.code` is `PATH`, `PARSE`, `IO`, `VALIDATION`, `DEFINITION`, or `LOCK`; `.is(code)` narrows `details`. A `VALIDATION` error names the file in its message and in `details.path`, with one entry per field in `details.issues`. A strict store's refusals are `PATH` with `details.reason` set to `"symlink"` or `"directory"`; `LOCK` means a strict lock was not acquired before its deadline.

Store has no encryption, migrations, other formats, or synchronous methods. The [package entry point](https://github.com/chenxin-yan/crust/blob/main/packages/store/src/index.ts) lists every export.
