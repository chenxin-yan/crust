`@crustjs/env` declares environment variables with the same vocabulary as flags and exposes the validated values as a [Context](/docs/guide/contexts).

## Install

```npm
npm install @crustjs/env
```

`@crustjs/core` is a required peer. TypeScript is an optional peer.

## Quick example

<include lang="ts" meta="twoslash">

</include>

`defineEnv(name, vars, options?)` returns an ordinary Context factory. Provide it at the root for the whole tree, or on a subcommand for that subtree.

Setup is lazy: variables are read and validated on the first `ctx.env` read, so commands that never read it never fail. Read it first thing in the action, as with every Context.

## Variable definitions

Keys are literal variable names. Each value is a [flag definition](/docs/api/types#flagdef) minus the argv-only keys:

| Keys                                                                                                | Behavior                                                                                                                                         |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`, `choices`, `required`, `default`, `multiple`, `delimiter`, `parse`, `description`, `schema` | As for a flag read from its [environment fallback](/docs/guide/arguments-and-flags#environment-variables); value types are inferred the same way |
| `short`, `aliases`, `negatable`, `noNegate`, `hidden`, `env`                                        | Type errors; `defineEnv()` throws a `DEFINITION` `CrustError` if an untyped caller passes one                                                    |

- `defineEnv()` checks and copies each definition as `defineFlag()` does. A default outside `choices` or an empty `delimiter` throws a `DEFINITION` `CrustError`; a literal default outside literal `choices` or an async `parse` is also a compile error. Changing the definition object afterwards has no effect.
- Values run through Core's flag pipeline: `choices`, then `parse` or built-in coercion, then defaults and requiredness, then Standard Schemas (async schemas are awaited).
- `type: "boolean"` is `true` for `true` or `1` and `false` for any other text. A boolean `schema` receives that boolean, not the raw text.
- `multiple: true` treats the text as one occurrence. With `delimiter`, the text is split and empty segments are dropped; zero segments counts as unset.
- Only own properties of the source are read, so a name like `constructor` never reads `Object.prototype`.

## Options

<include lang="ts">../../../examples/modules/env.ts#source</include>

- Options are read once, when `defineEnv()` is called. The values in `source` are read at first access, so tests can fill the record after defining the Context.
- An empty string is a value by default: `PORT=""` fails `type: "number"`, and `NAME=""` is `""` rather than its default. Set `emptyStringAsUndefined` when blank variables mean unset.
- `skipValidation: true` is an escape hatch for build steps that run without the real environment. A literal `true` types every declared variable as `string | undefined`; a non-literal boolean types the value as either the raw or the validated shape. Undeclared variables are never returned.

## Errors

A failed read rejects with one `CrustError` whose `code` is `"ENV"`. `details.issues` lists every missing or invalid variable in declaration order as `{ name, expected, received }`:

<include lang="ts">../../../examples/modules/env.ts#errors</include>

- `received` is `"missing"` or `"invalid"`.
- `expected` describes the declaration, such as `"number"`, `"one of: debug, info, warn"`, `"list of string"`, `"value accepted by parse"`, or `"value accepted by schema"`.
- Values never appear in the message, details, or `toJSON()`. The error carries no `cause`, because parser and schema messages can quote a secret.

## Help and man pages

`.provide(env())` adds an "Environment" section (man `ENVIRONMENT`) to the providing command, listing each variable with its description, default, and choices:

```text
Environment:
  DATABASE_URL  Postgres connection
  PORT          [default: 3000]
  LOG_LEVEL     [default: "info"] [choices: debug, info, warn]
  TAGS
```

The section appears only on the command where the Context is provided, not on its descendants, and never shows source values.

## Out of scope

Loading `.env` files, a `prefix` option (names are literal), and a warn-only mode are not supported.
