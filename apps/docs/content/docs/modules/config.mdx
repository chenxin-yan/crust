title: "Config"

`@crustjs/config` defines a CLI's settings once and reads them from config files into ordinary flags. A command takes a setting as a flag under any name, and when a run does not give that flag, its value comes from the files, so the action reads the final value from `flags`. `get`, `list` and `set` read and save settings from anywhere, and an optional `config` command lets users do the same.

## Install

```npm
npm install @crustjs/config
```

`@crustjs/core` is a required peer. TypeScript is an optional peer.

`defineConfig({ name, user?, project?, both?, format?, files?, command? })` takes the settings in three groups, by the file that may hold them, and returns:

- `flag(key)`: the flag definition for a setting, to put in a command's `.flags({...})`.
- `extension`: binds the files' values into those flags (`.extend(config.extension)`).
- `get(key)`, `list()` and `set(values)`: read and save settings from anywhere.
- `jsonSchema()`: the JSON Schema of a JSON config file.

## Where a value comes from

A flag from `config.flag()` is the first of:

1. the command line (`--region`), or its key in [`--input`](/docs/modules/extensions/json-input) or in typed [`run()`](/docs/api/crust#runpath-input-options) input;
2. its environment variable (`$ACME_ORG`);
3. the project file, `acme.config.json`, the nearest one from the working directory up, for a setting in `project` or `both`;
4. the user's file, `config.json` in the [configuration directory](/docs/modules/store#storage-paths) of the app (`~/.config/acme` on Linux and macOS, `%APPDATA%\acme` on Windows), for a setting in `user` or `both`;
5. its `default`.

```sh
$ acme config set org acme-corp
Saved org in /home/me/.config/acme/config.json
$ acme deploy
deploying acme-corp to us
$ echo '{"region":"eu"}' > ../acme.config.json
$ acme deploy
deploying acme-corp to eu
$ ACME_ORG=env-org acme deploy --region us
deploying env-org to us
```

Each setting is settled on its own: here `org` comes from the user's file and `region` from the project file. Core resolves the command line and the variable as for any flag; the Extension binds a file's value only into a flag the run left without one, or with only its default. So `--help` shows the flag's `default` and `env`, `required` is checked after the files, and [`prompts()`](/docs/modules/prompts#ask-for-missing-values) does not ask for a value a file gave.

List `config.extension` after [`jsonInput()`](/docs/modules/extensions/json-input) and before `prompts()`: `.extend(jsonInput(), config.extension, prompts())`. An error in a file surfaces in that order, so a broken file then fails before anything is asked, and a flag given in `--input` does not fail on the file.

The files are read when the command has such a flag, and not for `--help` output to fail on: an error in a file waits for the action.

## Settings

A setting is the [flag definition](/docs/api/types#flagdef) of a string, number or boolean flag: `type`, `description`, `short`, `aliases`, `env`, `multiple`, `delimiter`, `choices`, `negatable`, `min`, `max`, `parse`, `default`, `required`, `valueName`, `hidden` and `deprecated`. Other types, `schema` and `requires` are not settings, and an unknown property is a compile error.

`config.flag(key)` returns that definition with the config's name and the setting's key in a `config` property (`"acme:region"`), which only `config.flag()` can write, so two configs with a same-named setting each fill their own flag. A command gives the flag any name, and two commands can give two settings the same flag name:

<include lang="ts">../../../examples/modules/config.ts#flag-name</include>

- The flag's value is typed from the setting, as for any flag: `required` and `default` remove `undefined`, `choices` give a union, and `parse` gives its return type.
- To change one command's flag, spread it: `{ ...config.flag("region"), prompt: "Region" }` keeps the setting's key.
- A command that uses a flag from `config.flag()` needs `config.extension` in the app. Without it, the `config` key is a `DEFINITION` error (`unowned-key`), from source and in `crust build`.
- A setting no command takes as a flag is still read by `get()`, `list()` and the `config` command.

## The groups

The group a setting is in says which file may hold it:

| Group     | The user's file | The project file | For                                                               |
| --------- | --------------- | ---------------- | ----------------------------------------------------------------- |
| `both`    | Yes             | Yes, and it wins | What a person sets once and a repository may choose for itself    |
| `user`    | Yes             | No               | What a repository must not choose, such as a command the app runs |
| `project` | No              | Yes              | What describes the project itself, such as its entry file or name |

- A setting is in one group: its key in two is a compile error where the config is used (`FIX_SETTING_IN_TWO_GROUPS`).
- A file exists only when a group names it. A config with only `user` settings never looks for a project file, and one with only `project` settings never reads the user's file.
- A setting found in a file that may not hold it is ignored with a warning naming the key and both files. A run prints a warning once, however often it reads the files.

### Why the project file is limited

A project file arrives with a cloned repository, so whoever can commit to it sets its values for everyone who runs your CLI there:

```sh
$ cat ../acme.config.json
{"region":"eu","pager":"touch PWNED"}
$ acme deploy
Warning: /home/me/repo/acme.config.json sets "pager", which only /home/me/.config/acme/config.json may set; ignored.
deploying acme-corp to eu
```

Put in `both` or `project` only what is safe for a repository to choose. Keep in `user` anything run as a command (`pager`, `editor`, `browser`) and anything that says where data or credentials are sent. Secrets do not belong in settings at all: take them from the environment or a [login](/docs/modules/auth).

## The files

- The user's file is `config.json` in `configDir(name)`. The project file is `<name>.config.json`, the first one found in the working directory, then in each parent up to the root.
- `files: { user, project }` changes the names, written without their extension: `files: { user: "settings", project: "acme" }` reads `settings.json` and `acme.json`.
- A missing file holds no values, and reading creates nothing. A value that converts to nothing, an empty list or empty text, is no value either: the next file, then the default, applies. Keys that are not settings, such as `"$schema"`, are ignored.
- The files are read and saved through [`@crustjs/store`](/docs/modules/store), loaded when a command first needs a file: a regular file of at most 16 MiB, replaced in one step under the store's lock.

### Formats

JSON is the default. `format` reads and writes another format with a parser package of your choice, as a store's [`format`](/docs/modules/store#formats) does; Crust adds no parser of its own. Its `extension` ends both files' names:

```ts
import { defineConfig } from "@crustjs/config";
import { parse, stringify } from "smol-toml";

export const config = defineConfig({
  name: "acme",
  both: { region: { type: "string", choices: ["us", "eu"], default: "us" } },
  format: { extension: "toml", parse, stringify }, // config.toml and acme.config.toml
});
```

- `parse` must return an object of settings.
- A text value from a file is converted as the same text in the setting's environment variable: `"3"` for a number setting is `3`, `"a,b"` splits on a `delimiter`, and a `parse` setting parses it. A number or a boolean is converted as its text, and a list for a `multiple` setting item by item. So an INI file, which holds only text, works like JSON.
- Saving rewrites the file through `stringify`: comments and formatting in it are lost.

### Errors

```text
$ acme serve                                    # config.json: {"port": "80x"}
Error: Expected a number for "port" in /home/me/.config/acme/config.json.
$ acme deploy                                   # acme.config.json is not JSON
Error: Malformed config file: /home/me/repo/acme.config.json
```

- A file that cannot be read, such as a folder of that name, a device, a file above 16 MiB or one without read permission, fails with `Cannot read config file: <path>` and exit code 2. One that does not parse, or does not hold an object, fails with `Malformed config file: <path>`.
- A value that does not convert fails as an invalid environment value does, naming the setting and the file, with exit code 2. The built-in conversions never repeat the value; a setting's own `parse` error is shown as on the command line.
- A file is read only for the settings a command takes and its run did not give: `acme serve --listen 8080` works whatever the files hold.
- A broken file fails only a read of a setting it may hold: with a malformed project file, a `user` setting is still read from the user's file.
- `--help` works whatever the files hold.

## Read and save settings

<include lang="ts">../../../examples/modules/config.ts#get-set</include>

- `await config.get(key)` reads a setting as a flag would get it, without the command line: its variable, the project file, the user's file, its default. It throws a `VALIDATION` `CrustError` for a `required` setting that none of them gives.
- `await config.list()` returns every setting with its value and source: `{ key, value, source }`, where `source` is `{ kind: "env", name }`, `{ kind: "file", path }`, `{ kind: "default" }` or `{ kind: "unset" }`.
- `await config.set(values)` saves settings in the user's file; `config.set(values, { project: true })` saves them in the nearest project file, or a new one in the working directory. A value is what a file holds (the text of a `parse` setting), and `undefined` removes a setting. The keys and values are checked at compile time: each form takes only the settings its file may hold, so `config.set({ entry })` without `{ project: true }` does not compile. A value the setting's rules refuse (`min`, `choices`, `parse`) throws before anything is saved.
- Saving keeps the other keys and the mode of the file, creates the folder when needed, and replaces the file in one step; a save that would make the file larger than 16 MiB is refused (`Cannot save <path>: the file would be larger than 16 MiB`). Saves of one config run one at a time, in the order they were called, and every save holds the store's lock file `<file>.lock` next to the file (see [Concurrency](/docs/modules/store#concurrency)), so another config or process saving at the same time keeps its keys too. A linked user file stays a link when the file it points to has the same extension; saving in a linked project file is refused.
- `get()` and `list()` print a file's warnings on the process's stderr, unless the run they are called in has printed them.

## The `config` command

`command: true` adds `config get`, `set`, `unset` and `list`:

```sh
$ acme config set org acme-corp
Saved org in /home/me/.config/acme/config.json
$ acme config set region mars
Error: Invalid value for "region". Expected one of: us, eu
$ acme config set --project pager less
Error: acme.config.json cannot set "pager"; it may set only: org, region, entry
$ acme config set entry src/main.ts
Error: "entry" is a setting of acme.config.json: pass --project
$ acme config set --project entry src/main.ts
Saved entry in /home/me/repo/acme.config.json
$ acme config get region
eu
$ acme config list
org     acme-corp    /home/me/.config/acme/config.json
region  eu           /home/me/repo/acme.config.json
port                 unset
pager                unset
entry   src/main.ts  /home/me/repo/acme.config.json
$ acme config unset org
Removed org from /home/me/.config/acme/config.json
```

- `set` converts the text as the setting's environment variable would and saves the value, or the text for a `parse` setting.
- `--project`, on `set` and `unset` when the config has both files, writes the project file, and refuses a `user` setting. Without it, a `project` setting is refused with a message naming the flag. A config with one file saves in it and has no such flag.
- `list` shows the `both` settings first, then `user`, then `project`.
- `get` prints nothing for a setting with no value, and a list one item per line.
- Typed `run()` does not know the subcommands of `config`: run them through argv, as with `captureExecute(app, ["config", "list"])`.
- Without `command: true`, write the commands your CLI needs with `get()`, `list()` and `set()`.

## Run in another folder

There is no option for the folder the project file is searched from. A `-C <dir>` flag, "run as if started in `<dir>`" as in `git -C` and `make -C`, is an Extension that changes the working directory in its `setup`, listed before `config.extension`:

<include lang="ts">../../../examples/modules/config.ts#chdir</include>

```sh
$ acme -C ~/work/api config get region
eu
```

## JSON Schema

`config.jsonSchema()` returns the JSON Schema (draft 2020-12) of the user's JSON config file, and `config.jsonSchema({ project: true })` that of the project file: one property per setting the file may hold, as the user writes it (a `choices` setting is an `enum`, a `multiple` one an array, a `parse` one a string, `min` and `max` as `minimum` and `maximum`), plus `"$schema"`, and no other property. Point a file's `"$schema"` at it for completion and checks in editors. To write it at `crust build`, add a small [build Extension](/docs/guide/extensions):

## Help

`.extend(config.extension)` adds a "Configuration" section to the root's help, `--llms` output and man page, listing the files and every setting that is not `hidden`:

```text
Configuration:
  A flag for a setting that the run does not give takes its environment variable, then acme.config.json (the nearest from the working directory up), then config.json in the configuration directory of acme, then its default.
  org     Organization [env: ACME_ORG]
  region  Region [default: "us"] [choices: us, eu]
  port    Port (config.json only)
  pager   Pager for long output (config.json only)
  entry   The project's entry file (acme.config.json only)
```

## Testing

Give a setting's flag in the test's argv or typed `run()` input, as for any flag. To test the files themselves, point `XDG_CONFIG_HOME` (`APPDATA` on Windows) at a temporary folder for the user's file, and run in a temporary working directory for the project file, with the `env` and `cwd` options of [`captureExecute()`](/docs/modules/testing).
