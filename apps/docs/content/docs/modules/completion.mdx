`@crustjs/completion` generates tab-completion scripts for bash, zsh, fish, and PowerShell from your command definitions, and owns the `complete` key that gives an argument or flag live values.

## Install

```npm
npm install @crustjs/completion
```

The package has a peer dependency on `@crustjs/core`.

## Usage

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/modules/completion.ts
</include>

`completion()` adds a `completion <shell>` root command and a build hook. The generated scripts contain the commands, flags, and choices, so the shell completes them without running the CLI. Only an argument or flag with a [`complete` function](#live-values), or with [choices the scripts cannot hold](#value-candidates), runs the CLI when the user presses Tab.

## Quick shell setup

```sh
# Bash, in ~/.bashrc
source <(my-cli completion bash)

# Zsh, after compinit in ~/.zshrc
source <(my-cli completion zsh)

# Fish, in ~/.config/fish/config.fish
status --is-interactive; and my-cli completion fish | source
```

```powershell
# PowerShell, in $PROFILE
my-cli completion powershell | Out-String | Invoke-Expression
```

Here, `my-cli` is the installed application executable. Source output only from a CLI you trust, and use one loading method per shell. `my-cli completion --help` prints these lines with your CLI's name in a `Setup` section, so users find them without the docs; the section is for [`help`](/docs/modules/extensions/help) only.

New shells generate completion from the installed CLI at startup. Open a new shell after updating the CLI to refresh the definitions.

## Live values

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/modules/completion-complete.ts
</include>

```sh
$ my-cli checkout re<Tab>
$ my-cli checkout release
```

`complete: (typed) => string[] | Promise<string[]>` on an argument, or on a flag that takes a value, supplies its candidates when the user presses Tab. It receives the word being completed, possibly empty; the shell keeps the values that start with it. Its values replace the definition's `choices` and file completion.

- The generated script runs `my-cli __complete`, a hidden command `completion()` adds, which calls the function and prints one value per line. A value containing a line break or a tab is left out.
- A required flag that another Extension adds to every command applies to `__complete` too, so completion offers no values until that flag is given. Give such a flag an [`env`](/docs/guide/arguments-and-flags#environment-variables) so the shell can supply it.
- Bash, zsh, and PowerShell insert each value quoted for the shell. Zsh passes the function the word unquoted; bash passes it as typed, so after `pro\ ` the function receives `pro\ `, backslash included, and keeps a value that starts with the word as typed or as inserted. Bash completes no value for a word that opens with a quote.
- Errors and output on stderr stay off the terminal; a failing function offers nothing.
- The key exists in every file of a project that imports `@crustjs/completion`. Without `completion()` in `.extend()`, a `complete` key is a `DEFINITION` error (`unowned-key`), from source and in `crust build`. See [Own a definition key](/docs/guide/extensions#own-a-definition-key).
- `complete` never changes how a value parses: the command still validates what the user types.

## API

```ts
const snapshot = await app.snapshot();
const bash = await renderBashCompletion(snapshot);
const zsh = await renderZshCompletion(snapshot);
const fish = await renderFishCompletion(snapshot);
const powershell = await renderPowerShellCompletion(snapshot);
```

<auto-type-table path="../../../../../packages/completion/src/index.ts" name="CompletionOptions" />

The renderers take a root Command Snapshot and an optional `{ version }` override, and resolve to the script text. A script with live values, or with choices the scripts cannot hold, calls the app's `__complete` command, so it works only for an app with `completion()` installed.

- **Version required.** Scripts embed a version from the `version` option or root metadata. Without a string `version` option, `.extend(completion())` is a type error unless the root declares `version`, like [`version()`](/docs/modules/extensions/version). Untyped callers that supply neither get a `DEFINITION` error when a script is rendered.
- **`<shell>`** accepts `bash`, `zsh`, `fish`, or `powershell`; anything else fails as an invalid value.
- **`command`** renames the contributed command and the regenerate hint in script headers; the standalone renderers always name `completion`. Pass a string literal so `app.run()` keeps type-checking command paths and flags: a `command` typed as `string` leaves the command tree unchecked.
- **Executable name.** Every script completes the root command name, which [`crust build` requires to match the installed command](/docs/modules/crust#commands-and-entries-bin), so it must follow the [installed command name rule](/docs/modules/core#tooling-subpath).

## Value candidates

```ts
command.flags({
  target: {
    type: "string",
    choices: ["browser", "bun", "node"],
  },
});
// my-cli build --target <Tab> offers browser, bun, and node
```

String `choices` become candidates, and so does the string `enum` of a flag's schema. Choices that start with a letter or digit and hold only letters, digits, and `_ . + : @ / -` are written into the scripts. A definition with any other choice, such as `"free tier"`, is completed like one with a [`complete`](#live-values) function: the script asks the CLI, which answers with the choices, and the shell inserts the value quoted (`free\ tier`). `path` and unconstrained `string` values use file completion where supported, while `url` and `json` values do not. PowerShell offers file names wherever a value has no candidates.

Boolean flags do not consume a value. Hidden commands and their descendants are omitted.

A short may be any character Core accepts, such as ripgrep's `-.`; each script quotes it for its shell. Zsh completes the value of a short `-+` or `-=` only when it is typed `-\+` or `-\=`.

After `--`, no flags or subcommands are offered, and later words keep filling argument slots, as Core parses them. A [`variadic: "afterDoubleDash"`](/docs/guide/arguments-and-flags#only-after---) argument's values are offered only after `--`, and the other arguments' only before it. A command with a [`variadic: "passthrough"`](/docs/guide/arguments-and-flags#from-the-first-positional) argument offers no flags after its first positional. Zsh completes arguments only for commands without subcommands.

Bash completes a value past a `=` or `:` it holds, such as `node:22`. A file path that holds an unescaped `:` may get the wrong ending, a `/` or a space, because Readline looks up only the text after the colon; bash-completion's own colon handling has the same limit.

## Package-manager and advanced setup

```sh
$ my-cli completion bash --output-dir completions/
$ ls -1 completions
_my-cli
my-cli
my-cli.fish
my-cli.ps1
```

With `--output-dir`, the required `<shell>` still selects a valid invocation, but the command writes all four files. The directory is a [`path`](/docs/guide/values-and-validation) value: relative to the working directory, with `~` expanded. It preserves unrelated files in that directory.

Without `--output-dir`, the command also returns the script it prints, so [`--json`](/docs/modules/extensions/json) prints it as one JSON string instead of an empty stdout; with `--output-dir` it returns nothing.

### Build artifacts

```text
.crust/artifacts/completions/my-cli
.crust/artifacts/completions/_my-cli
.crust/artifacts/completions/my-cli.fish
.crust/artifacts/completions/my-cli.ps1
```

The build hook renders these four files; `crust build` writes them and records them as artifacts owned by `crust:completion`.

### Saved files and autoload

```sh
mkdir -p "${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion/completions"
my-cli completion bash > "${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion/completions/my-cli"
```

Saved files avoid running the generator at shell startup. Autoloading the Bash file requires [bash-completion to be installed and initialized](https://github.com/scop/bash-completion#installation).

For Zsh, initialize its [completion system](https://zsh.sourceforge.io/Doc/Release/Completion-System.html) and explicitly source the saved file:

```sh
mkdir -p ~/.zsh/completions
my-cli completion zsh > ~/.zsh/completions/_my-cli
source ~/.zsh/completions/_my-cli # after compinit or framework initialization
```

Crust's generated Zsh script misses the first Tab completion when loaded from `$fpath` for binary names containing `-` or `.`. Explicit sourcing avoids that issue.

PowerShell has no autoload directory: dot-source a saved `my-cli.ps1` from `$PROFILE`. Regenerate or replace saved files after CLI changes.
