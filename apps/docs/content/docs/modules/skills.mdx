`@crustjs/skills` renders agent skills from a Command Snapshot. Build output is shipped with the CLI, then linked into agent directories when a user installs it.

An installed skill saves an agent the discovery calls, and the agent still runs your CLI from its shell; [how agents use your CLI](/docs/guide/agents#how-agents-use-your-cli) shows where skills fit beside on-demand discovery and MCP.

## Install

```npm
npm install @crustjs/skills
```

## Packaged skills workflow

<include lang="ts">../../../examples/modules/skills.ts#write</include>

`writeSkills()` generates one skill directory from `app` (a `SKILL.md` plus one file per command under `commands/`) and copies any authored `extras`.

- `outDir` must be a dedicated directory named `skills`: it is replaced on every call. The returned paths are relative to it.
- Relative `outDir` and `extras` paths resolve against the working directory.
- An authored skill with the generated skill's name replaces the generated one.
- An authored `SKILL.md` must give `name` and `description` as one-line plain or quoted YAML values; block scalars (`|`, `>-`) are rejected.
- A runnable command with an [`.output()`](/docs/api/crust#outputschema) schema that converts to JSON Schema gets an `Output` section with that JSON Schema on one line, without its `$schema` key.

### Generated file names

Command file names are trimmed and lowercased: each command renders to `<name>.md`, and each nested command group also gets a `<name>` directory. Before replacing output, generation fails on:

- command names containing path separators, or equal to `.` or `..`;
- file or directory names with control characters, Windows-reserved characters, device names (such as `con.md` or `nul.txt.md`), or a trailing dot (a `trailing.` group fails, while a `trailing.` command renders to `trailing..md`);
- names that collide after lowercasing and Unicode normalization, including composed/decomposed spellings that alias on macOS.

Normalization is only used for collision checks; generated paths and command invocations keep their original Unicode spelling.

## Enable discovery and installation

<include lang="ts">../../../examples/modules/skills.ts#extension</include>

The Extension registers `my-cli skills` (alias `skill`) with `install`, `uninstall`, and `repair` subcommands; bare `my-cli skills` is shorthand for `skills install`.

- A custom `command` name replaces the default command, without the alias. Pass it as a string literal so `app.run()` keeps type-checking command paths and flags; a `command` typed as `string` leaves the command tree unchecked.
- A command name that collides with an app command fails with a `DEFINITION` error when the app prepares.
- It adds an `Agent skills` section to the root command's documentation, such as help and man pages, listing each packaged skill and its source directory. It uses `except: [skill]`, so generated skills leave it out.

During `crust build`, the Extension's build hook renders generated and authored skills under `skills/`, recorded as artifacts owned by `crust:skills`. A bundle that `crust build` produces does not register the hook, so the CLI it ships does not carry the renderer. At runtime the commands read them from [`artifactPath("skills")`](/docs/api/crust#artifactpathpath), so run `crust build` before using them; until then help shows a note instead of failing.

The section's source paths are resolved when help or man output is generated. Build from the project root that contains the packaged skills directory so man pages do not embed absolute build-machine paths.

```sh
my-cli skills install
my-cli skills install --all --scope project
my-cli skills install --agent claude-code --skill my-cli --scope project
my-cli skills            # shorthand for `skills install`
my-cli skills uninstall
my-cli skills uninstall --skill my-cli --scope global
my-cli skills repair
```

`--scope` accepts `project` or `global`. With `--all`, scope comes from `--scope`, then `defaultScope`, then `global`; otherwise an interactive run prompts when neither setting is supplied.

Each flag answers its prompt, and whatever is left is asked: `--skill <name>` (repeatable) skips the skill prompt, `--agent <id>` (repeatable, `install` only) skips the agent prompt, and `--scope` skips the scope prompt. Agent ids are listed under [supported agents](#supported-agents); an agent that reads the shared folder at that scope is accepted and needs no link of its own. With `--agent`, a directory the skill does not own is skipped with a warning instead of a confirmation. An unknown agent or skill, or `--all` together with `--agent` or `--skill`, is a usage error.

- **Install is additive.** It always links the shared folder, then the selected agents, and never removes links. Interactively, it asks which skills (when more than one is packaged) and which agents, and confirms before overwriting each directory it does not own. The agent prompt lists only agents that need their own link at that scope, those [detected](#supported-agents) and those already holding one of the skills, and is skipped when there are none. `--all` links the shared folder and all of them.
- **Uninstall removes selected links.** It lists the skills linked at the chosen scope, with nothing preselected, and removes the shared link and every owned agent link of the selected ones. `--all` or `--skill` skips the prompt.
- **Repair** re-points the shared link to this copy, then every owned agent link that does not lead to it, without prompting.

## Link lifecycle and ownership

```text
project: .agents/skills/my-cli   -> ../../node_modules/my-cli/skills/my-cli   (shared link)
         .claude/skills/my-cli   -> ../../.agents/skills/my-cli               (agent link)
global:  ~/.agents/skills/my-cli -> /usr/lib/node_modules/my-cli/skills/my-cli
         ~/.claude/skills/my-cli -> /home/me/.agents/skills/my-cli
```

Only the shared link in `.agents/skills` points at the packaged skill. An agent with its own skills folder at that scope gets a link to the shared link; an agent that reads `.agents/skills` needs nothing else. This is the layout `npx skills` writes. If the shared link cannot be made (a directory the skill does not own, left in place), no agent link is made for that skill at that scope. Project links are relative and global links are absolute.

Before each Command Action, an installed CLI checks only the shared link of each scope, unless `autoUpdate: false`. Agent links point at the shared link, which does not move, so they are not inspected:

- It re-links a Crust-owned shared link whose target no longer exists, silently, and never creates one that was not installed. A repair that fails prints one line and does not stop the command.
- Anything else is left alone and nothing is printed: a working link, even one that leads to another installed copy of the CLI, and a directory or foreign link at the shared path. Which copy should own a link cannot be told reliably across npm, version managers, and other installs, so links move only when broken or when you run `skills repair` or `skills install`.
- Running from source (`bun run`, `node`) skips the check, so trying a checkout never moves an installed CLI's links to its build. Run `skills repair` there to relink deliberately.

When another installed copy of the CLI holds the link, for example after an upgrade that keeps the old version installed, run `skills repair` from the copy you want.

`skills repair` re-points the shared link even when it leads to another live copy, then every owned agent link that does not lead to this copy, so that it targets the shared link. An agent link from an older version that points straight at the packaged skill still leads to this copy and is left as it is.

A link is Crust-owned when its textual target ends in `skills/<name>`; shared and agent links both do. Real directories and foreign links conflict unless low-level installation gets `force: true`, or `force` listing their exact paths; `skills install` asks about each such path separately.

## Supported agents

```text
project: .agents/skills/<name>
global:  ~/.agents/skills/<name>
```

Universal targets, such as codex, cline, and pi, read the shared folders at both scopes and never need a link of their own. Additional targets, such as claude-code, use an agent-specific location in at least one scope (cursor, for example, shares `.agents/skills` only at project scope). An agent without a global directory, such as eve, is available only at project scope; naming it at global scope is an error.

An additional agent is detected when the folder containing its global skills directory exists, such as `~/.claude` for `~/.claude/skills`. Project folders, the home directory itself, and the shared `~/.agents` do not count.

The agent list is generated from the registry of the [`skills`](https://www.npmjs.com/package/skills) package; [`agents.generated.ts`](https://github.com/chenxin-yan/crust/blob/main/packages/skills/src/agents.generated.ts) lists every target and its directories. The table also records the environment variables upstream honors for a global directory, such as `CLAUDE_CONFIG_DIR` for Claude Code or `XDG_CONFIG_HOME` for OpenCode: when one is set to a non-blank value, the global directory moves under it, and detection follows. Values are trimmed, a blank value is ignored, and a relative value resolves against the working directory; upstream differs only for a padded or blank `XDG_CONFIG_HOME`. Per-platform paths are not carried: every agent uses the POSIX directories in that file on every platform.

When the working directory is the home directory, project scope becomes global scope. Result objects include the effective scope.

## Low-level link operations

```ts
await installSkill({ sourceDir, agents: ["opencode"], scope: "global" });
const status = await getSkillStatus({ name: "my-cli", sourceDir });
await uninstallSkill({ name: "my-cli" });
```

`installSkill()` links the shared `.agents/skills/<name>` first and reports it as `shared`, then links each requested agent's own folder to it; omitted `agents` means the detected agents. A shared link it may not overwrite throws `SkillConflictError` without `details.agent`, and no agent link is made. `getSkillStatus()` reports `linked`, `dangling`, `conflict`, or `absent` per agent directory. A link is `linked` when it leads to the given `sourceDir`, directly or through another link, such as an agent directory that links to `.agents/skills/<name>`; real paths are compared. `uninstallSkill()` removes only owned links, including dangling ones; with `agents` it removes only those agents' own links and keeps the shared link, which other agents read. Only missing paths (`ENOENT`) count as absent; permission and other filesystem failures reject. Each result lists one entry per agent with its effective `scope` and status.

## Command sections

<include lang="ts">../../../examples/modules/skills.ts#sections</include>

Command metadata sections render as `## Title` blocks in each command's file under `commands/`. Passing the `skill` factory in `only` limits a section to the skills renderer.

Sections with the same exact title share one heading and join their bodies. See [`CommandSectionInput`](/docs/api/types#commandsectioninput) for audience rules.

## Name validation

```ts
isValidSkillName("deploy-guide"); // true
isValidSkillName("Deploy Guide"); // false
```

Names contain 1 to 64 lowercase letters, digits, and hyphens. They cannot start or end with a hyphen or contain consecutive hyphens, matching the [Agent Skills specification](https://agentskills.io/specification).

## Source helpers and errors

```ts
import { loadPackagedSkills } from "@crustjs/skills";

const skills = loadPackagedSkills();
```

`loadPackagedSkills()` reads the skills shipped with the CLI, or the directory you pass, validates each `SKILL.md` name and non-empty description, and skips directories without a `SKILL.md`.

`SkillConflictError` covers install conflicts, `SkillSourceConflictError` covers duplicate authored names, and `SkillSourceUnavailableError` means the root is missing or empty: the CLI has not been built yet.
