`@crustjs/effect` lets you author Command Actions and Contexts in [Effect](https://effect.website) idiom. Crust remains the runtime: routing, parsing, rendering, and cleanup are unchanged. It is a set of helpers, not an Extension, so it registers no flags, commands, or hooks.

<Callout type="warn" title="Effect v4 prerelease">
  The adaptor targets `effect@4.x` prereleases. Install the exact `effect` version the package was
  tested against; a second copy of `effect` breaks service identity, so it is a peer dependency.
</Callout>

## Install

```npm
npm install @crustjs/effect effect@4.0.0-rc.115
```

`@crustjs/core` and `effect` are required peers. TypeScript is an optional peer.

## How it fits

Each `handler()` invocation runs one Effect program, provided with every `layer()` on the command path. The Layers are released by Crust's normal Context cleanup afterwards.

| Boundary                         | Crust side                             | Effect side                                            |
| -------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| Action                           | `.action(handler(fn))`                 | `fn` returns an Effect or is a generator (`function*`) |
| Layer-backed Context             | `.provide(db())`, `.use(db)`, `ctx.db` | `yield* Db`: services are provided automatically       |
| Plain Context inside a program   | `defineContext("config", …)`           | `yield* service(config)`                               |
| Throwing Crust code in a program | prompts, `CrustError`, `AbortError`    | `tryCrust(() => …)`: tagged failure or interruption    |

### Error outcomes

| Program outcome                  | What the user sees                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------ |
| Success                          | The action resolves with the value                                                   |
| `Fail` with a tagged Crust error | The wrapped `CrustError` is rethrown; Core renders it as if the action threw it      |
| `Fail` with any other error      | Rethrown as-is; rendered like a plain thrown error (exit 1)                          |
| `Die` (defect)                   | Rethrown as-is; rendered like a plain thrown error (exit 1)                          |
| Interruption                     | An `AbortError` is rethrown; Core exits 130 with no output, like prompt cancellation |

The program and Layer builds run with the invocation's `ctx.signal`, so caller cancellation or Ctrl-C interrupts them. Interruption always becomes an `AbortError`, even when the caller aborted with a custom reason such as a `TimeoutError`. Layer finalizers still run; uninterruptible acquisition must settle before cleanup finishes.

## `layer(name, layer)`

Turns one fully composed Layer into an ordinary Crust Context factory whose value is the built `Context.Context`. The Layer must have no remaining requirements: compose it in Effect first, then pass the result. Attach it with `.provide(db())`, declare it in reusable definitions with `.use(db)`, and read it outside a handler as `Context.get(await ctx.db, Db)`.

Each invocation builds the Layer in a fresh `Scope`, closed with the other Contexts after `postRun` hooks. Finalizers receive the handler's `Exit`, so an `Effect.acquireRelease` release can commit on success and roll back on failure or interruption. A Layer pulled without a `handler()` closes with `Exit.void`.

<Callout title="Every layer() on the path is built eagerly">
  When a `handler()` action starts, every `layer()` Context on the command path is built, whether or
  not the program uses it. Plain Contexts stay lazy. Attach Layers to the commands that need them.
</Callout>

## `handler(fn)`

<include lang="ts">../../../examples/modules/effect.ts#handler</include>

`fn` receives the same input a plain action receives, with the same inference, and the action resolves with the program's success value. The program's requirements are checked against `ServicesOf<Input>`, the services of the `layer()` Contexts on the path: requiring a service with no `layer()` there is a compile error. A plain `defineContext()` returning a `Context.Context`, or a `layer()` without a literal name, does not count.

## `service(factory)`

<include lang="ts">../../../examples/modules/effect.ts#service</include>

Pulls a plain Crust Context inside a `handler()` program, typed by the factory's value. It is lazy like `ctx.<name>`, and repeated pulls share one build. It works only inside `handler()`.

The effective provider on the path must come from the **same factory**, including its `.of(...)` test doubles. A missing factory, or a different factory with the same name, fails with a `CrustDefinitionError`. This is checked at runtime, not compile time.

## Environment variables

Install [`@crustjs/env`](/docs/modules/env) alongside the Effect adaptor. `defineEnv()` returns a plain Crust Context, so the existing `service()` helper provides typed values and catchable errors without an additional Layer or adapter:

<include lang="ts">../../../examples/modules/effect-env.ts#env-example</include>

`PORT` is a `number` and `API_TOKEN` is a `string`. Validation runs only when the program reads `service(env)`; repeated reads share the invocation's result. Providing the Context adds its Environment section to help and man pages without reading source values. Unhandled failures are restored to the original Core error for CLI reporting.

For commands that intentionally recover, such as a configuration diagnostic, catch `CrustEnvError`:

<include lang="ts">../../../examples/modules/effect-env.ts#env-recovery</include>

`error.details.issues` contains all invalid or missing variables. Each `received` field is only `"missing"` or `"invalid"`, never the raw value. `service(env)` has the full `CrustTaggedError` error union: catching `CrustEnvError` leaves other failures, such as a missing provider, in the error channel. Definition mistakes still throw when `defineEnv()` is called, before the handler runs.

Use `tryCrust(() => ctx.env)` for explicit action-input access. Avoid `Effect.promise(() => ctx.env)` when you want typed recovery: rejected promises become defects rather than catchable tagged failures.

## Tagged errors

<include lang="ts">../../../examples/modules/effect.ts#tagged-errors</include>

Each Core error code has a `Data.TaggedError` class: `CrustDefinitionError`, `CrustValidationError`, `CrustParseError`, `CrustCommandNotFoundError`, and `CrustEnvError`. Each carries `message`, typed `details`, and `cause` (the original `CrustError`). `CrustTaggedError` is their union.

- `fromCrustError(error)` wraps a caught `CrustError` in the class for its `code`.
- `tryCrust(thunk)` lifts a sync or async thunk into an Effect: a thrown `CrustError` fails with its tagged class, an `AbortError` interrupts the fiber, and anything else is a defect.

`import * as CrustEffect from "@crustjs/effect"` keeps these names out of your module scope if they clash with Effect's own.
