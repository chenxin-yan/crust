title: "Effect"

`@crustjs/effect` lets you write Command Actions and Contexts as [Effect](https://effect.website) programs. Crust still routes, parses, renders, and cleans up. It is a set of helpers, not an Extension, so it adds no flags, commands, or hooks.

<Callout type="warn" title="Single copy of effect">
  `effect` is a peer dependency because a second copy breaks service identity. Make sure your app
  resolves one `effect@4` install.
</Callout>

## Install

```npm
npm install @crustjs/effect effect@4
```

`@crustjs/core` and `effect` are required peers. TypeScript is an optional peer.

## How it fits

Each `handler()` invocation runs one Effect program, provided with every `layer()` on the command path. The Layers are released by Crust's normal Context cleanup afterwards.

| Boundary                         | Crust side                             | Effect side                                            |
| -------------------------------- | -------------------------------------- | ------------------------------------------------------ |
| Action                           | `.action(handler(fn))`                 | `fn` returns an Effect or is a generator (`function*`) |
| Layer-backed Context             | `.provide(db())`, `.use(db)`, `ctx.db` | `yield* Db`: services are provided automatically       |
| Plain Context inside a program   | `defineContext("config").setup(…)`     | `yield* service(config)`                               |
| Throwing Crust code in a program | prompts, `CrustError`, `AbortError`    | `tryCrust(() => …)`: tagged failure or interruption    |

### Error outcomes

| Program outcome                  | What the user sees                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Success                          | The action resolves with the value                                                                         |
| `Fail` with a tagged Crust error | The wrapped `CrustError` is rethrown; Core renders it as if the action threw it                            |
| `Fail` with any other error      | Rethrown as-is; rendered like a plain thrown error (exit 1)                                                |
| `Die` (defect)                   | Rethrown as-is; rendered like a plain thrown error (exit 1)                                                |
| Interruption                     | An `AbortError` is rethrown; Core exits 130 (143 after `SIGTERM`) with no output, like prompt cancellation |

The program and Layer builds run with the invocation's `signal`, so caller cancellation, Ctrl-C, or `SIGTERM` interrupts them.

- Interruption always becomes an `AbortError`, even when the caller aborted with a custom reason such as a `TimeoutError`.
- Layer finalizers still run; uninterruptible acquisition must settle before cleanup finishes.

## `layer(name, layer)`

Turns one fully composed Layer into an ordinary Crust Context factory. Its value is the built `Context.Context`, typed `LayerValue<S>`.

- The Layer must have no remaining requirements: compose it in Effect first, then pass the result.
- Attach it with `.provide(db())`, or declare it in a reusable definition with `.use(db)`.
- Outside a handler, read a service as `Context.get(await ctx.db, Db)`.

Each invocation builds the Layer in a fresh `Scope`, closed with the other Contexts after `postRun` hooks.

- Finalizers receive the handler's `Exit`, so an `Effect.acquireRelease` release can commit on success and roll back on failure or interruption.
- A Layer pulled without a `handler()` closes with `Exit.void`.

<Callout title="Unshadowed layer() providers are built eagerly">
  When a `handler()` action starts, every `layer()` Context on the command path is built, whether or
  not the program uses it. A `layer()` replaced by a same-name provider on a descendant command is
  not built. Plain Contexts stay lazy. Attach Layers to the commands that need them.
</Callout>

## `handler(fn)`

<include lang="ts">../../../examples/modules/effect.ts#handler</include>

`fn` receives the same input as a plain action, with the same inference. The action resolves with the program's success value.

The program's requirements are checked against `ServicesOf<Input>`, the services of the `layer()` Contexts on the path. Requiring any other service is a compile error. A plain Context whose setup returns a `Context.Context`, or a `layer()` without a literal name, provides nothing.

## `service(factory)`

<include lang="ts">../../../examples/modules/effect.ts#service</include>

Pulls a plain Crust Context inside a `handler()` program, typed by the factory's value.

- It is lazy like `ctx.<name>`, and repeated pulls share one build.
- It works only inside `handler()`: its Effect requires `HandlerInput`, which is exported for annotating reusable programs.
- The effective provider on the path must come from the **same factory**, including its `.of(...)` test doubles. A missing provider, or a different factory with the same name, fails with a `CrustDefinitionError` at runtime, not compile time.

## Environment variables

[`@crustjs/env`](/docs/modules/env)'s `defineEnv()` returns a plain Crust Context, so `service()` reads it with typed values and catchable errors. No extra Layer or adapter is needed:

<include lang="ts" meta="twoslash">
  ../../../examples/modules/effect-env.ts#env-example
</include>

- Validation runs only when the program reads `service(env)`; repeated reads share the invocation's result.
- Unhandled failures are reported as the original Core `ENV` error.

To recover, for example in a configuration diagnostic, catch `CrustEnvError`:

<include lang="ts">../../../examples/modules/effect-env.ts#env-recovery</include>

- `error.details.issues` lists every invalid or missing variable, [without values](/docs/modules/env#errors).
- `service(env)` fails with the full `CrustTaggedError` union: catching `CrustEnvError` leaves other failures, such as a missing provider, in the error channel.
- Definition mistakes throw when `defineEnv()` is called, before the handler runs.

<Callout type="warn">
  To read `ctx.env` from the action input instead, use `tryCrust(() => ctx.env)`. With
  `Effect.promise(() => ctx.env)`, a rejection becomes a defect, not a catchable tagged failure.
</Callout>

## Tagged errors

<include lang="ts">../../../examples/modules/effect.ts#tagged-errors</include>

Each [Core error code](/docs/api/errors#codes) has a `Data.TaggedError` class: `CrustDefinitionError`, `CrustValidationError`, `CrustParseError`, `CrustCommandNotFoundError`, `CrustEnvError`, and `CrustOutputError`. Each carries `message`, typed `details`, and `cause` (the original `CrustError`). `CrustTaggedError` is their union.

- `fromCrustError(error)` wraps a caught `CrustError` in the class for its `code`.
- `tryCrust(thunk)` lifts a sync or async thunk into an Effect: a thrown `CrustError` fails with its tagged class, an `AbortError` interrupts the fiber, and anything else is a defect.

`import * as CrustEffect from "@crustjs/effect"` keeps these names out of your module scope if they clash with Effect's own.
