`@crustjs/core` defines commands, routes and validates argv, constructs Contexts, applies Extensions, and runs Command Actions.

## Install

```npm
npm install @crustjs/core
```

The package supports Bun 1.4+ and Node 24+.

## Context-owned flags

<include lang="ts" meta='title="src/cli.ts"'>

</include>

A Context can own the flags needed by its setup. `.provide()` installs that Context on the current command and commands added later. Its flags are parsed by the providing command, its inline `.command()` children, and reusable commands that declare it with `.use()`; see [Flags owned by a Context](/docs/guide/contexts#flags-owned-by-a-context).

## Typed invocation

```ts
const outcome = await app.run(["wave"]);
if (outcome.status === "completed") console.log(outcome.stdout); // => o/
```

`run()` returns a captured outcome after cleanup. See [`run()` input and I/O](/docs/api/crust#runpath-input-options) for typed paths, structured input, validation, output capture, and failure behavior.

## Tooling subpath

```ts
import { defineExtensionId } from "@crustjs/core";
import { buildCommandDocumentation, visibleSectionsFor } from "@crustjs/core/tooling";

const snapshot = await app.snapshot();
const documentation = buildCommandDocumentation(snapshot);
const visible = visibleSectionsFor(snapshot, defineExtensionId("acme:web-docs"));
```

| Export                                                                             | Role                                                               |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `BUILD_OUT_DIR_ENV` / `SNAPSHOT_PATH_ENV`                                          | Environment variable names for the first-party subprocess protocol |
| `buildCommandDocumentation()`                                                      | Builds a renderer-ready documentation tree from a Command Snapshot |
| `formatDefault()` / `formatDescription()`                                          | Formats input defaults and descriptions                            |
| `isListed()` / `sectionsFor()` / `visibleSectionsFor()`                            | Filters commands and sections for an Extension identity            |
| `isInstalledCommandName()` / `INSTALLED_COMMAND_NAME_RULE`                         | Checks and describes the installed command name rule               |
| `CommandDocumentation` / `DocumentationArg` / `DocumentationFlag` / `UsageSegment` | Documentation model types                                          |
| `CommandSnapshot`                                                                  | Same type as the root export, for tooling-only imports             |
| `parseFlagValues()` / `FlagEnvironment`                                            | Resolves flags from their `env` bindings without argv              |
| `commandInputSchema()` / `CommandInputSchema` / `CommandInputPropertySchema`       | Describes a command's flat JSON input as JSON Schema               |
| `parseCommandInput()` / `RunInputPayload` / `RunInputValue`                        | Splits flat JSON input into structured `run()` input               |
| `commandInputFields()` / `CommandInputFields`                                      | Lists a command's arg names and `url` fields for that split        |
| `RAW_INPUT_PROPERTY`                                                               | Name of the passthrough input property (`"raw"`)                   |
| `standardJsonSchema()`                                                             | Converts a Standard Schema's input or output type to JSON Schema   |

`@crustjs/core/tooling` contains build- and render-time helpers for Command Snapshots, documentation trees, [section filtering](/docs/guide/extensions#section-consumers), and formatting. They move in lockstep with first-party tooling. Application authoring and invocation APIs stay at the package root. `SNAPSHOT_PATH_ENV` and `BUILD_OUT_DIR_ENV` name the variables `crust build` sets when it runs a source entry to prepare its snapshot; do not set them in your CLI.

An installed command name uses letters, digits, `.`, `_`, and `-`, and starts with a letter or digit. `crust build` applies this rule to `bin` keys, `create-crust` to project names, and `completion()` to the root command name, which `crust build` requires to match the installed command.

`parseFlagValues(flags, env)` reuses terminal flag conversion without argv: environment splitting, choices, parsers or built-in coercion, defaults, requiredness, and Standard Schemas. Invalid definitions reject with `DEFINITION`; value failures reject with `PARSE` or `VALIDATION`. Core's messages name the variable, never its value; Standard Schema issue messages are the validator's own and may quote it. [`@crustjs/env`](/docs/modules/env) aggregates and redacts those failures for environment validation.

`commandInputSchema(command, path)` describes a command's input as one flat JSON object: every arg and flag by name, plus `raw` for passthrough values the action receives as `rawArgs`. A Standard Schema definition appears as its snapshot `inputSchema` when `run()` accepts what that describes, otherwise by its token type. [`@crustjs/mcp`](/docs/modules/mcp#tools) advertises it as each tool's `inputSchema`, and the MCP page lists how each definition maps; [`input()`](/docs/modules/extensions/input) accepts the same object from `--input`, and [`schema()`](/docs/modules/extensions/schema) prints it. It throws, naming `path`, when an arg and a flag share a name or a definition is named `raw`. `parseCommandInput(command, values)` turns such an object back into `run()` input: arg names fill `args`, `raw` fills `raw`, other names go to `flags`, and `url` strings become `URL`s; `commandInputFields(command)` returns those arg and `url` field names. `undefined` entries are skipped; any other value that is not JSON data, or a `raw` that is not an array of strings, rejects with `PARSE`, and an invalid `url` string throws the `URL` constructor's `TypeError`; `run()` then validates the input like any structured invocation.

`standardJsonSchema(schema, "input" | "output")` returns the draft 2020-12 JSON Schema of a Standard Schema's input or output type through its [Standard JSON Schema](https://standardschema.dev/json-schema) converter, `~standard.jsonSchema`. Zod 4.2+ and ArkType 2.1.28+ provide one; wrap a Valibot schema with `toStandardJsonSchema()` from `@valibot/to-json-schema`. It returns `undefined` when the schema has no converter or the converter throws, as Zod does for a transform's output. Snapshots carry a command's [`.output()`](/docs/api/crust#outputschema) schema converted this way as `outputSchema`, and an arg or flag schema's input as `inputSchema`.
