`@crustjs/core` defines commands, routes and validates argv, constructs Contexts, applies Extensions, and runs Command Actions.

## Install

```npm
npm install @crustjs/core
```

The package supports Bun 1.4+ and Node 24+.

## Typed invocation

```ts
const outcome = await app.run(["wave"]);
if (outcome.status === "completed") console.log(outcome.stdout); // => o/
```

`run()` returns a captured outcome after cleanup. See [`run()` input and I/O](/docs/api/crust#runpath-input-options) for typed paths, structured input, validation, output capture, and failure behavior.

## Tooling subpath

`@crustjs/core/tooling` holds build- and render-time helpers for Command Snapshots, documentation trees, [section filtering](/docs/guide/extensions#section-consumers), and formatting. It moves in lockstep with first-party tooling; application authoring and invocation APIs stay at the package root.

```ts
import { defineExtensionId } from "@crustjs/core";
import { buildCommandDocumentation, visibleSectionsFor } from "@crustjs/core/tooling";

const snapshot = await app.snapshot();
const documentation = buildCommandDocumentation(snapshot);
const visible = visibleSectionsFor(snapshot, defineExtensionId("acme:web-docs"));
```

| Export                                                                             | Role                                                               |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `BUILD_OUT_DIR_ENV` / `SNAPSHOT_PATH_ENV`                                          | Environment variable names for the first-party subprocess protocol |
| `buildCommandDocumentation()`                                                      | Builds a renderer-ready documentation tree from a Command Snapshot |
| `formatDefault()` / `formatDescription()`                                          | Formats input defaults and descriptions                            |
| `isListed()` / `sectionsFor()` / `visibleSectionsFor()`                            | Filters commands and sections for an Extension identity            |
| `isInstalledCommandName()` / `INSTALLED_COMMAND_NAME_RULE`                         | Checks and describes the installed command name rule               |
| `CommandDocumentation` / `DocumentationArg` / `DocumentationFlag` / `UsageSegment` | Documentation model types                                          |
| `CommandSnapshot`                                                                  | Same type as the root export, for tooling-only imports             |
| `parseFlagValues()` / `FlagEnvironment`                                            | Resolves flags from their `env` bindings without argv              |
| `commandInputSchema()` / `CommandInputSchema` / `CommandInputPropertySchema`       | Describes a command's flat JSON input as JSON Schema               |
| `parseCommandInput()` / `RunInputPayload` / `RunInputValue`                        | Splits flat JSON input into structured `run()` input               |
| `commandInputFields()` / `CommandInputFields`                                      | Lists a command's arg names and `url` fields for that split        |
| `RAW_INPUT_PROPERTY`                                                               | Name of the passthrough input property (`"raw"`)                   |
| `standardJsonSchema()`                                                             | Converts a Standard Schema's input or output type to JSON Schema   |

The [tooling entry point](https://github.com/chenxin-yan/crust/blob/main/packages/core/src/tooling.ts) is the full export list.

### Installed command names

An installed command name uses letters, digits, `.`, `_`, and `-`, and starts with a letter or digit. Use it to check a name before installing a command under it.

### Flag values without argv

`parseFlagValues(flags, env)` runs the flag pipeline on environment values only: delimiter splitting, choices, `parse` or built-in coercion, defaults, requiredness, and Standard Schemas.

- Invalid definitions reject with `DEFINITION`; bad values reject with `PARSE` or `VALIDATION`.
- Core's messages name the variable, never its value. Standard Schema issue messages are the validator's own and may quote it.

### Command input as JSON

`commandInputSchema(command, path)` describes a command's input as one flat JSON object: every arg and flag by name, plus `raw` for the passthrough values the action receives as `rawArgs`. Flags an Extension declares (`--help`, `--json`, `--input`, …, marked by `extension` in their [`FlagSnapshot`](/docs/api/types#flagsnapshot)) configure the invocation, not the command, so they are left out; Context-owned flags such as `confirm()`'s `--yes` stay.

It throws, naming `path`, when an arg and a flag share a name or a definition is named `raw`.

| Definition                     | Schema                                                                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `type: "string"` / `"path"`    | `{ type: "string" }`                                                                                                |
| `type: "number"` / `"boolean"` | `{ type: "number" }` / `{ type: "boolean" }`                                                                        |
| `type: "url"`                  | `{ type: "string", format: "uri" }`; the string becomes a `URL` before `run()`                                      |
| `type: "json"`                 | `{}` (any JSON)                                                                                                     |
| `choices`                      | `{ type: "string", enum }`                                                                                          |
| `variadic` / `multiple`        | `{ type: "array", items }`                                                                                          |
| `required` without `default`   | listed in `required`, unless the flag has an `env` binding                                                          |
| flag `env`                     | The description ends with `(falls back to $NAME)`, or is `Falls back to $NAME`                                      |
| Standard Schema                | Its input JSON Schema when `run()` accepts that shape; otherwise the declared token type (`string` for schema args) |
| custom `parse`                 | The declared token type; the command validates and transforms when it runs                                          |
| every command                  | `raw: { type: "array", items: { type: "string" } }`, delivered to the action as `rawArgs`                           |

Standard Schema definitions:

- Their input JSON Schema comes from the schema's converter (Zod 4.2+, ArkType 2.1.28+, Valibot through `toStandardJsonSchema()`); see [`standardJsonSchema()`](#json-schema-from-a-standard-schema).
- Schema-backed values reach `run()` as their token: a string, or a boolean for `type: "boolean"` flags. So the JSON Schema is used, without `$schema`, only when its top-level `type` is that token type (or `array` of it, without `prefixItems`, for `variadic` and `multiple`) and it has no `$ref`, `$defs`, or other `$` keyword.
- `z.enum([...])`, `z.string().min(3)`, and `z.url()` keep their `enum`, `minLength`, and `format`. `z.coerce.number()` (JSON Schema `number`) falls back to `{ type: "string" }`, since a JSON number would fail the string binding.
- The definition's `description` fills in when the JSON Schema has none.
- Schema-owned requiredness is invisible: schema-backed definitions are advertised as optional. A custom `parse` definition keeps its declared `required`.

Defaults are advertised as `JSON.stringify` copies: `URL`s become strings, and nested `undefined`, functions, and symbols are dropped. Defaults that fail to serialize or hold non-finite numbers are omitted. Either way, `run()` still applies the declared default.

`parseCommandInput(command, values)` turns such an object back into `run()` input; `run()` then validates it like any structured invocation.

- Arg names fill `args`, `raw` fills `raw`, and every other name goes to `flags`, where `run()` rejects unknown ones. An Extension flag's name is rejected the same way, `Unknown flag "--json"`, here.
- Strings for `url` definitions become `URL`s. `commandInputFields(command)` returns the arg names and `url` field names it uses.
- `undefined` entries are skipped.
- It rejects with `PARSE` for an Extension flag, a value that is not JSON data, a `raw` that is not an array of strings, or an invalid URL (the same `Invalid URL for --name.` error argv gives, without the value).

### JSON Schema from a Standard Schema

`standardJsonSchema(schema, "input" | "output")` returns the draft 2020-12 JSON Schema of a Standard Schema's input or output type, through its [Standard JSON Schema](https://standardschema.dev/json-schema) converter (`~standard.jsonSchema`).

- Zod 4.2+ and ArkType 2.1.28+ provide a converter. Wrap a Valibot schema with `toStandardJsonSchema()` from `@valibot/to-json-schema`.
- It returns `undefined` when the schema has no converter or the converter throws, as Zod does for a transform's output.

Snapshots use it: a command's [`.output()`](/docs/api/crust#outputschema) schema appears as `outputSchema`, and an arg or flag schema's input as `inputSchema`.
