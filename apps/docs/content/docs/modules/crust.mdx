`@crustjs/crust` provides the `crust` CLI and its [`build()`](#programmatic-api) library. The [Build and distribution guide](/docs/guide/build-and-distribution) walks through the workflow; this page is the reference.

## Install

```npm
npm install -D @crustjs/crust
```

These are requirements of the build machine, not of users running your binaries:

- The `crust` command runs on Node: it is a Node launcher for a standalone executable with Bun embedded, so no separate Bun install is needed.
- Exception: on arm64 hosts, building the host's own target needs `bun` on `PATH`. The error names the targets you can build without it.
- [Node.js binaries](/docs/guide/build-and-distribution#nodejs-binaries) need the optional dependencies `tsdown` and `@tsdown/exe`, plus `node` on `PATH`. Other builds never load them, so an install that skipped them still builds everything else.
- The [`build()`](#programmatic-api) library needs `bun` on `PATH` unless the script runs under Bun.
- `@crustjs/core` is a peer dependency, so `BuildReport` is the same type your Extensions see.

### npm installation caveat

<Callout type="warn">
  npm 10.9.8 can report a successful install but remove the root command shim while skipping
  incompatible optional platform packages with the same bin name. npm 11.19.1 is verified on Linux
  with Node 22.23.2. The minimum fixed npm version has not been established; this does not imply
  every npm 11 release is fixed.
</Callout>

## Commands

```sh
crust build --artifact binary --target bun-linux-x64
# Runtime: bun (default)
# Artifact: binary
# Compiler: bun 1.4.2 (/usr/local/bin/bun)
# Staging 1 distribution target(s) in .../.crust...
#   → linux-x64: .../.crust/linux-x64/bin/my-cli-bun-linux-x64
# ✓ Staged 2 npm package(s) successfully: (excerpt)
```

- [`crust build`](/docs/guide/build-and-distribution#build) validates your CLI and stages runtime packages or standalone binaries, with npm packaging metadata, in `.crust/`.
- [`crust publish`](/docs/guide/build-and-distribution#publish-with-crust-publish) publishes the staged npm packages. Release downloads, Homebrew, and other [custom channels](/docs/guide/build-and-distribution#custom-distribution) use the built binaries directly.

### `crust build` options

| Option                        | Type                | Default             | Description                                                                                                                                                                         |
| ----------------------------- | ------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--artifact`                  | `package`, `binary` | none                | Artifact kind: a runtime package or standalone binaries. Overrides `crust.artifact`; one of them is required                                                                        |
| `-t, --target`                | string, repeatable  | none                | Canonical compiler target(s) for binaries, or `host` for this machine. Omit to stage `crust.targets`, or every target of the compiler. Rejected for runtime packages                |
| `--env-file`                  | string, repeatable  | none                | Env file(s) whose [`PUBLIC_*` values](/docs/guide/build-and-distribution#environment-variables) are inlined                                                                         |
| `--validate`, `--no-validate` | boolean             | `true`              | Materialize command definitions before compiling; `--no-validate` also skips Extension build hooks                                                                                  |
| `--minify`, `--no-minify`     | boolean             | `true`              | Minify the output                                                                                                                                                                   |
| `--bytecode`, `--no-bytecode` | boolean             | on for Bun binaries | Precompile Bun binaries to [bytecode](/docs/guide/build-and-distribution#bun-binary-startup) for faster startup. `--bytecode` is rejected for runtime packages and Node.js binaries |

Command names, entry files, runtime, default targets, Bun bundler plugins, extra directories, and external dependencies are not flags: they come from [`bin`](#commands-and-entries-bin) and the [`crust` block](#packagejson-configuration) in `package.json`.

### `crust publish` options

```sh title="Dry-run output (excerpt)"
crust publish --dry-run
# Publish order: linux-x64 -> ... -> root
#   → linux-x64: npm publish
```

| Option       | Type    | Default | Description                                         |
| ------------ | ------- | ------- | --------------------------------------------------- |
| `--tag`      | string  | none    | Override the npm dist-tag passed to npm publish     |
| `--dry-run`  | boolean | `false` | Print publish order and commands without publishing |
| `--registry` | string  | none    | Override the registry passed to npm publish         |

`crust publish` reads `.crust/manifest.json`. It fails with `Staged manifest not found` if there is none, and with `Stage is stale` if your `package.json` name or version no longer matches it; both tell you to run `crust build` first. It uses `npm`, which must be on `PATH`, because npm supports [trusted publishing](https://docs.npmjs.com/trusted-publishers) from CI.

- For each staged package, it checks `name@version` with `npm view` and runs `npm publish` only if that version is missing. Existing versions are skipped and never re-tagged, so rerunning after a failure resumes. `--dry-run` stays offline.
- Before anything publishes, it verifies the manifest, that package names are unique, and that every package directory resolves inside the staging root.
- When stdin is a TTY, npm inherits the terminal so browser or OTP authentication can complete.
- npm reads `publishConfig.access` from each staged `package.json`, copied from your project. Scoped public packages need `"publishConfig": { "access": "public" }`. See [Publishing from CI](/docs/guide/build-and-distribution#publishing-from-ci) for credentials.

<Callout type="warn">
  The version lookup replays the staged `publishConfig` registry settings to `npm view` using npm
  10.6+ precedence, where CLI flags override `publishConfig`. npm 9 gives `publishConfig` priority,
  so a conflicting `--registry` can make the lookup and the upload use different registries. Avoid
  that combination or upgrade npm.
</Callout>

## Programmatic API

`build(options?)` runs the `crust build` pipeline and resolves to what it staged. See [Programmatic builds](/docs/guide/build-and-distribution#programmatic-builds) for a release-script example.

<auto-type-table path="../../../../../packages/crust/src/build.ts" name="BuildOptions" />

<auto-type-table path="../../../../../packages/crust/src/build.ts" name="BuildResult" />

| `BuildArtifact` kind | Path                                               | Extra fields                   |
| -------------------- | -------------------------------------------------- | ------------------------------ |
| `package-json`       | Root manifest first, then one per platform package | `target` on platform manifests |
| `launcher`           | `root/bin/<command>.js` for binaries               | `command`                      |
| `executable`         | `<platform>/bin/<command>-<target>`                | `command`, canonical `target`  |
| `bundle`             | `root/bin/<command>.js` for runtime packages       | `command`                      |

`build()` runs in this order:

1. Validates `bin`, the `crust` block, and its options, with the same errors the CLI prints.
2. Selects the compiler and checks it against `engines` (binaries) and tsdown's requirements (Node.js binaries). Node.js binary targets are downloaded and unpacked here.
3. Wipes `.crust/` and stages every package, writing `manifest.json` last.

- It prints nothing and throws on failure; `onLog` receives each progress line with its stream.
- `BuildReport` is `@crustjs/core`'s type, re-exported.

<Callout type="warn">
  Overlapping builds of the same project directory reject before staging, across processes and
  symlink aliases. The lock is a `.crust.lock` directory beside `.crust/`, removed on success or
  failure; after an interrupted build, remove it only once no build is running. The lock does not
  protect publishing or other readers, so consume staged artifacts before rebuilding.
</Callout>

## Build output

`crust build` stages its output in `.crust/` (see [Build](/docs/guide/build-and-distribution#build) for the tree):

| Path            | Contents                                                                                |
| --------------- | --------------------------------------------------------------------------------------- |
| `manifest.json` | Package paths, publish order, `runtime`, `artifact`, and Extension build hook output    |
| `root/`         | The root npm package: the npm launcher for binaries, or the bundle for runtime packages |
| `<platform>/`   | One package per selected target (binaries only), with the executables in `bin/`         |
| `artifacts/`    | Files from [Extension build hooks](#extension-artifacts)                                |

- npm is optional: distribute `<platform>/bin/` with its adjacent data for [direct installation](/docs/guide/build-and-distribution#custom-distribution). The executable embeds its runtime; only the npm launcher needs Node.js.
- Runtime packages use `root/` only and need the user's installed runtime.
- Binary builds record `embeddedRuntimeVersion` in `manifest.json`: the compiler version embedded in every platform binary. See [Binary runtime version](/docs/guide/build-and-distribution#binary-runtime-version).
- The build checks that `package.json` has a non-empty `name` and `version` before wiping the previous stage, even with `--no-validate`.

### Staged `package.json` files

Staged manifests are generated rather than copied:

| Project field                                         | Staged behavior                                                                                                                         |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `name`, `version`                                     | Required; platform names append the alias, such as `@scope/my-cli-linux-x64`                                                            |
| npm metadata                                          | `description`, `license`, `author`, `homepage`, `bugs`, `repository`, `keywords`, `publishConfig`, `funding`, and `engines` are copied¹ |
| `bin`, `files`, `type`                                | Generated for the output; the root always uses `"type": "module"`                                                                       |
| `dependencies`, `devDependencies`                     | Omitted, except `crust.external` names, copied with their ranges; the compiler bundles everything else                                  |
| `optionalDependencies`                                | Generated for binary platform packages; absent for runtime packages                                                                     |
| `exports`, `peerDependencies`, `peerDependenciesMeta` | Preserved in the root only, subject to the rules below                                                                                  |
| `private`, source scripts, `$schema`                  | Omitted                                                                                                                                 |

¹ For binary builds without library `exports`, the root's `engines.node` is replaced by the npm launcher's requirement, `>=24`; a root with `exports` keeps your range, because its importers run that code on their own Node.js. Platform packages of Node.js binaries omit `engines.node`, which constrained the Node.js that built and is embedded in the executables. Other `engines` keys are copied.

`README.md` is copied into the root package and the license file into every package. Platform manifests carry `os`, `cpu`, and, on Linux, `libc`.

To ship a library alongside the CLI:

- `exports` targets must be `./` paths to staged files: a `crust.include` file, an Extension artifact, or `./package.json`. Nested conditions and `null` are supported; wildcards, fallback arrays, missing files, and `.`, `..`, `node_modules`, or empty segments are rejected.
- Included files are copied, not transformed. A CommonJS source package needs an included nested `package.json` such as `dist/package.json` with `{"type":"commonjs"}`, or explicit `.cjs`/`.d.cts` extensions.
- Peer ranges are published as written: `workspace:`, `catalog:`, `file:`, `link:`, and `portal:` ranges are rejected, as are local paths (`./native`, `../native`, `/opt/native`, `~/native`) and local tarballs (`native.tgz`). `peerDependenciesMeta` entries must name declared peers.

## Supported targets

Targets apply to binaries. `--target` overrides `crust.targets`; without either, all targets of the compiler are built. `host` selects this machine's OS, architecture, and Linux C library and can be mixed with explicit targets. Runtime packages reject both `--target` and `crust.targets`.

| Bun target                                   | Node.js target               | Platform alias                       |
| -------------------------------------------- | ---------------------------- | ------------------------------------ |
| `bun-linux-x64`, `bun-linux-arm64`           | `linux-x64`, `linux-arm64`   | `linux-x64`, `linux-arm64`           |
| `bun-linux-x64-musl`, `bun-linux-arm64-musl` | none                         | `linux-x64-musl`, `linux-arm64-musl` |
| `bun-darwin-x64`, `bun-darwin-arm64`         | `darwin-x64`, `darwin-arm64` | `darwin-x64`, `darwin-arm64`         |
| `bun-windows-x64`, `bun-windows-arm64`       | `win-x64`, `win-arm64`       | `windows-x64`, `windows-arm64`       |

Node.js targets use Node.js's own release names. Cross-platform builds download that target's official Node.js archive of the same version; see [Node.js binaries](/docs/guide/build-and-distribution#nodejs-binaries) for the unpacking tools and macOS signing.

### Platform packages and the npm launcher

Each platform package contains `bin/<command>-<target>` (`.exe` on Windows) per command, and its `bin` points at those executables. Installing a platform package directly skips the launcher and the Node.js start it adds to every run; see [choose an artifact to ship](/docs/guide/build-and-distribution#choose-an-artifact-to-ship).

The root package's launcher selects the platform package for the host:

- It supports only the targets included in the build.
- On POSIX it replaces itself with the binary (`process.execve`), so signals sent to the command reach the binary and the exit status is the binary's. This needs Node.js `>=24`, which binary-only root packages declare in `engines.node`; roots that also publish library `exports` keep the project's range.
- Signals ignored by whatever starts the command are not passed on: Node.js resets inherited ignores (except `SIGPIPE` and `SIGXFSZ`) before the launcher runs. Under `nohup` the binary still ends on `SIGHUP`, and as a background job of a non-interactive shell (`my-cli &` in a script) it still takes `SIGINT`. Run the platform binary directly when those ignores matter.
- On Windows, which has no `execve`, it starts the binary, forwards `SIGTERM` and `SIGHUP`, and exits with the binary's exit code or signal. `SIGINT` is never forwarded: the console delivers Ctrl-C to the binary directly.

### Linux glibc and musl

Plain Linux targets use glibc; Alpine needs Bun's `-musl` targets. The launcher detects the host C library and selects the matching binary. Node.js has no musl target.

<Callout type="warn">
  Bun's musl executables still load `libstdc++` and `libgcc` dynamically. A bare Alpine image needs
  `apk add libstdc++ libgcc`; `node:alpine` already includes them.
</Callout>

## Commands and entries (`bin`)

```json title="package.json"
{
  "bin": { "my-cli": "src/cli.ts", "my-cli-admin": "src/admin.ts" }
}
```

Each `bin` key is an installed command name and each value is the TypeScript entry compiled for it. Every entry becomes `bin/<command>.js` in the root package and, for binaries, a `<command>-<target>` binary in every platform package. A string `bin` names one command after the unscoped package name; without `bin`, the build compiles `src/cli.ts` under that name.

- Entries must be relative paths to existing files inside the project. Containment is checked lexically; symlinks may point elsewhere. Two commands cannot share one entry (compared by real path).
- Command names follow the [installed command name rule](/docs/modules/core#tooling-subpath): letters, digits, `.`, `_`, and `-`, starting with a letter or digit. They cannot differ only by case.
- A validated build requires each entry's root command to be named after its key, such as `new Crust("my-cli-admin")` for `"my-cli-admin": "src/admin.ts"`. `--no-validate` skips this check.
- `npm link` runs the source entry directly, so it needs the runtime's shebang (`#!/usr/bin/env bun` or `#!/usr/bin/env node`). `create-crust` templates include it. Link `.crust/root` to exercise the built distribution instead.

## `package.json` configuration

```json title="package.json"
{
  "crust": {
    "runtime": "bun",
    "artifact": "binary",
    "targets": ["bun-linux-x64", "bun-linux-arm64", "bun-darwin-arm64"],
    "bunPlugins": ["@opentui/solid/bun-plugin", "./build/plugin.ts"],
    "include": ["templates"]
  }
}
```

`crust.artifact` is required unless every build passes `--artifact`; the other keys are optional. Unknown keys under `crust` fail the build, so typos such as `bunPlugin` are not ignored.

| Key                | Description                                                                                                                                                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crust.runtime`    | `bun` or `node`. Without it, `@types/node` without `@types/bun` selects Node; otherwise Bun.                                                                                                                                                                                                      |
| `crust.artifact`   | `package` (a root-only runtime package for `bun` or `node`) or `binary` (standalone executables for `bun` or `node`). `--artifact` overrides it.                                                                                                                                                  |
| `crust.targets`    | Canonical compiler targets staged when a binary build runs without `--target`, `host` included. Without it every target of the compiler is staged. Rejected for runtime packages.                                                                                                                 |
| `crust.bunPlugins` | [Bun bundler plugin](https://bun.com/docs/bundler/plugins) modules applied to Bun builds and Node runtime packages, in order. A bare name resolves from `node_modules`, a path from the project root; each must default-export the plugin. Rejected for Node binaries.                            |
| `crust.include`    | Directories relative to the project root that `crust build` copies into `.crust/root/` (listed in `files`) and into each platform package's `bin/`.                                                                                                                                               |
| `crust.external`   | Packages a Node or Bun runtime package leaves out of its bundles and ships as `dependencies` of the staged root package, with their `dependencies` ranges, in this order. See [Keep dependencies external](/docs/guide/build-and-distribution#keep-dependencies-external). Rejected for binaries. |

`crust.include` rules:

- Entries must be existing directories inside the project. Symlinks are copied dereferenced and must resolve inside the project.
- An entry cannot be named `bin`, be inside `.crust`, or reuse an Extension artifact directory name. Names are compared ignoring letter case (`Bin`, `Assets` vs `assets`), because they alias on case-insensitive file systems.
- Names that npm leaves out of every published package, in any directory, fail the build, including in the path to a nested entry (`templates/app.orig/src`): `.gitignore`, `.npmignore`, `.npmrc`, `.git`, `.DS_Store`, `*.orig`, and the rest of npm's built-in ignore list. Rename them (`_gitignore`) and restore the name when your CLI copies them; [`scaffold()`](/docs/modules/create#template-conventions) restores a leading `_` as `.`.

`crust.external` rules, checked before `.crust/` is wiped:

- Each entry is listed once and must be a key of `dependencies`. A package only in `devDependencies`, `optionalDependencies`, or `peerDependencies` is rejected, as are subpaths and wildcards.
- Its range must be publishable, by the same rules as [peer ranges](#staged-packagejson-files).
- `@crustjs/*` packages, and npm aliases of them such as `npm:@crustjs/utils@0.2.2`, cannot be external: an external Crust package would load a second copy of Core.
- An empty list does nothing.

### Editor completion

`@crustjs/crust` ships a JSON schema for this block. It extends the [SchemaStore package.json schema](https://json.schemastore.org/package.json), so completion for the standard fields keeps working. `create-crust` templates set it; `crust build` never copies `$schema` into staged packages.

```json title="package.json"
{
  "$schema": "./node_modules/@crustjs/crust/schema/package.json"
}
```

## Extension artifacts

```text
.crust/artifacts/
├── man/<name>.1
├── skills/
└── completions/
```

Registered Extensions such as [`man()`](/docs/modules/man), [`skill()`](/docs/modules/skills), and [`completion()`](/docs/modules/extensions/completion) contribute build hooks. `crust build` runs those hooks while preparing each entry, writes the files they return, and copies each top-level directory into `.crust/root/` and every platform package's `bin/`. A CLI reads them back with [`resolveArtifactDir(name)`](/docs/api/crust#resolveartifactdirname).

- Each hook's returned paths are recorded per `bin` entry under `build` in `.crust/manifest.json`. Loose top-level files are recorded but not copied into packages.
- With several `bin` entries, same-named directories merge, so `man/greet.1` and `man/admin.1` coexist. A path two entries both write fails the build naming both commands; collisions are compared case-insensitively.
- Upgrade `@crustjs/core`, `@crustjs/crust`, and build-hook Extensions together. Reports from an incompatible Core fail preparation with upgrade guidance.
- `--no-validate` skips all build hooks, so no artifact directories are staged and the manifest has no `build` field.

Entry modules run during preparation and are not sandboxed; files they write elsewhere are not reported.
