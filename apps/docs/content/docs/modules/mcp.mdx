`@crustjs/mcp` serves your commands as [MCP](https://modelcontextprotocol.io) tools. Each tool's JSON Schema comes from the same definitions that drive parsing and help, and every call runs through `app.run()`, with no per-command glue.

MCP serves clients that call tools instead of running a shell; [how agents use your CLI](/docs/guide/agents#how-agents-use-your-cli) shows where it fits beside the shell and skills.

## Install

```npm
npm install @crustjs/mcp
```

The package has a peer dependency on `@crustjs/core` and depends on `@modelcontextprotocol/sdk`. Only the stdio transport is supported.

## `mcpExtension(options)`

<include lang="ts">../../../examples/modules/mcp.ts#extension</include>

`mcpExtension()` owns two commands:

- `<cli> mcp` serves the application over stdio until the client disconnects. Stdout carries protocol frames, so the Command Action writes nothing else to it; command output is captured per call instead.
- `<cli> mcp config [--client claude|cursor|vscode]` prints the client configuration snippet on stdout. `--client` defaults to `claude`, which also prints a `claude mcp add` one-liner on stderr.

`app` is a callback, called when `mcp` runs, because the Extension is installed before the application is complete. To return the variable being assigned, annotate the callback `(): AnyCrust =>`; otherwise TypeScript reports the variable as referenced in its own initializer. `mcpExtension.id` is the Extension identity.

### Client configuration

`mcp config` derives the launch command from the running process:

- A compiled executable (`bun build --compile` or a Node single executable application) launches itself with `args: ["mcp"]`.
- A Node or Bun source entry, or a Node bundle, relaunches through `process.execPath`, with `process.execArgv` before the entry path.
- Claude Code, Claude Desktop, and Cursor read `mcpServers`; VS Code's `.vscode/mcp.json` reads `servers`.

Set `launch: { command, args }` to override it, for example to drop development-only flags such as inspectors or watch mode; `args` must include `mcp`. The working directory and environment, such as `NODE_OPTIONS`, are not preserved: use absolute paths and configure the client's environment separately. Flag [`env` fallbacks](#tools) read the server's environment, so the client's `env` setting configures them.

```json
{
  "mcpServers": {
    "my-cli": { "type": "stdio", "command": "/usr/local/bin/my-cli", "args": ["mcp"] }
  }
}
```

```text
Or run: claude mcp add my-cli -- /usr/local/bin/my-cli mcp
```

Nothing is written into client configuration files; paste the snippet or run the one-liner.

## Tools

A command becomes a tool when it:

- has a Command Action (so the root is a tool only when it has one)
- is visible: not `hidden`, nor under a hidden command
- is not the `mcp` command, an `exclude` path, or under one
- is the application's own command, not one an Extension contributed (such as `completion`, `schema`, `skills install`, or [`@crustjs/openapi`](/docs/modules/openapi)'s `api`), unless an `include` path selects it or a command it is under

Every `exclude` and `include` path must be a canonical command path; hidden commands and paths under another excluded command count. A misspelled path or an alias throws, listing each unknown path, instead of leaving the command exposed or hidden. `exclude` wins over `include`, and `mcp` is never a tool.

The tool name is the canonical command path joined with `_` (`deploy api` becomes `deploy_api`); the root uses its own name, and aliases never become tools. Building the tool list throws, naming the paths, when:

- two commands map to one name, such as `a_b` and `a b`, or the root and a subcommand named after it
- a name breaks the MCP tool-name rule: 1–128 characters of `A-Z a-z 0-9 _ - .`

Each tool's `inputSchema` comes from [`commandInputSchema()`](/docs/modules/core#command-input-as-json), and call arguments go back through `parseCommandInput()`:

- Flags an Extension declares, such as `--help`, `--json`, or `--input`, are not tool inputs. A call that sends one fails with `PARSE: Unknown flag "--json"`, so it never selects a flag handler or reads stdin. Context-owned flags such as [`confirm()`](/docs/modules/extensions/confirm)'s `yes` stay.
- A flag with an `env` binding is optional, and its description names the variable. An omitted value falls back to the variable in the server's environment, then to the default, as on the command line; a required flag still fails when neither supplies it.

## Results

The outcome of `app.run()` decides the tool result:

- A `completed` result that is plain JSON (finite numbers, strings, booleans, `null`, arrays, and plain objects of those) is returned as `structuredContent` plus a text block with the same JSON. Arrays and primitives are wrapped as `{ "result": value }`.
- Any other `completed` result (`undefined`, `Date`, `Map`, class instances, `BigInt`, `NaN`, cycles) and every `handled` outcome return the captured stdout as text. The result is copied once before serialization, so getters run once and `toJSON` is not called.
- A `failed` outcome sets `isError` with `<code>: <message>` for a `CrustError`, `<name>: <message>` for other errors. Arguments that cannot become `run()` input, such as an invalid URL or a `raw` that is not an array of strings, fail the same way with `PARSE`.

Whatever the outcome, non-empty captured stderr follows as one more text block, so warnings and [`nextSteps()`](/docs/modules/extensions/next-steps)' `Next steps:` block (recovery steps included on failure) reach the client. It changes neither `structuredContent` nor `isError`.

Unknown tool names are protocol errors (`InvalidParams`), which is also how hidden and excluded commands present.

### Output schema

A command whose [`.output()`](/docs/api/crust#outputschema) schema converts to JSON Schema advertises it as the tool's `outputSchema`, in the shape of its `structuredContent`:

| Output JSON Schema                                                                                   | Advertised `outputSchema`                                                                         |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `type: "object"`                                                                                     | As is                                                                                             |
| A `type` that excludes objects (`number`, `array`, `["string", "null"]`, …)                          | `{ type: "object", properties: { result }, required: ["result"] }`, `$schema` and `$defs` at root |
| May or may not be an object (no top-level `type`, such as `anyOf`, or a `type` list with `"object"`) | None, since results may be sent either way                                                        |
| Non-object, with a `$ref` outside `#/$defs/` (such as `"#"`) or another `$` keyword such as `$id`    | None, since wrapping would break it                                                               |

MCP requires `structuredContent` from a tool with an `outputSchema`. When such a tool's call ends with only captured stdout (a `handled` outcome, or a result that is not plain JSON), the result sets `isError`, with a line saying the result is missing before the stdout text.

## Progress

When a `tools/call` request carries `_meta.progressToken`, each value an [async generator action](/docs/guide/commands#stream-events) yields sends a `notifications/progress` for that token:

- `progress` counts the events so far (1, 2, …).
- A string event becomes its `message`; other events send no `message`.
- A notification that fails to send is dropped without failing the call.

Without a token, no notifications are sent. Either way, the tool result is the action's return value.

## Headless primitives

<include lang="ts">../../../examples/modules/mcp.ts#headless</include>

`createMcpServer(app, options?)` returns the SDK's low-level `Server` with `tools/list` and `tools/call` handlers. `serveStdio(server)` connects the stdio transport and resolves when the client disconnects.

- The server is named after the root command, with its `version` or `DEFAULT_SERVER_VERSION` (`0.0.0`).
- Each call runs `app.run(path, input, { signal })` with its own captured output, plus an `onEvent` that sends [progress](#progress) when the request carries a progress token.
- Client cancellation aborts only that call; disconnecting aborts all of them. Actions must honor `signal` to stop.
- `toolResultFromOutcome(outcome)` is the outcome-to-result conversion described in [Results](#results), without the `outputSchema` check.

<Callout type="warn">
  Over stdio, protocol frames own the process's stdout. Output written through the invocation's
  `stdout` / `stderr` is captured per call, but direct `console.log` or `process.stdout.write` calls
  corrupt the protocol stream. Keep them out of code that runs under `mcp`, or write to stderr.
</Callout>

Protocol frames also arrive on stdin. While the transport reads it, a `-` value that reads all of stdin, such as [`@crustjs/openapi`](/docs/modules/openapi)'s `--body -`, fails with `stdin is in use by another reader` instead of waiting for the client to disconnect.

## `toolsFromSnapshot(snapshot, options?)`

<include lang="ts">../../../examples/modules/mcp.ts#manifest</include>

The pure manifest, for tests or tooling that ships tool definitions without a server. Pass `await app.snapshot()`, which marks Extension commands and flags, so `include` can name Extension commands and tool inputs leave Extension flags out. Each entry carries the tool `name`, `description`, `inputSchema`, `outputSchema` when it applies, and the canonical `path` for `app.run()`.

## Other exports

These build the [`mcp config`](#client-configuration) output yourself:

- `currentLaunch()` returns the launch for the running process; `resolveLaunch(execPath, entry, compiled, execArgv?)` computes one from explicit values.
- `renderClientConfig(client, name, launch)` and `renderClaudeAddCommand(name, launch)` render the snippet and the one-liner.
- `MCP_CLIENTS` lists the supported `--client` values, and `MCP` is the Extension identity, the same as `mcpExtension.id`.

The [package entry point](https://github.com/chenxin-yan/crust/blob/main/packages/mcp/src/index.ts) is the complete export list, including the `McpClient`, `McpLaunch`, and schema types.
