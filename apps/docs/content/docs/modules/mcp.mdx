`@crustjs/mcp` turns the Command Snapshot into an MCP tool manifest and routes every tool call through typed `app.run()`. No per-command glue: the same definitions that drive parsing, help, and completion drive the JSON Schema each tool advertises.

## Install

```npm
npm install @crustjs/mcp
```

The package has a peer dependency on `@crustjs/core` and depends on `@modelcontextprotocol/sdk`. Only the stdio transport is supported.

## `mcpExtension(options)`

<include lang="ts">../../../examples/modules/mcp.ts#extension</include>

`mcpExtension()` owns two commands:

- `<cli> mcp` serves the application over stdio until the client disconnects. Stdout carries protocol frames, so the Command Action writes nothing else to it; command output is captured per call instead.
- `<cli> mcp config [--client claude|cursor|vscode]` prints the client configuration snippet on stdout, and for Claude also prints a `claude mcp add` one-liner on stderr.

`app` is a callback because the Extension is installed while the application is still being assembled; it runs when `mcp` runs. Returning the variable being assigned needs an explicit `(): AnyCrust =>` return annotation, or TypeScript reports the variable as referenced in its own initializer. `mcpExtension.id` is the Extension identity.

### Client configuration

`mcp config` derives the launch command from the running process. A compiled executable (`bun build --compile` or a Node single executable application) launches itself with `args: ["mcp"]`; a Node or Bun source entry or Node bundle relaunches through `process.execPath` with `process.execArgv` before the entry path. Claude Code, Claude Desktop, and Cursor read `mcpServers`; VS Code's `.vscode/mcp.json` reads `servers`.

Set `launch: { command, args }` to override it; `args` must include `mcp`.

- Use it to drop development-only flags such as inspectors or watch mode.
- The working directory and environment such as `NODE_OPTIONS` are not preserved. Use absolute paths and configure the client's environment separately.

```json
{
  "mcpServers": {
    "my-cli": { "type": "stdio", "command": "/usr/local/bin/my-cli", "args": ["mcp"] }
  }
}
```

```text
Or run: claude mcp add my-cli -- /usr/local/bin/my-cli mcp
```

Nothing is written into client configuration files; paste the snippet or run the one-liner.

## Tools

A command becomes a tool when it is visible (not `hidden`, nor under a hidden command), has a Command Action, is not the `mcp` command, and is not under an `exclude` path. The root is a tool only when it has an action. Every `exclude` path must be a canonical command path (hidden commands and paths under another excluded command count); a misspelled path or an alias throws, listing each unknown path, instead of leaving the command exposed.

The tool name is the canonical command path joined with `_` (`deploy api` becomes `deploy_api`); the root uses its own name, and aliases never become tools. That join is not injective, so `toolsFromSnapshot` throws when two commands map to one name (`a_b` and `a b`, or the root and a subcommand named after it), naming both paths. It also throws when a name falls outside the MCP tool-name rule (1–128 characters of `A-Z a-z 0-9 _ - .`).

Each tool's `inputSchema` is one flat object built from the snapshot by [`commandInputSchema()`](/docs/modules/core#tooling-subpath), and call arguments go back through `parseCommandInput()`:

| Definition                     | Schema                                                                                                              |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `type: "string"` / `"path"`    | `{ type: "string" }`                                                                                                |
| `type: "number"` / `"boolean"` | `{ type: "number" }` / `{ type: "boolean" }`                                                                        |
| `type: "url"`                  | `{ type: "string", format: "uri" }`; the string becomes a `URL` before `run()`                                      |
| `type: "json"`                 | `{}` (any JSON)                                                                                                     |
| `choices`                      | `{ type: "string", enum }`                                                                                          |
| `variadic` / `multiple`        | `{ type: "array", items }`                                                                                          |
| `required` without `default`   | listed in `required`                                                                                                |
| Standard Schema                | Its input JSON Schema when `run()` accepts that shape; otherwise the declared token type (`string` for schema args) |
| custom `parse`                 | The declared token type; the command validates and transforms when it runs                                          |
| every tool                     | `raw: { type: "array", items: { type: "string" } }`, delivered to the action as `rawArgs`                           |

A Standard Schema definition's snapshot carries the schema's input JSON Schema (`inputSchema`) when it can produce one (Zod 4.2+, ArkType 2.1.28+, Valibot through `toStandardJsonSchema()`). Schema-backed values reach `run()` as their token, a string (a boolean for `type: "boolean"` flags), so that JSON Schema is advertised, without `$schema`, only when its top-level `type` is that token type, or `array` with such `items` for `variadic` and `multiple`, and it has no `$ref`, `$defs`, or other `$` keyword. `z.enum([...])`, `z.string().min(3)`, and `z.url()` keep their `enum`, `minLength`, and `format`; `z.coerce.number()` (JSON Schema `number`) falls back to `{ type: "string" }`, since a JSON number would fail the string binding. The definition's `description` fills in when the JSON Schema has none. Schema-owned requiredness is invisible: schema-backed definitions are advertised as optional, while a custom `parse` definition keeps its declared `required`. An arg and a flag with the same name, or a definition named `raw`, are rejected. Defaults are advertised as `JSON.stringify` copies, so `URL`s become strings and nested `undefined`, functions, and symbols are dropped; defaults that fail to serialize or hold non-finite numbers are omitted from the manifest. Either way, `run()` still applies the declared default.

## Results

The outcome of `app.run()` decides the tool result:

- A `completed` result that is plain JSON (finite numbers, strings, booleans, `null`, arrays, and plain objects of those) is returned as `structuredContent` plus a text block with the same JSON. Arrays and primitives are wrapped as `{ "result": value }`.
- Any other `completed` result (`undefined`, `Date`, `Map`, class instances, `BigInt`, `NaN`, cycles) and every `handled` outcome return the captured stdout as text. The result is copied once before serialization, so getters run once and `toJSON` is not called.
- A `failed` outcome sets `isError` with `<code>: <message>` for a `CrustError`, `<name>: <message>` for other errors.

A command with an [`.output()`](/docs/api/crust#outputschema) schema whose snapshot carries `outputSchema` advertises it as the tool's `outputSchema`, in the shape of its `structuredContent`. An object schema is advertised as is. A schema whose `type` excludes objects (`number`, `array`, `["string", "null"]`, …) is wrapped as `{ type: "object", properties: { result }, required: ["result"] }`, with `$schema` and `$defs` kept at the root. A schema that may describe an object or not (no top-level `type`, such as `anyOf`, or a `type` list including `"object"`), is not advertised, since its results may be sent either way; neither is a non-object schema that wrapping would break (a `$ref` outside `#/$defs/`, such as `"#"` or `"#/prefixItems/0"`, or another `$` keyword such as `$id`). MCP requires `structuredContent` from a tool with an `outputSchema`, so when such a tool's call ends with only captured stdout (a `handled` outcome, or a result that is not plain JSON), the result sets `isError`, with a line saying the result is missing before the stdout text.

A command marked [`destructive`](/docs/api/types#commandmeta) advertises `annotations: { destructiveHint: true }`; other tools carry no `annotations`.

Unknown tool names are protocol errors (`InvalidParams`), which is also how hidden and excluded commands present.

## Progress

When a `tools/call` request carries `_meta.progressToken`, each value an [async generator action](/docs/guide/commands#stream-events) yields sends a `notifications/progress` for that token: `progress` counts the events so far (1, 2, …), and a string event becomes its `message`; other events send no `message`. Without a token, no notifications are sent. A notification that fails to send is dropped without failing the call. The tool result is still the action's return value.

## Headless primitives

<include lang="ts">../../../examples/modules/mcp.ts#headless</include>

`createMcpServer(app, options?)` returns the SDK's low-level `Server` with `tools/list` and `tools/call` handlers, named after the root command with its `version` (or `0.0.0`). Each call runs `app.run(path, input, { signal })` with its own captured output, plus an `onEvent` that sends [progress](#progress) when the request carries a progress token. Client cancellation aborts only that call and disconnecting aborts all of them; actions must honor `signal` to stop. `serveStdio(server)` connects the stdio transport and resolves when the client disconnects.

<Callout type="warn">
  Over stdio, protocol frames own the process's stdout. Output written through the invocation's
  `stdout` / `stderr` is captured per call, but direct `console.log` or `process.stdout.write` calls
  corrupt the protocol stream. Keep them out of code that runs under `mcp`, or write to stderr.
</Callout>
