`@crustjs/prompts` exports terminal prompts, shared themes, injected terminal IO, and helpers for custom prompts. Prompt UI writes to stderr by default.

## Install

```npm
npm install @crustjs/prompts
```

## Quick example

<include lang="ts">../../../examples/modules/prompts.ts#builtins</include>

Built-in prompts return the submitted value. `input()` and `password()` also accept a Standard Schema v1 `schema` or a throw-based `validate` callback, but not both.

```text
┃ Project name?
  crust-app│
✓ Project name? crust-app
```

## Injecting IO

<include lang="ts">../../../examples/modules/prompts.ts#io</include>

Each prompt accepts an optional second `TerminalIO` argument with optional `input`, `output`, and `signal`. Resolution is explicit IO, ambient `withTerminalIO()` IO, then `process.stdin` and `process.stderr`. Inside a Crust command the ambient `signal` is the invocation's, so a `SIGTERM`, a Ctrl-C delivered as a signal, or an aborted `execute({ signal })` cancels a waiting prompt without passing it.

The ambient `withTerminalIO()` scope is shared with `@crustjs/progress`.

## Prompts

All prompt functions accept `(options, io?)`. Choice functions preserve literal choice value types when their choices are not widened. A plain-string choice is its own value, so `Choice<T>` only accepts plain strings that are themselves a `T`; non-string values such as numbers must use `{ label, value }` objects.

### `input(options, io?)`

```ts
const name = await input({ message: "Name?", default: "anonymous" });
```

Single-line text input supports cursor editing, placeholder text, defaults, and validation.

### `confirm(options, io?)`

```ts
const proceed = await confirm({ message: "Continue?", default: false });
```

## Validation

```text
┃ Project name?
  │
  Name is required
```

A `validate` callback throws to reject input, and its error message renders inline. A Standard Schema parses the raw string, returns its transformed output type, and renders the first issue or `Validation failed`.

Async validators and schemas are supported. `initial` and non-interactive `default` values also pass through a configured schema or `validate` callback before being returned; a rejected value throws, for example `initial value rejected: Name is required`.

## Themes

<include lang="ts">../../../examples/modules/prompts.ts#theme</include>

Instance overrides from `createPrompts()` sit between `defaultTheme` and per-prompt overrides. Each theme slot is a style function:

<auto-type-table path="../../../../../packages/prompts/src/core/types.ts" name="PromptTheme" />

Default theme slots decide color from the prompt's output stream (stderr unless injected), applying the `NO_COLOR` and `FORCE_COLOR` rules from [`@crustjs/style` color control](/docs/modules/style#color-control). Theme functions you pass, including the exported `defaultTheme`, keep their own detection, which checks stdout.

## Non-interactive environments

```text
# input({ message: "Name?", default: "ci-user" }) on a non-TTY
ci-user

# input({ message: "Name?" }) on a non-TTY
NonInteractiveError: Prompts require an interactive terminal (TTY).
```

- With `initial`, every prompt returns it without rendering.
- A prompt renders only when both its input and its output are TTYs.
- Otherwise, such as when stdin is piped or stderr is redirected, a prompt returns an explicitly supplied `default` (`password()` has none) or rejects with `NonInteractiveError`. `confirm()` defaults to yes interactively, but without a TTY only an explicit `default` counts.
- Ctrl+C rejects with a `DOMException` whose name is `AbortError`.
- When the resolved `signal` aborts, the prompt restores the terminal (cursor shown, raw mode off) and rejects with `signal.reason`. An already-aborted signal rejects before rendering.

To check before prompting, `isTTY(input?)` reports whether the resolved input stream is a TTY, and `assertTTY(input?)` throws `NonInteractiveError` when it is not. Neither checks the output stream.

## Custom prompts

<include lang="ts">../../../examples/modules/prompts.ts#custom</include>

`runPrompt()` owns rendering, input, submission, cancellation (Ctrl+C and the resolved `signal`), and theme merging. Accept `(options, io?)` and forward the IO argument to `runPrompt()`, like the built-ins, so callers and tests can inject streams.

- Only one prompt may use a given input or output stream at a time.
- An error thrown by `render`, `handleKey`, or `renderSubmitted` rejects the promise after the terminal is restored.
- `handleTextEdit()` provides the built-ins' cursor editing and returns `null` for keys it does not handle. The root also exports the fuzzy matching, list rendering, formatting, and glyph helpers the built-ins use; see [`index.ts`](https://github.com/chenxin-yan/crust/blob/main/packages/prompts/src/index.ts).

### Testing custom prompts

`renderPrompt()` from `@crustjs/prompts/testing` runs a prompt against a fake TTY, as in the example above. `type()` and `keys()` send input, `screen()` returns the latest ANSI-stripped frame (wrapped at 80 columns like a real terminal), and `answer` settles after submission. The subpath also exports `createPromptIO()` and `encodeKey()` for lower-level harnesses.
