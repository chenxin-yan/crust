## Usage

<include lang="ts" meta='title="cli.ts"'>
  ../../../../examples/modules/extensions/config.ts
</include>

```sh
$ cat acme.config.json
{ "org": "acme-corp", "region": "eu" }

$ acme
org=acme-corp region=eu
$ ACME_ORG=other acme --region us
org=other region=us
```

A flag opts in with `config: "<key>"`, a top-level key of the file. The flag stays the only declaration: keys no flag on the routed command declares are ignored, so one file can serve every command. A key must be non-empty and must not contain `.`, which is kept for nested keys; TypeScript rejects such a literal, and a computed one throws a `DEFINITION` error.

## Files

`config({ name, project?, user? })` reads up to two JSON files:

- **Project file** (`project`): the first entry with that name found from the working directory up to the filesystem root. The search stops at that entry, so a directory or other non-file with the name is an error, not skipped.
- **User file** (`user: true`): `config.json` in [`configDir(name)`](/docs/modules/store#storage-paths) from `@crustjs/store`, such as `~/.config/acme/config.json` on Linux and macOS (`$XDG_CONFIG_HOME` when set) or `%APPDATA%\acme\config.json` on Windows.

The project file wins over the user file key by key. A missing file is skipped. Each file must be a regular file (a symlink to one is followed) of at most 1 MiB holding a JSON object; a byte order mark is allowed. TypeScript config files and commands that write the file are not included: write the user file with [`@crustjs/store`](/docs/modules/store) if your CLI needs to.

`config()` reads the files in `setup`, so every `preRun` sees the values whatever the `.extend()` order, and it reads nothing when the routed command has no flag with a `config` key.

## Precedence

A config value fills a flag only when nothing but its default supplied one:

| Entry point                                      | Order                                               |
| ------------------------------------------------ | --------------------------------------------------- |
| [`execute()`](/docs/api/crust#executeoptions)    | argv > bound > `env` > config file > `default`      |
| [`run()`](/docs/api/crust#runpath-input-options) | bound > run input > `env` > config file > `default` |

"Bound" is [`ctx.bindInput()`](/docs/api/types#extensioncontext), for example [`input()`](/docs/modules/extensions/input)'s `--input` values; they win over the file in either `.extend()` order. [`ctx.sources`](/docs/api/types#extensioncontext) reports `config` for a value taken from a file.

A `required` flag with a `config` key may be omitted from typed `run()` input, as with `env`; it still fails at run time when nothing supplies it. [`commandInputSchema()`](/docs/modules/core#command-input-as-json), `--llms`, and the [MCP](/docs/modules/mcp) server list it as optional, and help, man pages, and skills show the key as `[config: org]`, never the value.

## Values

Values are converted and validated as typed `run()` input, then by the flag's `choices`, `parse`, and schema:

- `multiple` flags take a JSON array; strings are not split by `delimiter`. An empty array supplies nothing.
- `url` flags take a URL string.
- `null` is a value, not "unset": it fails for every type except `json`. Delete the key to unset it.

## Errors

- **Malformed file**: a path that cannot be searched or read, a directory, FIFO, or other non-regular file, a file larger than 1 MiB, invalid JSON, or JSON that is not an object fails every command that reads the file with a `PARSE` [`CrustError`](/docs/api/errors) naming the path, such as `Invalid JSON in config file /repo/acme.config.json.` The message never quotes the file. `config()` raises it in `preRun`, when the action is about to run, so `--help` and `--version` still answer; until then no hook sees a value from either file.
- **Invalid value**: a value of the wrong type fails like an invalid environment value, naming the file and key but not the value, such as `Expected a number for --port (from /repo/acme.config.json key "port").` It does not block `--help` or `--version`.
- **Schema issues**: a schema-backed flag's issue names its origin, such as `flags.region (from /repo/acme.config.json key "region"): …`. The message after it is the schema's own and may quote the value.

## What `crust build` checks and writes

`config()` adds a build hook, so [`crust build`](/docs/modules/crust#extension-artifacts) checks every flag that declares a key, across all commands, and writes a JSON Schema of the config file. Run time checks nothing.

### One shape per key

One file serves every command, so every flag that names a key must accept the same value: the flag's JSON Schema as [command input](/docs/modules/core#command-input-as-json) shows it, without its description and default. Flags may share a key when those are equal, also within one command. A flag with a custom `parse`, or a schema that cannot produce a JSON Schema command input uses, compares as its token type: a `string` flag with `parse: Number` is a string.

```sh
$ crust build
Error: Extension "crust:config" build failed: config: 1 problem needs a decision before this CLI can be built.

  config key "port" is declared with different types:
    acme serve --port  number
    acme proxy --port  string
    fix: give them one type, or give one of them another key
```

The error lists every such key. A flag may not declare the key `$schema`, which names the file's schema; that fails the build the same way.

### The config file's JSON Schema

When any flag declares a key, the build writes `config/schema.json` (draft 2020-12): one property per key with the flags' shared shape and the first description in command-tree order, a `$schema` property, and `additionalProperties: false`. For the [usage](#usage) example:

```json title="config/schema.json"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "acme config file",
  "type": "object",
  "properties": {
    "$schema": { "type": "string", "description": "The JSON Schema this file follows" },
    "org": { "type": "string" },
    "region": { "type": "string", "enum": ["us", "eu"] }
  },
  "additionalProperties": false
}
```

The file is in `.crust/root/config/` and beside each executable, `.crust/<platform>/bin/config/`, so an npm install has it at `node_modules/acme/config/schema.json`. Publish it where your users can reach it, and they point a config file at it so editors complete and check the keys:

```json title="acme.config.json"
{ "$schema": "https://acme.dev/config.schema.json", "org": "acme-corp" }
```

The schema describes the project file and the user file alike. `config()` ignores `$schema` and every other key no flag on the routed command declares, so an older CLI still reads a file written for a newer one. `--no-validate` skips build hooks, and with them the check and the schema.

## Security

- Keep secrets out of config files: read tokens from `env` or a prompt. A project file is found in any parent directory, including one a cloned repository ships, so a config key must never choose where credentials are sent.
- Under tests, `config()` reads the real working directory and user directory, even through `run()`; leave it out of apps under test, or test the values through `env` or `run()` input.

## Custom sources

`config()` is built on [`ctx.bindInput(input, { source: "config", from })`](/docs/api/types#extensioncontext). An Extension that reads values from somewhere else can bind them with the same rank, `config` source, and deferred errors labeled by `from`.
