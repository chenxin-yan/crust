---
title: Search
description: Find the commands that match a task, for agents working with large CLIs.
---

`--llms` lists every visible command, which no longer fits an agent's context once a CLI has hundreds of them, such as one generated from an OpenAPI spec. `search()` adds a command that returns only the few that match a task.

## Usage

<include lang="ts" meta='title="cli.ts"'>
  ../../../../examples/modules/extensions/search.ts#usage
</include>

```sh
$ my-cli search "rotate an api key"
my-cli keys rotate  Rotate an API key
my-cli keys         Manage API keys
my-cli keys list    List API keys

$ my-cli search rotate an api key --json
[{"command":"my-cli keys rotate","description":"Rotate an API key","hasAction":true},{"command":"my-cli keys","description":"Manage API keys","hasAction":false},{"command":"my-cli keys list","description":"List API keys","hasAction":true}]
```

## `search <task...>`

Ranks every visible command against the words of the task and prints up to five matches, best first, one per line. The words may be quoted or not. Each match has:

- `command`: the command line without its arguments, such as `my-cli keys rotate`;
- `description`: the command's description, when it has one;
- `hasAction`: `false` for a command that only groups subcommands.

The index covers every visible command, including group commands and commands Extensions contribute, such as `search` itself. Hidden commands, and everything under them, are left out. A task that matches nothing prints `No command matches "<task>".` and returns `[]`; the exit code is 0 either way.

The command declares an [`.output()`](/docs/api/crust#outputschema) schema and returns the matches, so [`run()`](/docs/api/crust#runpath-input-options) gets them as the outcome's `result`, and with [`json()`](/docs/modules/extensions/json) `--json` prints only the JSON array:

<include lang="ts">../../../../examples/modules/extensions/search.ts#run</include>

`search()` also contributes a "Find a command" section, `my-cli search "<task>"`, to the root command's [documentation](/docs/guide/extensions#section-consumers). [`help()`](/docs/modules/extensions/help) and [`schema()`](/docs/modules/extensions/schema), when installed, render it in `--help` and `--llms`, so those point agents at it. An application that defines its own `search` command renames this one with `command`; the section names it too:

```ts
new Crust("my-cli").extend(search({ command: "find" }));
// $ my-cli find "rotate an api key"
```

A literal name keeps the command tree typed, so `app.run(["find"], …)` type-checks; a name typed `string` leaves it open.

## Ranking

Words are matched without letter case and split at camelCase and punctuation. A word counts most when it matches as written, less when only its singular form matches (`keys` matches `key`; `news` also matches `new`, below an exact `news`), and least when it only starts a longer word (`rot` matches `rotate`). Words in a command's name, path, and aliases have the highest base weight, words in its description less, and words in its argument and flag names and descriptions the least, all else equal; flags an Extension declares, such as `--help`, are left out. Ties keep the order of the command tree.

A word counts more the fewer commands it matches, so `for` or `a` in a long generated name weighs little next to a rare word such as `purge`, and a match counts more in a short name or description than in a long one. A command's score therefore depends on the other commands, and [MCP](/docs/modules/mcp#discovery)'s `search_tools`, which ranks tools the same way, can order two results differently.

To find a word rather than a task, filter `--llms` instead: `my-cli --llms | grep -i '^## .*purge'` prints the command headings containing `purge` (also `purged`), and `my-cli --llms | grep '^## ' | grep -iw purge` only those with the whole word.
