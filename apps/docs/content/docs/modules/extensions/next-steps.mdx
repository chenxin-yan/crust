## Usage

<include lang="ts" meta='title="cli.ts"'>
  ../../../../examples/modules/extensions/next-steps.ts
</include>

```sh
$ my-cli deploy prod
Deployed to prod
Next steps:
  Follow the logs:
    my-cli logs --env prod

$ MY_CLI_TOKEN= my-cli deploy prod
Error: Not logged in.
Next steps:
  Log in:
    my-cli login --sso
```

`nextSteps(options?)` provides `nextStepsContext`, a [Context](/docs/guide/contexts) named `next`. A command declares it with `.use(nextStepsContext)` and calls `(await ctx.next).add(command, input?, description?)` from its action:

- `command`: the command path below the application root, by canonical names, such as `["db", "migrate"]`; `[]` is the root command.
- `input`: arguments, flags, and `raw` tokens in the shape [`run()`](/docs/api/crust#runpath-input-options) takes them, such as `{ args: { env: "prod" }, flags: { force: true } }`.
- `description`: what the step is for, printed above its command line.

`options.onError(error)` returns recovery steps for a failed invocation, as `{ command, input?, description? }` objects, or `undefined` for none. It receives the thrown value as-is: match it yourself, for example with `instanceof`. `nextSteps()` never reads fields such as `name` or `message` to pick steps.

## Behavior

After the invocation completes or fails, `nextSteps()` prints a `Next steps:` block to stderr as plain text, whatever other Extensions are registered, including [`json()`](/docs/modules/extensions/json). On a failure, `onError` steps come first, then the steps the action added before it failed. In `execute()`, the block follows the error message. Nothing is printed when there are no steps, or when a flag handler such as `--help` took over.

Each step is rendered as a shell-quoted command line from the target command's [Command Snapshot](/docs/api/types#commandsnapshot): flags as `--name value` (`--name=value` when the value starts with `-`), `true` as `--name` and `false` as `--no-name`, `multiple` flag and variadic argument arrays as repeated values, `json` values as JSON, and positional arguments in declaration order, after `--` when one starts with `-`. Under [`run()`](/docs/api/crust#runpath-input-options) the block is captured in `outcome.stderr`.

Paths and input are checked when the block is printed. A step whose command does not exist, that names an unknown argument or flag, that gives a positional argument after an omitted earlier one, or whose `raw` tokens would fill a positional argument is skipped with a `nextSteps():` note on stderr. A throwing `onError` is reported the same way. Printing never changes the invocation's exit code or result.

## Limitations

Steps print from `postRun`, so they follow failures in the action, in validation, and in Context setup. Routing failures, such as an unknown command, argv syntax errors, such as a missing flag value, and invalid typed `run()` input fail before `postRun` runs, so no steps are printed for them; [`didYouMean()`](/docs/modules/extensions/did-you-mean) covers unknown commands.

A `false` value for a `noNegate` boolean flag has no command-line spelling and is left out.
