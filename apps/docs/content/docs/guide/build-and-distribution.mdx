Use `crust build` when your CLI is ready to run without its TypeScript source, then follow this path to an npm release.

```sh
crust build --target bun-linux-x64 --name my-cli
./dist/my-cli --help
crust build --package
crust publish --dry-run
crust publish
```

## Build for one runtime

```sh
crust build --runtime bun --target bun-linux-x64 --name my-cli
# ✓ Built successfully: .../dist/my-cli
```

Every build prints the runtime it resolved and where it came from, for example `Runtime: node (inferred from @types/node)`. The order is:

1. `--runtime bun|deno|node`
2. `"crust": { "runtime": "deno" }` in `package.json`
3. Inference: a `deno.json` or `deno.jsonc` in the project selects Deno; `@types/node` in `dependencies` or `devDependencies` without `@types/bun` selects Node
4. Bun

Lockfiles are not a signal, because the package manager that installed your dependencies says nothing about the runtime your CLI runs on. `--runtime node` writes an executable JavaScript bundle at `dist/<name>.js`.

| Runtime | Output                                     | Needed by the user |
| ------- | ------------------------------------------ | ------------------ |
| Bun     | Standalone executable                      | Nothing            |
| Deno    | Standalone executable with all permissions | Nothing            |
| Node    | Executable JavaScript bundle               | Node               |

Use `--entry` to replace `src/cli.ts`, `--outfile` for one exact output path, or `--name` for the derived filename. See all flags in the [`crust build` options](/docs/modules/crust#crust-build-options).

## Build more than one target

```sh
crust build --target bun-linux-x64 --target bun-darwin-arm64 --name my-cli
# dist/cli, dist/cli.cmd, and one my-cli-* binary per target
```

Repeat `--target` for the platforms you ship; omitting it builds every supported Bun or Deno target. A multi-target build writes platform binaries plus `cli` and `cli.cmd` resolver scripts, so `package.json` can point `bin` at `dist/cli`.

| Bun target                                   | Deno target                                             | Platform alias                       |
| -------------------------------------------- | ------------------------------------------------------- | ------------------------------------ |
| `bun-linux-x64`, `bun-linux-arm64`           | `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` | `linux-x64`, `linux-arm64`           |
| `bun-linux-x64-musl`, `bun-linux-arm64-musl` | none                                                    | `linux-x64-musl`, `linux-arm64-musl` |
| `bun-darwin-x64`, `bun-darwin-arm64`         | `x86_64-apple-darwin`, `aarch64-apple-darwin`           | `darwin-x64`, `darwin-arm64`         |
| `bun-windows-x64`, `bun-windows-arm64`       | `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`     | `windows-x64`, `windows-arm64`       |

### Linux glibc and musl

The plain Linux targets link against glibc and do not start on musl-based distributions such as Alpine; the `-musl` targets cover those. Both resolver scripts and the npm launcher detect the host C library and pick the matching binary, so shipping both is enough for the default `node:alpine` images.

<Callout type="warn">
  Bun's musl executables still load `libstdc++` and `libgcc` dynamically. A bare Alpine image needs
  `apk add libstdc++ libgcc`; `node:alpine` already includes them.
</Callout>

## Add Bun bundler plugins

```sh
crust build --bun-plugin ./build/plugin.ts
```

`--bun-plugin` applies a [Bun bundler plugin](https://bun.com/docs/bundler/plugins) to Bun and Node builds; repeat it for several. The specifier is imported from your project (a bare name resolves from `node_modules`, a path from the project root) and must default-export the plugin. Deno builds reject the flag.

Validation runs the entry under Bun's runtime without bundler plugins, so a plugin that transforms sources at import time needs a matching runtime plugin in `bunfig.toml` `preload`; otherwise pass `--no-validate`.

## Prepare Extension artifacts

```sh
crust build
# Preparing Command Snapshot... (excerpt)
#   crust:man  1 file  man/my-cli.1
```

Before compilation, the build materializes and validates the command tree and runs Extension build hooks. The entry module's top-level code runs during this step, but Command Actions and code after `await app.execute()` do not.

Use `--no-validate` only when preparation cannot run; it skips Extension build hooks and keeps their artifact directories out of `--package` staging, as described in [Extension artifacts](/docs/modules/crust#extension-artifacts).

## Stage npm packages

```sh
crust build --package --target bun-linux-x64 --target bun-darwin-arm64
# Manifest: .../dist/npm/manifest.json (excerpt)
```

`--package` stages the npm packages for the resolved runtime. It requires `name` and `version` in `package.json`, and the shape follows from the runtime:

| Runtime | Staged packages                                                                                             |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| Bun     | Root package with a Node launcher plus one platform package per target                                      |
| Deno    | Same layout as Bun; Linux platform packages are glibc only                                                  |
| Node    | Root package only: `bin/<command>.js` is the self-contained bundle, so no launcher and no platform packages |

| Path                     | Contains                                                         |
| ------------------------ | ---------------------------------------------------------------- |
| `dist/npm/root/`         | Root `package.json`, launcher or bundle, artifacts, and includes |
| `dist/npm/<platform>/`   | One platform `package.json` and binary (Bun and Deno)            |
| `dist/npm/manifest.json` | Staged package list and publish order                            |

The staged `package.json` files are generated, not copied: they take `name`, `version`, and npm metadata (`description`, `license`, `author`, `repository`, `keywords`, `engines`, and similar) from your `package.json`, and a Bun or Deno root package lists the platform packages as `optionalDependencies`. Your own `dependencies` and `devDependencies` are not carried over, because the binaries and the Node bundle already inline them, so keep the usual split in your project: Crust packages your code imports in `dependencies`, `@crustjs/crust` in `devDependencies`. A Node root package therefore has no dependency fields at all.

Platform package names append the platform alias, such as `my-cli-linux-x64` or `@scope/my-cli-linux-x64`; use `--stage-dir` to change the staging directory. Linux packages also carry an npm `libc` field (`glibc` or `musl`), so package managers download only the platform package that matches the host.

### Ship extra directories with `crust.include`

```json title="package.json"
{
  "crust": { "include": ["templates"] }
}
```

`crust.include` lists directories, relative to the project root, that `--package` copies into the staged root package (and adds to its `files`) and into each platform package's `bin/`, exactly like [Extension artifacts](/docs/modules/crust#extension-artifacts). A Node bundle at `root/bin/my-cli.js` can then read them with `new URL("../templates/", import.meta.url)`. Plain `crust build` does not copy them; they are a packaging concern only.

## Publishing with `crust publish`

```sh
crust publish --dry-run
# Publish order: linux-x64 -> darwin-arm64 -> root (excerpt)
crust publish
```

The dry run prints the order and commands without publishing. The publish command reads the staged manifest, verifies package metadata, publishes platform packages before the root with `npm publish` (a Node manifest publishes just `root`), and stops at the first failure; see its [options](/docs/modules/crust#crust-publish-options). Because npm does the upload, [trusted publishing](https://docs.npmjs.com/trusted-publishers) works from GitHub Actions: give the job `id-token: write` and configure a trusted publisher for the root package and each platform package.

```sh tab="npm" tab-group="package-manager"
npm install -g my-cli
my-cli --help
```

```sh tab="pnpm"
pnpm add -g my-cli
my-cli --help
```

```sh tab="yarn"
yarn dlx my-cli --help
```

```sh tab="bun"
bun add -g my-cli
my-cli --help
```

Users install the root package; for Bun and Deno builds the package manager pulls only the platform package for their machine, and for Node builds the root package is the whole CLI. Yarn 2+ has no global install, so Yarn users run the CLI once with `yarn dlx` or add it to a project and run it with `yarn my-cli`.

## Environment variables

<include lang="ts">../../../examples/guide/build.ts#runtime-secret</include>

Read secrets and deployment configuration from the runtime environment; Crust adds no abstraction, and [Bun environment variables](https://bun.sh/docs/runtime/environment-variables) covers Bun's `.env` loading and precedence.

### Build-time constants

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/guide/build.ts
</include>

```sh
cat > .env.production <<'EOF'
PUBLIC_API_ORIGIN=https://api.example.com
API_TOKEN=private-value
EOF
crust build --env-file .env.production --target bun-linux-x64 --name deploy
env -u PUBLIC_API_ORIGIN -u API_TOKEN ./dist/deploy origin
# https://api.example.com
grep -a -o 'private-value' dist/deploy || echo 'private-value: not embedded'
# private-value: not embedded
```

For Bun and Node builds, `--env-file` passes explicit files to the compiler, embeds only `PUBLIC_*` values, and reaches snapshot preparation.

<Callout type="warn">
  Embedded `PUBLIC_*` values are visible in the output. Keep secrets in runtime environment
  variables without that prefix.
</Callout>

Deno builds reject `--env-file`, so load their configuration at runtime instead.

### Runtime autoloading

Bun executables built by `crust build` autoload `.env` from the directory they start in, but not its `bunfig.toml`.
