`crust build` turns your TypeScript entry into one of two artifacts:

- a **runtime package**: JavaScript for the runtime the user has installed;
- **standalone executables**: one per platform, with the runtime embedded.

The examples below use the `my-cli` command from [Quick Start](/docs/quick-start).

**Building does not commit you to npm.** [`crust publish`](#publish-with-crust-publish) handles npm; [other channels](#custom-distribution) such as release downloads, Homebrew, or Scoop use the built binaries with your own tooling. Running a binary directly needs no Node.js or Bun; only the generated npm launcher needs Node.js.

## Set up `package.json`

Scaffolded projects are already set up. For an existing project, install the tool:

```npm
npm install -D @crustjs/crust
```

Merge these fields into your `package.json`, keeping your dependencies:

```json title="package.json"
{
  "name": "my-cli",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "bin": { "my-cli": "src/cli.ts" },
  "crust": { "runtime": "bun", "artifact": "binary" },
  "scripts": {
    "build": "crust build",
    "start": "node .crust/root/bin/my-cli.js",
    "release": "crust publish"
  }
}
```

- **`bin`:** the key must match your root command, `new Crust("my-cli")`.
- **`private`:** keeps the source project from being published. Crust generates separate publishable packages in `.crust/`.
- **`crust.runtime`:** the runtime your CLI runs on. [Without it](/docs/modules/crust#packagejson-configuration), Crust infers one.
- **`crust.artifact`:** required; what the build distributes, independent of the runtime. `--artifact package` or `--artifact binary` overrides it for one build.

| Runtime | `"artifact": "package"`                         | `"artifact": "binary"`                                    |
| ------- | ----------------------------------------------- | --------------------------------------------------------- |
| `bun`   | Bun-targeted JavaScript; users need Bun         | Standalone executable per platform, with Bun embedded     |
| `node`  | Node.js-targeted JavaScript; users need Node.js | Standalone executable per platform, with Node.js embedded |

Runtime packages embed no runtime: a Bun package starts with `#!/usr/bin/env bun`, however it is installed. Either artifact also gets npm metadata, even if you never publish to npm; see [choose an artifact to ship](#choose-an-artifact-to-ship).

The commands below assume Node.js and Bun are installed. Node.js binaries also need a `node` on `PATH` that [tsdown can build with](#nodejs-binaries). See [tooling requirements](/docs/modules/crust#install) and [runtime versions](/docs/guide/runtime-support#run-the-same-cli).

## Build

For a quick local binary, build only for your machine:

```sh
npm run build -- --target host
```

Runtime packages have no targets: run `npm run build` without `--target`.

Each build replaces `.crust/`; add it to `.gitignore`. On Linux x64 with Bun binaries:

```text
.crust/
├── manifest.json                       # package paths and publish order
├── root/                               # root package for npm distribution
│   ├── package.json
│   └── bin/my-cli.js                    # npm launcher; needs Node.js
└── linux-x64/
    ├── package.json
    └── bin/my-cli-bun-linux-x64         # standalone executable
```

Runtime packages have no platform directories; `root/bin/my-cli.js` is the bundle itself. See [staged `package.json` files](/docs/modules/crust#staged-packagejson-files) for the generated metadata, and [`crust build` options](/docs/modules/crust#crust-build-options) for every flag.

### Choose release targets

```sh
# Build all supported targets, or the subset in crust.targets
npm run build

# Override the subset for this build (Bun example)
npm run build -- --target bun-linux-x64 --target bun-darwin-arm64
```

Publish every platform you intend to support, not just `host`. Keep a release subset in [`crust.targets`](/docs/modules/crust#packagejson-configuration). See [supported targets](/docs/modules/crust#supported-targets), including musl targets for Alpine Linux.

### Binary runtime version

Every binary embeds the runtime version of the compiler that builds it:

- **Bun:** the first `bun` on `PATH`, else the Bun inside the `crust` executable.
- **Node.js:** the `node` on `PATH`.

The build prints it as `Compiler:` and records it as `embeddedRuntimeVersion` in `.crust/manifest.json`, for cross-platform targets too.

If `package.json` declares `engines.bun` or `engines.node`, that compiler must satisfy the range, or the build fails before replacing `.crust/`. It also fails if the compiler's `--version` hangs.

<Callout>
  Crust never installs or upgrades a compiler, even for an exact `engines` version. Pin one with
  your version manager or CI. Runtime packages embed no runtime; their `engines` only tells users
  what they need.
</Callout>

### Bun binary startup

Bun binaries are precompiled to [bytecode](https://bun.com/docs/compiler/bytecode) by default, so they start without parsing their JavaScript. Pass `--no-bytecode` to opt out.

- Cross-compiled targets need Bun 1.4.1 or later to embed bytecode; older versions build them without it.
- `--bytecode` is rejected for runtime packages, which run on whatever Bun the user has, and for Node.js binaries, which use a different engine.

### Choose an artifact to ship

A binary installed from the root npm package runs through the launcher, `root/bin/my-cli.js`. This small Node.js script finds the platform package npm installed for the user's OS, CPU, and C library, then replaces itself with that binary (Windows starts it as a child process). Every run pays for one extra Node.js start, roughly 20 ms on Linux x64.

| Situation                                               | Ship                                                                                                                                                                                                              |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Users install from npm; your CLI needs no Bun-only APIs | A Node.js runtime package (`"runtime": "node", "artifact": "package"`). No launcher, often faster to start than a launched binary, and kilobytes instead of a ~100 MB binary.                                     |
| Users want a binary                                     | [Release downloads](#release-downloads) or [Homebrew, Scoop, and other installers](#homebrew-scoop-and-other-installers): no launcher, no Node.js. On npm, users can install a platform package directly (below). |
| Your CLI needs Bun's runtime and users may not have Bun | Binaries through the root npm package. Users need only Node.js `>=24` and accept the launcher's startup cost.                                                                                                     |

A platform package, such as `npm install -g my-cli-linux-x64`, runs the binary without the launcher:

- It is [named](/docs/modules/crust#staged-packagejson-files) after your package plus the [platform alias](/docs/modules/crust#supported-targets).
- Its `bin` points straight at the executable, and its `os`, `cpu`, and `libc` fields make npm reject the wrong platform.
- Users pick it themselves, such as `my-cli-linux-x64-musl` on Alpine, and install either it or the root package: both provide the same command.

### Node.js binaries

Crust builds Node.js binaries with [tsdown's executable support](https://tsdown.dev/options/exe) (Node.js single executable applications). `@crustjs/crust` ships `tsdown` and `@tsdown/exe` as optional dependencies, so no global tsdown is needed.

**Build machine requirements** (not your users'):

- **tsdown installed:** package managers skip optional dependencies when they are disabled or the installing Node.js is outside tsdown's engines. The build then reports the missing backend. Reinstall `@crustjs/crust` with optional dependencies under the Node.js you build with. A project's own tsdown is never used.
- **A qualifying `node` on `PATH`:** it runs the build and is embedded, so it must satisfy your `engines.node`, tsdown's engines, and tsdown's executable minimum. With the bundled tsdown 0.23, that means Node.js 26 or later. The build names the requirement that fails.
- **Bun:** each command is first bundled by Bun, even with `--no-validate`.
- **Unpacking tools:** for each target, tsdown downloads the official Node.js archive of the same version once, verifies its checksum, and caches it. Archives unpack with the host's `tar`, plus `xz` for Linux targets under GNU tar, or `unzip` for Windows targets on non-Windows hosts. On Windows, put the native `tar` before Git Bash's GNU tar on `PATH`. Cached targets need none of these tools.

All of this is checked, and every archive downloaded, before `.crust/` is replaced, so a failure keeps the previous build.

**Your users:** running the executable needs no Node.js, so platform packages omit `engines.node`. The root package declares the launcher's own `>=24` instead, unless it also publishes library `exports`, which keep your range. Your `engines.node` can stay as wide as you like, such as `>=24`, as long as the build machine satisfies it.

**What gets bundled:** each command is its own executable, bundled like a Node.js runtime package, with all application dependencies and the same `PUBLIC_*` [env file values](#environment-variables). `import.meta.main` and `require.main === module` are true only in the command's entry.

- A build fails if any import other than a Node.js built-in would be left unbundled.
- Native addons, computed imports, `crust.bunPlugins`, and `crust.external` are not supported.
- macOS executables are code-signed only when built on macOS. Sign cross-built ones yourself before running them on Apple silicon.

**V8 code cache:** when the `node` on `PATH` is the official nodejs.org binary for the host's own target (as most version managers and `actions/setup-node` install), Crust also embeds a [V8 code cache](https://nodejs.org/api/single-executable-applications.html#v8-code-cache-support), so the command starts without compiling its JavaScript.

- Other targets, distribution or Homebrew builds of Node.js, and builds with `NODE_OPTIONS` set get no cache.
- The build prints `Code cache: on`, or `off` with a reason such as `cross-built`; mixed targets are listed per group, as in `on for linux-x64; off for darwin-arm64 (cross-built)`.
- Running a binary with V8 flags such as `--jitless` in `NODE_OPTIONS` makes Node.js reject the cache and print a warning.

## Run locally

Run the entry you intend to distribute before publishing:

```sh
# npm's launcher route; requires Node.js:
npm run start -- --help
# Equivalent with the configuration above:
node .crust/root/bin/my-cli.js --help

# Direct executable for the Linux x64 Bun example above; no installed JS runtime:
./.crust/linux-x64/bin/my-cli-bun-linux-x64 --help
```

- The executable's name depends on your command and target; Windows executables end in `.exe`.
- The launcher finds its executables in the sibling platform directories.
- A runtime package's bundle runs directly: start a Bun package with `bun .crust/root/bin/my-cli.js`.
- To test through `npm link`, link from `.crust/root`. Linking from the project root runs the source entry instead.

## Publish with `crust publish`

Use a package name you own and a new version, then build your release targets:

```sh
npm run build
npm run release -- --dry-run
# Publish order: ... -> root

npm login
npm run release
```

- `--dry-run` validates staged metadata and prints the plan **without contacting the registry**.
- A real publish uses npm, uploads platform packages before the root, and stops on failure.
- Rerun to resume: existing `name@version` pairs are skipped, never overwritten or re-tagged.

For a scoped public package, add `"publishConfig": { "access": "public" }` to your `package.json` before building. Users install only the root package:

```sh
npm install -g my-cli
my-cli --help
```

For binaries, the package manager selects the matching platform dependency. See the [npm installation caveat](/docs/modules/crust#npm-installation-caveat) for an affected npm version and a verified alternative.

### Publishing from CI

For GitHub Actions [trusted publishing](https://docs.npmjs.com/trusted-publishers), configure a trusted publisher on npm for **the root and every platform package**, then give the release job:

```yaml title="Workflow permissions"
permissions:
  contents: read
  id-token: write
```

After installing dependencies and building the release targets, run `npm run release`; do not run `npm login` in CI.

npm runs inside each staged package, so it does not read the project's `.npmrc`. To use a credentials file, select it explicitly, and keep it out of version control:

```sh
NPM_CONFIG_USERCONFIG="$PWD/.npmrc" npm run release
```

Pass `--registry` or `--tag` through the release script as needed; see [publish options and registry precedence](/docs/modules/crust#crust-publish-options).

## Custom distribution

For standalone binaries, ship the contents of `.crust/<platform>/bin/`: each command's executable **and its adjacent data directories**. No npm launcher or manifest is needed. Users need a compatible OS, architecture, and system libraries, plus any external tools your CLI calls.

### Release downloads

With `crust.runtime` set to `"bun"`, build and archive a Linux x64/glibc release:

```sh
npm run build -- --artifact binary --target bun-linux-x64
tar -czf my-cli-linux-x64.tar.gz -C .crust/linux-x64/bin .
sha256sum my-cli-linux-x64.tar.gz
```

Upload the archive and its checksum to your release host, such as GitHub Releases. Users verify the checksum, extract the matching archive, and run the executable directly:

```sh
mkdir my-cli
tar -xzf my-cli-linux-x64.tar.gz -C my-cli
./my-cli/my-cli-bun-linux-x64 --help
```

- Create one archive per supported platform, with your license and other required files.
- Node.js binaries work the same with their [target names](/docs/modules/crust#supported-targets) and filenames.
- Preserve executable permissions, keep shipped directories next to the executable, and sign for each platform as required before archiving.

### Homebrew, Scoop, and other installers

These channels use the same release archives:

1. Build and host an archive for each platform you support.
2. Create a [Homebrew formula](https://docs.brew.sh/Formula-Cookbook) or [Scoop manifest](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifests) that selects the matching archive and verifies its checksum.
3. Install the executable together with its adjacent data directories, then expose the command with the installer's link or shim mechanism. Do not move the executable away from its data directories.
4. Test the installed command from an unrelated working directory, including commands that read shipped assets.

The installer selects the platform instead of the npm launcher, so **the installed binary does not need Node.js**. Crust does not generate formulas or manifests or publish to these channels. You can offer npm and direct-binary installation for the same build.

Runtime packages can be archived too, but must keep the layout of `.crust/root/` and still need their runtime. Copy any output you keep before the next build replaces `.crust/`.

## Customize the build

### Ship extra directories with `crust.include`

```json title="package.json (partial)"
{
  "crust": { "include": ["templates"] }
}
```

Create `templates/` in your project, then build. Read the shipped copy with [`resolveArtifactDir("templates")`](/docs/api/crust#resolveartifactdirname) from `@crustjs/core`, not a path relative to the working directory. It works from the staged tree, an npm install, or a standalone executable.

Extensions can generate their own directories during build preparation. Preparation runs your entry module's top-level code, but not Command Actions. `--no-validate` skips preparation **and those directories**; see [Extension artifacts](/docs/modules/crust#extension-artifacts).

### Keep dependencies external

Runtime packages bundle every dependency by default. `crust.external` leaves the named packages out of the bundle and adds them to the staged root package's `dependencies`, with the ranges from your `dependencies`, so npm installs them beside the bundle.

```json title="package.json (partial)"
{
  "dependencies": { "better-sqlite3": "^12.0.0", "typescript": "7.0.2" },
  "crust": {
    "runtime": "node",
    "artifact": "package",
    "external": ["better-sqlite3", "typescript"]
  }
}
```

Use it for packages the CLI needs on disk at runtime:

- native addons such as `better-sqlite3`, whose compiled binary cannot be bundled;
- packages the CLI spawns or reads files from, such as running `typescript`'s `tsc`, even if never imported;
- very large dependencies you would rather install than bundle.

Rules:

- Node and Bun runtime packages only; binaries reject it.
- Each entry must be a `dependencies` key with a publishable range. `@crustjs/*` packages must stay bundled; see [`package.json` configuration](/docs/modules/crust#packagejson-configuration).
- Validation runs each entry under Bun with your project's dependencies, so externals must be installed when you build. An entry that does not run a Crust app needs `--no-validate`.

Limits:

- A named ESM import of a CommonJS external, such as `import { open } from "some-cjs-package"`, may fail on Node.js. Use the default import (`import pkg from "some-cjs-package"`) or `require()`.
- A third-party package that depends on `@crustjs/core` should stay bundled; as an external it would load its own copy of core.

### Environment variables

Keep secrets in runtime variables; use `PUBLIC_*` only for values safe to embed. This entry reads one of each:

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/guide/build.ts
</include>

```dotenv title=".env.production"
PUBLIC_API_ORIGIN=https://api.example.com
```

Pass env files with `--env-file` (repeatable) for either artifact. Here with Bun binaries behind the Node launcher:

```sh
npm run build -- --env-file .env.production
node .crust/root/bin/my-cli.js origin
# https://api.example.com

API_TOKEN=your-token node .crust/root/bin/my-cli.js
# Deploying
```

<Callout type="warn">
  Only `PUBLIC_*` variables are embedded from env files; anyone with the output can read them.
</Callout>

Bun executables also load `.env` from their working directory at startup, but not that directory's `bunfig.toml`.

### Add Bun bundler plugins

```json title="package.json (partial)"
{
  "crust": { "bunPlugins": ["@opentui/solid/bun-plugin"] }
}
```

Plugins apply to Bun binaries and to Bun and Node.js runtime packages, not to build preparation; Node.js binaries reject them. If entry imports need the same transform during preparation, also register a runtime plugin in `bunfig.toml` `preload`. See [plugin configuration](/docs/modules/crust#packagejson-configuration) and the [TUI setup](/docs/modules/tui).

### Programmatic builds

```ts title="scripts/build.ts"
import { build } from "@crustjs/crust";

const result = await build({
  artifact: "binary", // overrides crust.artifact
  onLog: (line) => console.log(line),
});

console.log(result.stageDir); // <cwd>/.crust
```

`build()` uses the same configuration as the CLI, returns artifact paths and Extension reports, and throws on failure. Run it with Bun, or with Node.js and `bun` on `PATH`; Node.js binaries also need a qualifying `node` on `PATH`. See the [options and result types](/docs/modules/crust#programmatic-api).
