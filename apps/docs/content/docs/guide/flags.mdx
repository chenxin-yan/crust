---
title: Flags
description: Define typed named inputs, aliases, repeated values, and shared flag capabilities.
---

`.flags(...defs)` takes named flag definitions — values from `defineFlag(name, def)` or inline literals carrying `name`:

```ts
import { Crust } from "@crustjs/core";

const command = new Crust("serve")
  .flags(
    { name: "port", type: "number", default: 3000, short: "p" },
    { name: "verbose", type: "boolean", short: "v" },
  )
  .action(({ flags, stdout }) => stdout(`${flags.port} ${flags.verbose ?? false}`));
```

See [`FlagDef`](/docs/api/types#flagdef) for the complete definition.

Repeated `.flags()` calls accumulate: `.flags(a).flags(b)` defines both flags. A statically known name, short form, or alias collision with an earlier call or an existing Context-owned flag fails typecheck with `FIX_ALIAS_COLLISION` at the call that introduces it.

Builder chaining follows the same accumulation rule for `.flags()`, `.args()`, `.provide()`, `.add()`, and root-only `.extend()` (except duplicate `ExtensionId`s, where `.extend()` keeps only the last registration). Definition correctness is enforced by TypeScript rather than repeated at runtime.

## Aliases and negation

`short` defines one single-character form. `aliases` adds other short or long forms:

```ts
.flags({ name: "output", type: "path", short: "o", aliases: ["out"] })
```

Boolean flags support `--no-<spelling>` negation for the canonical name and every long alias — an alias is a full synonym, so `--no-out` behaves like `--no-output`. Set `noNegate: true` to reject negation entirely (a `PARSE` error for any spelling). Boolean flags do not accept `--name=true`. Flag names, short forms, and aliases must be unique, and the `no-` prefix is reserved. TypeScript reports statically known violations as `FIX_ALIAS_COLLISION` or `FIX_NO_PREFIX`.

## Required and defaulted values

```ts
.flags(
  { name: "token", type: "string", required: true },
  { name: "format", type: "string", default: "json" },
)
```

Both values are non-optional in the Command Action. Other flags include `undefined` in their inferred type.

## Repeated values

```ts
.flags({ name: "target", type: "string", multiple: true, short: "t" })
```

`--target linux --target darwin` produces `string[]`. Repeated boolean flags also collect booleans when `multiple: true`.

## Choices

```ts
.flags({ name: "target", type: "string", choices: ["bun", "node"] })
```

Choices are supported on string flags. When `choices` and `default` are literals, TypeScript reports `FIX_DEFAULT_CHOICE` if the default falls outside the set. Widened `string[]` choices opt out of that compile-time comparison. An argv value outside the choices is a `PARSE` error during invocation.

When the choices list is a literal tuple (an inline array as above, or a variable declared `as const`), the flag's inferred type narrows to the union of those literals — `"bun" | "node"` here instead of `string`. A widened `string[]` variable keeps the type as plain `string`.

## Reusing flag definitions

Flags declared with `.flags()` belong only to that command. Define a descriptor once and attach it to each command that parses the value directly:

```ts
import { Crust, defineCommand, defineFlag } from "@crustjs/core";

const format = defineFlag("format", { type: "string", default: "json" });
const print = defineCommand("print", (command) => command.flags(format));
const inspect = defineCommand("inspect", (command) => command.flags(format));

const app = new Crust("app").add(print, inspect);
```

This keeps one source of truth without adding the flag to commands that do not use it.

## Propagating flags with Contexts

When one flag configures shared behavior for a command subtree, let a Context own and consume it. Actions depend on the derived capability rather than the raw flag:

```ts
import { Crust, defineCommand, defineContext, defineFlag } from "@crustjs/core";

const verbose = defineFlag("verbose", { type: "boolean" });
const logging = defineContext("logging", { flags: [verbose] }, ({ flags, stderr }) => ({
  debug(message: string) {
    if (flags.verbose) stderr(message);
  },
}));

const deploy = defineCommand("deploy", { uses: [logging] }, (command) =>
  command.action(async ({ ctx }) => (await ctx.logging).debug("deploying")),
);

const app = new Crust("app").provide(logging()).add(deploy);
```

The Context declares, parses, and consumes `--verbose`, then wraps the invocation's injected `stderr` as behavior. Actions call the logging capability without re-checking the flag. Renaming the flag or deriving log levels later changes the Context rather than every action.

Context-owned flags are parsed and shown in help at the provider and later-added descendants. They can appear before, between, or after subcommand names. Command-local flags do not propagate: writing one before a subcommand name is a `PARSE` error, because the routed subcommand cannot parse it. See [Contexts: Owned flags](/docs/guide/contexts#owned-flags).

If an action needs the raw value, expose it from the owning Context as part of that capability. Cross-command dependencies are always Context capabilities; raw flags are never injected into an added action's types.

## Standard Schemas

For a schema-backed flag, `type` controls token grammar only: `"string"` consumes a token and `"boolean"` does not. The schema owns the resulting value.

```ts
import { z } from "zod";

new Crust("serve")
  .flags({ name: "port", type: "string", schema: z.coerce.number().int() })
  .action(({ flags }) => {
    flags.port; // number
  });
```

A schema cannot be combined with core value options — see [Schema-backed definitions](/docs/guide/types#schema-backed-definitions) for the full rule.

## Unsupported flag grammars

Crust's parser is built on `node:util.parseArgs`, and three grammars found in some other CLI libraries are intentionally **not supported**. They conflict with `parseArgs` token rules or make flag/positional boundaries ambiguous. If your app needs one of them, rewrite argv app-side before `execute()`.

### Greedy multi-value flags

Variadic options that consume every following token until the next flag (`--locales en fr de`) are not supported. Crust `multiple` flags require one option token per value — `--locales en --locales fr --locales de`. An unrepeated trailing value becomes an unmatched positional.

### Optional-valued flags

A Crust flag is either `boolean` or value-taking — there is no option that accepts both `--tag` and `--tag v1.2`, because whether the next token is the flag's value or a positional would depend on runtime lookahead. Split it into a boolean flag plus a value-taking flag (e.g. `--tag` and `--tag-name v1.2`).

### Separated dash-leading values

`--timeout -5` is rejected by `parseArgs` as ambiguous (`-5` looks like a flag). Use the `=` form: `--timeout=-5`.
