An agent runs your CLI the way a script does: it passes argv, reads stdout and stderr, and checks the exit code. It has no TTY to answer prompts and no eyes for colors or tables, and it pays for every token of output it reads. A CLI works well for agents when its input and output have a documented shape, it describes itself, and it fails loudly instead of waiting or guessing.

Crust adds none of this by default. Each piece below is an opt-in Extension or command declaration, and each section links to its reference page. Register the agent-facing Extensions on the root, in any order:

## How agents use your CLI

An agent runs commands in one of two ways: from a shell, with argv, `--input`, `--json`, and exit codes, or as [MCP](#mcp) tool calls. From a shell, it finds commands on demand with `--help`, `--llms`, and `schema <path>`, or ahead of time from an installed [skill](#skills); either way it then runs the same CLI, so `json()`, `input()`, `confirm()`, and `nextSteps()` serve both.

| Path          | Fits                                                                              |
| ------------- | --------------------------------------------------------------------------------- |
| Shell         | Any coding agent, since every one has a shell; the foundation the others build on |
| Shell + skill | Agents that load skills; the skill saves the discovery calls                      |
| MCP           | Clients that call tools instead of running a shell                                |

Skills and MCP each add one `.extend()`, and every path reads the same command snapshot, so a command declared once reaches all of them.

## Structured input

[`input()`](/docs/modules/extensions/input) adds `--input`, which takes every argument and flag as one JSON object, inline, from a file (`@path`), or from stdin (`-`). An agent writes one JSON object instead of quoting and ordering argv tokens:

```sh
$ my-cli deploy --input '{"target":"staging","release":"v2"}'
Deploying v2 to staging
Next steps:
  Watch the rollout:
    my-cli status staging
```

The object is converted and validated exactly like argv, and arguments and flags given on argv win over its keys. It has the same shape `schema` describes and the [MCP](#mcp) server accepts.

## JSON output

Write for people with `stdout(text)` and return data for programs. [`json()`](/docs/modules/extensions/json) adds `--json`, which prints the Command Action's return value as one line of JSON on stdout and moves the action's and Contexts' `stdout()` writes to stderr:

```sh
$ my-cli deploy staging --json
Deploying latest to staging                              # stderr
{"target":"staging","release":"latest","dryRun":false}   # stdout
Next steps:                                              # stderr, see below
  Watch the rollout:
    my-cli status staging
```

Failures become one line of JSON on stderr: [`CrustError`](/docs/api/errors)'s `toJSON()`, or `{ "message" }` for any other error. Failures before flags are bound, such as an unknown flag, still print Core's plain `Error:` line (see [`json()` limitations](/docs/modules/extensions/json#limitations)). Exit codes don't change, so an agent still checks them first. Make the message itself actionable; see [error handling](/docs/guide/error-handling).

One declaration does three jobs: TypeScript checks the action's return value against the schema, Crust validates it at runtime (a mismatch fails with the `OUTPUT` code instead of printing a wrong shape), and, when the schema library can produce JSON Schema, it reaches `schema`, MCP, and skills. Code that calls [`app.run()`](/docs/api/crust#runpath-input-options) gets `outcome.result` typed as the schema's output.

## Streaming

A long-running command can report progress as data. Write its action as an [async generator](/docs/guide/commands#stream-events): each `yield` is an event and the `return` value is the result.

<include lang="ts">../../../examples/guide/agents.ts#status</include>

People see only what the action writes. With `--json`, [`json()` streams NDJSON](/docs/modules/extensions/json#generator-actions) that ends with one result or error line:

```sh
$ my-cli status prod --json
{"type":"event","data":{"step":"build"}}
{"type":"event","data":{"step":"ship"}}
{"type":"result","data":{"target":"prod","healthy":true}}
```

A cancelled invocation (exit code 130), or a failure another Extension's `onError` hook claims, ends the stream without that line (see [`json()` limitations](/docs/modules/extensions/json#limitations)), so check the exit status rather than waiting for it.

The same events reach `run()`'s `onEvent` callback. Under MCP, each yield sends a [progress notification](/docs/modules/mcp#progress) when the client asks for progress; it carries a count, and a string event becomes its message.

## Discovery

An agent learns a CLI from what it prints about itself, so write `description`s for commands, arguments, and flags: every surface below reads them.

| Surface                                                            | When it fits                                                                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `--help` from [`help()`](/docs/modules/extensions/help)            | One command, for people and agents                                                                                          |
| `--llms` from [`schema()`](/docs/modules/extensions/schema)        | The whole CLI in compact Markdown, documentation sections included; an agent's first call                                   |
| `schema <path>` from [`schema()`](/docs/modules/extensions/schema) | One command's `input` and `output` JSON Schema, before building `--input` or parsing `--json`, or for code generation       |
| [Skills](#skills)                                                  | The same information, installed ahead of time into an agent's skill directory; the agent still runs the CLI                 |
| [MCP](#mcp)                                                        | Tools for clients that call tools instead of a shell, with the same input schema and, where MCP can carry it, output schema |

They all read the same command snapshot (descriptions, arguments and flags, `.output()`, sections), so declaring something once updates every surface. [How agents use your CLI](#how-agents-use-your-cli) says which path fits which agent.

```sh
$ my-cli schema deploy
{"input":{"type":"object","properties":{"target":{"type":"string","enum":["staging","prod"]},…},"required":["target"]},"output":{…}}
```

`json()` and `input()` document themselves in root help, with "JSON output" and "JSON input" sections. Document your CLI's own conventions an agent needs, such as exit codes and environment variables, with [documentation sections](/docs/guide/commands#documentation-sections).

## Dry run

A command that can preview declares its own `dry-run` flag and branches on it, as `deploy` does above. It returns the preview before it asks for [confirmation](#confirmation), so a dry run never prompts. Commands without the flag reject `--dry-run` as an unknown flag instead of running for real:

```sh
$ my-cli deploy prod --dry-run
Would deploy latest to prod
```

## Confirmation

Ask before a change that is hard to undo, without stalling an agent on a prompt. With [`confirm()`](/docs/modules/extensions/confirm), a command that `.use(confirm)` awaits `ctx.confirm` for the function, then awaits it with the message before the change, as `deploy` does for `prod`. `--yes`, or `"yes": true` in `--input`, confirms up front; on a terminal, the user answers a yes/no prompt; without a TTY, the command fails with `ConfirmationRequiredError` instead of waiting:

```sh
$ my-cli deploy prod < /dev/null
Error: Confirmation required: Deploy latest to prod? Pass --yes to confirm.
$ my-cli deploy prod --yes
Deploying latest to prod
Next steps:
  Watch the rollout:
    my-cli status prod
```

`.use(confirm)` and `.use(nextSteps)` take the Extension itself: [using an Extension](/docs/guide/extensions#use-an-extensions-contexts-from-a-command) uses the Contexts it provides, and the app must `.extend()` it.

## Next steps

Tell the agent what to run next instead of leaving it to guess. With [`nextSteps()`](/docs/modules/extensions/next-steps), a command that `.use(nextSteps)` awaits `ctx.nextSteps` and calls `.add(status, input, description)` on it to add follow-up commands by definition, as `deploy` does above, and `nextSteps({ onError })` returns recovery commands for errors you recognize with `instanceof`. The steps print to stderr as runnable command lines, after success or failure:

```sh
$ my-cli deploy staging
Deploying latest to staging
Next steps:
  Watch the rollout:
    my-cli status staging
```

## Prompts without a TTY

A prompt waits for an answer an agent can't give. Make every prompt answerable from the command line, and fail when it isn't:

<include lang="ts">../../../examples/guide/agents.ts#prompts</include>

- `initial` from a flag skips the prompt when the flag is given, on any terminal.
- An explicit `default` is returned without asking when there is no TTY (except for `password()`).
- A prompt with neither rejects with [`NonInteractiveError`](/docs/modules/prompts#non-interactive-environments) without a TTY, so the command fails instead of hanging:

```sh
$ my-cli init < /dev/null
Error: Prompts require an interactive terminal (TTY).
$ my-cli init --name demo < /dev/null
Created demo in us-east-1
```

Crust doesn't detect agents or add a global `--no-input`: the TTY check is the rule.

## MCP

[`@crustjs/mcp`](/docs/modules/mcp) serves your commands as MCP tools with `<cli> mcp`. Each tool's input schema is the same flat object `--input` takes; `.output()` schemas and generator events become the tool's output schema and progress notifications. What a call writes to stderr, next steps included, follows its result in the tool result.

## Skills

[`@crustjs/skills`](/docs/modules/skills) renders an agent skill from your commands at build time, with output schemas, and adds a `skills` command that installs it into agents' skill directories.

## The `api` command

For a CLI backed by an HTTP API, [`@crustjs/openapi`](/docs/modules/openapi) adds a `gh api`-style `api` command: an agent can list and read the bundled OpenAPI document offline and call endpoints your commands don't wrap yet, with your CLI's base URL and auth.

## Checklist

- Every command, argument, and flag has a `description`.
- Results are returned, not only printed, and declared with `.output()`.
- [`json()`](/docs/modules/extensions/json), [`input()`](/docs/modules/extensions/input), and [`schema()`](/docs/modules/extensions/schema) are registered.
- Long-running commands yield events.
- Commands that can preview declare a `dry-run` flag.
- Commands that change things call [`confirm()`](/docs/modules/extensions/confirm)'s `ctx.confirm` first, after any dry-run preview.
- Error messages say what to do next; known failures have recovery steps from [`nextSteps()`](/docs/modules/extensions/next-steps).
- Every prompt has a flag for `initial` or a `default`.
- Optionally: an MCP server, a packaged skill, and an `api` command.
