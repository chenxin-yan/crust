Pick the helper that matches what you assert:

| Helper             | Input                    | Checks                                                 |
| ------------------ | ------------------------ | ------------------------------------------------------ |
| `run()`            | A typed path and input   | The action's typed result or error                     |
| `captureExecute()` | Argv, as a user types it | What a terminal user sees, and the exit code           |
| `runInteractive()` | Argv, as a user types it | Prompts answered on a fake terminal, and the exit code |

`run()` is built into every app. The other two come from `@crustjs/testing`:

```npm
npm install -D @crustjs/testing
```

`@crustjs/testing` requires `@crustjs/core` as a peer. `runInteractive()` lives in `@crustjs/testing/interactive` and also needs `@crustjs/prompts`; install it if your project doesn't already use it.

## Inspect values and errors

<include lang="ts" meta="twoslash">
  ../../../examples/guide/testing.ts#run
</include>

`run()` reports whether a Command Action completed, was handled early by an Extension, or failed, with its result, error, `stdout`, and `stderr`.

- Its `RunOutcome` type is a union on `status`: narrow to `"completed"` before reading the typed `result`.
- When many tests target one subcommand, bind it once with [`app.at(path)`](/docs/api/crust#atpath) and call `handle.run(input?, options?)`, with the same typed input and outcome.

See the [full `run()` contract](/docs/api/crust#runpath-input-options).

## Capture terminal behavior

<include lang="ts">../../../examples/guide/testing.ts#capture-execute</include>

`captureExecute()` runs argv through `execute()` and resolves to `{ stdout, stderr, exitCode }`: what a user would see and the exit code the shell would get, including Extension error rendering. `stdout` and `stderr` are exactly what was written, so a line printed with `stdout(text)` ends in a newline, as in `run()`'s outcome. It restores the prior process exit state afterwards. Its `stdin`, `isTTY`, and `columns` options set what the action reads from [`stdin`](/docs/guide/terminal-io) and whether its output is a terminal; see the [`captureExecute()` reference](/docs/modules/testing#captureexecuteapp-argv).

<Callout type="warn">
  Patching `process.stdout.write` doesn't capture Crust's output: outside Windows, `execute()`
  writes synchronously to file descriptors 1 and 2. Use `captureExecute()`, or pass `io` to
  `execute()`.
</Callout>

## Drive prompts

<include lang="ts">../../../examples/guide/testing.ts#interactive</include>

`runInteractive()` runs argv through `execute()` on a fake terminal and returns a handle that types into it.

- `screen()` contains prompt, progress, and `stderr` output. The action's `stdout` is captured apart, as a pipe: read it with the handle's `stdout()` method.
- `keys()` takes named keys and `ctrl+<letter>`; a misspelled name is a compile error. `resize(columns, rows)` resizes the terminal, and `cancel()` cancels the run as Ctrl-C does.
- `await run.done` gives `{ stdout, stderr, exitCode }`, like `captureExecute()`. It never rejects: a failure is its rendered error and exit code.
- Prompts show even when `CI` is set, so the test passes on CI runners as well.

## Isolate the environment

<include lang="ts">../../../examples/guide/testing.ts#env</include>

A test's result shouldn't depend on the shell that runs it. The `env` option of `captureExecute()` and `runInteractive()` replaces `process.env` for the run and restores it afterwards, so flags' `env` fallbacks, config directories, app code, and child processes see only those variables: `{}` is an empty environment, and `{ ...process.env, NAME: "value" }` changes one. Without `XDG_*` variables (`APPDATA` and `LOCALAPPDATA` on Windows), config and state directories stay under the home directory, so a test that writes them points those variables at a temporary folder. A `HOME` in `env` moves them on Node on macOS and Linux but not under Bun, which keeps the home directory it started with. The `cwd` option replaces the working directory for the run in the same way. For a typed `run()`, wrap the call in `withEnv(env, fn)`, which keeps the result's type.

The environment and working directory belong to the process, so run these tests one after another: a run that replaces them while another run is active throws, and a run without `env` that starts during a replacement sees the replaced environment. See [`CaptureOptions`](/docs/modules/testing#captureoptions).

`captureExecute()` and `runInteractive()` return plain text unless `raw: true` keeps escape codes. `run()` returns styled text with its escape codes (see [Styled output](/docs/modules/testing#styled-output)).

See the [`@crustjs/testing` reference](/docs/modules/testing).
