---
title: Add login to your CLI
description: Sign users in from a terminal with a browser or a device code, using @crustjs/auth.
---

A CLI that calls an API on the user's behalf needs their token. [`@crustjs/auth`](/docs/modules/auth) provides the OAuth pieces; this guide composes them into a `login` command that opens the browser on a desktop and falls back to a device code anywhere else.

## Before you start

Register your CLI with your authorization server as a **public client**, with redirect URI `http://127.0.0.1/callback` (any port) and, if you use it, the device grant. Do not ship a client secret: one bundled in a CLI is readable by every user.

What it does:

1. `detectLoginMode()` picks the login: `--device` or `--no-browser` always mean a device code; on CI, without an explicit flag, it refuses; with no TTY, over SSH, or on Linux without a display it uses a device code; otherwise the browser. See [Choosing a login](/docs/modules/auth#choosing-a-login).
2. `discover()` reads the server's metadata once per process.
3. **Device code:** `startDeviceFlow()` returns the code to show. `deviceCodeMessage()` prints it with the URL and an anti-phishing line, and `flow.poll()` waits for approval at the pace the server asks for.
4. **Browser:** `createAuthorizationSession()` listens on `127.0.0.1` and returns the URL to open. The command prints it, offers to open it with a [`confirm()`](/docs/modules/prompts) prompt, and `session.wait()` exchanges the code when the browser comes back. `session.close()` in `finally` frees the port on every path.
5. The [spinner](/docs/modules/progress) shows while either login waits, and the command's `ctx.signal` cancels the wait on Ctrl-C.
6. The tokens go to a [private store](/docs/modules/store#secret-files) (`0600` on Unix).

Print instructions to stderr, as above, so `--json` output and pipes stay clean.

## More than one server

If your CLI signs in with several authorization servers, each must send the `iss` response parameter or have its own `redirectPath`, or the browser login refuses to start. [Several servers and mix-up](/docs/modules/auth#several-servers-and-mix-up) explains why and how to declare them.

## Testing against a local server

For a local development server, set `allowInsecureLoopback: true` on its entry and use an issuer such as `http://127.0.0.1:9000`. See [Development servers](/docs/modules/auth#development-servers).
