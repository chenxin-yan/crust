```sh
crust build
```

`crust build` reads `src/cli.ts` and writes to `dist` by default. Bun and Deno builds produce standalone executables, while Node builds produce an executable JavaScript bundle.

Choose the runtime with `--runtime`, or set `crust.runtime` in `package.json`:

```json title="package.json"
{
  "crust": { "runtime": "deno" }
}
```

The flag overrides project configuration, and Bun is the default. The packaged `crust` command uses a Node launcher, so Node is required to start the build tool.

## Basic usage

```sh
# Default entry and output directory
crust build

# Custom entry and output name
crust build --entry src/main.ts --name my-cli

# One Bun target
crust build --target bun-darwin-arm64

# One Deno target
crust build --runtime deno --target aarch64-apple-darwin

# One Node bundle
crust build --runtime node --name my-cli
# Building .../src/cli.ts → .../dist/my-cli.js...
# ✓ Built successfully: .../dist/my-cli.js
```

Bun compilation uses `bun` on `PATH` when available and otherwise uses the Bun runtime embedded in packaged Crust. Deno must be on `PATH` while building; Node builds use the Bun bundler available to Crust.

Run `crust build --help` for all options.

## Runtime outputs

```sh
crust build --target bun-linux-x64-baseline --name my-cli
# dist/my-cli

crust build --runtime deno --target x86_64-unknown-linux-gnu --name my-cli
# dist/my-cli

crust build --runtime node --name my-cli
# dist/my-cli.js
```

| Runtime | Build tool                | Output                                     | End-user runtime |
| ------- | ------------------------- | ------------------------------------------ | ---------------- |
| Bun     | `bun build --compile`     | Standalone executable                      | None             |
| Deno    | `deno compile`            | Standalone executable                      | None             |
| Node    | `bun build --target node` | Executable `dist/<name>.js` with a shebang | Node             |

Node produces one JavaScript artifact, so it rejects `--target` and `--package`. Resolver settings do not apply to Node builds.

### Choosing targets

```sh
crust build --target bun-linux-x64-baseline --target bun-darwin-arm64
```

Use canonical compiler target names. Repeat `--target` for selected platforms, or omit it to build every supported Bun or Deno target.

See the current `BUN_TARGET_NAMES` and `DENO_TARGET_NAMES` in the [build target source](https://github.com/chenxin-yan/crust/blob/main/packages/crust/src/utils/build-helpers.ts).

<Callout type="info">
  Deno binaries are compiled with all permissions. Bun and Node builds do not add a runtime sandbox.
</Callout>

## Multi-target build (Bun and Deno)

```sh
crust build --name my-cli
# Building .../src/cli.ts for 6 target(s)...
# ✓ Built 6 target(s) successfully:
# Resolver: .../dist/cli (+ .../dist/cli.cmd)
```

With no target or more than one target, Bun and Deno builds write one binary per platform plus shell and Windows resolver scripts:

```text
 dist/
 ├── cli
 ├── cli.cmd
 ├── my-cli-bun-linux-x64-baseline
 ├── my-cli-bun-linux-arm64
 ├── my-cli-bun-darwin-x64
 ├── my-cli-bun-darwin-arm64
 ├── my-cli-bun-windows-x64-baseline.exe
 └── my-cli-bun-windows-arm64.exe
```

### The resolver script

```json title="package.json"
{
  "bin": { "my-cli": "dist/cli" }
}
```

The Unix resolver detects the host with `uname`, makes the selected binary executable, then replaces itself with that binary. `dist/cli.cmd` handles Windows.

## Single-target build

```sh
crust build --target bun-darwin-arm64 --name my-cli
# dist/my-cli
```

Exactly one target writes one binary and no resolver. A Windows target adds `.exe` to a derived output name.

### Custom output path

```sh
crust build --target bun-linux-x64-baseline --outfile ./bin/my-cli
# bin/my-cli
```

`--outfile` requires exactly one target. Use `--name` to set the base name for a multi-target build.

## Binary naming

```sh
crust build --name my-tool       # my-tool
crust build                      # package.json name, without an npm scope
crust build --entry src/main.ts  # main
```

The priority is `--name`, the project package name, then the entry filename. Derived Node names receive `.js`, and derived Windows binary names receive `.exe`.

## Disabling minification

```sh
crust build --no-minify
crust build --runtime deno --minify
# Error: --minify is not supported with --runtime deno.
#   deno compile has no minification step; drop the flag.
```

Minification defaults to on for Bun and Node. Deno has no minification step and rejects explicit `--minify`.

## Environment variables

```sh
crust build --env-file .env.production
```

See [build-time constants](/docs/guide/environment#build-time-constants) for `PUBLIC_*` embedding, explicit `--env-file` inputs, and Deno behavior.

## Pre-compile snapshot preparation

```sh
# With @crustjs/man registered:
crust build
# Preparing Command Snapshot...
#   crust:man  1 file  man/my-cli.1
```

Before compilation, `crust build` runs the entry under Bun to prepare a Command Snapshot, validate the materialized command tree, and run Extension build hooks. Command Actions and code after `await app.execute()` do not run in this subprocess.

The entry module's top-level side effects do run, and preparation has a 30-second timeout. Use `--no-validate` only when those side effects or the project's module resolution prevent preparation:

```sh
crust build --no-validate
```

This skips runtime validation and Extension build hooks. With `--package`, it also stages no existing artifact directories. For snapshot re-evaluation, see [Command Snapshot](/docs/api/crust#snapshot); for hook inputs, artifacts, and reports, see [Extension build context](/docs/api/types#extensionbuildcontext), [build artifacts](/docs/api/types#buildartifacts), and [Build Report](/docs/api/types#buildreport).

Each build hook must own and clean a unique top-level directory in the artifact output directory. The `bin` directory is reserved for generated npm executables. `--stage-dir` must not contain the artifact output directory because staging replaces its contents.

Raw build output has no npm `files` list. Distribute Extension artifact directories beside raw binaries, or use `--package` to stage them with npm metadata.

## Per-OS distribution with `--package`

```sh
crust build --package --target bun-linux-x64-baseline --target bun-darwin-arm64
# Staging 2 distribution target(s) in .../dist/npm...
# ✓ Staged 3 npm package(s) successfully
# Manifest: .../dist/npm/manifest.json
```

`--package` supports Bun builds and requires a project `package.json` with `name` and `version`. It rejects `--outfile`; use `--stage-dir` to change the staging directory.

If `bin` is an object, it must contain one entry. A string is accepted, and an omitted `bin` uses the resolved binary name.

### What `--package` creates

```text
 dist/npm/
 ├── manifest.json
 ├── root/
 │   ├── package.json
 │   ├── bin/my-cli.js
 │   ├── man/
 │   └── skills/
 ├── linux-x64/
 │   ├── package.json
 │   └── bin/my-cli-bun-linux-x64-baseline
 └── darwin-arm64/
     ├── package.json
     └── bin/my-cli-bun-darwin-arm64
```

The root package contains a Node launcher and optional dependencies on platform packages. Each platform package contains its Bun binary; discovered Extension artifact directories are copied to the root and beside each platform binary. The `man/` and `skills/` entries above appear only when those Extensions are registered.

The staged root metadata includes those discovered directories in `files`:

```json title="dist/npm/root/package.json"
{
  "files": ["bin", "man", "skills"]
}
```

The manifest records package metadata and publishes platform packages before the root:

```json title="dist/npm/manifest.json (excerpt)"
{
  "packages": [
    { "target": "linux-x64", "dir": "linux-x64" },
    { "target": "darwin-arm64", "dir": "darwin-arm64" }
  ],
  "publishOrder": ["linux-x64", "darwin-arm64", "root"]
}
```

### Publishing with `crust publish`

The dry-run transcript below is an excerpt for the two targets shown above:

```sh
crust publish --dry-run
# Publish order: linux-x64 -> darwin-arm64 -> root
#   → linux-x64: <path-to-executable> publish --access public --no-git-checks
#   → darwin-arm64: <path-to-executable> publish --access public --no-git-checks
#   → root: <path-to-executable> publish --access public --no-git-checks
```

`crust publish` reads `manifest.json`, verifies staged metadata, and stops on the first failed publish. `--access`, `--tag`, and `--registry` change publish options; `--no-verify` skips verification.

### Distribution package names

```text
my-cli        -> my-cli-linux-x64
@scope/my-cli -> @scope/my-cli-linux-x64
```

Platform package names append the platform alias. Their `os` and `cpu` metadata lets npm choose the matching optional dependency.

```json title="package.json"
{
  "name": "my-cli",
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli" },
  "scripts": {
    "build": "crust build",
    "prepack": "bun run build"
  }
}
```

The resolver starts the matching standalone binary. Use `crust build --package` for split npm packages.

<Tab value="Deno standalone">

```json title="package.json"
{
  "name": "my-cli",
  "crust": { "runtime": "deno" },
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli" },
  "scripts": {
    "build": "crust build --target x86_64-unknown-linux-gnu --outfile dist/cli"
  }
}
```

Building requires Deno on `PATH`; running the executable does not.

</Tab>
<Tab value="Node runtime package">

```json title="package.json"
{
  "name": "my-cli",
  "crust": { "runtime": "node" },
  "type": "module",
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli.js" },
  "scripts": {
    "build": "crust build --name cli",
    "prepack": "npm run build"
  }
}
```

End users need Node but not Bun. The bundle is ESM, so publish it from a package with `"type": "module"` or rename the output to `.mjs`.
