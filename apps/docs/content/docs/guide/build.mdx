Use `crust build` when your CLI is ready to run without its TypeScript source, then follow this path to an npm release.

```sh
crust build --target bun-linux-x64-baseline --name my-cli
./dist/my-cli --help
crust build --package
crust publish --dry-run
crust publish
```

## Build for one runtime

```sh
crust build --runtime bun --target bun-linux-x64-baseline --name my-cli
# ✓ Built successfully: .../dist/my-cli
```

Bun is the default and `--runtime` overrides `"crust": { "runtime": "deno" }` in `package.json`; `--runtime node` writes an executable JavaScript bundle at `dist/<name>.js`.

| Runtime | Output | Needed by the user |
| --- | --- | --- |
| Bun | Standalone executable | Nothing |
| Deno | Standalone executable with all permissions | Nothing |
| Node | Executable JavaScript bundle | Node |

Use `--entry` to replace `src/cli.ts`, `--outfile` for one exact output path, or `--name` for the derived filename. See all flags in the [`crust build` options](/docs/modules/crust#crust-build-options).

## Build more than one target

```sh
crust build --target bun-linux-x64-baseline --target bun-darwin-arm64 --name my-cli
# dist/cli, dist/cli.cmd, and one my-cli-* binary per target
```

Repeat `--target` for the platforms you ship; omitting it builds every supported Bun or Deno target. A multi-target build writes platform binaries plus `cli` and `cli.cmd` resolver scripts, so `package.json` can point `bin` at `dist/cli`.

## Prepare Extension artifacts

```sh
crust build
# Preparing Command Snapshot... (excerpt)
#   crust:man  1 file  man/my-cli.1
```

Before compilation, the build materializes and validates the command tree and runs Extension build hooks. The entry module's top-level code runs during this step, but Command Actions and code after `await app.execute()` do not.

Use `--no-validate` only when preparation cannot run; it skips Extension build hooks and keeps their artifact directories out of `--package` staging, as described in [Extension artifacts](/docs/modules/crust#extension-artifacts).

## Stage npm packages

```sh
crust build --package --target bun-linux-x64-baseline --target bun-darwin-arm64
# Manifest: .../dist/npm/manifest.json (excerpt)
```

`--package` stages Bun binaries as platform packages plus a root package with a Node launcher. It requires `name` and `version` in `package.json`.

| Path | Contains |
| --- | --- |
| `dist/npm/root/` | Root `package.json`, launcher, and Extension artifacts |
| `dist/npm/<platform>/` | One platform `package.json` and binary |
| `dist/npm/manifest.json` | Staged package list and publish order |

Platform package names append the platform alias, such as `my-cli-linux-x64` or `@scope/my-cli-linux-x64`; use `--stage-dir` to change the staging directory.

## Publishing with `crust publish`

```sh
crust publish --dry-run
# Publish order: linux-x64 -> darwin-arm64 -> root (excerpt)
crust publish
```

The dry run prints the order and commands without publishing. The publish command reads the staged manifest, verifies package metadata, publishes platform packages before the root, and stops at the first failure; see its [options](/docs/modules/crust#crust-publish-options).

```sh
npm install -g my-cli
my-cli --help
```

Users install the root package; npm pulls only the platform package for their machine.

## Environment variables

<include lang="ts">../../../examples/guide/build.ts#runtime-secret</include>

Read secrets and deployment configuration from the runtime environment; Crust adds no abstraction, and [Bun environment variables](https://bun.sh/docs/runtime/environment-variables) covers Bun's `.env` loading and precedence.

### Build-time constants

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/guide/build.ts
</include>

```sh
cat > .env.production <<'EOF'
PUBLIC_API_ORIGIN=https://api.example.com
API_TOKEN=private-value
EOF
crust build --env-file .env.production --target bun-linux-x64-baseline --name deploy
env -u PUBLIC_API_ORIGIN -u API_TOKEN ./dist/deploy origin
# https://api.example.com
grep -a -o 'private-value' dist/deploy || echo 'private-value: not embedded'
# private-value: not embedded
```

For Bun and Node builds, `--env-file` passes explicit files to the compiler, embeds only `PUBLIC_*` values, and reaches snapshot preparation.

<Callout type="warn">
  Embedded `PUBLIC_*` values are visible in the output. Keep secrets in runtime environment variables without that prefix.
</Callout>

Deno builds reject `--env-file`, so load their configuration at runtime instead.

## Set up `package.json`

<Tabs items={["Bun standalone", "Deno standalone", "Node runtime package"]}>
<Tab value="Bun standalone">

```json title="package.json"
{
  "name": "my-cli",
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli" },
  "scripts": {
    "build": "crust build",
    "prepack": "bun run build"
  }
}
```

Use `crust build --package` instead when you want split npm packages.

</Tab>
<Tab value="Deno standalone">

```json title="package.json"
{
  "name": "my-cli",
  "crust": { "runtime": "deno" },
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli" },
  "scripts": {
    "build": "crust build --target x86_64-unknown-linux-gnu --outfile dist/cli"
  }
}
```

Deno must be on `PATH` for the build, but the built executable does not need it.

</Tab>
<Tab value="Node runtime package">

```json title="package.json"
{
  "name": "my-cli",
  "crust": { "runtime": "node" },
  "type": "module",
  "files": ["dist"],
  "bin": { "my-cli": "dist/cli.js" },
  "scripts": {
    "build": "crust build --name cli",
    "prepack": "npm run build"
  }
}
```

End users need Node but not Bun; publish the ESM bundle from a package with `"type": "module"` or rename it to `.mjs`.

</Tab>
</Tabs>
