Crust adds no environment variable abstraction. For Bun's `.env` loading order and shell precedence, see [Bun's environment variable documentation](https://bun.sh/docs/runtime/env).

## Build-time constants

```sh
printf 'PUBLIC_API_ORIGIN=https://api.dev.example.com\n' > .env
cat > .env.production <<'EOF'
PUBLIC_API_ORIGIN=https://api.example.com
API_TOKEN=private-value
EOF
crust build --env-file .env --env-file .env.production --target bun-linux-x64-baseline --name deploy
grep -a -o 'https://api.example.com' dist/deploy
grep -a -o 'private-value' dist/deploy || echo 'private-value: not embedded'
# https://api.example.com
# private-value: not embedded
```

`--env-file` is repeatable, and later files override earlier files. Crust passes the files to Bun in order and limits embedded values to `PUBLIC_*` keys.

<Callout type="warn">
  Embedded `PUBLIC_*` values are visible in the binary. Never use that prefix for secrets.
</Callout>

| Value                                       | Location                        |
| ------------------------------------------- | ------------------------------- |
| API keys, tokens, private deployment config | Runtime environment             |
| Public API origins, public build labels     | `PUBLIC_*` build-time constants |

`--env-file` works for Bun and Node builds. `crust build --runtime deno` rejects it because Deno has no matching `PUBLIC_*` filter, so load Deno configuration at runtime instead.
