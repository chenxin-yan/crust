Crust adds no environment-variable abstraction. Read runtime configuration from `process.env`; Bun loads `.env` files according to its normal runtime rules.

```ts
import { Crust } from "@crustjs/core";

const deploy = new Crust("deploy").action(({ stdout }) => {
  const token = process.env.API_TOKEN;
  if (!token) throw new Error("Missing API_TOKEN");
  stdout("Deploying");
});
```

## Build-time constants

`crust build` follows Bun's `PUBLIC_*` model. It can use Bun's auto-loaded current-directory environment or explicit repeatable `--env-file` flags:

```sh
crust build --env-file .env.production
crust build --env-file .env --env-file .env.local
```

Later files override earlier files, and the shell environment wins. Only `PUBLIC_*` keys are eligible for embedding.

<Callout type="warn">
  Embedded `PUBLIC_*` values are visible in the binary. Never use that prefix for secrets.
</Callout>

| Value                                       | Location                        |
| ------------------------------------------- | ------------------------------- |
| API keys, tokens, private deployment config | Runtime environment             |
| Public API origins, public build labels     | `PUBLIC_*` build-time constants |

`--env-file` applies to Bun and Node builds only. `crust build --runtime deno` rejects it because `deno compile` embeds every variable from the file — secrets included — with no `PUBLIC_*` filter; load configuration at runtime instead (e.g. `deno run --env-file`).

If Extension configuration reads environment values while definitions are prepared, pass the same `--env-file` values to `crust build` so its snapshot subprocess sees them. See [Building and Distribution](/docs/guide/build).
