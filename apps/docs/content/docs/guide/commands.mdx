Create a CLI with `new Crust(name)`, define what it does with `.action()`, and call `.execute()` to run it.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/guide/hello.ts
</include>

```sh
$ bun src/cli.ts
Hello!
```

Print through the action's `stdout(text)` and `stderr(text)` rather than `console.log` or `process.stdout.write`. Crust owns only what goes through them: [`run()`](/docs/api/crust#runpath-input-options), [tests](/docs/guide/testing), and [MCP tools](/docs/modules/mcp) capture it, and it stays in order with Crust's own output, such as rendered errors. Direct writes bypass all of that.

Choose how to add subcommands based on your app's size and how you want to organize and reuse its commands:

- **Define inline with `.command()`** for small CLIs or short subcommands used only by this app.
- **Use `defineCommand()` with `.add()`** when a growing CLI needs separate command files or reusable definitions.

You can use both approaches in the same app.

## Grow in one file

Keep small subcommands alongside the root with `.command()`. Its callback defines the subcommand's flags and action, and can call `.command()` again to nest another level.

</include>

```sh
$ tool build --minify
minify: true
```

## Split across files

```text
src/
├── commands/greet.ts
├── app.ts
└── cli.ts
```

## Run commands from code

`.execute()` is the terminal entry point: it parses argv, renders errors, and sets the exit code. To call a command from your own code, such as a script, server, or test, use `.run()` with a typed path and structured input instead.

<include lang="ts" meta='title="src/script.ts"'>
  ../../../examples/guide/commands-split-files/script.ts
</include>

`run()` resolves to an outcome with the captured `stdout` and `stderr` and never renders errors, changes `process.exitCode`, or applies flag `env` fallbacks. Check `status` before reading the action's `result`. See the [`run()` reference](/docs/api/crust#runpath-input-options) for input rules and capture behavior, and [Testing](/docs/guide/testing) for using it in tests.

## Stream events

A long-running command can report progress to programs while it works. Write its action as an `async function*`: each `yield` emits an event, and the `return` value becomes the result.

<include lang="ts" meta='title="src/script.ts"'>
  ../../../examples/guide/commands-stream.ts
</include>

Events are for programs, not people: Crust never prints them, so a terminal user sees only what the action writes through `stdout(text)` and `stderr(text)`. `run()` and `execute()` deliver each event live to `options.onEvent`, after the [renderer](/docs/guide/extensions#renderers) an Extension selected, if any, receives it as `event`. The `run()` outcome carries every event as `events`, typed from the yields, both when the command completes and when it fails mid-stream; `events` is absent for ordinary actions. The action pauses at each `yield` until the renderer and callback have run. When the invocation's `signal` aborts, Crust closes the generator with `return()` at its next `yield`, so its `finally` blocks run, and the invocation fails with the abort reason; pass `signal` to the work between yields to stop sooner. A throwing renderer `event` or `onEvent` callback closes the generator the same way and fails the invocation. If closing the generator throws too, the invocation fails with a `SuppressedError` whose `error` is the cleanup failure and whose `suppressed` is the original failure, as with a failed [Context disposal](/docs/api/errors#propagation-boundaries); a cancelled invocation still exits `130` and prints the cleanup failure. An action that returns an async generator object, such as `async () => watch()`, streams the same way; other async iterables are ordinary results.

To print events on the command line, add the [`json()`](/docs/modules/extensions/json#generator-actions) Extension: with `--json`, a generator action streams its events and final result as NDJSON on stdout.

## Unknown commands

```sh
$ tool deploy
Error: Unknown command "deploy".
$ echo $?
1
```

The single-file `tool` example defines `build`, not `deploy`. Because `tool` has subcommands but no action of its own, an unrecognized name produces an error and exit code `1`.

If the root has its own `.action()`, matching subcommands still take priority. Unmatched words are parsed as the root's [positional arguments](/docs/guide/arguments-and-flags#arguments) instead.
