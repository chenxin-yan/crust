Add subcommands in either way, or mix both in one app:

- **`.command()` inline:** small CLIs, or short subcommands used only by this app.
- **`defineCommand()` + `.add()`:** separate command files or reusable definitions.

## How a command line is routed

Crust reads a command line from the left to choose the command that runs:

- **Subcommand names choose the command.** `tool build` runs `build`. A subcommand's name or alias always wins.
- **The command that runs reads every flag, wherever it was typed.** `tool -c prod build` and `tool build -c prod` are the same: `build` reads `-c`. A subcommand may reuse a letter its parent uses for something else; the meaning of the command that runs applies. This follows [clig.dev](https://clig.dev/#arguments-and-flags), which asks for flags that work in any order, not git or docker, where a flag belongs to the command it follows.
- **A flag only a subcommand knows goes after its name.** Before the name, Crust can't tell whether the flag takes a value, so `tool --minify build` fails with `Unknown flag "--minify"; flags of subcommand "build" go after its name`. A flag the command that runs doesn't know is the same `Unknown flag` error on either side of its name.
- **A reused spelling takes a value at every level or at none.** A parent's `-c <file>` and a subcommand's boolean `-c` would split `tool -c a.txt build` differently from `tool build -c a.txt`. This is a [definition check](/docs/api/crust#definition-checks): a `DEFINITION` error from source and in `crust build`.
- **A command's action is its default.** `tool` alone runs the root's `.action()`, if it has one. Words that name no subcommand are the action's [arguments](/docs/guide/arguments-and-flags#arguments) when it declares any, and an [unknown command](#unknown-commands) when it declares none.
- **A group shows its help.** With [`help()`](/docs/modules/extensions/help) installed, `tool` alone prints its help and exits `0`, even when a required flag is unset; without `help()`, it fails with `Missing command. Available: build` and exit code `2`. Anything typed after a group's name is checked like any command's input first, so `tool --level bogus` is a usage error.

## Grow in one file

`.command(name, config?, callback)` defines a subcommand's flags and action in place. The optional `config` is the same metadata `defineCommand()` takes, such as the `description` help lists. Call `.command()` inside the callback to nest another level.

## Documentation sections

Document what help can't infer, such as exit codes or environment variables, with `sections`: in a command's `defineCommand()` config, or in `new Crust()` metadata for the root.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/guide/commands-sections.ts
</include>

```sh
$ my-cli deploy --help
my-cli deploy - Deploy a release

Usage:
  my-cli deploy [options]

Options:
  -h, --help                   Show help

Exit codes:
  0  Deployed
  1  Deploy failed
```

- A section renders on its own command only, in every Extension that documents commands.
- Limit it to some of them with `only` or `except`; see [`CommandSectionInput`](/docs/api/types#commandsectioninput).
- [Contexts](/docs/guide/contexts#documentation-owned-by-a-context) and [Extensions](/docs/guide/extensions#command-sections) can add sections too.

## Run commands from code

`.execute()` is the terminal entry point: it parses argv, renders errors, and sets the exit code. From a script, server, or test, call `.run()` with a typed path and structured input instead.

<include lang="ts" meta='title="src/script.ts"'>
  ../../../examples/guide/commands-split-files/script.ts
</include>

`run()` resolves to an outcome with captured `stdout` and `stderr`. Check `status` before reading `result`.

Unlike `.execute()`, it never renders errors or sets `process.exitCode`. Flags the input omits fall back to their `env` variables in `process.env`, as on the command line; a test isolates a call from the caller's shell with [`withEnv()`](/docs/modules/testing#withenvenv-fn). See the [`run()` reference](/docs/api/crust#runpath-input-options) for input rules and [Testing](/docs/guide/testing) for tests.

## Stream events

To report progress to programs while a command works, write its action as an `async function*`: each `yield` emits an event, and the `return` value becomes the result.

<include lang="ts" meta='title="src/script.ts"'>
  ../../../examples/guide/commands-stream.ts
</include>

Events are for programs: Crust never prints them. A terminal user sees only the action's `stdout(text)` and `stderr(text)`.

- **Delivery:** each event goes live to the selected [renderer's](/docs/guide/extensions#renderers) `event`, if any, then to `options.onEvent` of `run()` or `execute()`. The action pauses at each `yield` until both return.
- **Outcome:** `run()` collects every event in `outcome.events`, typed from the yields, whether the command completes or fails mid-stream. Ordinary actions have no `events`.
- **Cancellation:** when the invocation's `signal` aborts, Crust closes the generator at its next `yield`, so its `finally` blocks run, and the invocation fails with the abort reason. Pass `signal` to the work between yields to stop sooner.
- **Throwing consumers:** a throwing renderer `event` or `onEvent` closes the generator the same way and fails the invocation.
- **Failed cleanup:** if closing the generator throws, the invocation fails with a `SuppressedError` (`error`: the cleanup failure, `suppressed`: the original), as with a failed [Context disposal](/docs/api/errors#propagation-boundaries). A cancelled invocation still exits `130` (`143` after `SIGTERM`, `141` after a closed stdout).
- **Returned generators:** an action that returns an async generator object, such as `async () => watch()`, streams the same way. Other async iterables are ordinary results.

## Unknown commands

```sh
$ tool deploy
Error: Unknown command "deploy".
$ echo $?
2
```

`tool` from [Grow in one file](#grow-in-one-file) has subcommands but no action of its own, so an unknown name fails with exit code `2`, the [usage error](/docs/guide/error-handling#exit-status) status. A parent whose `.action()` declares no arguments fails the same way.

If the parent's `.action()` declares arguments, matching subcommands still win, and other words become its [arguments](/docs/guide/arguments-and-flags#arguments). The action can still decline a word: `throw unknownCommand(command, name)` (from `@crustjs/core`, with the action's `command`) raises the same `COMMAND_NOT_FOUND` error Crust raises, so [`didYouMean()`](/docs/modules/extensions/did-you-mean) still suggests a subcommand.
