## Built-in value types

Arguments and flags support `string`, `number`, `boolean`, `url`, `path`, and `json`.

```ts
new Crust("inspect")
  .args({ name: "file", type: "path", required: true })
  .flags({ name: "config", type: "json" })
  .action(({ args, flags }) => {
    args.file; // string
    flags.config; // unknown
  });
```

`type` determines token consumption and built-in conversion. Invalid numbers, URLs, paths, and JSON produce `PARSE` errors. Number conversion follows `Number()`, so an empty token becomes `0`. Boolean positional arguments become `true` only for the exact tokens `"true"` and `"1"`; every other token becomes `false`. Use a string argument with `choices` or a schema when other spellings should be rejected.

## Custom parsing

Use `parse` for a small synchronous transformation when a full schema is unnecessary:

```ts
.flags({
  name: "date",
  type: "string",
  parse: (value) => new Date(value),
})
```

The Command Action receives the return type. A parser must be synchronous: TypeScript rejects Promise-returning parsers with `FIX_ASYNC_PARSE`.

## Compile-time definition checks

Crust is TypeScript-first: command, flag, argument, Context, and Extension definitions are checked at compile time. `FIX_*` brands let the editor point at collisions, invalid alias shapes, asynchronous parsers, duplicate names, and invalid variadic positions. Direct flag/argument helpers and attachments require proof of local spellings, synchronous parsers, choice defaults, and positional layout. Unproven definitions and collections must cross `runtime(...)`; consuming them checks the local facts and destination relations. Trusted authoring and composition do not repeat those checks at runtime.

Argv remains untrusted input. CLI syntax, incoming choices, and required occurrences remain runtime-owned. Typed structured input skips already-proven checks; custom-parser requiredness, empty multiple arrays, and Standard Schema validation still run when needed after `preRun`. Context dependency declarations are checked statically; lazy bag access retains runtime guards for missing providers on dynamically assembled paths, dependency cycles, and lifecycle misuse.

## Runtime input

For command names, local definitions/configuration, flag/argument/provider/command collections, and structured invocation, use `runtime(value)` when TypeScript cannot prove the input. The wrapper does not validate, normalize, or copy its value. The consuming operation checks it against its actual destination.

```ts
import { Crust, runtime } from "@crustjs/core";

const commandName: string = "generated";
const app = new Crust(runtime(commandName))
  .args({ name: "file", type: "string", required: true })
  .action(({ args }) => args.file);

const outcome = await app.run([], runtime({ args: { file: "input.txt" } }));
```

Wrapping the root name does not erase the known `file` argument or the action's return type. `defineCommand(runtime(name), recipe)`, `.as(runtime(name))`, and `.command(runtime(name), recipe)` also accept checked names. Blank and reserved command names are rejected when consumed. Ordinary literal names are checked by TypeScript.

`defineFlag(runtime(name), runtime(def))` and `defineArg(runtime(name), runtime(def))` check local definitions; either argument may remain ordinary when proven. Open aliases, unproven default/choice membership, and parser results typed as `unknown`, `any`, or `object` require a checked definition. Parsers are never called during authoring; checked parser results still must be synchronous when invoked. Wrapping only the name does not recheck a trusted parser. An optional checked parser produces the union of its parsed and unparsed output types. Helpers preserve every conditional definition branch, including parser, default, requiredness and negation fields; local checking does not turn alternatives into a single closed definition.

Wrap one collection for checked attachment: `.flags(runtime(defs))`, `.args(runtime(defs))`, `.provide(runtime(instances))`, or `.add(runtime(definitions))`, on roots or recipe builders. Root Extension collections use `.extend(runtime(extensions))`. Local validity is not collision-free composition. Narrow tuples preserve their known types; conditional argument tuples and conditional flag-record input types require checked invocation. Infinite template name domains such as `` `mode-${string}` `` and `` `${number}` `` need `runtime(name)` and remain open at attachment. Finite unions still identify only one actual canonical name, not every alternative key. Open spellings/layout stay open and require checked subsequent attachment and, when input shapes are open, checked invocation. Collections retained by normalization are copied and exposed readonly; contained JSON/URL/schema values are not cloned or frozen. Flag and argument helper results are shallow-frozen because they retain local proof reused by later checked consumers.

```ts
import { Crust, defineFlag, runtime } from "@crustjs/core";

const choices: string[] = ["fast", "safe"];
const mode = defineFlag("mode", runtime({ type: "string", choices, default: "safe" }));
const app = new Crust("build", runtime({ sections: [{ title: "Modes", body: "Choose a mode." }] }))
  .flags(runtime([mode]))
  .args(runtime([{ name: "file", type: "path" }]));
```

Use `new Crust(name, runtime(meta))` or `defineCommand(name, runtime(config), recipe)` for unproven section text/audiences or command aliases. Trusted section titles are nonblank single lines, bodies are nonblank, and `only`/`except` audiences are nonempty and mutually exclusive. Checked configs validate text and audience nonemptiness at consumption; their typed shape still enforces audience exclusivity and minted consumer IDs. Ordinary `.add()` requires statically known names/aliases and compatibility with inherited Context flags. Use `.add(runtime(definitions))` for unproven destination relations; local checking alone does not prove compatibility with siblings. Repeated aliases within one command remain allowed. Extension metadata and Context callback-value demands remain TypeScript-owned, including in checked collections. Unknown provider outputs cannot establish a known demanded value; use an unknown-valued demand and narrow its result when that is the intended contract.

`app.run(path, runtime(input))` keeps the known path's result type. Use `app.run(runtime(path), runtime(input))` when the selected command is dynamic; its result is `unknown`. Checked invocation validates input names, value kinds, occurrence arrays, positional order, choices, and `noNegate`. Required and schema validation still happen after `preRun`, so `finish()` can skip them. Widened or conditional choices, including fixed tuples with infinite template-valued members, need checked supplied input even after `runtime(def)`; local checking cannot prove future membership. A definition union needs checked supplied values even when all branches have the same primitive kind. Exported input types allow omission only when every branch is optional or has a definitely present default. Possible `noNegate` on a single definition permits only `true` on the trusted path; uncertain primitive kinds and multiple/variadic layouts need checked supplied values. Unrelated known inputs and safe omission remain available.

This is a boundary for typed dynamic data, not an `unknown` decoder or a JSON configuration loader. Decode external data first. It does not replace Standard Schema or inspect arbitrary callback return shapes; custom parsers still must return synchronously.

A bare `Crust` type now describes an empty argument tuple. Prefer inferred builder types. Use `AnyCrust` for inspection, `execute()`, and checked `run()` on arbitrary completed apps. It deliberately has no authoring methods and cannot regain an empty-root type. Preserve concrete builder generics while authoring, or construct `Crust<Flags, ArgsDef>` when an open argument state is intentional. Those broad holders require checked invocation. If you supply earlier class type arguments explicitly, TypeScript cannot infer the trailing name parameter; pass `runtime(name)` in that case.

## Schema-backed definitions

Crust uses one Standard Schema contract across core, store, and prompts: put the schema on a plain definition's `schema` key. The schema receives the surface's raw value (including `undefined` when an argument or persisted field is missing), and the caller receives its exact output type. Any Standard Schema v1 vendor works, and validation may be synchronous or asynchronous.

Standard Schema support adds no install-time dependency: Crust vendors the protocol types instead of requiring a separate specification package. Schema code runs only for definitions carrying `schema`.

```ts
import { z } from "zod";

const command = new Crust("serve")
  .args({ name: "port", schema: z.coerce.number().int().positive() })
  .flags(
    { name: "host", type: "string", schema: z.string().default("localhost") },
    { name: "secure", type: "boolean", schema: z.boolean().default(false) },
  )
  .action(({ args, flags }) => {
    args.port; // number
    flags.host; // string
    flags.secure; // boolean
  });
```

For arguments, the schema receives `string | undefined`, or `string[]` for a variadic argument. For flags it receives `string | undefined` or `boolean | undefined`. With `multiple: true`, it receives `string[]` or `boolean[]` when the flag appears at least once, and `undefined` when omitted. Unlike repeated flags, variadic arguments always supply an array.

On a schema-backed flag, `type` remains necessary to define token grammar: `"string"` consumes the next token, while `"boolean"` is a switch. It does not own output conversion.

Schemas exclusively own coercion, defaults, requiredness, choices, and validation. Do not mix `schema` with core value options (`type` on arguments, or `default`, `required`, `choices`, and `parse`); TypeScript rejects invalid combinations.

All schema failures in an invocation are aggregated into one `CrustError` with code `VALIDATION`:

```ts
import { CrustError } from "@crustjs/core";

try {
  // `command` is the schema-backed "serve" example above.
  await command.run([] as const, { args: { port: "not-a-number" } });
} catch (error) {
  if (error instanceof CrustError && error.is("VALIDATION")) {
    for (const issue of error.details?.issues ?? []) {
      console.error(issue.path, issue.message);
    }
  }
}
```

Issue paths identify inputs, for example `args.port` or `flags.host`.

### The same shape across packages

Define a schema once and attach it with the same `schema` key:

```ts
import { Crust } from "@crustjs/core";
import { input } from "@crustjs/prompts";
import { configDir, createStore } from "@crustjs/store";
import { z } from "zod";

const Port = z.coerce.number().int().min(1).max(65535);

new Crust("serve").flags({ name: "port", type: "string", schema: Port }).action(({ flags }) => {
  flags.port; // number
});

const store = createStore({
  dirPath: configDir("my-cli"),
  name: "config",
  fields: { port: { schema: Port.default(3000) } },
});
const config = await store.read();
config.port; // number

const port = await input({ message: "Port?", schema: Port });
//    ^? number
```

A schema exclusively owns validation, transformation, semantic defaults, and optionality. Do not combine `schema` with core value options or a hand-written `validate` callback. Invalid combinations fail at the definition or call boundary.

### Where defaults live

Put semantic defaults in the schema everywhere:

```ts
const Port = z.coerce.number().default(3000);
```

Core arguments and flags and store fields do not accept an outer `default` beside `schema`. Prompt `initial` and `default` remain raw UI fallback values rather than schema defaults; Crust passes either value through `schema` before returning it. Store fields additionally require the schema's output to be recursively JSON-compatible (named interfaces are accepted; non-JSON properties are not) because values persist to JSON.

## Choosing an approach

- Use a built-in type for direct token conversion.
- Use `parse` for one synchronous custom transform.
- Use `schema` for validation, defaults, coercion, or an existing schema ecosystem.
