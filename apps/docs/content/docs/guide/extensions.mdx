Extensions add behavior across your CLI. Start with the built-ins for help, version output, color control, and command suggestions:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-install.ts
</include>

```sh
$ my-cli --version
my-cli v0.2.0
$ my-cli deply
Unknown command "deply". Did you mean "deploy"?

Available commands: deploy
# exit 1
```

- `help()` adds `-h` and `--help`, and shows help when an actionless command, like this root, runs.
- `.extend()` order doesn't change behavior. When several such flags are passed, the first one wins, as in GNU tools: `--help --version` prints help, `--version --help` the version.
- `--no-color` applies to help output too.

Call `.extend()` on the root builder; registering Extensions inside a command recipe is a `DEFINITION` error. See [built-in Extensions](/docs/modules/extensions) for the full list.

## Write your own

Use an Extension when shared behavior needs flags, commands, or lifecycle hooks. For a helper used only inside actions, a plain function is enough.

This Extension adds a preview mode that skips the action:

<include lang="ts" meta='title="deploy.ts"'>
  ../../../examples/guide/extensions-preview.ts
</include>

```sh
$ deploy
deployed
$ deploy --preview
nothing changed
```

`.handle(flag, run)` takes over the invocation when the user passes that flag:

- `run` replaces `preRun`, validation, and the action; `run()` reports a `handled` outcome.
- A negated boolean such as `--no-preview` doesn't trigger it.
- The flag must come from the Extension's own `.flags()`, so a typo is a compile error.
- Invalid argv or environment values don't stop a handler. They read as `undefined` in `ctx.flags` and `ctx.args`, not as their default, and an invalid value of a handled flag doesn't trigger its handler.
- When several handled flags are passed, the one given first on the command line wins, whatever the `.extend()` order. Pass `{ eager: true }` to rank a flag before every non-eager handler, as `help()` and `version()` do: `deploy --preview --help` shows help.

See [`ExtensionHandleOptions`](/docs/api/types#extensionhandleoptions) for how `env` values and typed `run()` input rank.

### Ids and builders

- Give each Extension a namespaced id, such as `acme:preview`, with `defineExtensionId()`.
- Registering the same id again replaces the earlier registration. TypeScript doesn't track ids, though: if the re-registration contributes the same literal command names, or a later command reuses one, it is a compile-time collision even though the app runs.
- Builder methods other than `.factory()` return new frozen Extensions; there is no build step.
- Declare flags and Contexts before the hooks that read them. Collection methods such as `.flags()` append; setting a hook again replaces its callback.

## Owned flags and commands

The preview flag above is available on every command, so no command may declare its own `--preview`. Set `recursive: false` on a flag definition to make it root-only; then only the root's flags must avoid its spellings.

An Extension can also install top-level commands:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-diagnostics.ts
</include>

```sh
$ my-cli doctor
checking my-cli
```

Contributed commands work like commands added with `.add()`, including typed `run()` paths.

- A name or alias that collides with an app command or another Extension's command is a compile error.
- A collision TypeScript can't see, such as a name chosen by a factory option, is a `DEFINITION` error when the app prepares.
- Such a runtime-only name makes `run()` results `unknown` for the Extension commands registered up to and in that `.extend()` call, since a same-id re-registration may replace them. Your own commands keep their result types.

[`@crustjs/mcp`](/docs/modules/mcp) uses this pattern to install an `mcp` command that serves your commands as MCP tools.

## Hooks

After routing and parsing, an invocation runs these hooks:

```text
setup → handle → preRun → validation → action → postRun
            └─ no handler and no action → noAction
```

<include lang="ts" meta='title="hooks.ts" twoslash'>
  ../../../examples/guide/extensions-hooks.ts
</include>

| Hook        | Runs                                                                   | Use it for                                                                            |
| ----------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `setup`     | Every invocation, in `.extend()` order, before any handler             | Process settings such as color or log level                                           |
| `.handle()` | When its flag is passed; ends the invocation as `handled`              | Flags that take over, like `--help`                                                   |
| `noAction`  | The command has no action and no handler took over; ends `handled`     | Fallbacks such as help for a command group                                            |
| `preRun`    | Only when the action will run, in `.extend()` order, before validation | Login checks, deprecation warnings                                                    |
| `postRun`   | After every invocation that reached hooks, in reverse order            | Reporting the outcome                                                                 |
| `onError`   | `execute()` failures, in `.extend()` order                             | Custom error output; see [Error handling](/docs/guide/error-handling#suggest-the-fix) |

- **`setup`:** every setup runs, so setups must not depend on each other. Register cleanup with `ctx.defer()`, as in a Context's setup. It runs after `postRun` hooks, in reverse order together with Context cleanup, including after a failure.
- **`preRun`:** never runs for `--help`, `--version`, or `noAction`. Throw to fail the invocation; `preRun` can't end it successfully.
- **`postRun`:** a `completed` outcome carries `outcome.result`: the [`.output()`](/docs/api/crust#outputschema) schema's output if the command declares one, otherwise the action's awaited return value. After an [async generator action](/docs/guide/commands#stream-events), `completed` and `failed` outcomes also carry its yielded values as `outcome.events`.
- **Early failures:** routing, argv-parse, and typed `run()` input failures happen before the other hooks. Under `execute()`, `onError` still sees routing and argv-parse failures; `run()` never calls `onError` and returns a `failed` outcome.
- **One per app:** only one Extension may set `noAction`, and only one `.renderer()`. A second is a `DEFINITION` error when the app prepares.

Only handlers and `noAction` can end an invocation early, and reordering `.extend()` changes neither choice. It only orders setups, `preRun` checks, and `onError` hooks (registration order) and `postRun` hooks and cleanups (reverse).

<Callout type="warn">
  Hook flags are **pre-validation values**, not schema outputs. Check values before using them.
</Callout>

See [`ExtensionHooks`](/docs/api/types#extensionhooks) for the full lifecycle.

### Hook context

Besides `args`, `flags`, and output, a hook's `ctx` offers:

- **`ctx.bindInput({ args, flags, raw })`** in `setup` or `preRun` binds structured input, such as JSON read from a flag, as [`input()`](/docs/modules/extensions/input) does. Values given explicitly on argv win; other supplied keys replace environment values and defaults, converted as typed `run()` input. Later hooks, validation, and the action see the bound values.
  - Bind in `setup` so every `preRun` sees the values; it then also happens for `--help` and `--version`. Bind in `preRun` to bind only when the action will run.
  - The last call wins, and a bound flag never selects a handler.
  - An unknown key or a value that fails conversion throws a `PARSE` error from the calling hook.
- **`ctx.sources`** reports where each value came from: `"argv"`, `"run"`, `"env"`, `"bound"`, or `"default"`. For example, with a boolean `verbose` flag (short `-V`) and a `port` flag read from `PORT`, `my-cli -V` with `PORT=9000` set gives `{ args: {}, flags: { verbose: "argv", port: "env" }, raw: undefined }`. Use it to skip the keys argv gave before converting input yourself.
- **`ctx.commandPathOf(definition)`** returns where a command definition is mounted, such as `["my-cli", "deploy"]`, or `undefined`. Use it to print command lines for definitions that app code passes to your Extension.

See [`ExtensionContext`](/docs/api/types#extensioncontext) for the exact rules.

### Renderers

Core decides when output happens; one Extension can decide how. `.renderer(select)` returns a [`Renderer`](/docs/api/types#renderer) for the invocation, or `undefined` to keep the default:

<include lang="ts" meta='title="renderer.ts"'>
  ../../../examples/guide/extensions-renderer.ts
</include>

| Member            | Receives                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `text`, `diag`    | Each line the action or a Context writes with `stdout()` and `stderr()`                                       |
| `result`          | The action's return value, after any `.output()` schema validated it, before `postRun`                        |
| `stream`, `event` | A signal that the action is an [async generator](/docs/guide/commands#stream-events), then each yielded value |
| `error`           | In `execute()` only, a failure no `onError` hook claimed; never a cancellation                                |
| `cleanup`         | In `execute()` only, each cleanup failure Core would print as `Cleanup failed:`                               |

- An Extension's own `ctx.stdout` and `ctx.stderr` bypass the renderer, so help and notices print as usual.
- Optional members fall back to Core's behavior; without `event`, events aren't printed. Exit codes never change.
- Throwing from `result`, `stream`, or `event` fails the invocation. If `error` or `cleanup` throws, Core prints the failure itself.
- `select` runs once per invocation, after every setup and before any handler, and may be `async`, for example to `import()` a formatter lazily. Output written before it returns waits for the chosen renderer.
- Routing and argv syntax errors happen before flags are bound, so they render by default.

## Dependency injection

Extensions can install [Contexts](/docs/guide/contexts) and use them from hooks:

<include lang="ts" meta='title="cli.ts" twoslash'>
  ../../../examples/guide/extensions-providers.ts
</include>

```sh
$ my-cli
ready
outcome: completed
```

- `.provide()` installs Context instances across the command tree.
- `.use()` declares which factories the hooks need. An Extension that supplies and reads a Context needs both.
- To use an app-supplied Context instead, omit the Extension's `.provide()` and call `.provide(logger())` on the app before `.extend(logging)`. TypeScript requires that order; at runtime, the reverse works too.
- A provided Context's [documentation sections](/docs/guide/contexts#documentation-owned-by-a-context) appear once, on the root.

A provided Context's [flags](/docs/guide/contexts#flags-owned-by-a-context) are parsed by the root, its inline `.command()` children, and the commands that `.use()` the Context or [the Extension](#use-an-extensions-contexts-from-a-command):

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-provider-flags.ts#use-site
</include>

```sh
$ my-cli remove --yes
removed
$ my-cli list --yes
Error: Unknown flag "--yes"
```

When the Extension's own hooks `.use()` the Context, every command parses its flags, because hooks run on every command. With `.extend(audited)`, `my-cli list --yes` is accepted:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-provider-flags.ts#hooks
</include>

A flag-owning Context requires successful validation. Read it in the action, or in `postRun` after a `completed` outcome—not after a handler skipped validation.

### Use an Extension's Contexts from a command

A [reusable command](/docs/guide/contexts#use-from-a-reusable-command) can pass an Extension, or its factory, to `.use()` to use every Context that Extension provides:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-use.ts
</include>

```sh
$ my-cli now
12:00
```

- `.use(time)` and `.use(time())` both declare the Contexts `time()` provides, here `ctx.clock`, and the command parses the flags they own.
- The command doesn't need to import the Context factory.
- TypeScript requires those Contexts where the command is added. At runtime, an app that doesn't extend the Extension throws a `DEFINITION` error (`missing-extension`) when it prepares.

## Build hooks

A build hook returns files; Crust writes them. This one saves the frozen Command Snapshot as JSON:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-build.ts
</include>

During `crust build`:

```text
Preparing Command Snapshot for my-cli...
  acme:manifest  1 file  acme-manifest/manifest.json
```

- Return file contents; don't write into the build output yourself.
- Put files under an Extension-specific directory such as `acme-manifest/`. Loose files at the root of `.crust/artifacts/` aren't copied into staged packages.
- Hooks run in registration order, and section callbacks refresh after each one, so later hooks see sections based on earlier files. For example, register `skill()` before `man()` to list packaged skills in the man page.

See [`ExtensionBuildContext`](/docs/api/types#extensionbuildcontext) and [`BuildFile`](/docs/api/types#buildfile) for output and path rules.

## Section consumers

The built-in `help`, `man`, `schema`, and `skill` Extensions render sections for different audiences. A custom generator can do the same with `visibleSectionsFor()`:

<include lang="ts" meta='title="web-docs.ts" twoslash'>
  ../../../examples/guide/extensions-consumer.ts
</include>

The generated `web-docs/docs.md` contains:

```md
# my-cli deploy

## Safety

Run preview first.

## Screenshots

![preview](preview.png)
```

- `only: [webDocs]` keeps the Screenshots section out of other consumers, such as help. Use `except` to exclude consumers instead; both accept Extension values or ids.
- `visibleSectionsFor(snapshot, id)` selects visible commands and merges same-title sections for that consumer. For one command, use `sectionsFor(sections, id)`.

Both come from [`@crustjs/core/tooling`](/docs/modules/core#tooling-subpath).
