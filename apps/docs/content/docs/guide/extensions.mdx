<Callout type="warn">
  `.extend()` is root-only. `CommandDefinitionBuilder` does not expose it, so Extensions cannot be
  registered inside `defineCommand()` callbacks.
</Callout>

Two consequences of the root-only model:

- Added definitions are materialized into ordinary command nodes before root Extensions prepare the application, so Extensions apply to every added command, inline or file-split.
- Statically declared Extension commands and flags become typed `run()` and testing-harness inputs. Use a Context-owned flag when downstream actions need the flag as a typed action dependency.

## Author an Extension

`defineExtension(id, config)` returns a frozen plain value. The config can contain `flags`, `commands`, `provides`, `sections`, `build`, and `hooks`:

Official Extension identities use the `crust:` namespace, reserved by convention for official Crust identities (the prefix is not enforced at runtime). Third-party packages should namespace published Extension ids with their own prefix; application-local ids can remain plain.

## Owned flags and commands

Extension flags are a readonly array of named definitions. Use `defineFlag()` values for ordinary recursive flags, or write a named definition inline. Extension flags default to `recursive: true`, which contributes them to every command. The documented way to set the Extension-only `recursive` option for a root-only flag is an inline definition:

```ts
const rootOnlyVersion = defineExtension(defineExtensionId("version"), {
  flags: [{ name: "version", type: "boolean", recursive: false }],
});
```

`defineExtension()` infers owned flags in its hooks, so `ctx.flags.trace` in the example above is `boolean | undefined`; a root-only flag also includes `undefined` because a subcommand does not receive it. Other, command-specific flag names remain accessible as `unknown`. Hook contexts retain syntax-parsed values; schema validation produces separate values for Contexts and the Command Action.

Ordinary command flags are always local; Context-owned flags are the application-level propagation mechanism.

Extension commands are `defineCommand()` definitions attached at the root. `new Crust()` creates only the application root; every contributed command is a definition. Their names, aliases, inputs, and action results flow into typed `run()` and `captureRun()` paths. Recursive Extension flags appear on root and descendant typed inputs; `recursive: false` flags appear only on the root input, as does a flag whose `recursive` scope is a widened `boolean` (a runtime-`false` scope installs it on the root only). Their `.action()` callbacks receive the same typed action context as application commands, including `rootCommand` and the lazy Context bag.

Only contributions preserved as literals by `defineExtension()` can be represented statically. An Extension annotated with a widened `Extension` type, one whose contribution arrays are assembled dynamically or conditionally (`condition ? [foo] : [bar]`, `[condition ? foo : bar]`, a variable-length `(typeof foo)[]` array), an Extension selected conditionally (`.extend(condition ? a : b)`), or a variable-length Extension list (`.extend(...list)`) remains runtime-only; invoke those paths with `execute({ argv })`.

Extension contributions are applied in `.extend()` registration order. Extension flag spellings — declared flags and provided Context-owned flags alike — must not collide with application flags (root or any subcommand's) or with earlier Extensions: `.extend()` and `.add()` reject statically known collisions at compile time (`FIX_ALIAS_COLLISION`). At runtime, dynamically assembled declared Extension flag collisions fail during invocation preparation, while provided Context-owned collisions throw from `.extend()`; both use a `DEFINITION` error because a silent overwrite would retype an already-bound action's flag at parse time. Statically declared Extension flags are also checked against the local flags of commands contributed in the same call: preparation materializes contributed commands before injecting Extension flags, so a shared spelling would throw on every invocation. `provides` Context names likewise must not replace a Context already on the path: statically known replacements are rejected at `.extend()` (`FIX_DUPLICATE_CONTEXT`); dynamically assembled duplicate names keep last-write-wins when their owned flag spellings do not collide. Extension command spellings likewise must not collide within one `defineExtension()` tuple, with already-added application commands, or with other statically declared Extension commands: `defineExtension()`, `.extend()`, and `.add()` reject statically known collisions at compile time (`FIX_COMMAND_COLLISION`) because runtime preparation would otherwise dispatch a command that typed `run()` was not checked against. Dynamically assembled contributions keep deterministic last-write-wins at prepare time, so namespace Extension-owned command names and aliases to avoid accidental overrides. During routing, canonical command names beat aliases; among colliding aliases, the alias of the earliest-inserted sibling wins (replacing an existing canonical command keeps its original insertion slot).

Registering an `ExtensionId` more than once keeps only its last registration. Its contributions and providers come from that registration, and its lifecycle, section, and build hooks run once. Re-registering the same id with statically known literal commands or flags is still rejected by `FIX_COMMAND_COLLISION` or `FIX_ALIAS_COLLISION`; widen the replacement to `Extension` when its contributions are assembled dynamically. Replacement is runtime-only: the discarded registration's contributions already merged into the builder's static types remain visible, so its commands stay accepted by typed `run()` and fail at runtime with `COMMAND_NOT_FOUND` — invoke dynamically replaced paths with `execute({ argv })`.

## Command sections

Sections are named documentation blocks — like man-page sections — that render into `--help`, man pages, and generated agent skills from a single declaration. Commands can declare plain-text documentation sections in their metadata. Help renders them after Options. Man-page generation emits root entries as mdoc sections and groups visible subcommand entries under subsections for their canonical command paths:

```ts
const deploy = defineCommand(
  "deploy",
  {
    sections: [{ title: "Examples", body: "deploy production\ndeploy staging" }],
  },
  (command) => command.action(() => {}),
);
```

Extensions can append sections to any command while the application prepares. The `sections` field is a contribution point into the target commands' `meta.sections`, not documentation of the Extension itself:

```ts
const guidance = defineExtension(defineExtensionId("guidance"), {
  sections: () => [
    { command: [], title: "Environment", body: "Set DEPLOY_TOKEN before running." },
    { command: ["deploy"], title: "Policy", body: "Production deploys require approval." },
  ],
});
```

`command` is a canonical path relative to the root; `[]` targets the root. Unknown paths and aliases are rejected with a `DEFINITION` error instead of being silently omitted. Contributions are appended after authored `meta.sections`, in Extension registration order. The callback receives a frozen snapshot containing the fully materialized command tree and authored sections; renderers consume only each target command's merged `meta.sections`.

Titles must be non-empty single lines, and bodies are non-empty plain text so the same content is safe for terminal help and mdoc output.

Sections are visible to every renderer by default. Pass renderer factories to the mutually exclusive `only` or `except` fields to narrow a section:

```ts
import { defineCommand } from "@crustjs/core";
import { help } from "@crustjs/extensions";
import { skill } from "@crustjs/skills";

const deploy = defineCommand(
  "deploy",
  {
    sections: [
      { title: "Safety", body: "Use preview mode first." },
      { title: "Agent notes", body: "Inspect the plan before deploying.", only: [skill] },
      { title: "Examples", body: "deploy production", only: [help, skill] },
    ],
  },
  (command) => command.action(() => {}),
);
```

A renderer exposes its identity on its factory. Render-time helpers are imported from `@crustjs/core/tooling`: a single-command renderer selects from that command with `sectionsFor()`, and a full-tree renderer uses `visibleSectionsFor(snapshot, consumer)`, which returns section-bearing visible commands in canonical path order, represents the root as `[]`, skips hidden command trees, and applies audience filtering. Section audiences accept the factory itself, such as `only: [help]`, while renderer integrations pass a branded `ExtensionId` such as `help.id`. Raw strings are not accepted, and core does not maintain a fixed list of identities.

## Build hooks

`build(ctx)` generates artifacts when invoked by build tooling such as `crust build`; it does not run during ordinary `run()` or `execute()` dispatch. The snapshot subprocess invokes registered hooks in Extension registration order, so Extension presence is the source of intent. The context contains the frozen root Command Snapshot prepared before that hook starts and a resolved absolute `outDir`. After each hook, Crust re-evaluates section callbacks on a fresh copy of the materialized tree — command recipes still run once — so later hooks and the final snapshot observe earlier hook outputs. A hook cannot observe its own outputs through its initial `ctx.snapshot`; register a later renderer hook when those outputs must appear in an artifact. Build hooks may be async; errors propagate with the Extension id. `crust build --no-validate` skips entry preparation and all build hooks.

## Dependency injection

Hooks and command actions share the Context system. An Extension declares consumed services with `uses`, and hooks await them from the same lazy bag:

```ts
const telemetry = defineExtension(defineExtensionId("telemetry"), {
  uses: [logger],
  hooks: {
    async preRun({ ctx }) {
      const log = await ctx.logger;
      log.info("start");
    },
  },
});
```

An Extension can install services on the root with `provides`; commands and other Extensions can consume them:

```ts
const logging = defineExtension(defineExtensionId("logging"), {
  provides: [logger({ level: "info" })],
});
```

Extension providers use the same compile-time name and owned-flag collision brands as `.provide()`; widened or dynamically assembled owned-flag collisions throw a `DEFINITION` error from `.extend()`. Duplicate Context names without owned-flag collisions remain last-write-wins. Resolution is lazy and memoized for the invocation.

A `preRun` hook runs before flag validation, so it cannot pull a Context that owns flags. A flagless Context may pull other flagless Contexts, but its pull of a flag-owning Context rejects. That rejection is not memoized: after validation, the next pull re-runs the whole setup from the start, so a setup that acquires resources before the failing pull leaks them and repeats its side effects. Pull dependencies before acquiring resources. Flag-owning Contexts are available from the action and from `postRun` after validation; they remain unavailable after `ctx.finish()`, which skips validation. Values stay live through all `postRun` hooks and are disposed afterwards.

## Hooks

Hooks run after routing and syntax parsing. Where each hook sits in the invocation, and how failures flow through them, is defined once in the [Execution Model](/docs/guide/lifecycle).

### `preRun`

`preRun(ctx)` runs before validation and the Command Action, in `.extend()` order. Return `ctx.finish()` to end the invocation successfully and skip the remaining work:

<include lang="ts">../../../examples/extensions/hooks.ts#cached</include>

### `postRun`

`postRun(ctx, outcome)` runs after every invocation that reached the hooks — including failures and `ctx.finish()` short-circuits — in reverse `.extend()` order. It is the cleanup and post-run side-effect slot. `outcome` is frozen:

```ts
type InvocationOutcome =
  | { status: "completed" }
  | { status: "finished"; by: ExtensionId }
  | { status: "failed"; error: unknown; by?: ExtensionId };
```

For a finished invocation, `outcome.by` is the Extension id. A failed outcome carries `by` when an Extension handled it in `onError`; Core fallback rendering leaves `by` undefined. Official Extensions therefore report names such as `crust:help`; diagnostics that label an Extension use the same exact identity. The same context identity reaches all hooks for one invocation. Declare injectable services in `uses` and access them through `ctx`; a `WeakMap<ExtensionContext, State>` remains suitable for private per-invocation ephemera shared by a hook pair.

### `onError`

`onError(error, ctx)` presents failures reached during `execute()` dispatch, in `.extend()` order. Return `true` after rendering to stop presentation; return nothing (or `false`) to delegate to the next Extension and ultimately Core's default renderer. A hook that throws ends the chain: remaining hooks are skipped and Core's default renderer reports the original failure.

Failures before dispatch do not enter the hook chain. Extension application and command-tree materialization failures render directly to `io.stderr`; snapshot preparation and build-hook failures are printed directly.

<include lang="ts">../../../examples/extensions/hooks.ts#service-errors</include>

Rendering never turns a failure into success, and programmatic `run()` throws the original error instead of invoking `onError` — see [Error flow](/docs/guide/lifecycle#error-flow). For failures reached during dispatch, `onError` settles before `postRun`, so cleanup hooks observe the attributed outcome and invocation Contexts remain available until cleanup completes.

Unlike `preRun`/`postRun`, `onError` does not infer owned flags: routing and syntax-parse failures render with a fallback context whose `flags` are empty, so its `ctx.flags` stays `Record<string, unknown>`.
