Extensions add behavior across your CLI. Start with the built-ins for help, version output, color control, and command suggestions:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-install.ts
</include>

```sh
$ my-cli --version
my-cli v0.2.0
$ my-cli deply
Unknown command "deply". Did you mean "deploy"?

Available commands: deploy
# exit 1
```

`help()` adds `-h` and `--help` and shows help when this actionless root is invoked. Registration order matters for `noColor()`, which configures color before output hooks. `version()` and `help()` work in either order: help for an actionless command runs from `noAction`, after every `preRun`.

Call `.extend()` on the root builder, not inside a command recipe. See [built-in Extensions](/docs/modules/extensions) for the full list.

## Write your own

Use an Extension when shared behavior needs flags, commands, or lifecycle hooks. For a helper used only inside actions, a plain function is enough.

This Extension adds a preview mode that skips the action:

<include lang="ts" meta='title="deploy.ts"'>
  ../../../examples/guide/extensions-preview.ts
</include>

```sh
$ deploy
deployed
$ deploy --preview
nothing changed
```

Return `ctx.handled()` from `preRun` to stop before validation and the action. Calling it without returning it does not stop the invocation. Validation includes invalid argv and environment values, so a handling hook wins over them; until then, an invalid flag or argument reads as `undefined` in `ctx.flags` and `ctx.args`, not as its default.

Give each Extension a namespaced id such as `acme:preview`. Registering the same id again replaces the earlier registration. The types don't track ids yet: they still see the earlier registration's commands, so a re-registration that contributes the same literal command names, or a later command reusing one of them, is a compile-time collision even though the app runs.

Builder methods other than `.factory()` return new frozen Extensions; there is no finalization step. Declare flags and Contexts before the hooks that read them. Collection methods append; setting a hook again replaces its callback.

For configurable Extensions, chain `.factory()`:

<include lang="ts" meta='title="banner.ts"'>
  ../../../examples/guide/extensions-factory.ts
</include>

Return a chain on the supplied Extension to keep its id. See [`ExtensionBuilder` and `ExtensionFactory`](/docs/api/types#extension-types) for the full contracts.

## Owned flags and commands

The preview flag above is available on every command. Set `recursive: false` on a flag definition to make it root-only.

An Extension can also install top-level commands:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-diagnostics.ts
</include>

```sh
$ my-cli doctor
checking my-cli
```

Contributed commands work like commands added with `.add()`, including typed `run()` paths. Like sibling commands, they cannot replace each other: a name or alias that collides with an app command or another Extension's command is a compile error, and a collision TypeScript can't see, such as a name chosen by a factory option, is a `DEFINITION` error when the app prepares. Such a name doesn't hide collisions among the other, statically known command names, but it makes `run()` results `unknown` for Extension commands registered up to and in that call, since a same-id re-registration may replace them; your own commands keep their types. [`@crustjs/mcp`](/docs/modules/mcp) uses this pattern to install an `mcp` command that serves your commands as MCP tools.

## Hooks

Use `preRun` for work before validation and the action, and `postRun` for work after the invocation settles:

<include lang="ts" meta='title="hooks.ts" twoslash'>
  ../../../examples/guide/extensions-hooks.ts
</include>

- `preRun` follows `.extend()` order. Returning `ctx.handled()` skips later `preRun` hooks and the action.
- `noAction` runs only for a command without an action, after every `preRun` hook declined. Put fallbacks there, such as showing help for a command group, so they cannot shadow another Extension's flag, whatever the `.extend()` order.
- `postRun` runs in reverse order, including after an Extension handles the invocation early or a failure once hooks start. Preparation, routing, and input-binding failures happen before hooks and skip it. Context cleanup runs afterwards.
- `onError` handles terminal errors from `.execute()`; see [Error handling](/docs/guide/error-handling).

Hook flags are **pre-validation values**, not schema outputs. Check values before using them. See [`ExtensionHooks`](/docs/api/types#extensionhooks) for the full lifecycle.

## Dependency injection

Extensions can install [Contexts](/docs/guide/contexts) and use them from hooks:

<include lang="ts" meta='title="cli.ts" twoslash'>
  ../../../examples/guide/extensions-providers.ts
</include>

```sh
$ my-cli
ready
outcome: completed
```

`.provide()` installs Context instances across the command tree; `.use()` declares which factories the hooks need. An Extension that supplies and reads a Context needs both. To use an app-supplied Context instead, omit the Extension's `.provide()` and call `.provide(logger())` on the app before `.extend(logging)`. That order is a TypeScript rule: the app checks an Extension's dependencies when it prepares, so at runtime the reverse order works too.

A provided Context's [documentation sections](/docs/guide/contexts#documentation-owned-by-a-context) appear once on the root, not on every command.

A flag-owning Context requires successful validation. Use it in the action, or in `postRun` after validation has succeeded—not after an Extension handled the invocation early and skipped validation.

## Required root metadata

An Extension that needs `version` can require it with `defineExtension<"version">(id)`:

<include lang="ts" meta='title="metadata.ts" twoslash'>
  ../../../examples/guide/extensions-metadata.ts
</include>

TypeScript rejects `.extend(stamp)` unless the root declares `version`. Bun and Node builds (`bun build`, or `crust build` for those runtimes) skip this check, so run `tsc --noEmit` first.

If a factory argument can supply the value instead, build the factory without a metadata requirement and annotate it with overloads. Only calls that omit the argument then require root metadata. Like the check above, TypeScript enforces this and the runtime [does not repeat it](/docs/api/crust#chaining-semantics), so in code that type-checks the implementation can rely on one of the two being set:

<include lang="ts" meta='title="metadata-optional.ts"'>

</include>

[`version()`](/docs/modules/extensions/version), [`updateNotifier()`](/docs/modules/extensions/update-notifier), and [`completion()`](/docs/modules/extensions/completion) use this pattern.

## Command sections

Add documentation with `.sections()`. `command: []` targets the root; `command: ["deploy"]` would target a `deploy` command:

<include lang="ts" meta='title="sections.ts"'>
  ../../../examples/guide/extensions-sections.ts
</include>

`my-cli --help` includes:

```text
Environment:
  Set DEPLOY_TOKEN before running.
```

The callback runs when the application prepares and receives a snapshot containing contributed commands and flags, but no Extension-contributed sections. Commands it reads are built on demand, so a callback that reads only root metadata leaves the rest of the tree unbuilt. See [`ExtensionSectionContribution`](/docs/api/types#extensionsectioncontribution) for validation and audience rules.

## Build hooks

A build hook returns files; Crust writes them. This one saves the frozen Command Snapshot as JSON:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/extensions-build.ts
</include>

During `crust build`:

```text
Preparing Command Snapshot for my-cli...
  acme:manifest  1 file  acme-manifest/manifest.json
```

Put files under an Extension-specific directory such as `acme-manifest/`. Loose files at the root of `.crust/artifacts/` are not copied into staged packages. Return file contents rather than writing into the build output yourself.

Hooks run in registration order. Section callbacks refresh after each hook, so later hooks can see sections based on earlier artifacts. For example, register `skill()` before `man()` to list packaged skills in the man page. See [`ExtensionBuildContext`](/docs/api/types#extensionbuildcontext) and [`BuildFile`](/docs/api/types#buildfile) for output and path rules.

## Section consumers

The built-in `help`, `man`, and `skill` Extensions render sections for different audiences. A custom generator can do the same with `visibleSectionsFor()`:

<include lang="ts" meta='title="web-docs.ts" twoslash'>
  ../../../examples/guide/extensions-consumer.ts
</include>

The generated `web-docs/docs.md` contains:

```md
# my-cli deploy

## Safety

Run preview first.

## Screenshots

![preview](preview.png)
```

`only: [webDocs]` keeps the Screenshots section out of other consumers, such as help. Use `except` to exclude consumers instead; both accept Extension values or ids.

`visibleSectionsFor(snapshot, id)` selects visible commands and merges same-title sections for that consumer. For one command, use `sectionsFor(sections, id)`. Both come from [`@crustjs/core/tooling`](/docs/modules/core#tooling-subpath).
