---
title: Contexts
description: Share dependencies across commands with lazy setup, automatic cleanup, and test replacements.
---

A Context supplies a dependency, such as an API client or database connection, to your commands through `ctx`.

Use a Context when commands share a service, setup or cleanup needs managing, or tests need a replacement. For stateless helpers, a plain import is enough.

## Define and provide

Start the definition with `defineContext()`, finish it with `.setup()`, provide an instance to the app, and await its value in the action:

<include lang="ts" meta='title="status.ts" twoslash'>
  ../../../examples/guide/contexts-provide.ts
</include>

```sh
$ status
https://api.example.com/status
```

- `api` is the factory returned by `.setup()`.
- `api()` creates an instance for `.provide()`; it does not run setup yet.
- `await ctx.api` runs setup on first access and returns its value. Context values are always accessed through promises, even when setup is synchronous.

Provide a Context before adding commands that need it. Later-added descendants inherit it. To accept factory options without losing inference, annotate setup's second parameter; see [configurable Contexts](/docs/api/types#contextbuilder).

## Use from a reusable command

A [reusable command](/docs/guide/commands) declares its dependencies with `.use()`. Using `api` from above:

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-use.ts#use
</include>

```sh
$ app health
https://api.example.com/health
```

`.use(api)` says “I need this Context”; `.provide(api())` supplies it. Add the command after providing its dependencies—reversing the order is a type error.

`ctx` also exposes the Contexts that a used Context's setup [uses](#contexts-that-use-other-contexts), and the command demands them too.

A group that only adds commands doesn't `.use()` their Contexts. Its demands include its children's, checked where the group is added:

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-use.ts#group
</include>

The group doesn't parse the Contexts' flags: they stay on the commands that `.use()` them.

To use the Contexts an [Extension](/docs/guide/extensions#use-an-extensions-contexts-from-a-command) provides, pass the Extension to `.use()` instead of each factory.

## Setup and cleanup

Setup starts on first access to `ctx.database`. Once it succeeds, its value is shared for the rest of the invocation. Register cleanup with `defer()` as soon as you acquire a resource:

<include lang="ts" meta='title="work.ts"'>
  ../../../examples/guide/contexts-lifecycle.ts
</include>

```sh
$ work ping
pong
$ work query
database opened
select 1: ok
database closed
$ work fail
database opened
Error: query failed
database closed
```

- `ping` never reads the Context, so setup never runs.
- Cleanup runs after `postRun` hooks, also when the action throws.
- Deferred callbacks can be async and run in reverse registration order.

Instead of `defer()`, the returned value can own its cleanup. Replace the `database` definition above with:

The commands and output stay the same. For asynchronous cleanup, use `async [Symbol.asyncDispose]()` instead of `[Symbol.dispose]()`.

<Callout type="warn">
  Crust disposes the value for you. Don't also close it with `defer()` or `await using`, or use it
  after the invocation ends.
</Callout>

See the [lifecycle rules](/docs/api/crust#context-lifecycle) for ordering and cleanup dependencies.

### Cancellable setup

Pass setup's `signal` to work that should stop when the invocation is cancelled:

<include lang="ts" meta='title="config.ts"'>

Crust waits for setup to settle before cleanup, so ignoring cancellation can delay shutdown. Cleanup that must finish should not use the aborted signal.

## Flags owned by a Context

When a flag configures the dependency rather than a particular command, declare it with the Context's `.flags()`:

<include lang="ts" meta='title="app.ts" twoslash'>
  ../../../examples/guide/contexts-flags.ts
</include>

```sh
$ app deploy --api-url https://staging.example.com
https://staging.example.com/deploy
$ app status --api-url https://staging.example.com
https://staging.example.com/status
$ app version --api-url https://staging.example.com
Error: Unknown flag "--api-url"
```

Setup receives the validated values. A flag appears only on commands whose `ctx` exposes its Context:

| Command                                                                                                                                  | Parses the flag?                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| The one that calls `.provide()`, and inline [`.command()`](/docs/api/crust#commandname-config-recipe) children added after it (`deploy`) | Yes, without `.use()`                                                                             |
| A reusable command that declares the Context with `.use()` (`status`)                                                                    | Yes, plus the flags of Contexts its setup [uses](#contexts-that-use-other-contexts), transitively |
| Any other command (`version`)                                                                                                            | No: rejected as unknown, and left out of its documentation                                        |

For a Context an Extension provides, see [Dependency injection](/docs/guide/extensions#dependency-injection).

A command that `.use()`s a Context may also `.provide()` it; the two share its flags.

- To replace only the value, provide the same factory, for example its [`.of()`](#replace-a-context-in-tests) double.
- To change a flag, change the declared Context. A different same-name Context must own exactly the same flags; otherwise preparing the app throws a `DEFINITION` error (`context-flags-not-parsed`). See [`.use()`](/docs/api/crust#usefactories) for the exact rule.
- Reading a flag-owning Context on a command that doesn't parse its flags, which only an untyped access such as a cast allows, throws the same error, naming the missing `.use()`.

See [`.provide()`](/docs/api/crust#provideinstances) for collision rules.

## Documentation owned by a Context

When a Context needs explaining, such as the environment variables it reads, document it with `.sections(...sections)` before `.setup()`. Sections take the same `{ title, body, only?, except? }` shape as a [command's own `sections`](/docs/api/types#commandsectioninput); repeated calls append.

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-sections.ts
</include>

```sh
$ app --help
app

Usage:
  app <command> [options]

Commands:
  deploy

Options:
  -h, --help                   Show help

Environment:
  API_TOKEN  Token sent with every request
```

- Unlike flags, sections document **only the command where the Context is provided**, not the commands below it. `.provide(api())` on the root puts them in root help; inside `db`, in `app db --help` only.
- A Context an [Extension](/docs/guide/extensions) provides documents the root.
- Consumers of the [command snapshot](/docs/api/crust#snapshot) render them after the command's own sections.
- A section title already on that command, from its own `sections` or another Context, makes preparing the app throw a `DEFINITION` error (`duplicate-section`).
- When an Extension replaces a same-name Context, only the final provider's sections are used, including for `.of()` replacements.

## Contexts that use other Contexts

Declare dependencies with `.use()`, then await them through `ctx` inside setup:

<include lang="ts" meta='title="app.ts" twoslash'>
  ../../../examples/guide/contexts-dependencies.ts
</include>

```sh
$ app regions
https://eu.api.example.com/regions
```

Provide every dependency. Order within one `.provide()` call does not matter. Setup stays lazy: `config` is built only because `api` reads it.
