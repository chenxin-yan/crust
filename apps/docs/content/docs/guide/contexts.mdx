---
title: Contexts
description: Share dependencies across commands with lazy setup, automatic cleanup, and test replacements.
---

A Context supplies a dependency, such as an API client or database connection, to your commands, exposing through `ctx`.

Use a Context when commands share a service, setup or cleanup needs managing, or tests need a replacement. For stateless helpers, a plain import is enough.

## Define and provide

Start the definition with `defineContext()`, finish it with `.setup()`, provide an instance to the app, and await its value in the action:

<include lang="ts" meta='title="status.ts" twoslash'>
  ../../../examples/guide/contexts-provide.ts
</include>

```sh
$ status
https://api.example.com/status
```

- `api` is the factory returned by `.setup()`.
- `api()` creates an instance for `.provide()`; it does not run setup yet.
- `await ctx.api` runs setup on first access and returns its value. Context values are always accessed through promises, even when setup is synchronous.

Provide a Context before adding commands that need it. Later-added descendants inherit it. To accept factory options without losing inference, annotate setup's second parameter; see [configurable Contexts](/docs/api/types#contextbuilder).

## Use from a reusable command

A [reusable command](/docs/guide/commands) declares its dependencies with `.use()`. Using `api` from above:

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-use.ts#use
</include>

```sh
$ app health
https://api.example.com/health
```

`.use(api)` says “I need this Context”; `.provide(api())` supplies it. Add the command after providing its dependencies—reversing the order is a type error.

## Setup and cleanup

Setup starts on first access to `ctx.database`. Once it succeeds, its value is shared for that invocation. Register cleanup with `defer()` as soon as you acquire a resource:

<include lang="ts" meta='title="work.ts"'>
  ../../../examples/guide/contexts-lifecycle.ts
</include>

```sh
$ work ping
pong
$ work query
database opened
select 1: ok
database closed
$ work fail
database opened
Error: query failed
database closed
```

Cleanup runs after `postRun` hooks. Deferred callbacks can be async and run in reverse registration order.

### Disposable values

Instead of `defer()`, the returned value can own its cleanup. Replace the `database` definition above with:

<include lang="ts" meta='title="database.ts"'>
  ../../../examples/guide/contexts-setup.ts#disposable
</include>

The commands and output stay the same. For asynchronous cleanup, use `async [Symbol.asyncDispose]()` instead of `[Symbol.dispose]()`.

Crust disposes the value for you. Do not also close it with `defer()` or `await using`, or use it after the invocation ends. See the [lifecycle rules](/docs/api/crust#context-lifecycle) for ordering and cleanup dependencies.

### Cancellable setup

Pass setup's `signal` to work that should stop when the invocation is cancelled:

<include lang="ts" meta='title="config.ts"'>
  ../../../examples/guide/contexts-setup.ts#cancellation
</include>

Crust waits for setup to settle before cleanup, so ignoring cancellation can delay shutdown. Cleanup that must finish should not use the aborted signal.

## Flags owned by a Context

When a flag configures the dependency rather than a particular command, declare it with the Context's `.flags()`:

<include lang="ts" meta='title="app.ts" twoslash'>
  ../../../examples/guide/contexts-flags.ts
</include>

```sh
$ app deploy
https://api.example.com/deploy
$ app deploy --api-url https://staging.example.com
https://staging.example.com/deploy
```

`.provide()` installs these flags on the providing command and later-added descendants. Setup receives their validated values. See [`.provide()`](/docs/api/crust#provideinstances) for collision rules.

## Contexts that use other Contexts

Declare dependencies with `.use()`, then await them through `ctx` inside setup:

<include lang="ts" meta='title="app.ts" twoslash'>
  ../../../examples/guide/contexts-uses.ts
</include>

```sh
$ app regions
https://eu.api.example.com/regions
```

Provide every dependency. Order within one `.provide()` call does not matter. Setup stays lazy: `config` is built only because `api` reads it.
