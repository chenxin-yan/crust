---
title: Contexts
description: Supply dependencies to commands with lazy setup, automatic cleanup, and test replacements.
---

A Context is a named dependency, such as an API client or database connection, that the app creates and commands consume. This is dependency injection: commands declare what they need, the app decides how to build it, and Crust runs setup lazily and cleans up afterwards.

Reach for a Context when several commands share a service, setup should run only when used, a resource must be released afterwards, or you want to swap in a fake for tests. For stateless helpers, a plain import is enough.

## Define and provide

<include lang="ts" meta='title="status.ts"'>
  ../../../examples/guide/contexts-provide.ts
</include>

```sh
$ status
https://api.example.com/status
```

`defineContext` returns a factory. `api()` creates an instance and `.provide()` attaches it to the app. In the action, `ctx.api` is the value setup returned; it is always awaited because setup may be asynchronous.

An inline command can shadow an inherited Context with a different value type **before** binding its action. After `.action()`, a local replacement must satisfy the Context value types that action received. Calling `.action()` again replaces the callback and binds the current Context contract. These obligations belong to that command, not its descendants: a child may still shadow independently.

## Use from a reusable command

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-use.ts#use
</include>

```sh
$ app health
https://api.example.com/health
```

`.use(api)` declares that the [reusable command](/docs/guide/commands) needs `api`; it creates nothing. The app supplies the instance with `.provide(api())` and then adds the command. Reversing that order is a type error: `Uses Context "api" which is not provided`.

## Setup and cleanup

<include lang="ts" meta='title="work.ts"'>
  ../../../examples/guide/contexts-lifecycle.ts
</include>

```sh
$ work ping
pong
$ work query
database opened
select 1: ok
database closed
$ work fail
database opened
Error: query failed
database closed
```

Setup runs the first time a command reads `ctx.database`, so `ping` never opens it. Each invocation gets its own value. `defer(cleanup)` registers cleanup for that value; Crust runs it after the action and `postRun` hooks, including when the action throws. Callbacks may be async and run in reverse registration order. Calling `defer` after setup has settled throws a `DEFINITION` error.

Setup receives the invocation's `signal: AbortSignal`, shared with actions and Extension hooks. Pass it to cancellable initialization, such as `fetch(url, { signal })`. Caller cancellation or the first Ctrl-C during `execute()` aborts it. Crust waits for setup to settle before disposal, so work that ignores the signal can delay shutdown. Do not reuse the aborted signal for cleanup work that must finish.

When setup acquires several resources, call `defer` right after each acquire. Then a later failure in the same setup still releases what was already opened. Returned values that implement `[Symbol.dispose]` or `[Symbol.asyncDispose]` are still disposed automatically, before that setup's deferred callbacks.

Read every Context a cleanup callback needs during setup. Once cleanup starts, `ctx` still resolves Contexts that were built during the invocation, but pulling one that was never built rejects with a `DEFINITION` error (`context-during-disposal`) instead of opening a resource nothing will close. A dependency read from a cleanup callback is live only if you registered that `defer` after awaiting it; otherwise it is torn down first.

A Context value belongs to the invocation. Crust disposes a returned disposable itself, so do not `await using` it or close it in the action as well, and do not let it escape through a return value, stored result, or shared variable that is read after the invocation ends: it is already disposed by then. Only automatic registration of returned values is deduplicated, by object identity within one invocation; a setup that returns a disposable and also `defer`s its close runs both. Pick one mechanism per resource.

## Flags owned by a Context

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-flags.ts
</include>

```sh
$ app deploy
https://api.example.com/deploy
$ app deploy --api-url https://staging.example.com
https://staging.example.com/deploy
```

When a flag configures the dependency rather than the command, list it in the Context's `flags`. `.provide()` installs it on that command and every command added below, and setup receives the validated value. See [`.provide()`](/docs/api/crust#provideinstances) for collision rules.

## Contexts that use other Contexts

<include lang="ts" meta='title="app.ts"'>
  ../../../examples/guide/contexts-uses.ts
</include>

```sh
$ app regions
https://eu.api.example.com/regions
```

List the factories a Context needs in `uses` and read them from `ctx` in setup, the same way an action does. Dependencies are lazy too: `config` is built only because `api` reads it. Provide every instance; order within one `.provide()` call does not matter.

## Replace a Context in tests

<include lang="ts" meta='title="work.test.ts"'>
  ../../../examples/guide/contexts-doubles.ts
</include>

`database.of(value)` builds an instance that returns `value` without running setup, so neither `database opened` nor the deferred `database closed` runs. It keeps the Context's name and value type, which is why `query` is unchanged. See [Testing](/docs/guide/testing) for `run()`.

Ownership still transfers: if `value` implements `[Symbol.dispose]` or `[Symbol.asyncDispose]`, every invocation that pulls the Context disposes it like a returned value; Crust leaves an unpulled value untouched. For a double that survives repeated `run()` calls, pass a fake without a disposer, or keep the real factory so setup builds a fresh resource per invocation.

For the full contracts, see [Context types](/docs/api/types#context-types) and [`.use()`](/docs/api/crust#usefactories).
