## Two invocation modes

Use `execute()` at a CLI entrypoint:

```ts
await app.execute();
```

It reads `process.argv.slice(2)` by default, presents dispatch failures through Extension `onError` hooks, sets `process.exitCode` to `1` (or `130` for cancellation), and resolves. Preparation failures render directly to `stderr` because the Extensions that would handle them have not been applied successfully.

Use `run()` for programmatic invocation:

```ts
const outcome = await app.run(["deploy"], { flags: { "dry-run": true } });
if (outcome.status === "failed") throw outcome.error;
console.log(outcome.stdout);
```

It requires an explicit typed command path and binds structured input directly. It is quiet by default, captures `stdout`/`stderr`, and does not modify `process.exitCode`. The outcome is `completed` with an action `result`, `finished` with an Extension `by`, or `failed` with the original escaping `error`. Optional per-invocation writers forward output live while retaining capture. For genuinely dynamic paths, use an `AnyCrust` completed-app view with an unknown result; see [Runtime input](/docs/guide/types#runtime-input).

## Successful invocation order

1. **Prepare definitions** — apply Extensions and validate deferred recipes, flag relations, and documentation sections. Authoring and attachment already check observable local and destination constraints; TypeScript also rejects provably invalid definitions. Dynamic Extension commands replace existing canonical names; dynamic duplicate Context names without owned-flag collisions use last-write-wins. Canonical names beat aliases, and the first-registered alias wins among colliding aliases.
2. **Route** — resolve the command path.
3. **Parse or bind input** — `execute()` parses tokens; `run()` binds own properties directly. Both check observable value kinds and choices, apply string parsers and path normalization, and resolve defaults.
4. **Run `preRun` hooks** — invoke hooks in registration order. Flagless Contexts remain lazy. Returning `ctx.finish()` skips remaining hooks, required checks, schemas, and the action.
5. **Validate structure** — enforce requiredness and post-transform rules.
6. **Apply schemas** — validate and transform schema-backed inputs, aggregating issues.
7. **Resolve Contexts on demand** — construct each declared Context once with validated owned flags.
8. **Run the Command Action**.
9. **Run `postRun` hooks** — reverse registration order with completed, finished, or failed lifecycle outcome; Contexts remain available.
10. **Dispose Contexts** — reverse construction order, including after failure. Public outcomes settle only after cleanup.

## Error flow

Authoring and attachment errors still throw at consumption, and `snapshot()` preparation errors still reject. The public `run()` boundary captures preparation and invocation failures as outcomes.

Preparation, routing, and parse failures occur before `preRun` and `postRun`. A failure from `preRun`, validation, schema application, Context construction, or the Command Action still runs every `postRun` hook. The original invocation failure wins over post-run hook failures; after a successful or finished invocation, the first post-run failure fails the invocation after remaining hooks run. Context disposal is LIFO. Crust uses native `AsyncDisposableStack` semantics where available; on Node 22, its fallback aggregates multiple disposal failures in an `AggregateError` rather than a native `SuppressedError` chain.

With `run()`, the original value is retained in a `failed` outcome unless disposal also fails. Partial output is retained, including cleanup output. If both invocation and disposal fail, `await using` combines them in a `SuppressedError`: `.error` holds the disposal failure and `.suppressed` holds the invocation failure. This is separate from the disposal stack's aggregation of multiple cleanup failures. Action and Context failures are not converted to `CrustError`.

For `execute()` failures raised during dispatch before `postRun`, Crust invokes Extension `onError` hooks in registration order while Contexts are live, allowing cleanup hooks to observe the handling Extension in `outcome.by`. A hook returns `true` when it rendered the failure; falsy results continue to the next hook and then Core's default renderer, which leaves `by` undefined. `onError` is presentation only and never runs for `run()`.

Routing and parse failures use a fallback hook context with empty `args` and `flags` and no available Contexts. If `postRun` or disposal fails after an otherwise successful or finished invocation, `onError` runs after cleanup and Context pulls reject with `context-after-disposal`. A failure already rendered during dispatch is not presented again after cleanup.

Any `Error` whose `name` is `"AbortError"`, including a `DOMException`, is cancellation. `execute()` sets status `130`, offers the error to `onError` hooks (so an application can render "Operation cancelled" centrally), and renders nothing by default when no hook claims it. `run()` returns it in a `failed` outcome.

## Setup and cleanup

Choose the mechanism that matches the setup's scope:

- use a Context for command-specific setup and native disposal
- use Extension `preRun` and `postRun` for app-wide behavior around an invocation
- keep ordinary local setup in the Command Action when it is not reusable

This keeps dependency construction lazy and guarantees reverse-order cleanup.
