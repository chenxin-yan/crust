## Two invocation modes

Use `execute()` at a CLI entrypoint:

```ts
await app.execute();
```

It reads `process.argv.slice(2)` by default, presents dispatch failures through Extension `onError` hooks, sets `process.exitCode` to `1` (or `130` for cancellation), and resolves. Preparation failures render directly to `stderr` because the Extensions that would handle them have not been applied successfully.

Use `run()` for programmatic invocation:

```ts
const output: string[] = [];
const diagnostics: string[] = [];

await app.run(
  ["deploy"],
  { flags: { "dry-run": true } },
  {
    stdout: (line) => output.push(line),
    stderr: (line) => diagnostics.push(line),
  },
);
```

It requires an explicit typed command path, binds structured input directly against the selected command's definitions, honors injected writers, throws failures to the caller without rendering them, and does not modify `process.exitCode`. It resolves to `{ status: "completed", result }` after an action (including actionless and `void` actions), or `{ status: "finished", by }` when an Extension `preRun` hook finishes first. Dynamic paths use `run(runtime(path), runtime(input))` or `execute({ argv })`.

## Successful invocation order

1. **Prepare definitions** — apply Extensions and validate Extension-contributed documentation sections. Command-authored sections are proven by TypeScript or checked when consumed by the constructor or `defineCommand()`. Definitions are compile-time checked, with runtime guards for dynamic definitions. Checked `.flags()` and Extension operations reject duplicate canonical names or colliding spellings with a `DEFINITION` error; Checked `.add()` rejects sibling spelling collisions; trusted `.add()` proves sibling compatibility statically. Alias collisions in still-dynamic Extension contributions route by the precedence below. Extension-contributed commands replace existing commands with the same canonical name, while duplicate Context names without owned-flag collisions use last-write-wins. Canonical command names beat aliases, and the first-registered alias wins among colliding aliases.
2. **Route** — resolve the command path.
3. **Parse or bind input** — `execute()` consumes positional and flag tokens and runs built-in conversions; `run()` binds own argument and flag properties directly, preserving typed values. Both apply string parse transforms and path normalization, and resolve defaults. Argv and checked `run()` validate incoming choices; ordinary `run()` relies on TypeScript membership proof.
4. **Run `preRun` hooks** — invoke Extension hooks in registration order. Hooks may lazily pull flagless Contexts. A hook can return `ctx.finish()` to skip the remaining hooks, validation, schemas, and the Command Action.
5. **Validate structure** — enforce runtime-owned requiredness and post-transform rules; trusted input presence is already type-owned.
6. **Apply schemas** — validate and transform every schema-backed input, aggregating issues.
7. **Resolve Contexts on demand** — each declared `ctx` property constructs that Context once; setup sees only its declared dependencies and validated owned flags.
8. **Run the Command Action**.
9. **Run `postRun` hooks** — invoke every Extension hook in reverse registration order with the completed, finished, or failed outcome. Hooks may pull or reuse Contexts here.
10. **Dispose Contexts** — run `Symbol.dispose` or `Symbol.asyncDispose` in reverse construction order after all post-run hooks, including after failure.

## Error flow

Preparation, routing, and parse failures occur before `preRun` and `postRun`. A failure from `preRun`, validation, schema application, Context construction, or the Command Action still runs every `postRun` hook. The original invocation failure wins over post-run hook failures; after a successful or finished invocation, the first post-run failure fails the invocation after remaining hooks run. Context disposal is LIFO. Crust uses native `AsyncDisposableStack` semantics where available; on Node 22, its fallback aggregates multiple disposal failures in an `AggregateError` rather than a native `SuppressedError` chain.

With `run()`, the original value is thrown to the caller unless disposal also fails. If both invocation and disposal fail, `await using` combines them in a `SuppressedError`: `.error` holds the disposal failure and `.suppressed` holds the invocation failure. This is separate from the disposal stack's aggregation of multiple cleanup failures. Action and Context failures are not converted to `CrustError`.

For `execute()` failures raised during dispatch before `postRun`, Crust invokes Extension `onError` hooks in registration order while Contexts are live, allowing cleanup hooks to observe the handling Extension in `outcome.by`. A hook returns `true` when it rendered the failure; falsy results continue to the next hook and then Core's default renderer, which leaves `by` undefined. `onError` is presentation only and never runs for `run()`.

Routing and parse failures use a fallback hook context with empty `args` and `flags` and no available Contexts. If `postRun` or disposal fails after an otherwise successful or finished invocation, `onError` runs after cleanup and Context pulls reject with `context-after-disposal`. A failure already rendered during dispatch is not presented again after cleanup.

Any `Error` whose `name` is `"AbortError"`, including a `DOMException`, is cancellation. `execute()` sets status `130`, offers the error to `onError` hooks (so an application can render "Operation cancelled" centrally), and renders nothing by default when no hook claims it. `run()` still throws it.

## Setup and cleanup

Choose the mechanism that matches the setup's scope:

- use a Context for command-specific setup and native disposal
- use Extension `preRun` and `postRun` for app-wide behavior around an invocation
- keep ordinary local setup in the Command Action when it is not reusable

This keeps dependency construction lazy and guarantees reverse-order cleanup.
