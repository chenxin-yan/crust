Use a positional argument for the thing a command acts on, and a flag for how it should act.

<include lang="ts" meta="twoslash">
  ../../../examples/guide/inputs.ts
</include>

```sh
$ convert report.md --format markdown
Converting report.md as markdown
```

The Command Action receives both values under the names in their definitions.

## Arguments

<include lang="ts" meta="twoslash">
  ../../../examples/guide/arguments-defaults.ts
</include>

```sh
$ convert report.md
report.md -> json
$ convert report.md yaml draft
report.md -> yaml (draft)
$ convert
Error: Missing required argument "<input>"
```

Positional values fill definitions in order. Each definition is one of:

| Definition       | Omitted value                | Type in the action    |
| ---------------- | ---------------------------- | --------------------- |
| `required: true` | Fails before the action runs | `string`              |
| `default: value` | The default                  | `string`              |
| Neither          | `undefined`                  | `string \| undefined` |

A required argument can't follow an optional one, since the optional one could then never be left out. TypeScript rejects that list.

See [`ArgDef`](/docs/api/types#argdef) for every option.

### Variadic arguments

<include lang="ts" meta="twoslash">
  ../../../examples/guide/arguments-variadic.ts
</include>

```sh
$ copy dist a.ts b.ts
2 files to /home/me/project/dist
```

A final `variadic: true` argument takes any number of values as an array. `type: "path"` resolves each value against the working directory.

### Choices

<include lang="ts" meta="twoslash">
  ../../../examples/guide/arguments-choices.ts
</include>

```sh
$ run python
Error: Invalid value for <runtime>. Expected one of: bun, node
```

`choices` types the value as their string union (plus `undefined` here, since the argument is neither required nor defaulted). Any other value fails before the action runs.

### Words after `--`

```sh
$ convert -- -report.md yaml
-report.md -> yaml
$ convert -- report.md yaml draft extra
Error: Unexpected positional argument: "extra"
```

Words after `--` are never read as flags. They fill arguments like any other positional values, so `--` passes a value that starts with `-`. A word no argument takes is a usage error (exit code `2`), before or after `--`.

This follows the POSIX utility syntax guidelines ([Guideline 10](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html#tag_12_02)): tokens after `--` are operands, like the positionals before it. getopt, Node.js `util.parseArgs`, Commander, and clap behave the same way by default.

### Wrapper commands

A command that hands words to another program declares a list argument for them. `variadic` says which words it collects:

| `variadic`          | Collects                                          | Like                                                         |
| ------------------- | ------------------------------------------------- | ------------------------------------------------------------ |
| `true`              | The remaining positional values                   | `cp <files...>`                                              |
| `"afterDoubleDash"` | Only the words after `--`                         | `npm run <script> -- <args...>`, `kubectl exec <pod> -- ...` |
| `"passthrough"`     | Every word from the first positional on, as typed | `docker run <image> <command...>`, `pnpm run <script> ...`   |

Each value is an array in the action. A command picks at most one of the last two, as every tool does: either the other program's words follow `--`, or they start at the first positional.

#### Only after `--`

<include lang="ts" meta="twoslash">
  ../../../examples/guide/arguments-after-double-dash.ts
</include>

```sh
$ run build core cli -- --watch
build in core, cli: --watch
```

`variadic: "afterDoubleDash"` makes an argument take only the words after `--`, like clap's [`Arg::last`](https://docs.rs/clap/latest/clap/struct.Arg.html#method.last). Use it when the arguments before `--` and the ones after it belong to different consumers, as in `run <task> [packages...] -- <args...>`:

- It must be the last argument. A `variadic: true` argument may come right before it.
- The other arguments fill only from words before `--`, so a variadic before it stops at `--`.
- If it is required and missing, the error says to pass it after `--`.
- Help shows it after `[options]` as `[-- <extra>...]` (`run <task> [packages...] [options] [-- <extra>...]`), or `-- <extra>...` when required. Shell completion offers its values only after `--`.
- [`run()`](/docs/api/crust#runpath-input-options), `--input`, and MCP supply it by name, as an array.

#### From the first positional

<include lang="ts" meta="twoslash">
  ../../../examples/guide/arguments-passthrough.ts
</include>

```sh
$ run --rm alpine ls -la --color
alpine (--rm): ls -la --color
$ run alpine sh -c 'echo $HOME' --rm
alpine: sh -c echo $HOME --rm
```

`variadic: "passthrough"` hands the other program its words as the user typed them, with no `--`:

- The command reads its flags only before its first positional. From there on every word is kept, flags and a later `--` included, so `--rm` after `alpine` belongs to the wrapped command, and so does `--help`. A `--` before the first positional still ends flags.
- It must be the last argument. The arguments before it take the first positional values; it takes the rest.
- Help shows `[options]` before every argument: `run [options] <image> [command...]`. Shell completion offers no flags after the first positional.
- [`run()`](/docs/api/crust#runpath-input-options), `--input`, and MCP supply it by name, as an array.

To fall back to plugins or scripts for words that name no subcommand, give the root action a `"passthrough"` argument; see [Unknown commands](/docs/guide/commands#unknown-commands).

## Flags

<include lang="ts" meta='title="src/cli.ts" twoslash'>
  ../../../examples/guide/flags.ts
</include>

```sh
$ serve --color --port 3000
color=true port=3000
$ serve
color=undefined port=undefined
$ serve --port nope
Error: Expected a number for --port.
```

`.flags()` takes one record keyed by flag name, without the `--` prefix. Use boolean flags for switches and value-taking flags for named settings.

- **Names:** quote a name that is not an identifier, such as `"dry-run"`, and read it as `flags["dry-run"]`. A name must not contain whitespace or `=`, or start with `-`; such a name throws a `DEFINITION` error when the CLI runs from source or in `crust build` (see [definition checks](/docs/api/crust#definition-checks)).
- **Omitted:** a flag without `required`, `default`, or an `env` binding is `undefined`.
- **Value name:** help shows a value-taking flag's type as its value, `--port <number>`; name it with `valueName`, such as `memory: { type: "string", valueName: "bytes" }` for `--memory <bytes>`. Flags that take no value (`boolean`, `count`) have none.
- **Values:** a value-taking flag needs one value, so `serve --port` fails. Built-in types convert the text and reject invalid input, including a blank number, before the action runs. There are no flags whose value is optional (`--color[=when]`), as [POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap12.html#tag_12_02) advises: give the flag `choices` and a `default` instead.

Malformed argv, such as an unknown flag or `serve --port --help`, fails before any hook runs; with [`help()`](/docs/modules/extensions/help), a `-h` or `--help` on that line prints the command's help instead, and the exit code stays `2`. Invalid values fail later, after [flag handlers and `preRun` hooks](/docs/guide/extensions#hooks), so `serve --port nope --help` still prints help and exits `0`. An invalid value is reported before a missing required one.

### Required and defaulted values

<include lang="ts" meta='title="src/publish.ts" twoslash'>
  ../../../examples/guide/flags-required.ts
</include>

```sh
$ publish --token example
publishing to npm
$ publish
Error: Missing required flag "--token"
$ echo $?
2
```

`default` fills in an omitted value, like `registry` above. `required: true` fails before the action runs when the value is missing. Either way, the value is non-optional in the action.

To ask for a missing value on a terminal instead, give it a `prompt` question and add the `prompts()` Extension from [`@crustjs/prompts/extension`](/docs/modules/prompts#ask-for-missing-values):

<include lang="ts" meta='title="src/create.ts"'>
  ../../../examples/guide/flags-prompt.ts
</include>

```sh
$ create
✓ Project name my-app
✓ Template vue
created my-app from vue
$ create < /dev/null
Error: Missing required argument "<name>"
```

A value given on the command line or through `env` is never asked for, and a default is preselected. Without a terminal, such as in CI or a pipe, nothing is asked and the command's own errors apply.

### Aliases and negation

<include lang="ts" meta='title="src/serve.ts"'>
  ../../../examples/guide/flags-aliases.ts
</include>

```sh
$ serve --colour
color=true
$ serve -c
color=true
$ serve --no-colour
color=false
$ serve --color=false
Error: Flag "--color" does not take a value; write --color or --no-color
```

- `short` sets a one-character (one code point) alias; `aliases` sets long aliases. Every spelling writes to the flag's key.
- A boolean flag is `true` when given and takes no value: `--color=false` fails with a hint, as in GNU tools, clap, and Node.js `util.parseArgs`.
- `--no-<name>` and `--no-<alias>` exist only for a flag with `default: true`, where they are the way to turn it off, or with `negatable: true`, such as to override an [environment variable](#environment-variables). Help lists them only for `default: true` flags.

See the [`.flags()` contract](/docs/api/crust#flagsflags) for all accepted spellings.

### Numbers and counts

<include lang="ts" meta='title="src/serve.ts" twoslash'>
  ../../../examples/guide/flags-numbers.ts
</include>

```sh
$ serve --port 8080 -vv
port=8080 ratio=0.5 verbose=2
$ serve --port 0
Error: Expected an integer from 1 to 65535 for --port.
$ serve --ratio 0x1
Error: Expected a number for --ratio.
```

- `type: "number"` reads a finite decimal, such as `-1.5` or `2e3`: no hex, `Infinity`, or surrounding spaces.
- `type: "integer"` reads digits with an optional leading minus.
- `min` and `max` bound a `number` or `integer`, inclusive. They check every value given on argv, in the environment, or in typed `run()` input, but not the `default`. Arguments take them too.
- `type: "count"` counts the flag's occurrences: `-vvv` is `3`, and an omitted flag is `0`, typed `number`. It takes no value, no negation, and no `env`.

### Repeated values

<include lang="ts" meta='title="src/serve-values.ts" twoslash'>
  ../../../examples/guide/flags-values.ts
</include>

```sh
$ serve --target linux -t darwin
targets=linux,darwin runtime=bun tag=undefined
```

`multiple: true` lets a flag occur more than once; each occurrence adds one value, in order. Omitted, it is `undefined` unless it has a default or `env` binding.

Repeat the flag for every value, or set a [`delimiter`](#delimiters). In `--target linux darwin`, `darwin` is a positional argument, not another target.

### Flag choices

`choices` restricts a flag to a fixed set of strings, like `runtime` above:

```sh
$ serve --runtime node
targets=undefined runtime=node tag=undefined
$ serve --runtime python
Error: Invalid value for --runtime. Expected one of: bun, node
$ echo $?
2
```

### Environment variables

<include lang="ts" meta='title="src/publish.ts"'>
  ../../../examples/guide/flags-env.ts
</include>

```sh
$ PUBLISH_TOKEN=example publish
publishing to npm tags=undefined
$ PUBLISH_TOKEN=example PUBLISH_REGISTRY=github publish --registry jsr
publishing to jsr tags=undefined
$ PUBLISH_TOKEN=example npm_config_registry=github publish
publishing to github tags=undefined
```

`env: "VARIABLE"` reads a flag from that variable when argv omits it. Variables are read when the command runs, not when the flag is defined.

- **Precedence:** argv, then env, then `default`. An environment value satisfies `required`.
- **Validation:** environment text goes through the same `type` conversion, `choices`, `parse`, and schemas as argv.
- **Lists:** `env: ["PUBLISH_REGISTRY", "npm_config_registry"]` reads the first variable that is set.
- **Booleans:** `true`, `1`, `yes`, and `on` are true; `false`, `0`, `no`, and `off` are false, in any letter case. Any other value fails, naming the variable. An empty variable counts as unset. A positional boolean argument reads the same words.
- **Invalid values:** an invalid argv value fails instead of trying env; an invalid environment value, including a blank `PORT=` for a number flag, fails instead of using the default. Neither blocks `--help` or `--version`.
- **Docs:** generated documentation lists the variables as `[env: PUBLISH_REGISTRY, npm_config_registry]`, never their values.
- **Programmatic calls:** [`run()`](/docs/api/crust#runpath-input-options) reads `process.env` too, for flags its input omits. To isolate a test from the caller's shell, wrap the call in [`withEnv()`](/docs/modules/testing#withenvenv-fn).
- **Arguments:** positional arguments have no `env`; use a flag.
- **Config files:** to also read a value from a config file, define it as a setting of [`@crustjs/config`](/docs/modules/config) and take its flag with `config.flag()`: the files are read after the variable, before `default`.
- **Secrets:** take tokens from `env`, stdin, or a prompt, not argv, which lands in shell history and process listings. Keep them out of [`nextSteps`](/docs/modules/extensions/next-steps) input too: steps print as command lines.

#### Delimiters

`delimiter` splits each string argv value of a `multiple: true` flag, and its environment variable's text, into separate values. Without it, each occurrence and the whole variable are one value each.

```sh
$ PUBLISH_TOKEN=example PUBLISH_TAGS=latest,,beta publish
publishing to npm tags=latest,beta
$ PUBLISH_TOKEN=example publish --tag latest,beta --tag next
publishing to npm tags=latest,beta,next
```

- It requires `multiple: true`, which TypeScript checks, and a nonempty separator. An empty `delimiter` or variable name throws a `DEFINITION` error when the CLI runs from source or in `crust build`.
- Empty segments are dropped. On the command line, a flag left with zero values (`--tag ""`) is an empty list, which wins over the default and the environment; a required flag still needs a value. A variable left with zero values counts as unset.
- [`run()`](/docs/api/crust#runpath-input-options) takes arrays and never splits them.
- Boolean argv stays `--flag`. Repeated booleans can split environment text such as `true,false` with `env: "FEATURES", delimiter: ","`.

### Values that start with `-`

```sh
$ serve --tag=-nightly
targets=undefined runtime=bun tag=-nightly
$ serve --tag -nightly
Error: Missing value for flag "--tag"; to pass a value starting with "-", write --tag=<value>
```

Attach a dash-leading flag value with `=`, as Node.js `util.parseArgs` and argparse require: a separate word that starts with `-` more likely means a forgotten value. The exception is a negative number for an `integer` or `number` flag, so `head -n -5` reads `-5`. For a positional argument, pass it after `--`, as in `seek -- -5`: POSIX treats every token after `--` as an operand, even one that starts with `-`; see [Words after `--`](#words-after---). Arguments before a [`variadic: "afterDoubleDash"`](#only-after---) argument read nothing after `--`, so give them such values through a flag instead.

A short flag's attached value is everything after the letter, `=` included, as in POSIX tools, `util.parseArgs`, and Commander: `cut -d=` splits on `=`. So `-t=vue` gives `--template` the value `=vue`, and when that value is rejected the error says what to write instead:

```sh
$ create -t=vue
Error: Invalid value for --template. Expected one of: vue, react. Write -t vue or --template=vue.
$ create -D=1
Error: Flag "-D" does not take a value.
```

### One of several flags

<include lang="ts" meta='title="src/deploy.ts" twoslash'>
  ../../../examples/guide/flags-groups.ts
</include>

```sh
$ deploy --org-id acme
deploying to acme
$ deploy --all --org-id acme
Error: Flags "--all" and "--org-id" cannot be used together
$ deploy
Error: Missing one of the required flags "--org-id", "--all"
$ DEPLOY_ORG_ID=acme deploy --all
deploying to every org
```

`type: "exclusive"` declares mutually exclusive flags as one entry. Its `flags` are the members, each a single-value flag with its own spellings; usage shows the group as `(--org-id <string> | --all)`.

- **Value:** the entry's key holds `{ flag, value }` for the member given, or `{ flag }` for a boolean member, so a `switch` on `flag` narrows `value`. Typed [`run()`](/docs/api/crust#runpath-input-options) takes the same shape under `flags`: `{ flags: { scope: { flag: "org-id", value: "acme" } } }`. `--input` and MCP take it under the group's key in their flat object: `{ "scope": { "flag": "org-id", "value": "acme" } }`.
- **Count:** without `required`, at most one member may be given and an absent group is `undefined`; with `required: true`, exactly one. Two members, or none when required, is a usage error (exit status 2).
- **Sources:** compared level by level. The first of the command line and the environment where any member has a value decides, so `--all` above wins over `DEPLOY_ORG_ID`; two members' variables both set is an error naming both. A boolean member's variable set to a false word counts as unset. Members take no `default`, `required`, `negatable`, `multiple`, or `requires`.
- **Names:** member names share the command's flag namespace with the group's key and every other flag; a collision throws a `DEFINITION` error when the CLI runs from source or in `crust build`. The key itself is no command-line spelling.

`requires` lists flags of the same record that a flag needs: above, `--jq` without `--json` is a usage error. A required flag counts as given from the command line, the environment, or typed input, but not from its `default`, and a boolean's `false` doesn't count. Requiring an exclusive group needs any one of its members. TypeScript checks that each name is a flag of the record.

### Hidden and deprecated flags

`hidden: true` keeps a flag working but leaves it out of help, man pages, completion, generated skills, search, and command input schemas, the same places as a hidden command. `deprecated: "Use --memory instead."` on a flag, or in a command's config, prints one warning on stderr when the command line uses it, and help marks it:

```sh
$ deploy --all --kernel-memory 1g
Warning: flag "--kernel-memory" is deprecated. Use --memory instead.
deploying to every org
```

The two are independent: set both to stop listing a deprecated flag, as `--kernel-memory` above. A value from the environment or from typed `run()` input prints no warning.

### Reuse across commands

<include lang="ts" meta='title="src/tools.ts"'>

```sh
$ tools print --format yaml
print as yaml
$ tools inspect
```

`defineFlag()` creates one definition for several commands. Attach it under a key on each command that should parse it; the key names the flag, so `{ format }` defines `--format`.

## Validation

Built-in types cover common values, such as the `number` flag above. For custom parsers and Standard Schemas, see [Values and validation](/docs/guide/values-and-validation).

A `json` flag with a schema takes a structured value. `body: { type: "json", schema: User }` parses `--body '{"name":"ada"}'` as JSON and validates the result with `User`. The schema's JSON Schema becomes the flag's shape for `--input`, the `schema` command, and MCP tools, so an agent sends an object. See [what the schema receives](/docs/guide/values-and-validation#what-the-schema-receives).
