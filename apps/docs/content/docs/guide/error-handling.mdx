## CrustError

Crust uses exactly four framework error codes:

| Code                | Meaning                                                                        |
| ------------------- | ------------------------------------------------------------------------------ |
| `DEFINITION`        | A runtime recipe, Extension injection, Context, or documentation-section error |
| `PARSE`             | Argv syntax, unknown flag, or built-in conversion failure                      |
| `VALIDATION`        | Missing/invalid values or aggregated Standard Schema issues                    |
| `COMMAND_NOT_FOUND` | An unknown subcommand at the current command path                              |

```ts
import { CrustError } from "@crustjs/core";

try {
  await app.run(path, input);
} catch (error) {
  if (error instanceof CrustError && error.is("VALIDATION")) {
    console.error(error.details?.issues);
  }
}
```

A `CrustError` exposes `code`, `message`, `details`, optional `cause`, `.is(code)`, and `toJSON()`.

## Trust boundaries

Crust checks developer-authored definitions at compile time through TypeScript. `FIX_*` brands report malformed definitions and collisions at their call sites; Core does not repeat those checks when the command tree is built.

Argv is untrusted and remains runtime-validated. Invalid tokens, choices, and built-in conversions throw `PARSE`; missing values and Standard Schema issues throw `VALIDATION`. Declared Context dependencies are checked statically; lazy bag access retains runtime `DEFINITION` guards for missing providers on dynamically assembled paths, dependency cycles, and lifecycle misuse. Materialization retains runtime checks that a command recipe returns the seeded builder and does not register nested Extensions, because recipe behavior is dynamic. Snapshot preparation also retains runtime checks for authored and Extension-contributed documentation sections.

`COMMAND_NOT_FOUND` details contain `input`, `available`, `commandPath`, and `parentCommand`, a readonly serializable Command Snapshot. `available` contains only visible child command names; hidden commands remain invocable but are omitted from user-facing choices.

## Application errors pass through

Errors from Command Actions and Context construction are not converted to `CrustError`. A single disposal failure is likewise rethrown unchanged; disposal stacks combine multiple failures as a native `SuppressedError` chain or, on the Node 22 fallback, an `AggregateError`:

```ts
const failure = new Error("service unavailable");
const app = new Crust("app").action(() => {
  throw failure;
});

try {
  await app.run([]);
} catch (error) {
  console.assert(error === failure);
}
```

Use ordinary application error classes when callers need to distinguish domain failures.

## Terminal presentation

Extension `onError` hooks present failures reached during `execute()` dispatch:

<include lang="ts">../../../examples/extensions/hooks.ts#service-errors</include>

A hook returns `true` after rendering, or a falsy value to delegate to the next hook. Core's default renderer is last. Core establishes a nonzero status before invoking the chain, so presentation cannot turn a failure into success.

Failures before dispatch bypass the hook chain. Extension application and command-tree materialization failures render directly to `io.stderr`; snapshot preparation and build-hook failures are printed directly.

`run()` never invokes these hooks. It throws the original error and leaves rendering and exit status to its caller.

## Cancellation

Prompt cancellation and other cooperative cancellation use a `DOMException` named `"AbortError"`:

```ts
try {
  await app.run(path, input);
} catch (error) {
  if (error instanceof DOMException && error.name === "AbortError") {
    return;
  }
  throw error;
}
```

`execute()` sets `process.exitCode` to `130` and offers the `AbortError` to Extension `onError` hooks, so an application can render a cancellation message in one place:

```ts
const cancelMessage = defineExtension(defineExtensionId("cancel-message"), {
  hooks: {
    onError(error, ctx) {
      if (error instanceof DOMException && error.name === "AbortError") {
        ctx.stderr("Operation cancelled");
        return true;
      }
    },
  },
});
```

When no hook claims it, cancellation stays silent — there is no default rendering. `run()` throws the same exception.
