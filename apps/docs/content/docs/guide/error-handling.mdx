Throw an actionable `Error`. At the CLI entry point, `execute()` writes its message to stderr and sets exit status 1:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/error-handling-cli.ts
</include>

```sh
$ bun cli.ts
Error: Could not connect to api.example.com. Check your network connection.
# exit 1
```

`execute()` resolves to the exit code rather than rethrowing the error. For tests and programmatic callers, use [`run()`](#handle-errors-in-code) to inspect failures without rendering them.

- Don't catch an error just to print it: that hides the failure from Crust and can leave the exit status at 0.
- Don't call `process.exit()`: it stops the process before cleanup can finish.

## Let Crust validate

Declare required values and allowed choices instead of checking them in the Command Action:

<include lang="ts">../../../examples/guide/error-handling.ts#validation</include>

```sh
$ greet
Error: Missing required flag "--name"
$ greet --name Linus
Error: Invalid value for --name. Expected one of: Ada, Grace
```

Both exit with status 2, the [usage error](#exit-status) status, before the action runs. These declarations also drive help text and inferred types. See [Values and validation](/docs/guide/values-and-validation) for custom parsing and schemas.

## Fail from anywhere

Throw from actions, awaited helpers, or Context setup. Crust still disposes constructed [Contexts](/docs/guide/contexts):

<include lang="ts">../../../examples/guide/error-handling.ts#cleanup</include>

```sh
$ deploy
Error: Deployment service is unavailable. Try again later.
Closed database
# exit 1
```

Context-managed resources don't need action-level `try`/`finally`. If disposal also fails, Crust adds `Cleanup failed: …` without hiding the original failure. See [failure propagation](/docs/api/errors#propagation-boundaries) for lifecycle details.

## Define error classes

When the same failure is thrown from several places, or tests and callers need to recognize it, give it a class:

<include lang="ts">../../../examples/guide/error-handling.ts#error-class</include>

```sh
$ app
Error: No app.config.json found. Run `app init` to create one.
# exit 1
```

- Recognize it with `instanceof`, never by message text, in [`run()` outcomes](#handle-errors-in-code), tests, and [`onError` hooks](#customize-error-output).
- Pass the underlying failure as `{ cause }` to keep it for [debugging](#print-stack-traces). Crust renders only the message.
- Setting `name` is optional: it labels stack traces. Crust never reads `name` or any other field of your errors to decide what to do, except `AbortError` for [cancellation](#cancellation) and a non-zero integer `exitCode` for the [exit status](#exit-status).

## Exit status

`execute()` ends every invocation with one exit code, resolves to it, and sets `process.exitCode` to it once at the end:

| Status        | When                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`           | The action completed, or an Extension handled the invocation, such as `--help`                                                                                            |
| `n`           | The action called `exitCode(n)` and completed                                                                                                                             |
| `1`           | The action, a hook, or cleanup threw, or a write to stdout failed (`app > /dev/full`); a thrown value with a non-zero integer `exitCode` property exits with that instead |
| `2`           | A usage error: a [`CrustError`](/docs/api/errors#codes) with code `PARSE`, `VALIDATION`, or `COMMAND_NOT_FOUND`                                                           |
| `130` / `143` | Ctrl+C or `SIGTERM` [cancelled](#cancellation) the run, whatever the action did                                                                                           |
| `141`         | The reader of stdout went away, as in `app \| head -1`: the run is [cancelled](#cancellation), whatever the action did                                                    |

To report an outcome without failing, as `grep` and `diff` do, call `exitCode(n)` with an integer `n` from the action's context. The action carries on, and the last call wins; `return` or `throw` to stop:

<include lang="ts">../../../examples/guide/error-handling.ts#exit-code</include>

```sh
$ search b a b
b
$ search z a
# exit 1
$ search
Error: Missing required argument "<pattern>"
# exit 2
```

- To fail with a status of your own, throw an error that carries it, such as `Object.assign(new Error("Container exited"), { exitCode: 137 })`. An error from a child process library that sets `exitCode` passes its status through unchanged, except a multiple of 256, which a shell would read as success: it exits `1`.
- Setting `process.exitCode` in an action or hook has no effect: `execute()` overwrites it. `onError` hooks change how a failure prints, never its status.
- [`run()` outcomes](#handle-errors-in-code) and [`captureExecute()`](/docs/guide/testing#capture-terminal-behavior) report the same `exitCode`. An [MCP](/docs/modules/mcp#results) tool call whose exit code is not 0 is a tool error (`isError`), a completed one included.

## Customize error output

To change how failures are presented, write an Extension with an [`onError`](/docs/api/types#extensionhooks) hook. The first hook that returns `true` claims the failure and replaces the default `Error:` line; the exit status doesn't change. A [renderer's `error`](/docs/guide/extensions#renderers) handles failures no hook claimed.

### Print stack traces

Crust prints only the message. To see the stack and the `cause` chain when debugging, add a `--debug` flag and an `onError` hook that prints the stack of the error and of each `cause` in turn:

<include lang="ts">../../../examples/guide/error-handling.ts#debug</include>

```sh
$ app --debug
ConfigNotFoundError: No app.config.json found. Run `app init` to create one.
    at loadConfig (cli.ts:…)
    …
Caused by: Error: ENOENT: no such file or directory, open 'app.config.json'
    at async loadConfig (cli.ts:…)
    …
# exit 1
```

- The hook prints only stacks, not other fields of the errors: a field such as a failed request's headers can hold a token. A `cause` cycle prints each error once.
- The hook skips cancellations, so Ctrl+C stays silent with `--debug`.
- Failures to route or parse argv, such as an unknown flag, reach `onError` before flags are parsed, so they print only the message.
- A claimed failure skips the renderer's `error`: under [`--json`](/docs/modules/extensions/json), `--debug` prints the stack instead of the JSON error line.

## Quiet output

Errors always print. To let users skip a command's optional output, such as progress lines, define a `--quiet` flag on a [Context](/docs/guide/contexts#flags-owned-by-a-context) and check it in the commands that [`.use()`](/docs/guide/contexts#use-from-a-reusable-command) it:

<include lang="ts">../../../examples/guide/error-handling.ts#quiet</include>

```sh
$ app publish
Uploading 3 files...
Published v1.2.0
$ app publish -q
Published v1.2.0
$ APP_QUIET=1 app publish
Published v1.2.0
```

- `APP_QUIET` applies when the flag is omitted: `1`, `true`, `yes`, or `on` turns quiet on. `negatable: true` adds `--no-quiet` to override it. See [environment variables](/docs/guide/arguments-and-flags#environment-variables).
- Each command decides what to skip. Other commands reject `--quiet` as an unknown flag, and Extensions keep their own output.

## Cancellation

Ctrl+C or Ctrl+D in a Crust prompt raises an `AbortError`. By default, `execute()` prints no error and returns exit code 130:

<include lang="ts">../../../examples/guide/error-handling.ts#cancellation</include>

Keep side effects after prompts so cancelling leaves nothing to undo.

- To cancel explicitly, throw `new DOMException("Cancelled", "AbortError")`.
- The first Ctrl+C during `execute()` aborts the action's `signal`. Pass it to cancellable APIs such as `fetch(url, { signal })`; work that ignores it keeps running.
- Cleanup still runs. If it fails, its failure prints and the exit code stays 130.
- `SIGTERM`, sent by `docker stop`, Kubernetes, `timeout`, and CI cancellation, cancels the same way and exits 143.
- When the reader of stdout goes away, as in `app | head -1`, the next `stdout(text)` or `stdout.write(chunk)` throws an `AbortError` and aborts the `signal` the same way: nothing prints and the exit code is 141 (128 + `SIGPIPE`, which Node.js and Bun ignore, so the process never dies by it). Any other failed write to stdout, such as a full disk, throws the system error and exits 1. A failed write to stderr is ignored. Windows keeps the stream writer, which never throws.
- `signal.reason.cause` names what cancelled the run: `"SIGINT"`, `"SIGTERM"`, or `"SIGPIPE"`. A caller's own `execute({ signal })` abort keeps the caller's reason. Read it, not the message, to pass the signal on to a child process.
- After a Ctrl+C or `SIGTERM`, `execute()` resolves 130 or 143 once cleanup finishes, even when the action ignored the `signal` and completed. Code after it still runs; then the process ends by that signal, so shells see 130 or 143 and a Ctrl+C stops a shell loop. Call `process.exit(code)` after `execute()` to exit with a code instead.

See [`execute()`](/docs/api/crust#executeoptions) for caller signals and repeated signals.

## Framework errors

Crust reports its own failures as [`CrustError`](/docs/api/errors): unknown commands, argv syntax, conversion and validation of arguments and flags, results that fail [`.output()`](/docs/guide/values-and-validation#command-results), missing or invalid [`@crustjs/env`](/docs/modules/env) variables, and mistakes in command or Extension definitions. Each carries a [`code`](/docs/api/errors#codes), such as `PARSE`, `VALIDATION`, or `COMMAND_NOT_FOUND`.

- Branch on the code, not message text: after `error instanceof CrustError`, `error.is("VALIDATION")` also narrows `details`, such as the schema issues and their `flags.<name>` paths.
- `toJSON()` returns `code`, `message`, and `details` when present.
- Don't throw `CrustError` for your own failures: its codes describe Crust's. Throw an `Error` or [your own class](#define-error-classes).

### Errors never echo values

Crust's own errors about an argument or flag value never print the value, in the message, `details`, or `cause`. They name the argument or flag, plus the environment variable when the value came from one, so a secret read from the environment stays out of CI logs and agent transcripts:

```sh
$ PORT=abc serve
Error: Expected a number for --port (from $PORT).
```

One exception: a command-line value Crust rejects that starts with `=`, as in `-t=vue`, is shown without the `=` in a hint (`Write -t vue or --template=vue.`). A value from the environment is never shown.

Tokens Crust cannot match to an argument or flag, such as an unknown command or an extra positional argument, are echoed so a typo is visible. Text you supply is printed as written: errors thrown by a custom `parse` and Standard Schema issue messages are yours to keep free of values.

See the [errors reference](/docs/api/errors) for every code, its `details`, and where failures propagate.
