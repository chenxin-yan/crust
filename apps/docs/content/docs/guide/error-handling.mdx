Throw an actionable `Error`. At the CLI entry point, `execute()` writes its message to stderr and sets exit status 1:

<include lang="ts" meta='title="cli.ts"'>
  ../../../examples/guide/error-handling-cli.ts
</include>

```sh
$ bun cli.ts
Error: Could not connect to api.example.com. Check your network connection.
# exit 1
```

`execute()` resolves to the exit code rather than rethrowing the error. For tests and programmatic callers, use [`run()`](#handle-errors-in-code) to inspect failures without rendering them.

- Don't catch an error just to print it: that hides the failure from Crust and can leave the exit status at 0.
- Don't call `process.exit()`: it stops the process before cleanup can finish.

## Let Crust validate

Declare required values and allowed choices instead of checking them in the Command Action:

<include lang="ts">../../../examples/guide/error-handling.ts#validation</include>

```sh
$ greet
Error: Missing required flag "--name"
$ greet --name Linus
Error: Invalid value "Linus" for --name. Expected one of: Ada, Grace
```

Both exit with status 1 before the action runs. These declarations also drive help text and inferred types. See [Values and validation](/docs/guide/values-and-validation) for custom parsing and schemas.

## Fail from anywhere

Throw from actions, awaited helpers, or Context setup. Crust still disposes constructed [Contexts](/docs/guide/contexts):

<include lang="ts">../../../examples/guide/error-handling.ts#cleanup</include>

```sh
$ deploy
Error: Deployment service is unavailable. Try again later.
Closed database
# exit 1
```

Context-managed resources don't need action-level `try`/`finally`. If disposal also fails, Crust adds `Cleanup failed: …` without hiding the original failure. See [failure propagation](/docs/api/errors#propagation-boundaries) for lifecycle details.

## Define error classes

When the same failure is thrown from several places, or tests and callers need to recognize it, give it a class:

<include lang="ts">../../../examples/guide/error-handling.ts#error-class</include>

```sh
$ app
Error: No app.config.json found. Run `app init` to create one.
# exit 1
```

- Recognize it with `instanceof`, never by message text, in [`run()` outcomes](#handle-errors-in-code), tests, and [`nextSteps({ onError })`](#suggest-the-fix).
- Pass the underlying failure as `{ cause }` to keep it for debugging. Crust renders only the message.
- Setting `name` is optional: it labels stack traces and [MCP](/docs/modules/mcp#results) tool errors (`<name>: <message>`). Crust never reads `name` or any other field of your errors to decide what to do, except `AbortError` for [cancellation](#cancellation).

## Suggest the fix

To print the fix as a runnable command, register [`nextSteps()`](/docs/modules/extensions/next-steps) and return recovery steps from its `onError` option for the errors you recognize with `instanceof`. They print after the error message as `Next steps:`, as shell-quoted command lines checked against your command tree.

To change how failures are presented, write an Extension with an [`onError`](/docs/api/types#extensionhooks) hook. The first hook that returns `true` claims the failure and replaces the default `Error:` line; the exit status stays 1. [`didYouMean()`](/docs/modules/extensions/did-you-mean) uses this hook for command suggestions.

## Cancellation

Ctrl+C in a Crust prompt raises an `AbortError`. By default, `execute()` prints no error and returns exit code 130:

<include lang="ts">../../../examples/guide/error-handling.ts#cancellation</include>

Keep side effects after prompts so cancelling leaves nothing to undo. To cancel explicitly, throw `new DOMException("Cancelled", "AbortError")`.

The first Ctrl+C during `execute()` aborts the action's `signal`. Pass it to cancellable APIs such as `fetch(url, { signal })`; work that ignores it keeps running. An `AbortError` still allows cleanup; failed cleanup changes the exit code to 1. See [`execute()`](/docs/api/crust#executeoptions) for caller signals and repeated Ctrl+C.

## Framework errors

Crust reports its own failures as [`CrustError`](/docs/api/errors): unknown commands, argv syntax, conversion and validation of arguments and flags, results that fail [`.output()`](/docs/guide/values-and-validation#command-results), and mistakes in command or Extension definitions. Each carries a `code`, such as `PARSE`, `VALIDATION`, or `COMMAND_NOT_FOUND`.

- Branch on the code, not message text: after `error instanceof CrustError`, `error.is("VALIDATION")` also narrows `details`, such as the schema issues and their `flags.<name>` paths.
- `toJSON()` returns `code`, `message`, and `details` when present. [`json()`](/docs/modules/extensions/json) prints it for `--json` failures, and MCP reports `<code>: <message>`.
- Don't throw `CrustError` for your own failures: its codes describe Crust's. Throw an `Error` or [your own class](#define-error-classes).

See the [errors reference](/docs/api/errors) for every code, its `details`, and where failures propagate.
