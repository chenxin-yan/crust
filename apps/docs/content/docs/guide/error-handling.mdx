Throw an `Error` with a message the user can act on. Crust prints the message and exits with status 1.

<include lang="ts">../../../examples/guide/error-handling-cli.ts</include>

```sh
$ deploy
Error: Could not connect to api.example.com. Check your network connection.
$ echo $?
1
```

## What your user sees

```sh
$ greet
Error: Missing required flag "--name"
$ echo $?
1
```

Crust uses one terminal failure format whether the error comes from your code or from its checks.

| Failure            | Stderr                                                                                                                                                                                                | Exit code |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------: |
| Your `Error`       | `Error: Could not connect to api.example.com. Check your network connection.`                                                                                                                         |         1 |
| A Crust check      | Missing flag: `Error: Missing required flag "--name"`<br />Bad choice: `Error: Invalid value "Linus" for --name. Expected one of: Ada, Grace`<br />Unknown command: `Error: Unknown command "stats".` |         1 |
| Ctrl+C in a prompt | Nothing                                                                                                                                                                                               |       130 |

## Let Crust validate

<include lang="ts">../../../examples/guide/error-handling.ts#validation</include>

Prefer `required: true` to checking for a missing value in the Command Action. The declaration keeps help text, inferred types, and terminal messages in sync. Put allowed values in `choices` for the same reason.

## Fail from anywhere

<include lang="ts">../../../examples/guide/error-handling.ts#cleanup</include>

```sh
$ deploy
Error: Deployment service is unavailable. Try again later.
Closed database
$ echo $?
1
```

An `Error` from the helper reaches the same renderer as one from a Command Action. Context disposal still runs after failure, so the Command Action does not need `try`/`finally` for Context cleanup.

Do not call `process.exit()`. It stops the process before Crust can run cleanup.

Do not catch an error just to print it. That hides the failure from `run()` and can leave the terminal exit code at 0.

## Cancellation

<include lang="ts">../../../examples/guide/error-handling.ts#cancellation</include>

```sh
$ scaffold
? Project name? ^C
$ echo $?
130
```

Ctrl+C in a prompt prints no error and exits with status 130. To cancel from your own code, throw `new DOMException("Cancelled", "AbortError")`. Put file writes and other side effects after prompts so cancellation leaves nothing to undo.

Outside prompts, Ctrl+C terminates the process immediately by default. When an action has work in flight that should stop cleanly (an HTTP request, a child process, a long loop), run the app with `execute({ sigint: "abort" })` and pass `ctx.signal` to that work: the first Ctrl+C aborts the signal with an `AbortError`, the action fails with it, cleanup runs, and the exit status is 130. A second Ctrl+C exits at once. See [`execute()`](/docs/api/crust#executeoptions).

## Customize the message

<include lang="ts">../../../examples/guide/error-handling.ts#custom-message</include>

Extending the root with `configErrors` adds a hint for this known error class; returning `true` prevents the default renderer from printing it again. [`didYouMean()`](/docs/modules/extensions/did-you-mean) is the built-in example. See [Extension hooks](/docs/api/types#extensionhooks) for the hook contract.

```text
Error: Config file not found.
Hint: Run init to create the config file.
```

## In tests

<include lang="ts">../../../examples/guide/error-handling.ts#tests</include>

`run()` hands your `Error` back unchanged in a failed outcome; `captureExecute()` from [`@crustjs/testing`](/docs/guide/testing) shows what the terminal user would see. Errors raised by Crust itself are `CrustError` values; narrow them with `.is(code)` as shown in the [error reference](/docs/api/errors#codes).
