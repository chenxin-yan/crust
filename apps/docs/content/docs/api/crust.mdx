`Crust` builds an executable application root. `defineCommand()` builds inert reusable definitions that become commands only when added. Every fluent method returns a new builder; the original is unchanged.

Exact overloads and generic constraints live in [`command/crust.ts`](https://github.com/chenxin-yan/crust/blob/main/packages/core/src/command/crust.ts). This page documents behavior; hover types in your editor for the inferred shapes.

## Reusable command definitions

### `defineCommand(name, config?, recipe)`

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#define
</include>

`defineCommand()` returns a frozen `CommandDefinition`: a name, static config, and a recipe. It has no command node and no `run()` or `execute()`. The recipe receives a `CommandDefinitionBuilder`, the configure-only form of `Crust`, and runs once for each `.add()`, not when the definition is created. Side effects in a recipe therefore repeat for every addition.

<auto-type-table path="../../../../../packages/core/src/command/crust.ts" name="CommandConfig" />

Application `version` belongs only in the root `Crust` constructor. Aliases must be non-empty, contain no whitespace, not start with `-`, and differ from the canonical name. Blank names and `__proto__` fail typecheck.

`.use(logging)` declares demand for a factory; `.provide(logging())` supplies an instance. A reusable definition sees only the Contexts it declares with `.use()`, and those demands are checked against the providers available where it is added.

`definition.as(name)` returns the same definition under another name, so one definition can be added twice. Its configured aliases travel with it and must stay unique among siblings.

## Chaining semantics

`.flags()`, `.args()`, `.provide()`, `.add()`, and `.extend()` are variadic, accept dynamic collections, and accumulate across calls. TypeScript rejects statically known invalid definitions and collisions; dynamically assembled definitions are checked when the builder consumes them and throw a `DEFINITION` [error](/docs/api/errors).

### Conditional chains

Each call returns a builder whose type records what was added so far, so a conditional can produce a union of builder types that the next call cannot infer from. Crust rejects such calls instead of silently losing types:

```ts
// Compile error: inputs cannot be inferred from this builder union.
(prod ? c.provide(db()) : c).provide(cache());
```

Keep the command shape static and put the condition in the Context value:

```ts
const db = defineContext("db", () => (prod ? connect() : null));
c.provide(db(), cache()); // db resolves to Connection | null
```

If the shape genuinely differs, write the full chain in each branch:

```ts
prod ? c.provide(db(), cache()) : c.provide(cache());
```

## `.args(...defs)`

Defines positional arguments in call order. Definitions come from `defineArg(name, def)` or inline literals; see [`ArgDef`](/docs/api/types#argdef).

```ts
const copy = new Crust("copy").args(
  { name: "source", type: "path", required: true },
  { name: "destinations", type: "path", variadic: true },
);
```

Names must be unique, custom `parse` functions must be synchronous, and only the last argument across all calls may be variadic. A schema-backed argument receives the raw string (`string[]` when variadic, `undefined` when absent); its schema owns coercion, defaults, requiredness, and validation, so it cannot also set `type`, `default`, `required`, `choices`, or `parse`.

## `.flags(...defs)`

Defines flags local to this command. Definitions come from `defineFlag(name, def)` or inline literals carrying `name`; names omit the `--` prefix. See [`FlagDef`](/docs/api/types#flagdef).

```ts
const serve = new Crust("serve").flags(
  { name: "verbose", type: "boolean", short: "v" },
  { name: "port", type: "number", default: 3000 },
  { name: "include", type: "string", multiple: true },
);
```

- Long names, aliases, and `short` spellings must not collide with other flags visible on the command.
- Boolean flags accept `--no-<spelling>` for the name and every long alias. `noNegate: true` rejects negation with a `PARSE` error and hides it from help, completion, and man output. Names and aliases beginning with `no-` are reserved.
- Schema-backed flags still set `type: "string" | "boolean"` to declare whether a value token follows; the schema receives the raw value, including `undefined` when omitted.
- Flags declared here do not reach subcommands. To share flags with descendants, give them to a [Context](/docs/guide/contexts) and `.provide()` it.

## `.use(...factories)`

Recipe-only. Declares the Context factories a reusable definition consumes, without providing instances. The call requires at least one factory; repeated calls accumulate. The demands and their transitive dependencies are checked when the definition reaches `.add()`.

## `.provide(...instances)`

Attaches Context instances created by invoking `defineContext()` factories. The Context is available to this command and to descendants added **after** this call, and is constructed lazily when its `ctx` property is first read.

```ts
const database = defineContext("database", ({ options }: { options: { url: string } }) => ({
  url: options.url,
  async [Symbol.asyncDispose]() {},
}));

const app = new Crust("my-cli")
  .provide(database({ url: "postgres://localhost/app" }))
  .action(async ({ ctx }) => (await ctx.database).url);
```

- A Context's `flags` are installed on this command and later-added descendants. The builder's flag type includes them.
- Within one call, dependencies may appear in any order; across calls, providers must precede their consumers.
- Names, dependencies, and owned-flag collisions are checked by TypeScript. Dynamic collections that collide throw a `DEFINITION` error. Missing providers, dependency cycles, and lifecycle misuse on dynamic paths are reported as `DEFINITION` errors when a Context is pulled.
- A command can shadow an inherited Context. After `.action()`, a local replacement must satisfy the value type that action received.

### Context lifecycle

- Cleanup registered with setup's `defer(cleanup)`, and returned values implementing `Symbol.dispose` or `Symbol.asyncDispose`, run in reverse registration order after `postRun` hooks, including when the action throws.
- Call `defer` immediately after acquiring each resource so a later setup failure still releases it. Calling `defer` after setup has settled throws a `DEFINITION` error.
- A returned disposable is disposed for you. Do not also close it with `defer`, `await using`, or in the action, and do not keep it after the invocation.
- A value supplied through `factory.of(value)` is disposed by every invocation that pulls it. Use a fake without a disposer for repeated invocations.
- Await dependencies during setup, before registering a `defer` callback that needs them, so they are still live when that callback runs.
- Setup receives the invocation's `signal`. Pass it to cancellable initialization such as `fetch(url, { signal })`; do not reuse it for cleanup work that must finish.

See [Contexts](/docs/guide/contexts) for worked examples.

## `.extend(...extensions)`

Root-only. Registers application-wide [Extensions](/docs/guide/extensions) in registration order. A repeated `ExtensionId` replaces the earlier registration.

```ts
import { help, version } from "@crustjs/extensions";

const app = new Crust("my-cli", { version: "1.2.3" }).extend(version(), help());
```

Extensions apply to every command, including definitions added before `.extend()`. Contexts an Extension provides reach the root and existing descendants while more-specific local providers win. Extension commands and flags are materialized when the application prepares. Extensions must come from `defineExtension()`.

## `.action(action)`

Defines the Command Action. It runs after routing, parsing, `preRun` hooks, and validation. Its awaited return value becomes the `result` of typed `run()` calls. A later `.action()` replaces both the action and its result type.

```ts
const greet = new Crust("greet")
  .args({ name: "name", type: "string", required: true })
  .action(({ args, stdout }) => stdout(`Hello, ${args.name}!`));
```

The action receives typed `args` and `flags`, the lazy `ctx` bag, `rawArgs` after `--`, a cancellation `signal`, the resolved `command` and `rootCommand` snapshots, and `stdout(text)` / `stderr(text)`. See [`CrustCommandContext`](/docs/api/types#crustcommandcontexta-f-ctx).

`signal` aborts on `execute({ signal })`, `run(path, input, { signal })`, or the first Ctrl-C during `execute()`. Pass it to `fetch`, timers, or child processes. When work throws the signal's reason, that error decides the exit path; see [cancellation](/docs/api/errors#cancellation).

## `.add(...definitions)`

Materializes definitions as fresh child commands under their carried names. See the [root example](#constructor), which adds `deploy` twice with `.as()`.

Sibling names and aliases must not collide. A definition can itself add definitions; nested ones access inherited Contexts by declaring them with `.use()`. An added command accepts the Context-owned flags already provided on its parent path, but not the parent's local flags.

<Callout type="info">
  A later `.provide()` does not reach an already-added definition. Register a definition's providers
  before `.add()`. Extension-provided Contexts are the exception.
</Callout>

## `.command(name, recipe)`

Root-only sugar for `.add(defineCommand(name, recipe))`, for short app-local leaf commands. Use `defineCommand()` for commands in separate files, reused commands, and packaged commands.

```ts
const app = new Crust("my-cli").provide(logging()).command("up", (command) =>
  command.flags({ name: "detach", type: "boolean" }).action(async ({ flags, ctx, stdout }) => {
    (await ctx.logging).debug(`detach: ${String(flags.detach)}`);
    stdout("up");
  }),
);
```

The recipe sees the Contexts and Context-owned flags provided before the call, so its `ctx` is typed without `.use()`. Contexts provided after `.command()` are not visible to it.

## `.snapshot()`

Resolves to a frozen [`CommandSnapshot`](/docs/api/types#commandsnapshot) for tooling such as help, man-page, skill, and build generators. It materializes Extension contributions and validates Extension sections, without calling Command Actions.

```ts
const snapshot = await app.snapshot();
```

Renderers filter sections for their audience, then merge entries with the same exact title in source order. During `crust build`, section callbacks are re-evaluated after each build hook, so later hooks see refreshed snapshots.

## `.run(path, input?, options?)`

Invokes a command programmatically with a typed path and structured input, capturing its output.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#run
</include>

Editors complete command names, argument and flag names, and the action's result type. Input rules:

- Values bind directly against definitions without producing argv, then flow through parsers, schemas, Contexts, and the action. Custom parsers and schemas still receive their raw input, usually strings.
- Supplied positionals must form a prefix. `undefined` means omitted. An empty `multiple` array means zero occurrences.
- `run()` never reads `process.env`, so a flag's `env` fallback does not apply. Only [`.execute()`](#executeoptions) consults the environment.
- Unknown argument or flag keys return a failed outcome before the action runs.
- `raw` reaches the action as `rawArgs`, like tokens after `--`.
- The path alone selects the command. Unknown path segments return a `COMMAND_NOT_FOUND` failure, even when the nearest parent has an action.
- For genuinely dynamic paths and input, use an `AnyCrust` view; it resolves to `RunOutcome<unknown>`.

`run()` resolves after cleanup to a [`RunOutcome`](/docs/api/types#runoutcomeresult), with captured output and a `completed`, `finished`, or `failed` status.

- `run()` never renders errors, calls `onError`, or changes `process.exitCode`. Authoring errors still throw where the builder consumes them.
- Captured writes are joined with `"\n"`. `stdout` and `stderr` are captured separately, so their relative order is not preserved.
- Default `@crustjs/prompts` and `@crustjs/progress` output is captured into `stderr`. Direct `console` or `process` writes, subprocesses, and files are not captured.
- `options.stdout` / `options.stderr` also receive writes live. `options.signal` cancels the invocation. `run()` never installs a `SIGINT` handler.
- Preparation runs once per builder and is shared by later `run()`, `execute()`, and `snapshot()` calls on it.

For terminal interaction in tests, use `execute()` or [`runInteractive`](/docs/modules/testing#runinteractiveapp-path-input).

## `.at(path)`

Binds a typed command path into a reusable `CommandHandle`. `handle.run(input?, options?)` accepts exactly what `run()` accepts after the path.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#at
</include>

`at()` validates the path immediately and throws `COMMAND_NOT_FOUND` with the same details as a failed `run()`. Aliases are accepted and `handle.path` keeps the caller's spelling. `at([])` binds the root. A handle belongs to the builder it was taken from, so take it from the finished application.

## `.execute(options?)`

Runs the terminal boundary: parses `process.argv.slice(2)` (or `options.argv`), renders failures, and resolves to the exit code. See [`ExecuteOptions`](/docs/api/types#executeoptions).

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#execute
</include>

- Exit codes are `0` on success, `1` on failure, and `130` for cancellation. `process.exitCode` is set on failure.
- A failure renders once, through Extension `onError` hooks and then Core's renderer. Cancellation is offered to `onError` hooks and renders nothing if none claims it. See [propagation boundaries](/docs/api/errors#propagation-boundaries).
- `options.io` captures rendered output in tests, including default prompt and progress output. It does not provide prompt input.
- The first Ctrl-C aborts `ctx.signal` with an `AbortError`. Work that honors the signal stops, then `postRun` hooks and Context cleanup run. A second Ctrl-C removes Core's listener and reaches the runtime's default handling unless another listener still owns the signal.

### Invocation order

`.execute()` and `.run()` follow the same sequence. Routing or parse failures skip steps 4 through 10.

1. Prepare the command tree: apply Extensions, recipes, flags, and sections.
2. Route the command path.
3. Parse argv (`execute()`) or bind structured input (`run()`).
4. Run Extension `preRun` hooks in registration order; `ctx.finish()` ends the invocation with a `finished` outcome.
5. Check required values and positional structure.
6. Apply Standard Schemas and aggregate their issues.
7. Construct Contexts as they are first pulled.
8. Run the Command Action.
9. Run Extension `postRun` hooks in reverse registration order with the outcome.
10. Run deferred cleanup and dispose Contexts in reverse registration order.

A failure in steps 4 through 8 still runs steps 9 and 10.

<Callout type="warn">
  `.action()` defines behavior. `.run()` is the programmatic entry point and `.execute()` is the
  terminal entry point. Command definitions expose neither.
</Callout>

## `resolveArtifactDir(name)`

Returns the absolute path of an Extension artifact directory or a [`crust.include`](/docs/guide/build-and-distribution#ship-extra-directories-with-crustinclude) directory shipped with the running CLI.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#artifact
</include>

`name` is one top-level directory name such as `"skills"` or `"templates"`; a path separator, `.`, `..`, or an empty string throws. The directory is not probed, so the caller reports a missing directory.

| Running as                                                    | Result                                                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Compiled executable (`bun build --compile`, `deno compile`)   | `<name>` next to the executable                                                                                       |
| Crust-built Node bundle                                       | `<name>` beside the bundle's `bin/` directory: `.crust/root/<name>` in place, `<installed root>/<name>` after install |
| Snapshot preparation inside `crust build`                     | `<name>` under the entry's build output directory, containing what earlier build hooks wrote                          |
| Source (`bun run`, `node`, `deno run`, source-linked command) | `.crust/root/<name>` under the nearest `package.json` above the real entrypoint: the output of the last `crust build` |

<Callout type="warn">
  `crust build` defines `process.env.CRUST_INTERNAL_BUILD` as `"1"` in the bundles it produces. The
  variable is reserved: every read of it in your CLI is replaced at bundle time.
</Callout>
