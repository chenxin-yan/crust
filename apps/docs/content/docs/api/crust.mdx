`Crust` builds an executable application root. `defineCommand()` builds inert reusable definitions that are registered when added and materialized on first use. Every fluent method returns a new builder; the original is unchanged.

Exact overloads and generic constraints live in [`command/crust.ts`](https://github.com/chenxin-yan/crust/blob/main/packages/core/src/command/crust.ts). This page documents behavior; hover types in your editor for the inferred shapes.

## Reusable command definitions

### `defineCommand(name, config?, recipe)`

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#define
</include>

`defineCommand()` returns a frozen `CommandDefinition`: a name, static config, and a recipe. It has no `run()` or `execute()`; register it with [`.add()`](#adddefinitions).

- The recipe receives a `CommandDefinitionBuilder`, the configure-only form of `Crust`.
- Neither `defineCommand()` nor `.add()` runs the recipe. Each addition materializes independently on first use by an invocation, snapshot, or documentation pass.
- Help and typo suggestions read only the config, never the recipe.
- Successful materialization is cached; a recipe that throws may run again on a later attempt. Don't rely on recipe side effects.
- `.use(logging)` declares demand for a Context factory; `.provide(logging())` supplies an instance. A reusable definition's `ctx` holds the Contexts it declares with [`.use()`](#usefactories) or provides, and the Contexts their setup uses, transitively.
- A definition demands the Contexts it declares with `.use()`, plus those demanded by the commands it adds with `.add()` or `.command()` that it doesn't provide itself. TypeScript checks the demands where the definition is added; the root reports one that nothing provides. At runtime, they are checked when the recipe materializes against the providers where it was added.
- `definition.as(name)` returns the same definition under another name, so one definition can be added twice. Its aliases travel with it and must stay unique among siblings.

Application `version` belongs only in the root `Crust` constructor.

### Command names

A child command name (from `defineCommand()`, `.command()`, or `.as()`) and each alias is matched as one argv token.

| Rule                                   | Name breaks it  | Alias breaks it   |
| -------------------------------------- | --------------- | ----------------- |
| Not blank                              | `empty-name`    | `invalid-alias`   |
| No whitespace; does not start with `-` | `invalid-name`  | `invalid-alias`   |
| Not `__proto__`                        | `reserved-name` |                   |
| An alias differs from the command name |                 | `alias-collision` |

The last two columns are the runtime `DEFINITION` reason.

- TypeScript rejects literal names and aliases that break these rules. A `.command()` name and aliases, and `defineCommand()` aliases, fail at that call. A `defineCommand()` or `.as()` name, and an alias equal to the command's own name, fail where the definition is passed to `.add()`, including when spread from an array.
- So a generic factory such as `<const N extends "staging" | "production">(name: N) => defineCommand(name, recipe)` compiles, and each name it is called with is checked when added.
- At runtime, `defineCommand()`, `.command()`, and `.as()` validate every name, including ones the types can't see.
- The root name given to `new Crust()` is never an argv token, so only the blank and `__proto__` rules apply to it.

## Chaining semantics

`.flags()` takes one record keyed by flag name; `.args()`, `.provide()`, `.add()`, and `.extend()` are variadic. All accept dynamic collections and accumulate across calls.

- TypeScript rejects statically known invalid definitions and collisions. Runtime checks cover what the types can't see: a name typed `string`, a spread array, a `Record` of definitions, or properties hidden by a structural view.
- A runtime-only name doesn't switch off compile-time checks among statically known names: after `.add(dynamicCommand)`, a later literal command that collides with an earlier one is still a compile error.
- Flags are the exception. Once a command's flags include a runtime-only spelling (from a dynamic record, a Context, or an Extension), later flags on that command are checked against the earlier ones only at runtime. Subcommands are still checked against the statically known Context and recursive Extension flags they inherit.
- Extension ids aren't tracked by the types, so a same-id re-registration that reuses an earlier registration's literal names is a compile-time collision, although the runtime replaces it.
- TypeScript-only constraints, such as requiring a command recipe, have no runtime check; `as never`, `any`, and plain JavaScript bypass them. Runtime checks still apply to all inputs, including conflicting section audiences, malformed flag `env` bindings, and delimiters on scalar flags.

Runtime checks throw a `DEFINITION` [error](/docs/api/errors) at different times:

| Check                                                                                               | When                                                      |
| --------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| Direct builder inputs, sibling names and aliases                                                    | At the builder call                                       |
| Recipe validation, inherited-flag collisions, Context demands of added definitions                  | When the command is first used                            |
| Extension flag and command collisions, missing Contexts for an Extension's `.use()` or `.provide()` | When the app prepares: first run, `snapshot()`, or `at()` |

Use `await app.snapshot()` to validate the full tree without running Command Actions.

Each call returns a builder of a new type, so register a dynamic list in one call instead of reassigning a variable in a loop:

```ts
const names = ["build", "deploy"];
const app = new Crust("cli").add(...names.map((name) => defineCommand(name, (command) => command)));

// Compile error: the result of .add() is not the type of `looped`.
// let looped = new Crust("cli");
// for (const name of names) looped = looped.add(defineCommand(name, (command) => command));
```

`.flags()`, `.args()`, `.add()`, and `.command()` infer their type arguments from the builder they are called on. Passing explicit type arguments, such as `.add<readonly [typeof deploy]>(deploy)`, is a compile error (`FIX_EXPLICIT_TYPE_ARGUMENTS`).

### Conditional chains

Each call returns a builder whose type records what was added so far, so a conditional can produce a union of builder types that the next call cannot infer from. Crust rejects such calls instead of silently losing types:

```ts
// Compile error: inputs cannot be inferred from this builder union.
(prod ? c.provide(db()) : c).provide(cache());
```

Keep the command shape static and put the condition in the Context value:

```ts
const db = defineContext("db").setup(() => (prod ? connect() : null));
c.provide(db(), cache()); // db resolves to Connection | null
```

If the shape genuinely differs, write the full chain in each branch:

```ts
prod ? c.provide(db(), cache()) : c.provide(cache());
```

## `.args(...defs)`

Defines positional arguments in call order. Definitions come from `defineArg(name, def)` or inline literals; see [`ArgDef`](/docs/api/types#argdef).

```ts
const copy = new Crust("copy").args(
  { name: "source", type: "path", required: true },
  { name: "destinations", type: "path", variadic: true },
);
```

Names must be unique, custom `parse` functions must be synchronous, and only the last argument across all calls may be variadic, or the one right before a final [`afterDoubleDash`](/docs/api/types#argdef) argument. Only the last argument may set `afterDoubleDash`. A schema-backed argument receives the raw string (`string[]` when variadic, `undefined` when absent); its schema owns coercion, defaults, requiredness, and validation, so it cannot also set `type`, `default`, `required`, `choices`, or `parse`.

## `.flags(flags)`

Defines flags local to this command from one record: each key is a flag's name without the `--` prefix, and each value is its [`FlagDef`](/docs/api/types#flagdef), written inline or created with [`defineFlag(def)`](/docs/api/types#defineflag-and-definearg). Quote names that are not identifiers, and read them the same way: `flags["dry-run"]`.

```ts
const serve = new Crust("serve").flags({
  verbose: { type: "boolean", short: "v" },
  port: { type: "number", default: 3000 },
  include: { type: "string", multiple: true },
  "dry-run": { type: "boolean" },
});
```

`.flags()` takes exactly one record per call; call it again to add more flags.

- Only own enumerable string keys are flags; TypeScript rejects symbol keys and unquoted number keys, so write `"1.5"` rather than `1.5`. Integer-like names (`"0"`, or digits without a leading zero such as `"2"`) are rejected at any length, because JavaScript lists array-index keys first and would reorder help. A record whose prototype is not `Object.prototype` or `null`, such as one written with a literal `__proto__` key, throws a `DEFINITION` error.
- A key written after a spread (`{ ...shared, out }`) silently replaces the spread's flag of the same name. Attach shared sets in their own `.flags()` call: collisions across calls are checked.
- A record with an index signature, such as one built with `Object.fromEntries()`, is checked when the call runs; literal keys beside it or in later `.flags()` calls are still checked by TypeScript, against each other but not against the dynamic flags.
- Long names, aliases, and `short` spellings must not collide with other flags visible on the command.
- Names, aliases, and `short` are written without dashes: each must be non-empty, contain no whitespace, and not start with `-`. Names and aliases must also not contain `=`, because `--name=value` splits there. TypeScript rejects literal spellings that break this; dynamic ones throw a `DEFINITION` error, with `reason: "empty-spelling"` for an empty spelling and `"invalid-spelling"` for the rest.
- One-character names and aliases accept one or two dashes: `aliases: ["P"]` accepts `-P` and `--P`. Generated docs list both.
- Boolean flags accept `--no-<spelling>` for the name and every long alias. `noNegate: true` rejects negation with a `PARSE` error and hides it from generated docs. Names and aliases beginning with `no-` are reserved.
- Schema-backed flags still set `type: "string" | "boolean"` to declare whether a value token follows; the schema receives the raw value, including `undefined` when omitted.
- Flags declared here do not reach subcommands. To share flags with descendants, give them to a [Context](/docs/guide/contexts) and `.provide()` it.

## `.use(...factories)`

Recipe-only. Declares the Context factories a reusable definition consumes, without providing instances.

- Requires at least one factory; repeated calls accumulate.
- Demands and their transitive dependencies are checked when the definition materializes, not at `.add()`.
- The command parses the flags these Contexts own, and those of the Contexts their setup uses, transitively. So do inline `.command()` children added after the call. The builder's flag type includes them.
- If the Context resolved under that name comes from a different same-name factory, that provider must own exactly the declared flags: the same names with equal definitions, where a `parse` function or schema must be the same object. The Contexts its setup uses may own only flags the command parses. Otherwise preparation throws `DEFINITION` (`context-flags-not-parsed`); change the declared Context, or provide the same factory.
- An `.of()` double parses the same flags as its factory. A command may also `.provide()` a Context it uses; the two share its flags. See [Flags owned by a Context](/docs/guide/contexts#flags-owned-by-a-context).

An Extension, or an Extension factory, also counts as a factory list: `.use(time)` declares every Context `time()` provides, with the same compile-time checks, and parses their flags.

- The app must extend that Extension (matched by id); otherwise preparation throws `DEFINITION` (`missing-extension`).
- When the definition materializes, an Extension value's provided Contexts are also checked as provided (a `.of()` value demands no dependencies). A factory's are known only per call, so only its id is checked.

See [Use an Extension's Contexts from a command](/docs/guide/extensions#use-an-extensions-contexts-from-a-command).

## `.provide(...instances)`

Attaches Context instances created by invoking `defineContext()` factories. The Context is available to this command and to descendants added **after** this call, and is constructed lazily when its `ctx` property is first read.

```ts
const database = defineContext("database").setup((_input, options: { url: string }) => ({
  url: options.url,
  async [Symbol.asyncDispose]() {},
}));

const app = new Crust("my-cli")
  .provide(database({ url: "postgres://localhost/app" }))
  .action(async ({ ctx }) => (await ctx.database).url);
```

- Flags declared with a Context's `.flags()` are installed on this command and on inline `.command()` children added afterwards. The builder's flag type includes them. A reusable definition parses them only if it declares the Context with [`.use()`](#usefactories); other commands reject them as unknown. See [Flags owned by a Context](/docs/guide/contexts#flags-owned-by-a-context).
- Its `.sections()` document only the providing command, after the command's own sections. Duplicate titles throw `DEFINITION` (`duplicate-section`) during preparation, not at `.provide()`. See [Context-owned documentation](/docs/guide/contexts#documentation-owned-by-a-context).
- Within one call, dependencies may appear in any order; across calls, providers must precede their consumers.
- Names, dependencies, and owned-flag collisions are checked by TypeScript. Runtime composition checks reject missing declared providers and dynamic flag collisions with a `DEFINITION` error, without running setup. Pulling a Context also checks missing providers, dependency cycles, and lifecycle misuse.
- A command can shadow an inherited Context. After `.action()`, a local replacement must satisfy the value type that action received.

### Context lifecycle

- Cleanup registered with setup's `defer(cleanup)`, and returned values implementing `Symbol.dispose` or `Symbol.asyncDispose`, run in reverse registration order after `postRun` hooks, including when the action throws.
- Call `defer` immediately after acquiring each resource so a later setup failure still releases it. Calling `defer` after setup has settled throws a `DEFINITION` error.
- A returned disposable is disposed for you. Do not also close it with `defer`, `await using`, or in the action, and do not keep it after the invocation.
- A value supplied through `factory.of(value)` is disposed by every invocation that pulls it. Use a fake without a disposer for repeated invocations.
- Await dependencies during setup, before registering a `defer` callback that needs them, so they are still live when that callback runs.
- Setup receives the invocation's `signal`. Pass it to cancellable initialization such as `fetch(url, { signal })`; do not reuse it for cleanup work that must finish.

See [Contexts](/docs/guide/contexts) for worked examples.

## `.extend(...extensions)`

Root-only. Registers application-wide [Extensions](/docs/guide/extensions) in registration order. Extensions must come from `defineExtension()`.

```ts
import { help, version } from "@crustjs/extensions";

const app = new Crust("my-cli", { version: "1.2.3" }).extend(version(), help());
```

- `.extend()` only records the list. The app applies and validates the final list when it prepares, so flag or command collisions and missing Contexts surface there as `DEFINITION` errors.
- A repeated `ExtensionId` replaces the earlier registration at runtime, which also rescues an earlier registration that conflicted. The types don't track ids: they still see the earlier registration's commands and flags, so reusing one of its literal names is a compile-time collision.
- Once a call includes an Extension with runtime-only command names, typed `run()` results are `unknown` for the commands of Extensions registered up to and in that call. Commands added with `.add()` or `.command()` keep their result types.
- Extensions apply to every command, whether it was added before or after `.extend()`. Extension commands are built on first use, like added definitions.
- Contexts an Extension provides reach every command. Between a root `.provide()` and an Extension-provided Context of the same name, the later call wins, as the types infer; a command's own `.provide()` always wins.
- Flags those Contexts own are parsed by the root, its inline `.command()` children, and the commands that `.use()` the Context or the Extension, before the command's own flags. Flags of a Context the Extension's hooks `.use()` are parsed by every command.
- Recursive Extension flags (the default) are registered on each command as it is built. `recursive: false` flags are registered only on the root, so only the root's flags can collide with them.

## `.output(schema)`

Declares the command's result with a [Standard Schema](https://standardschema.dev).

```ts
const whoami = new Crust("whoami")
  .output(z.object({ id: z.number(), name: z.string() }))
  .action(() => ({ id: 1, name: "ada" }));
```

- Called before `.action()`, TypeScript requires the action to return the schema's input type, or a promise of it; an async generator action must `return` it. Called after `.action()`, TypeScript checks the action's inferred awaited return against the schema's input.
- After the action resolves, Crust validates its result; the schema's awaited output becomes the `result`, typed in `run()`.
- A rejected result fails the invocation with an [`OUTPUT`](/docs/api/errors#outputerrordetails) error, exit `1` under `execute()`.
- A command without an action passes `undefined` to the schema, whose output becomes the result. A `handled` invocation (a flag handler or `noAction` took over) has no result to validate.
- A later `.output()` replaces the schema. Without `.output()`, results are not validated.
- The command's [`CommandSnapshot`](/docs/api/types#commandsnapshot) has `output: true` and, when the schema can produce one, its output JSON Schema in `outputSchema` (see [`standardJsonSchema()`](/docs/modules/core#tooling-subpath)).

## `.action(action)`

Defines the Command Action. It runs after validation, unless an Extension's flag handler took over (see [invocation order](#invocation-order)). Its awaited return value becomes the `result` of typed `run()` calls, unless [`.output()`](#outputschema) declares it. A later `.action()` replaces both the action and its result type.

An `async function*` action [streams events](/docs/guide/commands#stream-events): each yielded value is delivered live to the selected [renderer's `event`](/docs/api/types#renderer) and the caller's `onEvent` option, and collected in the outcome's `events`; its `return` value is the result. Crust never prints events. An action that returns an async generator object, an object with `next`, `return`, and `throw` methods and `Symbol.asyncIterator`, streams the same way.

```ts
const greet = new Crust("greet")
  .args({ name: "name", type: "string", required: true })
  .action(({ args, stdout }) => stdout(`Hello, ${args.name}!`));
```

The action receives typed `args` and `flags`, the lazy `ctx` bag, `rawArgs` (tokens after `--` that no declared argument consumed), a cancellation `signal`, the resolved `command` and `rootCommand` snapshots, and `stdout(text)` / `stderr(text)`, which are how the action prints (see [Commands](/docs/guide/commands)). See [`CrustCommandContext`](/docs/api/types#crustcommandcontexta-f-ctx).

Pass `signal` to `fetch`, timers, or child processes; see [cancellation](/docs/api/errors#cancellation) for when it aborts and how the exit path is decided.

## `.add(...definitions)`

Registers definitions under their carried names, deferring their recipes until first use. Each addition materializes as a fresh child command. See the [root example](#constructor), which adds `deploy` twice with `.as()`.

- Sibling names and aliases must not collide; `.add()` checks them immediately without running recipes.
- Recipe validation, inherited-flag collisions, and Context-demand checks are deferred until materialization.
- A definition can itself add definitions; nested ones access inherited Contexts by declaring them with `.use()`. A group without an action doesn't need to `.use()` them too: it forwards their demands to where it is added, without parsing those Contexts' flags.
- An added command accepts the flags of the Contexts it declares with `.use()`, but neither other Context-owned flags on its parent path nor the parent's local flags.

<Callout type="info">
  A later `.provide()` does not reach an already-added definition. Register a definition's providers
  before `.add()`. Extension-provided Contexts are the exception.
</Callout>

## `.command(name, config?, recipe)`

Defines a child like `.add(defineCommand(name, config?, recipe))`, for short inline commands. `config` takes the same [`CommandConfig`](#definecommandname-config-recipe) as `defineCommand()`: description, aliases, `hidden`, usage, and sections. It works on the root and inside another command's recipe, so subcommands can nest inline. Use `defineCommand()` for commands in separate files and reused commands.

```ts
const app = new Crust("my-cli").provide(logging()).command("up", (command) =>
  command.flags({ detach: { type: "boolean" } }).action(async ({ flags, ctx, stdout }) => {
    (await ctx.logging).debug(`detach: ${String(flags.detach)}`);
    stdout("up");
  }),
);
```

The recipe sees the Contexts and Context-owned flags available before the call, so its `ctx` is typed without `.use()` and the command parses those Contexts' flags; its action's `flags` type includes them. Inside a recipe, those are the Contexts the parent declared with `.use()` or `.provide()`. Contexts provided after `.command()` are not visible to it.

## `.snapshot()`

Resolves to a frozen [`CommandSnapshot`](/docs/api/types#commandsnapshot) for tooling such as documentation and build generators. It materializes all pending command recipes and Extension contributions and validates the full tree, including inherited flags, Context demands, and documentation sections, without calling Command Actions. Use it to catch deferred definition errors before accepting invocations; it rejects if validation fails.

```ts
const snapshot = await app.snapshot();
```

During `crust build`, section callbacks are re-evaluated after each build hook, so later hooks see refreshed snapshots.

## `.run(path, input?, options?)`

Invokes a command programmatically with a typed path and structured input, capturing its output.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#run
</include>

Editors complete command names, argument and flag names, and the action's result type. Input rules:

- Values bind directly against definitions without producing argv, then flow through parsers, schemas, Contexts, and the action. Custom parsers and schemas still receive their raw input, usually strings.
- Supplied positionals must form a prefix. `undefined` means omitted. An empty `multiple` array means zero occurrences.
- A flag the input omits falls back to its `env` variable, then to its default; a supplied value always wins. Variables come from `options.env`, which defaults to `process.env`, so `run()` resolves like the terminal; pass `{ env: {} }` (or chosen variables) so results don't depend on the caller's shell. An invalid environment value fails like on argv, naming the variable but not the value. TypeScript lets the input omit a `required` flag that has an `env` binding.
- TypeScript rejects unknown argument, flag, and top-level keys, including in inputs held in variables. Keys set to `undefined` count as omitted. At runtime, unknown argument or flag keys return a failed outcome before the action runs.
- `raw` reaches the action as `rawArgs`, like tokens after `--` that no declared argument consumed. It never fills `args`.
- The path alone selects the command. Unknown path segments return a `COMMAND_NOT_FOUND` failure, even when the nearest parent has an action.
- For genuinely dynamic paths and input, use an `AnyCrust` view; it resolves to `RunOutcome<unknown, readonly unknown[] | undefined>`, since any command may stream events.

`run()` resolves after cleanup to a [`RunOutcome`](/docs/api/types#runoutcomeresult-events), with captured output and a `completed`, `handled`, or `failed` status.

- `run()` never renders errors, calls `onError`, or changes `process.exitCode`. Eager authoring checks throw at the builder call; deferred definition errors encountered during `run()` produce a `failed` outcome.
- Captured writes are joined with `"\n"`. `stdout` and `stderr` are captured separately, so their relative order is not preserved.
- Default `@crustjs/prompts` and `@crustjs/progress` output is captured into `stderr`. Direct `console` or `process` writes, subprocesses, and files are not captured.
- `options.stdout` / `options.stderr` also receive writes live. `options.onEvent` receives each event an async generator action yields, live, typed like the outcome's `events`. `options.signal` cancels the invocation. `run()` never installs a `SIGINT` or `SIGTERM` handler.
- Preparation is cached per builder and shared by later `run()`, `execute()`, and `snapshot()` calls on it. Pending commands materialize as needed; `snapshot()` visits the full tree.

For terminal interaction in tests, use `execute()` or [`runInteractive`](/docs/modules/testing#runinteractiveapp-path-input).

## `.at(path)`

Binds a typed command path into a reusable `CommandHandle`. `handle.run(input?, options?)` accepts exactly what `run()` accepts after the path.

</include>

`at()` validates the path immediately and throws `COMMAND_NOT_FOUND` with the same details as a failed `run()`. This can materialize pending commands and throw deferred definition errors. Aliases are accepted and `handle.path` keeps the caller's spelling. `at([])` binds the root. A handle belongs to the builder it was taken from, so take it from the finished application.

## `.execute(options?)`

Runs the terminal boundary: parses `process.argv.slice(2)` (or `options.argv`), renders failures, and resolves to the exit code. See [`ExecuteOptions`](/docs/api/types#executeoptions).

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#execute
</include>

- Exit codes are `0` on success, `1` on failure, and `130` for cancellation (`143` when `SIGTERM` cancelled it). `process.exitCode` is set on failure.
- A failure renders once, through Extension `onError` hooks and then the selected [renderer's `error`](/docs/api/types#renderer) or Core's default rendering. Cancellation is offered to `onError` hooks; if none claims it, the abort itself renders nothing, but cleanup failures that accompany it still render. See [propagation boundaries](/docs/api/errors#propagation-boundaries).
- On macOS and Linux, each default `stdout(text)` / `stderr(text)` line is written synchronously to file descriptor 1 or 2, so it arrives complete even when the action calls `process.exit()` right after, and patching `process.stdout.write` does not capture it. On Windows, default output goes through `process.stdout` / `process.stderr`.
- `options.io` captures rendered output in tests, including default prompt and progress output. It does not provide prompt input. With `io` set, a cancelling signal only sets the exit code and never re-raises, so an in-process host keeps running.
- `options.onEvent` receives each event an async generator action yields, live. Events are never printed.
- `options.env` is the environment flags' `env` bindings read; it defaults to `process.env`. Pass `{}` (or chosen variables) to isolate a test from the caller's shell.

Ctrl-C (`SIGINT`) and `SIGTERM` (sent by `docker stop`, Kubernetes, systemd, `timeout`, and CI cancellation):

- The first signal aborts the invocation's `signal` with an `AbortError`. Work that honors the signal stops, then `postRun` hooks and Context cleanup run.
- Once they finish, the run ends by that signal, whether the action threw the `AbortError`, failed, or ignored the abort and completed: Core removes its listener, sets `process.exitCode`, and `execute()` resolves to `130` for Ctrl-C or `143` for `SIGTERM`, so code after it still runs. When the event loop then drains (`beforeExit`), Core re-raises the signal, so the process dies by it and shells see `130` / `143` (a Ctrl-C also stops a shell loop). Calling `process.exit()` or changing `process.exitCode` after `execute()` keeps that exit instead. When another listener for that signal is installed (for example by the `signal-exit` package), Core leaves the signal to it and the process ends with exit code `130` / `143` instead; the same holds on Windows and with `options.io`. A caller's `execute({ signal })` abort never re-raises and exits `130`. See [cancellation](/docs/api/errors#cancellation).
- A second signal within 50 ms counts as the same one: `npm run`, `npx`, `bun run`, and pnpm relay the terminal's `SIGINT`, and a forwarded `SIGTERM` can meet a process-group kill. Signals that arrive while the event loop is blocked are handled together and count as one; press again once it is responsive to force the exit. A signal that arrives during synchronous work still ends the run by that signal once the work returns.
- A later second signal removes Core's listener and reaches the runtime's default handling, unless another listener still owns the signal. A command that ignores the `signal` keeps running until it finishes or that second signal arrives.

### Invocation order

`.execute()` and `.run()` follow the same sequence. Routing or parse failures skip steps 4 through 12.

1. Prepare the application: apply Extensions, flags, and sections, deferring pending commands until needed.
2. Route the command path, materializing pending commands as needed.
3. Parse argv (`execute()`) or bind structured input (`run()`).
4. Run Extension `setup` hooks in registration order, then choose the [renderer](/docs/guide/extensions#renderers) for action and Context output.
5. If the user passed a flag with an Extension handler, run the selected handler (eager handlers first, then the flag given first) and end the invocation with a `handled` outcome. Otherwise, if the routed command has no Command Action, run the application's `noAction` hook, if any, and end it the same way.
6. Run Extension `preRun` hooks in registration order. They run only before a Command Action.
7. Check required values and positional structure.
8. Apply Standard Schemas and aggregate their issues.
9. Construct Contexts as they are first pulled.
10. Run the Command Action, validate its result with the [`.output()`](#outputschema) schema, if any, and pass it to the renderer's `result`, if any. An async generator action runs to its `return` first; Core calls the renderer's `stream` before its first event, then hands each event it yields to the renderer's `event` and then `options.onEvent` before it resumes.
11. Run Extension `postRun` hooks in reverse registration order with the outcome.
12. Run deferred cleanup, including cleanup deferred by Extension setups, and dispose Contexts in reverse registration order.

A failure in steps 4 through 10 still runs steps 11 and 12. The `.extend()` order never changes which handler runs; see [Hooks](/docs/guide/extensions#hooks).

<Callout type="warn">
  `.action()` defines behavior. `.run()` is the programmatic entry point and `.execute()` is the
  terminal entry point. Command definitions expose neither.
</Callout>

## `resolveArtifactDir(name)`

Returns the absolute path of an Extension artifact directory or a [`crust.include`](/docs/guide/build-and-distribution#ship-extra-directories-with-crustinclude) directory shipped with the running CLI.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/crust.ts#artifact
</include>

- `name` is one top-level directory name such as `"skills"` or `"templates"`; a path separator, `.`, `..`, or an empty string throws.
- The directory is not probed, so the caller reports a missing directory.
- From source, it throws when no `package.json` encloses the entrypoint.

Artifact paths do not depend on npm or its launcher. For [direct binary distribution](/docs/guide/build-and-distribution#custom-distribution), keep these directories next to the executable when archiving or installing it; copying only the executable leaves its data behind. Runtime packages use the different layout below.

| Running as                                                                         | Result                                                                                                                |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Compiled executable (`bun build --compile`, Node.js single executable application) | `<name>` next to the executable                                                                                       |
| Crust-built runtime package bundle (Bun or Node)                                   | `<name>` beside the bundle's `bin/` directory: `.crust/root/<name>` in place, `<installed root>/<name>` after install |
| Snapshot preparation inside `crust build`                                          | `<name>` under the entry's build output directory, containing what earlier build hooks wrote                          |
| Source (`bun run`, `node`, source-linked command)                                  | `.crust/root/<name>` under the nearest `package.json` above the real entrypoint: the output of the last `crust build` |

<Callout type="warn">
  `crust build` defines `process.env.CRUST_INTERNAL_BUILD` as `"1"` in the Bun and Node bundles it
  produces. The variable is reserved: every read of it in your CLI is replaced at bundle time.
</Callout>
