```ts
import {
  Crust,
  defineCommand,
  defineContext,
  defineFlag,
  type CommandConfig,
  type CommandDefinition,

  type ContextConfig,
  type RootCommandMeta,
} from "@crustjs/core";
```

`Crust` builds an executable application root. `defineCommand()` builds inert reusable definitions that become commands only when added. Every fluent method returns a new builder; the original is unchanged.

## Reusable command definitions

A sealed command declares consumed Context factories with `.use(...factories)` — `.use(logger)` is demand (a factory), `.provide(logger())` is supply (an instance). Like the other builder methods, `.use()` is variadic and accumulates across calls. Because declarations are type-only, `.use()` requires a statically known, non-empty factory tuple — an empty call or a widened array spread would declare nothing and fails typecheck. Actions and setup receive a typed lazy bag and await values with `await ctx.<name>`; missing wiring is reported at `.provide()`, `.add()`, or `.extend()`.

### `CommandDefinitionBuilder`

```ts
interface CommandDefinitionBuilder<
  Flags,
  A,
  Ctx,
  Sibs extends string = never,
  Sp extends string = LocalSpellingsOf<Flags>,
> {
  flags(...defs: readonly NamedFlagDef[]): CommandDefinitionBuilder;
  flags(defs: RuntimeInput<readonly NamedFlagDef[]>): CommandDefinitionBuilder;
  args(...defs: ArgsDef): CommandDefinitionBuilder;
  args(defs: RuntimeInput<ArgsDef>): CommandDefinitionBuilder;
  use(...factories: readonly [AnyContextFactory, ...AnyContextFactory[]]): CommandDefinitionBuilder;
  provide(...instances: readonly AnyContextInstance[]): CommandDefinitionBuilder;
  provide(instances: RuntimeInput<readonly AnyContextInstance[]>): CommandDefinitionBuilder;
  add(...definitions: readonly CommandDefinition[]): CommandDefinitionBuilder;
  action<R>(action: (ctx: CrustCommandContext<A, Flags, Ctx>) => R): CommandDefinitionBuilder;
}
```

This is the configure-only builder passed to a `defineCommand()` recipe. Its fluent methods preserve and refine argument, accumulated flag, and provided Context types. Each factory passed to `.use()` accumulates its value and transitive dependency closure into the action's typed `ctx` and into the sealed definition's declared dependencies. `Sibs` accumulates the sibling command names and aliases registered through `.add()`, and `Sp` caches the known flag spellings accumulated through `.flags()` and `.provide()`. Both are defaulted parameters. It intentionally has no `.extend()`, `.run()`, or `.execute()` methods.

### `CommandDefinition`

```ts
interface CommandDefinition<
  Name extends string = string,
  Aliases extends readonly string[] = readonly string[],
  Shape extends CommandShape = CommandShape,
  Deps extends ContextMap = {},
> {
  readonly name: Name;
  as<const N extends string>(
    name: (N & CommandNameBrand<N>) | RuntimeInput<N>,
  ): CommandDefinition<N, Aliases, Shape, Deps>;
}
```

A `CommandDefinition` is a frozen value carrying its name, static config, and configure recipe. `.as(name)` returns the same definition under a different name, so one definition can be added twice. Configured aliases travel with the renamed definition and must remain unique among siblings. It has no command node or execution methods.

### `defineCommand(name, config?, recipe)`

```ts
defineCommand<const Name extends string>(
  name: (Name & CommandNameBrand<Name>) | RuntimeInput<Name>,
  recipe: (command: CommandDefinitionBuilder) => CommandDefinitionBuilder,
): CommandDefinition<Name>;

defineCommand<const Name extends string, const C extends CommandConfig>(
  name: (Name & CommandNameBrand<Name>) | RuntimeInput<Name>,
  config: C & ValidateCommandConfig<Name, C>,
  recipe: (command: CommandDefinitionBuilder) => CommandDefinitionBuilder,
): CommandDefinition<Name, AliasesOf<C>>;
```

<auto-type-table path="../../../../../packages/core/src/command/crust.ts" name="CommandConfig" />

Creates an inert reusable definition under a required name. Static `description`, `usage`, `aliases`, and `hidden` belong in `config`; application `version` belongs only in the root `Crust` constructor:

```ts
const verbose = defineFlag("verbose", { type: "boolean" });
const logging = defineContext("logging", { flags: [verbose] }, ({ flags, stderr }) => ({
  debug(message: string) {
    if (flags.verbose) stderr(message);
  },
}));
const auth = defineContext("auth", () => ({ user: "Ada" }));

const deploy = defineCommand("deploy", { description: "Deploy an application" }, (command) =>
  command
    .use(logging, auth)
    .args({ name: "target", type: "string", required: true })
    .action(async ({ args, ctx }) => {
      (await ctx.logging).debug(`${(await ctx.auth).user}:${args.target}`);
    }),
);
```

The recipe does not execute when the definition is created. It executes once for each `.add()`, so keep configuration side-effect-free. Statically blank names and `__proto__` fail typecheck at command authoring and renaming. Widened or generic names require `runtime(name)` and are checked when consumed, including equality to a carried alias. TypeScript validates the definition shape; materialization checks at runtime that the recipe returns the seeded builder and does not register nested Extensions, because those behaviors are not type-expressible. The `.use()` factory-only contract belongs to TypeScript. Core retains the declared factory references so checked attachment can verify availability without running setup.

## Constructor

```ts
class Crust<

  CtxFlags = {},
  CollisionSp = CollisionSpellings,
  Result = void,
  const Meta = {},
  const Name extends string = string,
>

new Crust(
  name: (Name & CommandNameBrand<Name>) | RuntimeInput<Name>,
  meta?: Meta | RuntimeInput<Meta>
  // Overloads enforce local proof, allowed keys, and required metadata.
)
```

<auto-type-table path="../../../../../packages/core/src/command/crust.ts" name="RootCommandMeta" />

Creates a root command builder. Metadata is optional unless an installed Extension requires it. `Meta` retains the inferred constructor metadata through fluent calls; `.extend()` checks it against [extension-owned requirements](/docs/guide/extensions#required-root-metadata). Optional or widened metadata cannot promise a required field. Statically known extra root keys are rejected, including on pretyped metadata objects. Generic wrappers must also rule out extra keys; `M extends RootCommandMeta` alone is not sufficient. Broad metadata with unproven sections requires `runtime(meta)`; metadata requirements remain type-owned, including on checked configs.

Root metadata is declared at construction because aliases and hidden state only apply to subcommands. `version` is the application version exposed on `CommandSnapshot.meta.version` for Extensions and tooling. `sections` accepts the same ordered plain-text entries as subcommand metadata and is normalized immediately. Trusted literals are type-checked; `runtime(meta)` validates unproven local section facts when consumed.

```ts
const app = new Crust("my-cli", {
  description: "Manage issues",
  version: "1.2.3",
  usage: "my-cli <command>",
});
```

Definition aliases must be non-empty, contain no whitespace, not start with `-`, differ from their command's canonical name, and not collide with sibling names or aliases. TypeScript reports known alias-shape violations at `defineCommand()` with `FIX_ALIAS_SHAPE` and sibling collisions at `.add()` with `FIX_COMMAND_COLLISION`. `defineCommand(name, runtime(config), recipe)` checks unproven alias grammar and self-alias equality. Ordinary `.add()` requires statically known names and aliases to establish sibling compatibility; use `.add(runtime(definitions))` for dynamic attachment. Local checking is not destination proof. Repeated aliases within one command remain allowed. Checked command names also reject equality to a carried alias.

## Chaining semantics

Variadic builder methods accumulate across calls: `.flags()`, `.args()`, `.provide()`, `.add()`, and root-only `.extend()` preserve earlier registrations — with one exception: `.extend()` deduplicates by `ExtensionId`, keeping only the last registration for a given id. TypeScript brands reject statically known invalid definitions and collisions at compile time. On checked `runtime(...)` operations, `DEFINITION` checks cover flag spelling collisions and reserved names, duplicate or misplaced arguments, and duplicate `.add()` command names. Checked Extension operations also reject flag collisions, including Context-owned flags from providers. Dynamic Extension-contributed commands instead replace commands with the same canonical name at preparation time, as described under [`.extend()`](#extendextensions). Ordinary sibling alias compatibility and Extension metadata requirements remain type-owned. Recipe behavior, Context lifecycle, documentation sections, and argv input retain their runtime checks.

## `.args(...defs)`

```ts
args<const NewA extends ArgsDef>(
  ...defs: NewA & LocalAppendArgsChecks<A, NewA>,
): Crust
```

Defines positional arguments; repeated calls append in call order. Unproven collections/layout use `.args(runtime(defs))`; open previous layout stays open. Pass values from `defineArg(name, def)` or inline literals. Duplicate names fail typecheck with `FIX_DUPLICATE_ARG`, Promise-returning custom parsers fail with `FIX_ASYNC_PARSE`, and only the final argument across all calls may be variadic.

```ts
const app = new Crust("copy").args(
  { name: "source", type: "path", required: true },
  { name: "destinations", type: "path", variadic: true },
);
```

A definition can instead carry a Standard Schema. Schema-backed arguments receive the raw string, `undefined` when absent, or `string[]` when variadic. The schema owns coercion, defaults, requiredness, choices, and validation; do not mix it with `type`, `default`, `required`, `choices`, or `parse`.

```ts
const app = new Crust("serve").args({ name: "port", schema: z.coerce.number().int().min(1) });
```

## `.flags(...defs)`

```ts
flags<const Defs extends readonly NamedFlagDef[]>(
  ...defs: ValidateLocalFlagDefs<Defs, Sp>,
): Crust
```

Defines local flags from named flag definitions — values from `defineFlag(name, def)` or inline literals carrying `name`. Helper results are shallow-frozen: they retain local proof that later checked consumers reuse. Structural arrays are copied, but JSON/URL/schema payloads are not cloned or frozen. Flag names omit the `--` prefix.

```ts
const app = new Crust("serve").flags(
  { name: "verbose", type: "boolean", short: "v" },
  { name: "port", type: "number", default: 3000 },
  { name: "include", type: "string", multiple: true },
);
```

Repeated `.flags()` calls accumulate local flags and cache their statically known spellings — the union of flag names and aliases that `LocalSpellingsOf` computes — in the `Sp` parameter. Statically known spelling collisions fail typecheck with `FIX_ALIAS_COLLISION`. Open or conditional collections, broad spellings, and unproven local parsers/defaults require `.flags(runtime(defs))`. Keep the concrete builder type when using this checked form; `AnyCrust` exposes completed applications only, not authoring methods; an open spelling namespace cannot regain trusted composition merely by adding known flags. A narrow wrapped tuple preserves independently known fields. Local helpers and attachments reject known repeated own aliases and invalid short lengths. Promise-returning parsers fail with `FIX_ASYNC_PARSE`; unproven return contracts require the checked form.

Flags declared here are local to this command. Context-owned flags are the propagation mechanism for descendant parsers; downstream code receives their derived Context capability. Boolean flags support generated `--no-<spelling>` negation for the canonical name and every long alias; `noNegate: true` rejects negation with a `PARSE` error and hides the generated label from help, completion, and man output. Names and aliases beginning with `no-` are reserved.

Schema-backed flags require `type: "string" | "boolean"` only to declare whether the flag consumes a token. Their schema owns the value rules and receives the raw parsed value, including `undefined` when omitted even with `multiple: true`. See [schema-backed flags](/docs/api/types#flagdef).

```ts
const app = new Crust("serve").flags({
  name: "port",
  type: "string",
  schema: z.coerce.number().int().min(1),
});
```

## `.provide(...instances)`

The checked form is `.provide(runtime(instances))`. Contexts must come from `defineContext()`; attachment consumes immutable private defining data rather than overwritten public fields on structural copies. Same-name value replacement is supported on the checked path only when owned flag spellings do not collide and applicable callback-value demands remain satisfied. Opaque callback values are not runtime-decoded.

```ts
provide<const Cs extends readonly AnyContextInstance[]>(
  ...instances: KnownContextInstances<Cs> & ProvideChecks<Sp, Cs>
    & ValidateContextNames<Ctx, Cs> & ValidateContextDeps<Ctx, Cs>,
): Crust
provide<const Cs extends readonly AnyContextInstance[]>(
  instances: RuntimeInput<Cs>,
): Crust
// Simplified: both overloads retain callback-value demands and refine the returned provider/flag state.

```

Attaches Contexts produced by invoking `defineContext()` factories. Contexts are inherited by later-added descendants and constructed lazily when their bag property is accessed. The return type merges every instance's owned `flags` into the builder's accumulated flag type.

```ts
import { defineContext, Crust } from "@crustjs/core";

const database = defineContext("database", ({ options }: { options: { url: string } }) => ({
  url: options.url,
  async [Symbol.asyncDispose]() {},
}));

const app = new Crust("my-cli")
  .provide(database({ url: "postgres://localhost/app" }))
  .action(async ({ ctx }) => {
    (await ctx.database).url;
  });
```

Declared dependencies (Context `uses`, command `.use()`, Extension `uses`) are checked at composition time. Dependencies may appear in either order within one `.provide()` call; across calls, provide dependencies first. Use `.provide(runtime(instances))` and `.add(runtime(definitions))` for unproven collections or destination relations. These checked operations verify declared availability without running setup. `.use()` retains factory references but does not perform factory-shape validation. Actual missing-provider, cycle, and lifecycle checks remain at invocation.

A Context's top-level `flags` are installed as propagating flags on this builder and later-added descendants, without mutating the original definitions. Dependencies construct recursively on the first pull.

Values implementing `Symbol.dispose` or `Symbol.asyncDispose` are disposed in reverse construction order after post-run hooks. Context names, dependencies, and owned-flag collisions are checked by TypeScript; dynamically assembled owned-flag collisions throw a `DEFINITION` error from `.provide()`. Lazy bag access retains runtime `DEFINITION` guards for missing providers on dynamically assembled paths, dependency cycles, and lifecycle misuse.

## `.extend(...extensions)`

```ts
extend(...extensions: readonly Extension[]): Crust
extend(extensions: RuntimeInput<readonly Extension[]>): Crust
```

Registers application-wide Extensions. Repeated calls accumulate in registration order, with duplicate `ExtensionId`s deduplicated last-registration-wins. Statically known contributed command names and aliases must not collide (`FIX_COMMAND_COLLISION`); use `.extend(runtime(extensions))` for dynamic collections or replacements. Metadata demands remain TypeScript-owned even on this checked path. `.extend()` exists on `Crust` roots and is intentionally absent from `CommandDefinitionBuilder`.

Extensions must originate from `defineExtension()`. Core consumes immutable private defining data through structural copies; changing public contribution fields on a spread does not redefine that Extension. The checked collection validates declared availability without constructing Contexts; contributed command recipes are checked when prepared.

```ts
import { help, version } from "@crustjs/extensions";

const app = new Crust("my-cli", { version: "1.2.3" }).extend(help(), version());
```

Added definitions become ordinary command nodes before root Extensions prepare the application, so root Extensions apply to them. Extension-contributed definitions are materialized when the application prepares.

An Extension's `provides` instances and their owned flags are installed immediately across the root and existing descendants, preserving more-specific local providers on descendants. Later-added descendants inherit them too. Extension commands and declared flags are materialized during preparation. Statically known definitions are compile-time checked; preparation also checks dynamic flag collisions, recipe behavior, and documentation sections.

See [Extensions](/docs/guide/extensions) for authoring custom Extensions.

## `.action(action)`

```ts
action<R>(
  action: (ctx: CrustCommandContext<A, Flags, Ctx>) => R,
): Crust
```

Defines the Command Action. Its awaited return type is carried by the builder for typed `run()` calls. A later `.action()` call replaces both the action and its result type on the returned immutable builder. The action runs after routing, parsing, `preRun` hooks, and validation; Contexts construct on demand.

```ts
const app = new Crust("greet")
  .args({ name: "name", type: "string", required: true })
  .action(({ args, flags, ctx, rawArgs, command, rootCommand, stdout, stderr }) => {
    stdout(`Hello, ${args.name}!`);
  });
```

The context contains typed `args`, typed effective `flags`, the lazy typed `ctx` bag, `rawArgs` after `--`, the resolved `command` and application `rootCommand` snapshots, and injectable `stdout(text)` and `stderr(text)` callbacks from `InvocationIO`. `CrustCommandContext` extends `InvocationIO`; Context setups receive those same callbacks for the invocation.

## `.add(...definitions)`

```ts
add<const Ds extends readonly CommandDefinition<any>[]>(
  ...definitions: Ds & ValidateCommandDefinitions<Ds, Sibs>,
): Crust<
  Flags,
  A,
  Ctx,
  Sibs | CommandDefinitionSpellings<Ds[number]>,
  Sp
>
```

Materializes inert definitions as fresh child commands, each under its carried name. `.as(name)` renames a definition, so the same definition can route under different names:

```ts
const app = new Crust("git").provide(logging()).provide(auth()).add(deploy, deploy.as("ship"));
```

Inline one-off commands are added the same way:

```ts
const app = new Crust("my-cli").add(
  defineCommand("up", (command) => command.action(({ stdout }) => stdout("up"))),
);
```

Statically known sibling name and alias collisions fail at `.add()` with `FIX_COMMAND_COLLISION`; alias shape violations fail at `defineCommand()` with `FIX_ALIAS_SHAPE`. Use `.add(runtime(definitions))` for dynamically assembled definitions. It rejects duplicate names/aliases among materialized siblings and checks declared availability at the materialized destination without running setup. Pending Extension commands still follow their last-write-wins policy at preparation. Materialization always checks that each recipe returns its seeded builder and does not register nested Extensions. Checked materialization also validates Context-owned flag relations against ancestors; trusted attachment proves those relations statically.

A definition can add other definitions. Context providers are inherited on the materialized command path; a nested definition accesses one by declaring its factory with `.use()` and awaiting the corresponding `ctx` property.

The typed [`run()`](#runpath-input-io) shape of an added definition merges the Context-owned flags already provided on the parent path, matching the runtime parser: descendants accept inherited Context-owned flags, while parent-local flags stay excluded.

<Callout type="info">
  Finalize `.provide()` calls before `.add()`: a later `.provide()` does not backfill an
  already-added definition. Extension `provides` also reach existing descendants, but register them
  before `.add()` when a definition declares those dependencies with `.use()`.
</Callout>

## `.command(name, recipe)`

```ts
command<const N extends string, B extends CommandDefinitionBuilder>(
  name: (N & CommandNameBrand<N>) | RuntimeInput<N>,
  recipe: (command: CommandDefinitionBuilder) => B,
): Crust
```

Defines an app-local leaf subcommand inline — root-only sugar for `.add(defineCommand(name, recipe))`:

```ts
const app = new Crust("my-cli").provide(logging()).command("up", (command) =>
  command.flags({ name: "detach", type: "boolean" }).action(async ({ flags, ctx, stdout }) => {
    (await ctx.logging).debug(`detach: ${String(flags.detach)}`);
    stdout("up");
  }),
);
```

The recipe builder is seeded with the Contexts and Context-owned flags accumulated on the builder so far — the call site — so the inline action's `ctx` is typed without `.use()` declarations. Contexts provided after the `.command()` call are not visible to it, matching the positional semantics of `.provide()`. Inline `.use()` demands that the call site does not satisfy fail typecheck with `FIX_MISSING_DEPENDENCY`.

Use `.command()` for short, app-local leaf commands; extract to `defineCommand` when a command needs its own file, reuse, or a package. `.command()` exists on `Crust` roots and is intentionally absent from `CommandDefinitionBuilder`.

## `.snapshot()`

```ts
snapshot(): Promise<CommandSnapshot>
```

Prepares a frozen Command Snapshot for tooling such as man-page, skill, and build generators. It materializes Extension contributions and validates sections returned by Extension callbacks. Command-authored sections are validated when defined. It does not call Command Actions.

```ts
import type { CommandSnapshot } from "@crustjs/core";

const snapshot: CommandSnapshot = await app.snapshot();
```

The `CommandSnapshot` type is exported from `@crustjs/core` and re-exported from the `@crustjs/core/tooling` subpath; see the [core module reference](/docs/modules/core).

## `.run(path, input?, io?)`

```ts
run(path, input?, io?): Promise<RunOutcome<R>>
```

Invokes an application programmatically with a command path and structured input inferred from the application. Editors complete command names at each path level plus the selected command's argument and flag names. Required inputs, input value types, and the selected action's awaited return type are inferred by TypeScript.

```ts
const stdout: string[] = [];
const outcome = await app.run(
  ["greet"],
  { args: { name: "Ada" }, flags: { loud: true } },
  {
    stdout: (text) => stdout.push(text),
    stderr: (text) => stdout.push(text),
  },
);
if (outcome.status === "completed") {
  // outcome.result is the awaited return value of the "greet" action.
  console.log(outcome.result);
} else {
  // outcome.by identifies the Extension whose preRun hook finished first.
  console.log(`Finished by ${outcome.by}`);
}
```

Structured values are bound directly against the selected command's argument and flag definitions — no argv is produced — and then flow through the normal schema, Context, and Command Action pipeline. `parse` runs on the supplied string exactly as for argv; choice membership is TypeScript-owned for ordinary `run()` and runtime-checked for argv and `runtime(input)`. `type: "path"` values are resolved, and number, boolean, `URL`, and JSON values are passed through unchanged. Scalar arguments and flags declared with `type: "json"` accept JSON primitives, structurally JSON-compatible object types (including named interfaces), and mutable or readonly arrays/tuples; variadic JSON arguments and multiple JSON flags require a mutable array of JSON values as repeated occurrences. `Date`, `bigint`, functions, and other non-JSON values are excluded from JSON inputs. JSON objects and arrays retain their identity; no serialization check or copy is performed. `undefined` is treated as an omitted optional input. Multiple-flag arrays preserve occurrence order; an empty array means zero occurrences and uses the default, if any. When `io` contains at least one callback, the resolved callbacks are also ambient for the full invocation: progress indicators and prompt output default to the injected `stderr` callback. Progress uses non-TTY static lines, and prompt input remains a separate `PromptIO` concern.

Supplied positional values must form a prefix in definition order, even when an earlier argument has a default. Required core variadics without defaults require nonempty tuples. Omission requires every definition alternative to be optional or have a definitely present default. Widened or conditional choice collections cannot prove supplied membership, even after local definition checking: use `runtime(input)`. Definition unions require checked supplied values even when their primitive kind agrees. A possibly enabled `noNegate` on a single definition accepts only `true` on the trusted path. Uncertain primitive kinds or occurrence layouts require checked supplied values; safe omission and unrelated known inputs remain available. Conditional flag-record types cannot prove a trusted input, even when their possible keys are disjoint. These rules apply to direct calls and exported input types.

Use `app.run(path, runtime(input), io?)` for typed dynamic input. Core checks it against the selected command's actual definitions, including value kinds, occurrence arrays, names, positional order, choices, and `noNegate`; the result type remains path-specific. For a dynamic path, `app.run(runtime(path), runtime(input), io?)` returns `Promise<RunOutcome<unknown>>`. Broad app holders such as `AnyCrust` require checked invocation. The wrapper itself does not validate or snapshot input, and it is not an `unknown` decoder. See [Runtime input](/docs/guide/types#runtime-input).

Each declared own argument or flag value is read once during binding; name validation does not invoke its getter again.

Actual same-ID Extension replacement can remove canonical flag keys still retained by the builder's accumulated type. Runtime identity owns this check: `run()` rejects a supplied retired key when no current definition supplies it, including affected descendant and provider-owned flags. Surviving or reintroduced keys remain valid. This does not update an earlier action's assumptions about removed flags; in particular, omitting a removed defaulted flag can still give that action `undefined`.

The optional `raw` array reaches the Command Action unchanged as `rawArgs`, equivalent to tokens after a `--` separator in terminal input:

```ts
await app.run(["exec"], { args: { command: "lint" }, raw: ["--fix", "src"] });
```

Positional values may begin with `-` or equal a subcommand name or alias; the typed path alone selects the command. `run()` rejects unknown path segments even when the nearest resolved parent has an action. By contrast, argv routing can treat unmatched tokens as positionals; see [Unknown commands](/docs/guide/subcommands#unknown-commands). `ExtensionContext.argv` contains only that path for `run()` invocations. Use `execute({ argv })` when testing raw terminal syntax.

`run()` resolves to a `RunOutcome`: `{ status: "completed", result }` carries the selected Command Action's awaited return value after successful cleanup (including `undefined` from actionless or `void` actions), while `{ status: "finished", by }` identifies the Extension whose `preRun` hook finished the invocation first. It does not render errors, run Extension `onError` hooks, or change `process.exitCode`. Definition, parse, Context, Command Action, and cancellation failures are thrown unchanged unless disposal also fails, producing a combined failure. See [Error flow](/docs/guide/lifecycle#error-flow). Extension preparation happens before structured input is bound, so preparation errors can surface before dispatch.

Prepared invocations are cached once per immutable builder and shared by subsequent `run()`, `execute()`, and `snapshot()` calls on that builder. Command recipes, Extension commands and flags, and section callbacks therefore prepare once; a later fluent call returns a new builder with its own preparation.

Commands and flags declared directly in `defineExtension()` participate in typed paths and inputs. Recursive Extension flags (the default) appear on root and descendant inputs; `recursive: false` appears only on the root. A widened `boolean` scope leaves descendant inputs open and requires checked invocation. Contributions hidden behind a widened `Extension` type, assembled dynamically or conditionally (including variable-length arrays), selected conditionally, or held in a variable-length list require `.extend(runtime(extensions))` and remain runtime-only and require `run(runtime(path), runtime(input))` or `execute({ argv })`. Statically known Extension command collisions — inside one `defineExtension()` tuple, with authored commands, or with other Extensions — fail typecheck with `FIX_COMMAND_COLLISION`, and statically known Extension flags colliding with a contributed command's local flags fail with `FIX_ALIAS_COLLISION`; dynamically assembled commands keep last-write-wins at prepare time — namespace Extension command names to avoid that mismatch.

## `.execute(options?)`

```ts
execute(options?: {
  argv?: string[];
  io?: Partial<InvocationIO>;
}): Promise<number>
```

Runs the terminal boundary. By default it parses `process.argv.slice(2)`; `options.argv` overrides it, while `options.io` captures rendered output in tests. Explicit IO also captures default `@crustjs/progress` output and `@crustjs/prompts` output for the full invocation; it does not provide prompt input.

```ts
await app.execute();
```

`execute()` resolves to the terminal exit code: `0` on success, `1` on failure, or `130` for cancellation. It still renders a failure once through Extension `onError` hooks ending in Core's renderer and sets `process.exitCode` on failure. Any `Error` whose `name` is `"AbortError"`, including a `DOMException`, is cancellation. It is offered to `onError` hooks and renders nothing when no hook claims it.

<Callout type="warn">
  Use `.action(action)` to define behavior. `.run(path, input, io)` is only programmatic invocation;
  `.execute()` is the terminal entry point. Command definitions are inert and expose neither.
</Callout>
