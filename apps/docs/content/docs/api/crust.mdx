```ts
import {
  Crust,
  defineCommand,
  type CommandDefinition,
  type CommandDefinitionBuilder,
  type CommandRequirements,
} from "@crustjs/core";
```

`Crust` builds an executable application root. `defineCommand()` builds inert reusable definitions that become commands only when mounted. Every fluent method returns a new builder; the original is unchanged.

## Reusable command definitions

### `CommandRequirements`

```ts
interface CommandRequirements {
  readonly flags?: Record<string, FlagDef & { inherit: true }>;
  readonly ctx?: ContextMap;
}
```

Requirements describe values supplied by the parent at a mount point:

- `flags` lists required inherited flag definitions. Every required flag must have `inherit: true`.
- `ctx` maps required Context names to their constructed value types.

Requirements are type-only. They do not create flags, Contexts, or a runtime validation schema.

### `CommandDefinitionBuilder`

```ts
interface CommandDefinitionBuilder<Inherited, Local, A, Eff, Ctx> {
  meta(meta: Omit<CommandMeta, "name">): CommandDefinitionBuilder;
  flags(defs: FlagsDef): CommandDefinitionBuilder;
  args(defs: ArgsDef): CommandDefinitionBuilder;
  provide(context: ContextInstance): CommandDefinitionBuilder;
  handle(
    handler: (ctx: CrustCommandContext<A, Eff, Ctx>) => void | Promise<void>,
  ): CommandDefinitionBuilder;
  command(
    name: string,
    callback: (command: CommandDefinitionBuilder) => CommandDefinitionBuilder,
  ): CommandDefinitionBuilder;
  mount(name: string, definition: CommandDefinition): CommandDefinitionBuilder;
}
```

This is the configure-only builder passed to `defineCommand()` and inline `.command()`. Its fluent methods preserve and refine argument, flag, and Context types. It intentionally has no `.extend()`, `.run()`, or `.execute()` methods.

### `CommandDefinition`

```ts
interface CommandDefinition<R extends CommandRequirements = {}> {
  // Opaque command recipe
}
```

A `CommandDefinition<R>` is an opaque frozen value containing only the configure recipe. It has no name, command node, or execution methods.

### `defineCommand<R>()(configure)`

```ts
defineCommand<const R extends CommandRequirements = {}>(): (
  configure: (command: CommandDefinitionBuilder) => CommandDefinitionBuilder,
) => CommandDefinition<R>
```

Creates an inert reusable definition. The function is curried so requirements are fixed before TypeScript infers the configured command's local inputs:

```ts
const verbose = { type: "boolean", inherit: true } as const;

const deploy = defineCommand<{
  flags: { verbose: typeof verbose };
  ctx: { auth: { user: string } };
}>()((command) =>
  command
    .args([{ name: "target", type: "string", required: true }])
    .handle(({ args, flags, ctx, stdout }) => {
      stdout(`${ctx.auth.user}:${args.target}:${flags.verbose}`);
    }),
);
```

The recipe does not execute when the definition is created. It executes once for each `.mount()`, so keep configuration side-effect-free.

## Constructor

```ts
new Crust(name: string)
```

Creates a root command builder. An empty or whitespace-only name throws a `CrustError` with code `DEFINITION`.

```ts
const app = new Crust("my-cli");
```

## `.meta(meta)`

```ts
meta(meta: Omit<CommandMeta, "name">): Crust
```

Sets `description`, `usage`, `aliases`, or `hidden`. The constructor, inline `.command()`, or `.mount()` supplies the name.

```ts
const app = new Crust("issue").meta({
  description: "Manage issues",
  aliases: ["issues", "i"],
});
```

Aliases must be non-empty, contain no whitespace, not start with `-`, and not collide with sibling names or aliases.

## `.args(defs)`

```ts
args<const NewA extends ArgsDef>(
  defs: NewA & ValidateVariadicArgs<NewA>,
): Crust
```

Defines an ordered tuple of positional arguments. Only the last argument may be variadic.

```ts
const app = new Crust("copy").args([
  { name: "source", type: "path", required: true },
  { name: "destinations", type: "path", variadic: true },
] as const);
```

A definition can instead carry a Standard Schema. Schema-backed arguments receive the raw string, `undefined` when absent, or `string[]` when variadic. The schema owns coercion, defaults, requiredness, choices, and validation; do not mix it with `type`, `default`, `required`, `choices`, or `parse`.

```ts
const app = new Crust("serve").args([
  { name: "port", schema: z.coerce.number().int().min(1) },
] as const);
```

## `.flags(defs)`

```ts
flags<const F extends FlagsDef>(
  defs: F & ValidateNoPrefixedFlags<ValidateFlagAliases<F>>,
): Crust
```

Defines named flags. Flag keys omit the `--` prefix.

```ts
const app = new Crust("serve").flags({
  verbose: { type: "boolean", short: "v", inherit: true },
  port: { type: "number", default: 3000 },
  include: { type: "string", multiple: true },
});
```

`inherit: true` exposes a flag to descendant commands and allows it to satisfy mounted definition requirements. Boolean flags support generated `--no-name` negation unless `noNegate: true` is set. Names and aliases beginning with `no-` are reserved.

Schema-backed flags require `type: "string" | "boolean"` only to declare whether the flag consumes a token. Their schema owns the value rules and receives the raw parsed value.

```ts
const app = new Crust("serve").flags({
  port: { type: "string", schema: z.coerce.number().int().min(1) },
});
```

## `.provide(context)`

```ts
provide<const C extends ContextInstance>(context: C): Crust
```

Attaches a Context produced by invoking a `context()` factory. Contexts are inherited by descendants, constructed in registration order only for the resolved command path, and available through `ctx` in the Command Handler.

```ts
import { context, Crust } from "@crustjs/core";

const database = context("database", (options: { url: string }) => ({
  url: options.url,
  async [Symbol.asyncDispose]() {},
}));

const app = new Crust("my-cli")
  .provide(database({ url: "postgres://localhost/app" }))
  .handle(({ ctx }) => {
    ctx.database.url;
  });
```

Values implementing `Symbol.dispose` or `Symbol.asyncDispose` are disposed in reverse construction order after success or failure. A duplicate Context name on one command path throws `DEFINITION`.

## `.extend(...extensions)`

```ts
extend(...extensions: readonly Extension[]): Crust
```

Registers application-wide Extensions. `.extend()` exists on `Crust` roots and is intentionally absent from `CommandDefinitionBuilder`.

```ts
import { help, version } from "@crustjs/extensions";

const app = new Crust("my-cli").extend(help(), version("1.2.3"));
```

Mounted definitions become ordinary command nodes before root Extensions prepare the application, so root Extensions apply to them. Extension-owned command builders remain unchanged.

Extension-owned command or flag name and alias collisions throw `DEFINITION` when the application is prepared.

See [Extensions](/docs/guide/extensions) for authoring custom Extensions.

## `.handle(handler)`

```ts
handle(
  handler: (ctx: CrustCommandContext<A, Eff, Ctx>) => void | Promise<void>,
): Crust
```

Defines the Command Handler. It runs after routing, parsing, validation, Extension interception, and Context construction.

```ts
const app = new Crust("greet")
  .args([{ name: "name", type: "string", required: true }] as const)
  .handle(({ args, flags, ctx, rawArgs, command, stdout, stderr }) => {
    stdout(`Hello, ${args.name}!`);
  });
```

The context contains typed `args`, typed effective `flags`, typed Context values in `ctx`, `rawArgs` after `--`, the resolved `CommandSnapshot`, and injectable `stdout(text)` and `stderr(text)` callbacks.

## `.command(name, callback)`

```ts
command(
  name: string,
  callback: (command: CommandDefinitionBuilder) => CommandDefinitionBuilder,
): Crust
```

Defines and immediately mounts an inline child. The callback builder is typed with the parent's current inheritable flags and Contexts:

```ts
const app = new Crust("my-cli")
  .flags({ verbose: { type: "boolean", inherit: true } })
  .command("deploy", (command) =>
    command.flags({ environment: { type: "string", required: true } }).handle(({ flags }) => {
      flags.verbose;
      flags.environment;
    }),
  );
```

Inline `.command()` uses the same materialization path as `.mount()`. Use it for local one-off commands; use `defineCommand()` when the definition should live separately or be reused.

## `.mount(name, definition)`

```ts
mount<const R extends CommandRequirements>(
  name: string,
  definition: CommandDefinition<R> & Mountable<Eff, Ctx, NoInfer<R>>,
): Crust
```

Materializes an inert definition as a fresh child command. `name` controls routing and can differ between mounts:

```ts
const first = new Crust("first").flags({ verbose }).provide(auth()).mount("deploy", deploy);

const second = new Crust("second")
  .flags({ verbose: { ...verbose, required: true } })
  .provide(auth())
  .mount("release", deploy);
```

`Mountable` is internal declaration machinery that checks requirements. On failure, TypeScript reports one or more readable structural properties at the `.mount()` call:

- `"missing inherited flags"`
- `"incompatible inherited flags"`
- `"missing Contexts"`
- `"incompatible Contexts"`

Only `inherit: true` parent flags are considered. Compatibility compares inferred handler value types, including schema and custom-parser outputs: a provided value must be assignable to the required value. A stricter required parent flag can satisfy an optional requirement, but an optional parent flag cannot satisfy a required requirement. Context values use the same provided-to-required assignability direction.

At runtime, empty names, duplicate sibling names, alias collisions, duplicate Contexts, unrelated callback returns, and Extensions forced into an untyped definition throw `CrustError` code `DEFINITION`.

A definition can contain inline `.command()` calls and nested `.mount()` calls. Nested requirements are checked against the enclosing definition builder at that exact point.

<Callout type="info">
  Finalize inheritable flags and Contexts on the builder used for `.mount()`. Later fluent calls
  create a new builder and do not backfill an existing mount.
</Callout>

## `.run(argv, io?)`

```ts
run(
  argv: readonly string[],
  io?: {
    stdout?: (text: string) => void;
    stderr?: (text: string) => void;
  },
): Promise<void>
```

Invokes an application programmatically. `argv` is required and does not include the executable name.

```ts
const stdout: string[] = [];
await app.run(["Ada"], {
  stdout: (text) => stdout.push(text),
  stderr: (text) => stdout.push(text),
});
```

`run()` resolves after successful cleanup. It does not render errors, run Extension `handleError` hooks, or change `process.exitCode`. Definition, parse, Context, Command Handler, and cancellation failures are thrown unchanged.

## `.execute(options?)`

```ts
execute(options?: { argv?: string[] }): Promise<void>
```

Runs the terminal boundary. By default it parses `process.argv.slice(2)`; `options.argv` is useful in tests.

```ts
await app.execute();
```

`execute()` renders a failure once through the Extension `handleError` chain ending in Core's renderer, sets `process.exitCode` to `1`, and resolves. A standard `AbortError` cancellation is silent and sets exit code `130`.

<Callout type="warn">
  Use `.handle(handler)` to define behavior. `.run(argv, io)` is only programmatic invocation;
  `.execute()` is the terminal entry point. Command definitions are inert and expose neither.
</Callout>
