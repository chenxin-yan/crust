## `CrustError`

Framework definition, routing, parsing, and validation failures use `CrustError`. Branch on `code` or `.is(code)`, never on the message.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/errors.ts#handle
</include>

`.is(code)` narrows `details` to that code's shape. `.withCause(cause)` sets `cause` and returns the error. `toJSON()` returns `code`, `message`, and `details`, and omits `cause`. The constructor's details argument is required for `COMMAND_NOT_FOUND` and `ENV`. See the [declaration](https://github.com/chenxin-yan/crust/blob/main/packages/core/src/errors.ts) for the exact generic contract.

## Codes

| Code                | Meaning                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `DEFINITION`        | Malformed dynamic definition or collision, recipe, Extension, Context, or documentation-section failure |
| `PARSE`             | Argv syntax, structured `run()` input binding, or built-in value parsing failed                         |
| `VALIDATION`        | Required-value or Standard Schema validation failed                                                     |
| `COMMAND_NOT_FOUND` | An unknown command under the [routing rules](/docs/guide/commands#unknown-commands)                     |
| `ENV`               | [`@crustjs/env`](/docs/modules/env) variables were missing or invalid                                   |

With `execute()`, an unmatched subcommand token becomes a positional argument if the parent has a Command Action; without an action, the parent reports `COMMAND_NOT_FOUND`. Typed `run()` returns `COMMAND_NOT_FOUND` for any unknown path segment.

## Propagation boundaries

| Failure                                                          | `run()`                                | `execute()`                                   |
| ---------------------------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| Authoring and attachment (`.flags()`, `.provide()`, `.add()`, …) | Throws at the builder call             | Throws at the builder call                    |
| Preparation                                                      | `failed` outcome; no hooks run         | Rendered directly; exit `1`                   |
| Routing, parsing                                                 | `failed` outcome; no hooks run         | Rendered via `onError`; exit `1`              |
| `preRun`, validation, Context setup, Command Action              | `failed` outcome after `postRun` hooks | Rendered via `onError`; exit `1`              |
| Cancellation (`AbortError`)                                      | `failed` outcome                       | Offered to `onError`, else silent; exit `130` |

`snapshot()` rejects with preparation errors. Context setup and Command Action failures are not wrapped in `CrustError`.

- After a lifecycle failure, every `postRun` hook still runs in reverse registration order, and constructed Contexts are disposed afterwards.
- An invocation failure takes precedence over `postRun` failures. After a successful invocation, the first `postRun` failure escapes once the remaining hooks run.
- When invocation and disposal both fail, the escaping error is a `SuppressedError`: `.error` is the disposal failure and `.suppressed` is the invocation failure.
- `run()` returns the escaping error and all captured output, including cleanup output. It never calls `onError` or changes `process.exitCode`.

`execute()` renders a failure once. Extension `onError` hooks are presentation only and cannot turn a failure into success: they run in registration order until one returns a truthy value. If none claims the failure, Core's renderer writes one `Error: message` line per underlying failure (each member of a `SuppressedError` chain or `AggregateError`). If cleanup fails after a failure was already rendered, Core writes `Cleanup failed: message` lines without calling `onError` again.

For `preRun`, validation, setup, and action failures, `onError` runs before `postRun` while Contexts are live. A `postRun` or disposal failure reaches `onError` after cleanup, when Context pulls reject. Routing and parse failures receive empty `args` and `flags` and no Contexts. See [error handling](/docs/guide/error-handling) for worked examples.

## Cancellation

Any `Error` whose `name` is `"AbortError"`, including a `DOMException`, is cancellation.

Every invocation carries `ctx.signal`, shared by Context setups, Extension hooks, and the Command Action. It aborts when the caller aborts `execute({ signal })` or `run(path, input, { signal })`, or on the first Ctrl-C during `execute()`. Cancellation is cooperative: once the work settles, `postRun` hooks and Context disposal still run, and work that ignores the signal delays cleanup.

When work throws the signal's reason, as `signal.throwIfAborted()` does, that error decides the exit path. Ctrl-C and a bare `controller.abort()` supply an `AbortError`, which exits `130` silently; a custom reason such as a `TimeoutError` renders and exits `1`. [`@crustjs/effect`](/docs/modules/effect) turns interruption into an `AbortError` regardless of the reason.

If disposal fails after cancellation, the escaping error is a `SuppressedError` rather than cancellation, and `execute()` exits `1`.
