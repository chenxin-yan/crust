## `CrustError`

Framework definition, routing, parsing, and validation failures use `CrustError`.

```ts
class CrustError<C extends CrustErrorCode = CrustErrorCode> extends Error {
  readonly code: C;
  readonly details: CrustErrorDetails<C>;
  cause?: unknown;

  is<T extends CrustErrorCode>(code: T): this is CrustError<T>;
  withCause(cause: unknown): this;
  toJSON(): { code: C; message: string; details: CrustErrorDetails<C> };

  static is(value: unknown): value is CrustError;
  static definition(message: string, details?: DefinitionErrorDetails): CrustError<"DEFINITION">;
  static parse(message: string, details?: ParseErrorDetails): CrustError<"PARSE">;
  static validation(message: string, details?: ValidationErrorDetails): CrustError<"VALIDATION">;
  static commandNotFound(
    message: string,
    details: CommandNotFoundErrorDetails,
  ): CrustError<"COMMAND_NOT_FOUND">;
}
```

Use `code` or `.is(code)` instead of matching messages.

```ts
try {
  await app.run(argv);
} catch (error) {
  if (error instanceof CrustError && error.is("VALIDATION")) {
    for (const issue of error.details?.issues ?? []) {
      console.error(`${issue.path}: ${issue.message}`);
    }
  }
}
```

## Codes

```ts
type CrustErrorCode = "DEFINITION" | "PARSE" | "VALIDATION" | "COMMAND_NOT_FOUND";
```

| Code                | Meaning                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `DEFINITION`        | Invalid application definition: empty names, collisions, invalid combinations, or other setup errors |
| `PARSE`             | Argv syntax or built-in value parsing failed                                                         |
| `VALIDATION`        | Required-value or Standard Schema validation failed                                                  |
| `COMMAND_NOT_FOUND` | A token did not match a child command name or alias                                                  |

## Details

### `DefinitionErrorDetails`

```ts
interface DefinitionErrorDetails {
  readonly subject?: "arg" | "command" | "context" | "extension" | "flag";
  readonly name?: string;
  readonly reason?: string;
}
```

### `ParseErrorDetails`

```ts
interface ParseErrorDetails {
  readonly flag?: string;
  readonly argument?: string;
  readonly value?: string;
  readonly reason?: string;
}
```

### `ValidationErrorDetails`

```ts
interface ValidationErrorDetails {
  issues: readonly {
    readonly message: string;
    readonly path: string;
  }[];
}
```

Standard Schema failures are aggregated into one `VALIDATION` error. Paths are normalized under `args.<name>` or `flags.<name>`.

### `CommandNotFoundErrorDetails`

```ts
interface CommandNotFoundErrorDetails {
  input: string;
  available: string[];
  commandPath: string[];
  parentCommand: CommandSnapshot;
}
```

`parentCommand` is a readonly, serializable snapshot of the command whose child could not be resolved.

## Propagation boundaries

`.run(argv, io)` throws the original error without rendering it or changing process status. Context and Command Handler failures are not wrapped in `CrustError`.

```ts
const failure = new Error("database unavailable");
const app = new Crust("my-cli").handle(() => {
  throw failure;
});

await app.run([]); // throws the same `failure` object
```

`.execute()` renders a failure once, sets `process.exitCode = 1`, and resolves. Extension `handleError` hooks can replace or delegate presentation but cannot turn the invocation into success.

A prompt cancellation is a standard `DOMException` named `AbortError`. Programmatic `.run()` throws it; terminal `.execute()` handles it silently and sets exit code `130`.

```ts
try {
  await app.run(argv);
} catch (error) {
  if (error instanceof Error && error.name === "AbortError") {
    // cancellation
  }
}
```

`toJSON()` returns `code`, `message`, and `details`. It intentionally omits `cause`.
