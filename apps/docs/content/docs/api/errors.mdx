## `CrustError`

Framework definition, routing, parsing, and validation failures use `CrustError`. Branch on `code` or `.is(code)`, never on the message.

<include lang="ts" meta='title="src/cli.ts"'>
  ../../../examples/api/errors.ts#handle
</include>

After `instanceof CrustError`, `code` is the union of codes, and checking `code` or calling `.is(code)` narrows `details` to that code's shape. `.withCause(cause)` sets `cause` and returns the error. `toJSON()` returns `code`, `message`, and `details`, and omits `cause`. The constructor's details argument is required for `COMMAND_NOT_FOUND` and `ENV`. See the [declaration](https://github.com/chenxin-yan/crust/blob/main/packages/core/src/errors.ts) for the exact generic contract.

## Codes

| Code                | Meaning                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `DEFINITION`        | Malformed dynamic definition or collision, recipe, Extension, Context, or documentation-section failure |
| `PARSE`             | Argv syntax, structured `run()` input binding, or built-in value parsing failed                         |
| `VALIDATION`        | Required-value or Standard Schema validation failed                                                     |
| `COMMAND_NOT_FOUND` | An unknown command under the [routing rules](/docs/guide/commands#unknown-commands)                     |
| `ENV`               | [`@crustjs/env`](/docs/modules/env) variables were missing or invalid                                   |

With `execute()`, an unmatched subcommand token becomes a positional argument if the parent has a Command Action; without an action, the parent reports `COMMAND_NOT_FOUND`. Typed `run()` returns `COMMAND_NOT_FOUND` for any unknown path segment.

### `DefinitionErrorDetails`

<auto-type-table path="../../../../../packages/core/src/errors.ts" name="DefinitionErrorDetails" />

`reason` is typed as Core's known values (`DefinitionErrorReason`) but stays open to any string, since other packages add their own. Context failures set `reason`: `missing-context` for an unprovided Context, `context-cycle` for a dependency cycle, `flags-before-validation` when a flag-owning Context is pulled before validation, `context-during-disposal` when a never-built Context is pulled once cleanup has begun, and `context-after-disposal` for any pull after disposal.

Flag definitions set `reason: "integer-like-name"` for an integer-like flag name (`"0"`, `"10"`, any digit-only name without a leading zero), which JavaScript records can list before other keys, `reason: "invalid-spelling"` for a name, alias, or `short` that contains whitespace or starts with `-`, or a name or alias that contains `=`, and `reason: "invalid-flags"` when `.flags()` receives a `null` or `undefined` record or definition, or a record whose prototype is not `Object.prototype` or `null`, such as one written with a literal `__proto__` key. Any other non-object definition, such as a string or an array, is a TypeScript error and is not checked at runtime.

### `ParseErrorDetails`

<auto-type-table path="../../../../../packages/core/src/errors.ts" name="ParseErrorDetails" />

`reason` is typed as Core's known values (`ParseErrorReason`) but stays open to any string, since other packages add their own. These argv flag errors set `flag` and `reason`: `unknown-flag` for an unrecognized flag, `missing-value` when a value-taking flag has no value (`Missing value for flag "--count"`), and `unexpected-value` when a boolean flag is given one with `=` (`Flag "--force" does not take a value`). Negating a `noNegate` boolean (`--no-quiet`) is a `PARSE` error without details.

### `ValidationErrorDetails`

<auto-type-table path="../../../../../packages/core/src/errors.ts" name="ValidationErrorDetails" />

Every schema failure in one invocation is aggregated into one `VALIDATION` error. Issue paths are normalized under `args.<name>` or `flags.<name>`. Missing required values and unexpected positionals report `VALIDATION` without `details`.

## Propagation boundaries

| Failure                                                                      | `run()`                                | `execute()`                                   |
| ---------------------------------------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| Eager builder checks (direct inputs, sibling names/aliases)                  | Throws at the builder call             | Throws at the builder call                    |
| Deferred recipe, inherited-flag, or Context-demand checks                    | `failed` outcome when encountered      | Rendered when encountered; exit `1`           |
| Preparation                                                                  | `failed` outcome; no hooks run         | Rendered directly; exit `1`                   |
| Routing, argv syntax, structured input binding                               | `failed` outcome; no hooks run         | Rendered via `onError`; exit `1`              |
| Extension hooks before the action, validation, Context setup, Command Action | `failed` outcome after `postRun` hooks | Rendered via `onError`; exit `1`              |
| Cancellation (`AbortError`)                                                  | `failed` outcome                       | Offered to `onError`, else silent; exit `130` |

`.add()` checks sibling names and aliases immediately, but does not run recipes or validate their inherited flags and Context demands. Those checks happen when commands materialize on first use. `.extend()` checks nothing at the call: collisions between Extension-provided flags and the app's flags, Extension commands that collide with another root command, and missing Contexts for an Extension's `.use()` or `.provide()`, are preparation errors. `await app.snapshot()` materializes and validates the full tree without running Command Actions, rejecting with any deferred definition or preparation error. `at()` can also throw deferred definition errors while resolving a path. Context setup and Command Action failures are not wrapped in `CrustError`.

- After a lifecycle failure, every `postRun` hook still runs in reverse registration order, and constructed Contexts and cleanup deferred by Extension setups are disposed afterwards.
- An invocation failure takes precedence over `postRun` failures. After a successful invocation, the first `postRun` failure escapes once the remaining hooks run.
- When invocation and disposal both fail, the escaping error is a `SuppressedError`: `.error` is the disposal failure and `.suppressed` is the invocation failure.
- `run()` returns the escaping error and all captured output, including cleanup output. It never calls `onError` or changes `process.exitCode`.

`execute()` renders a failure once. Extension `onError` hooks are presentation only and cannot turn a failure into success: they run in registration order until one returns a truthy value. If none claims the failure, the [renderer's `error`](/docs/api/types#renderer) renders it when an Extension chose a renderer that has one; otherwise Core writes one `Error: message` line per underlying failure (each member of a `SuppressedError` chain or `AggregateError`). If cleanup fails after a failure was already rendered, Core writes `Cleanup failed: message` lines without calling `onError` or the renderer's `error` again.

For Extension `setup`, flag handler, `noAction`, and `preRun` failures, and validation, Context setup, and action failures, `onError` runs before `postRun` while Contexts are live. A `postRun` or disposal failure reaches `onError` after cleanup, when Context pulls reject. Routing and parse failures receive empty `args` and `flags` and no Contexts; `command` is the routed command when routing succeeded and the root otherwise. Argv syntax failures are unknown flags, missing option values, and negating a `noNegate` flag; an invalid argv or environment value (conversion, `choices`, `parse`) keeps code `PARSE` but surfaces during validation, after flag handlers and `preRun` and with live Contexts, so a `--help` handler still runs first. See [error handling](/docs/guide/error-handling) for worked examples.

## Cancellation

Any `Error` whose `name` is `"AbortError"`, including a `DOMException`, is cancellation.

Every invocation carries a `signal`, shared by Context setups, Extension hooks, and the Command Action. It aborts when the caller aborts `execute({ signal })` or `run(path, input, { signal })`, or on the first Ctrl-C during `execute()`. Cancellation is cooperative: once the work settles, `postRun` hooks and Context disposal still run, and work that ignores the signal delays cleanup.

When work throws the signal's reason, as `signal.throwIfAborted()` does, that error decides the exit path. Ctrl-C and a bare `controller.abort()` supply an `AbortError`, which exits `130` silently; a custom reason such as a `TimeoutError` renders and exits `1`. [`@crustjs/effect`](/docs/modules/effect) turns interruption into an `AbortError` regardless of the reason.

If disposal fails after cancellation, the escaping error is a `SuppressedError` rather than cancellation, and `execute()` exits `1`.
